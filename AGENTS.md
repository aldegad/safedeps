# AGENTS.md — safedeps

Conventions for agents (Claude Code, Codex CLI) working in this repo. Claude Code reads this through the `CLAUDE.md` symlink. Edit **this** file, not `CLAUDE.md`.

safedeps gates development dependency installs (npm/pip/cargo/go/gem/maven/nuget) with OSV-backed advisory checks, an approved-spec ledger, and post-install reorg rollback. Full design: [`ARCHITECTURE.md`](./ARCHITECTURE.md).

## Engine support

Claude Code + Codex CLI only — not Grok/Hermes yet. When a hook capability differs between engines, **detect and branch; never assume parity.** Codex sends `turn_id`/`model` in the hook payload; Claude does not.

## Architecture invariants (do not break)

- **npm enforcement authority = the PostToolUse effect gate** (lockfile closure vs ledger + OSV batch). The PreToolUse command guard is a fast advisory/UX layer, *not* the authority. **It reads npm's two records of a project install — `package-lock.json` and the hidden `node_modules/.package-lock.json` — in one directory, chosen before the command runs by asking npm: `npm prefix` and `npm root`, run where the command runs npm and with the statement's own arguments and environment (`lib/npm/ask.sh`).** **The ask never runs the command's code.** It is always the hook's own npm on the hook's PATH, and a name that chooses code when npm starts (`PATH`, `NODE_OPTIONS`, `NODE_PATH`, the OpenSSL and dynamic-loader settings, `BASH_ENV`, `npm_config_node_options`: `safedeps_npm_code_name`) is never carried, whatever the command says. The ask used to carry them, and `PATH=<dir> npm install x`, `NODE_OPTIONS=--require=<file> npm install x` and `<dir>/npm install x` ran the command's code three times per judgment, a command the gate then denied included. A gate must not run a command's code to decide whether to let it run. Do not answer that question in bash again. The ask's own flags go after the command's words, so npm is not asked when those words would take them as a value or an operand (`npm install x --cache` made npm create `--json` in the project), and each ask names a cache in its own scratch directory, because npm creates its cache directory on start. The install itself still creates `--ignore-scripts` there after a one-statement `npm install x --cache`, because it keeps the floor's end flag (below), as 7d66f8c did. Two copies of npm's rules each disagreed with npm and each disagreement was a silent pass: the named directory itself sent the gate to `src` while npm wrote the project's lockfiles, and a workspace resolver that resolved symlinks climbed to a root npm did not. **An install counts as read only when the directory the gate read shows this call's install trace; prediction chooses where to look, never whether it was covered.** Just before the command runs, the pre-guard touches a baseline file and notes the inode of both lockfiles there; the post hook counts a lockfile `find -newer` than the baseline, or one with another inode, as the trace. Where neither shows one it records `UNGATED` as the check that found nothing ("no install trace in <dir>: neither npm lockfile there is newer than the baseline taken before this command or has another inode") and runs no rebuild there. The record does not guess where the install went: "the install landed elsewhere or installed nothing" was a cause nobody had checked. Three rounds made the prediction better and each left a silent pass (a `cd` that never ran, `command cd`, a symlinked member); with the trace, a wrong prediction is a record. Do not compare content or whole seconds: a reinstall of what is already there rewrites the hidden lockfile with the same bytes, often inside the second the baseline was touched in. Two or more lockfile-writing npm statements share one trace only when nothing but inert statements (`echo`, `printf`, `tail`, `head`, `grep`, `ls`, `cat`, `true`, without redirection or substitution) runs between them and none relocates itself; otherwise the command is `UNGATED`, because the first one's trace hid the second one landing elsewhere. A `cd` that may not run (after `&&` or `||`, or inside a compound command) is followed only along the `&&` chain after it; `cd X || exit` is followed. Where npm cannot be asked or does not answer within its deadline, and where the command carries a word the shell decides at run time, the target is `?`, the reason is recorded, and the gate looks in the cwd. npm masks anything shaped like a UUID or a token in what it prints, paths included (11.19.0, measured), so a masked answer is never used as a path: it stands for the one directory from the cwd up that reads the same, and is `?` otherwise. npm's answer covers every `.npmrc` it reads. The environment it is asked with is every name the statement and the statements before it export, assign or unset (as `env -u`), not only `npm_config_*`, except the code names above: `export HOME=<dir>` makes npm read `<dir>/.npmrc`, and an export branch that carried only npm settings missed it (XH1-XH5). Whether npm writes a record where it installs is a separate question npm cannot be asked before the install, so the pre-guard still reads `global` and `location` in the project's and the user's `.npmrc` for that, and only for that: it can turn a read install into an `UNGATED` one, never choose a directory. `scripts/test/install-dir-differential.sh` holds the gate to `npm prefix` over 237 layouts. **This holds inside the hook budget only** — both hooks are killed at their registered timeout (30s when measured, 2026-08-04) and the effect gate's work is network- and project-bound, so do not write "npm is covered" without that qualifier. **The range is measured, so quote it rather than the word "structural"**: the gate crossed 30s at a closure of *four* packages until v2.16.0 stopped re-reading the whole ledger per package, and it crosses near 390 packages after. Re-measure with `scripts/measure/effect-gate-cost.sh` before writing a number — the crossing moves with host, network and cache, and a number from someone else's machine is decoration.
- **The effect gate cannot deny, so its answer to "I did not finish" is a record, not a block.** The install already ran. A rollback writes its journal entry *before* the first destructive act and clears it after it has reported itself, so an entry that outlives its run is itself the report — the next PostToolUse turns it into a durable incident plus a `REORG INTERRUPTED` line in `reorg.log`. **"Outlives its run" is a liveness claim, not a file test**: a rollback in progress has its own entry on disk by design, so the report is gated on the entry's recorded pid being gone (v2.16.1 — an unrelated Bash call used to read a live entry and report a working rollback as interrupted). The state lock cannot stand in for that check; it is released before the rollback begins. pid reuse is settled by process start time, and an owner that cannot be resolved counts as gone, because the failure to prefer is noise over silence. A zombie counts as gone too (v2.16.2): it keeps its table entry and its start time, so it clears both other tests, and it never goes away — reading one as alive loses the report permanently rather than delaying it. **A stopped owner is a third answer, not a gone one** (v2.17.0), so "gated on the pid being gone" is not the whole rule: a suspended process has not died and is not progressing, and calling it either way reproduces one of the two defects above. It is reported with its pid still alive, and the report says the owner pid is stopped. Stopped is judged only after the start-time check confirms the pid still belongs to this entry — ahead of it, any stopped process holding a recycled pid turned a genuinely interrupted rollback into "suspended, resume it" (caught in review). Do not move the record back after the work; that ordering is the whole defect (measured: a kill mid-rollback left `reorg.log` at zero lines with the project already reverted). And do not sell this as atomicity — safedeps does not own the atomicity of an npm tree rebuild. **A rollback runs no package manager.** It restores the files it snapshotted and removes the project's own `node_modules` only when that is a real directory and the command is seen to have written the project's node tree (an install trace in the directory, a node manifest or lockfile that differs from the snapshot taken before the command, or a `node_modules` that differs from the pre-guard's listing or is newer than that snapshot; compared before the restore, since the restore goes to the confirmed snapshot, which can be older, and with `find -newer`, since bash 3.2's `-nt` compares whole seconds), so every path it writes or removes is one it checked itself. The second condition keeps a rollback that has nothing to roll back from taking the project's dependencies with it. The closure is judged whether or not the command changed it (no install trace means `UNGATED` and no rebuild, not no judgment), so a command misread as an install, in a project whose closure was never approved, reaches the rollback, and the old reinstall had been hiding the removal. **The command-independent backstop (a command the pre-guard did not read as an install but `SAFEDEPS_G_BACKSTOP_RE` matches) judges the closure only where that command left a trace in the cwd's node tree**: the pre-guard writes an entry named by the call's top-level `tool_use_id` (both engines send it in PreToolUse and PostToolUse, measured) with the inodes of both npm lockfiles and `node_modules`, the lockfiles' status change times, and a baseline file (each value the path's own and, through a symbolic link, its target's: a write through a linked lockfile changes only the target's, and an entry that held the link's alone missed it, lumi r2 S1), and the post hook of the same call looks for another inode, a lockfile or `node_modules` that appeared or went away, a lockfile change time that is not the recorded one, or `find -H node_modules -cnewer <baseline>`. The baseline is set two seconds back unless the baseline file and every part of the project's node tree it reads, link targets included, show a time below the second: set back everywhere, it counted a pull 0.3 seconds before a grep as the grep's trace (lumi r1 R1), and left in place where one part was enough, it missed a write into a whole-second `node_modules` beside a nanosecond lockfile (lumi r2 P3). The post hook reads the call's entry before any record: the pre-guard writes a record or an entry for a call, never both, so a call with an entry is judged by its entry alone, whatever the entry holds, and no record is read or removed for it; read after the records, a grep was judged by another call's record whose snapshot was gone and rolled the project back (lumi r3 REC), and an entry taken in another directory than the post hook's sent its call on to the records (MM, lumi r4). Only a call with no entry (no `tool_use_id`, or an entry the pre-guard could not write) reaches the backstop through a record, and it counts as traced there, so it can be rolled back. Which install record is an install call's own is its `tool_use_id` (below). The post hook reads only its own call's entry. An entry whose post hook never ran (a call refused after the pre-guard let it through, one cancelled while it runs, or a failed one on Claude Code where `PostToolUseFailure` is not registered) moves no later call's baseline and is swept after a day; when entries were read by project and command, the oldest one made every later call judge from the one before it (lumi r1 P1). An input with no `tool_use_id` gets no entry and is judged as before, a trace. No trace is a `BACKSTOP UNTRACED` line in advisory.log and nothing else. Its pattern matches `grep -n "npm install" README.md`, and before this a grep rolled back any project whose closure had become unapproved outside the gate (a pull, an expired approval) and removed its `node_modules`. Three conditions that read npm's hidden lockfile to keep `node_modules` failed review the same way, the record not describing the disk, so do not put a record back in its place. What the check cannot settle (no entry, a gone baseline, a walk that fails or passes its deadline) counts as a trace, which is the old behavior; the reinstall is the next install, which the gate checks like any other, and a target that is a symbolic link is refused and named (`REORG REFUSED` in `reorg.log`), never followed. Each npm a rollback used to run reached past the project some way the gate had not predicted -- a linked `node_modules` (`npm ci` empties whatever it resolves to), the walk up to an enclosing project, a linked lockfile, a workspace outside, a `file:` dependency's scripts and bin links -- and three rounds of review found a new one each time, so do not put npm back into the rollback. The refusal is a warning on the rollback, not a stop. The rebuild after a verified inert install is not a rollback, and it is the one place safedeps still runs npm. It runs only when no root npm file is a link (`lib/gates/npm-reach.sh`) and the whole tree passes the check described under inert install, and it carries `--global=false --location=project --prefix <the project>`. A rebuild skipped for a link reports the link as the reason, never as a place to run npm, and a reason is a fact read from disk, never what npm would do with it ("npm would work in an enclosing project" was false where a real npm stayed put). The rollback and the interrupted-rollback report say what they did and what the files are, and give no reinstall command: three rounds of review found advice that sent the user's npm outside (a missing `package.json`, a workspace outside, a workspace member whose bare `npm ci` empties the workspace root), each time past a judgment that was silent.
- **What a rollback, a refused step, a skipped rebuild and the unfinished-rollback report say is a closed set of line forms, and the output is what is checked.** Every such line is printed by a function in `lib/gates/report-facts.sh` that runs its own check when it is called and prints what the check returned: a path and what a test of it returned, an exit status, or one of safedeps' own acts. A line never says what a path contains, why something happened, what npm would do, or what to do next. The same report was sent back three times for a false sentence, and each time the false part was a clause attached behind a true fact ("is still there, with whatever this install wrote in it" after an `rm -rf` that had removed most of it; "install scripts have not run" after the command's own `npm rebuild`; "most likely the hook hit the runtime's timeout" after a failed `cp`). A vocabulary check did not see them, and reading did not converge. So `scripts/test/e2e.sh` hands every line the post hook prints to `scripts/test/lib/report-oracle.sh`. A line is a frame matched whole, or it matches one anchored form and has that form's claim checked again on disk, or the run fails. The form table fails on a form no line matched. The reorg.log entries are read with the same grammar, not as a superset of the message: the oracle builds the entries the message calls for and the appended entries must be exactly those (advisory.log: only its two rollback lines, each a repeat of message lines). The oracle also reads the disk around a rollback (every changed top-level entry has a step line; "changed nothing" and `kept` against the listing and the pre-hook checks), a call that prints no message appends nothing to reorg.log, and prose is allowed per block with a cap. **A fact the hook and the oracle both read is read by the oracle with a different method** (a Python walk, `scripts/test/lib/report-oracle-read.py`): they once ran the same wrong check and agreed (F1 a find without `-H`). **Neither reads the shell command for a report line.** Whether it carries `--ignore-scripts` was read by both, the hook with the install grammar and the oracle with `shlex` and `npm config get`, and three rounds found both wrong on the same commands (F2 a substring test, F3 an assignment or an export of `npm_config_ignore_scripts` and a project `.npmrc`), because the two readers shared one model of a shell statement. So the line is a comparison of two strings, and a reader of the command is not put back. `scripts/test/report-mutations.sh` is the control: thirty-six mutations, each red at the oracle, and eight more, each red at its e2e row (seven that break the backstop's trace check, and one that drops the line saying a call named no `tool_use_id`), run on copies. A new line needs a fact function, a form with its check, and a row that prints it, in one change. Rule sentences live in the README, not in messages. A restore or a removal that fails is a line and the rollback goes on (a bare `cp` under `set -e` ended the hook mid-rollback). "safedeps added --ignore-scripts" is said only when the command the post hook received is byte for byte the command safedeps wrote (`updated_command` in the snapshot's meta); the pre-guard's record alone is "asked". A hook that did not find this command's record (the backstop) says none of the three, because the record can exist under a key it did not compute (bamdori r18 F4: `sh -c 'npm ci'`, rewritten, got "did not add"); the oracle finds an unused record by what it holds, not by the hook's key, and checks each record against the rewrite the pre-guard printed. A rewrite whose record cannot be written is not sent. A record the post hook cannot read gets no `--ignore-scripts` line and one `advisory.log` line, never "did not add" (that fallback was a silent one); the oracle learns of the failed read from the row that causes it, not from the hook. **A line is said only from a fact the record states, as version 2** (`"record": 2`, v2.18.0): `did not add` needs `ignore_scripts_injected` false, `added` and `asked` need it true and `updated_command` a string, and every other shape (no file, no version or another, a string, a null) says no line and names the record in `advisory.log`. No branch that says a line is reached by a default. Four rounds found a record answered by its missing field (F4, a failed read, a non-object, bamdori r22 U3), and a v2.17.2 false does not mean no rewrite (U3b), so do not add a fallback that turns a missing fact into one of the three. The oracle reads the same rule from the parsed record in Python, not with the hook's jq. **A record belongs to one call** (v2.18.1): the pre-guard keeps it as `pending/id-<tool_use_id>.json` (`lib/gates/call-id.sh`, the one reading of the id for both hooks), and the post hook of a call that names a `tool_use_id` reads that record and no other. Found by the directory the command ran in and the command with `--ignore-scripts` set aside, as v2.18.0 did, two calls of the same command that overlapped in the same directory each spoke from the other's record (bamdori r19 X1), a call whose post hook never ran left a record the next call of the command rolled back to, losing an edit made in between (O2), and the oracle, reading the record each call took, agreed. Do not put a lookup by directory and command back for a call that names an id, not even as a fallback for a record that is missing: that record is another call's. A call that names no `tool_use_id` keeps that lookup and both hooks say so in `advisory.log`; both engines send one (measured: Claude Code 2.1.288 and 2.1.289 `toolu_...`, Codex CLI 0.160.0 `exec-<uuid>`, the same in both hooks). The oracle reads the call from the hook input in Python and is red when the hook consumes a record that holds another call's id, and e2e runs overlapping calls (OV1, OV2, O2, MM). Records a pre-#5 pre-guard left (`current_state`, `current_snapshot_id`) are not read: they name no call, and a call one did not match ended the hook with no judgment. **A failed call is judged.** Claude Code runs PostToolUse only after a tool call succeeds and `PostToolUseFailure` after a Bash call that ran and failed, with the same `tool_use_id` and an `error` in place of `tool_response` (https://code.claude.com/docs/en/hooks, verified 2026-10-04), so the installer registers the post hook for both on Claude Code, and a failed install is judged and leaves no record. Codex runs PostToolUse after a failed Bash call too and documents no `PostToolUseFailure` (https://learn.chatgpt.com/docs/hooks), so its config gets PostToolUse alone. A call the user refuses after the pre-guard let it through still runs no post hook, and its record waits for the 24-hour sweep, where no other call reads it. A record whose snapshot has no meta file goes to the backstop, with one `advisory.log` line naming it and a headline that says the record was found and its snapshot has no meta file; the post hook used to exit there with nothing said, so the install was never judged (bamdori r23, since e315244). A record that names no snapshot (a damaged pending state) goes the same way, under a headline that says the record names no snapshot. So does a record that is not one JSON object, under a headline that says so: its jq read under `set -e` ended the hook, and the record, left in place, ended it on every call of the command for 24 hours. Do not put any of these exits back. A record with no `project_dir` is judged in the payload's `cwd`, never the hook's own working directory, which judged a directory the command never ran in. The hash that picks the confirmed snapshot is always computed from the project being judged, never read from the record: a record naming X with Z's hash restored Z's confirmed snapshot into X (bamdori J), and the oracle, which read the record's hash too, agreed. A record's fields count only as strings: a `snapshot_id` of 5 names no snapshot. Each call claims a snapshot id of its own (`<seconds>_<dir hash>-<pid>`, created exclusively): one id per second let a second call write over the first's record and lockfile copies (bamdori r19 SAME), and `oracle_pre` is red on a pre-guard call that writes over a record that was there before it. The effect gate's rebuild warnings ("review it, then run `npm rebuild` yourself", "confirm with the user before") are instructions by design and stay prose: the oracle lists them by exact prefix and counts them, and their grammar is a later plan's. Do not write "no false line is possible": the oracle checks each line it reads, not which lines were chosen, and not a check that it and the code both get wrong.
- **A hook that runs out of time must answer before the runtime kills it.** The runtime's timeout is fail-open: the hook dies and the tool call proceeds. So the pre-guard keeps its own smaller budget (`SAFEDEPS_SELF_BUDGET_SECONDS`) and denies when its judgment does not finish. **The deadline is read from the clock, never added up from the sleeps it asked for**: a loaded machine stretches every sleep, so the sum runs late by all the stretches together. The clock is bash's `SECONDS` (bash 3.2 has no finer one that costs no process), counted from the guard's start and compared as a distance from its starting value, because bash seeds it from the environment. Keep that deny phrased as *undecided*, never as a detection — the two are different claims and conflating them teaches people to route around the gate. **That budget is clamped below the runtime's, and the clamp is part of the boundary, not a nicety**: any value at or above the registered hook timeout hands the kill back to the runtime and restores the fail-open, and the motive to raise it (an `UNDECIDED` on a big command reads as "the budget is short") is ordinary enough that leaving it open is the same as leaving it off. Lowering stays free, and the clamp says out loud that it happened. **The same holds for `SAFEDEPS_BUDGET_ENGAGE_BYTES`**, which decides whether the budget runs at all: it is clamped to 4KB, because a tuning knob that can be raised without limit is an off switch. Turning the deadline off is a separate, differently named act (`SAFEDEPS_BUDGET_DISABLED`) that logs every use — the battery's mutation check needs it, and a test that cannot produce the unbounded case only knows it passes, not that it catches anything. Keep tuning and disabling separate levers. **The parent/child marker lives in argv, never in the environment** — as an env var it was a second, unnamed off switch (export it and the parent skipped the deadline, silently); the entry shim passes no arguments, so argv is a channel the environment cannot reach.
- **effect-primary is npm-only.** pip/cargo/go/gem/maven/nuget stay on the v2.1 command-gate + reorg model until their closure resolvers land.
- **Inert install (Claude only).** The PreToolUse hook injects `--ignore-scripts` via `hookSpecificOutput.updatedInput`, at the first place, from the last argument of each npm install (before a `--`, a redirection, a comment or the statement's end) back to its verb, where the statement read with the flag in it (`safedeps_npm_read_args`, both npm versions) leaves the option true and reads the same otherwise. After the last argument outlasts any later `=false`, because npm keeps the last value an option is given; a last word that takes the next word as its value (`--cache`, `-C`) took the flag there and the install ran its scripts, so a place is never assumed. **Every rewrite holds the floor**, 7d66f8c's rewrite, the one safedeps made before it read an install's words: the flag right after every verb, always, and for a command 7d66f8c appended to (one statement, no comment or heredoc: `inert_release_appends`), its flag at the end. 7d66f8c is a tree of this release cycle, not the published v2.17.2 (bb0787d). This release gives no `--ignore-scripts` to a command that runs an npm install it cannot read: one in a `ksh -c` script; one in a double-quoted `sh -c`, `bash -c`, `zsh -c`, `dash -c` or `eval` script that contains a backslash, a backquote or `$(`; or one beside a heredoc body that is piped to another command and contains an npm install. v2.17.2 gave such a command a flag npm read whenever it had a `;`, `&` or `|` outside quotes and every npm install verb in it was followed by whitespace or ended the command, or when it was an `eval` statement. Those commands are recorded downgrades here; v2.17.2 in turn missed shapes this release flags, such as a one-statement `sh -c` whose appended flag became the shell's `$0`. ROADMAP lists them under v2.18.2. A statement where no place reads as true keeps only that floor and is recorded as a downgrade; it is never left without a rewrite 7d66f8c gave it. The one exception is a pre-guard that cannot write its record (a disk or `jq` failure, logged in `advisory.log`): it sends no rewrite, because a version 2 record that says safedeps did not rewrite would then make the post hook say "did not add" of a command safedeps wrote. 7d66f8c sent the rewrite there; this is a disk-fault path, not a command form. That holds on every path that writes no rewrite, a script no offset reaches included: `npm ci eval "\npm"` got no rewrite there and ran its scripts, where 7d66f8c appended its flag and ran none. So deleting some of the flags safedeps inserted gives 7d66f8c's rewrite, which `scripts/test/lib/release-floor.sh` checks on every rewrite smoke and lockless see, against 7d66f8c's own output recorded in `scripts/test/inert-release-rewrites.json`. That property is the guarantee: npm receives at least the words 7d66f8c gave it. An exception that left the verb flag off where it changed npm's reading (`npm install true`) let a shell alias take the one flag left, so there is none. A statement holding a word the shell decides at run time gets the flag after its verb and after its last argument and is recorded in `advisory.log` as unread; a statement where no place passes keeps the floor and is a recorded downgrade. **Which words the shell decides is an allow-list, never a list of what expands** (`shell_expands`): a word is read as written only when every byte outside quotes is in `SAFEDEPS_SHELL_INERT_BYTES` (letters, digits, `._/@:+,=%-`) and it does not start with `~` or `=`; any other byte makes it dynamic. Bytes are read in their quoting: the noredir-then-live view for the set, the words after quote removal for `$` and backquotes, which expand inside double quotes. The expansion table in ARCHITECTURE.md is the reason for the set, not the judgment. Two deny-lists each missed a kind: the first knew `$`, backquotes and globs and not the tilde (`HOME=--cache; npm install x ~` gave npm `--cache` before the trailing flag, and the install ran its scripts with nothing recorded), and its `{` never fired because the pieces view blanks grouping characters inside a word; the second listed the expansion steps and missed zsh's named directories, its alternation glob and bash's extglob. Do not put a deny-list back, and do not widen the set past bytes no shell expansion acts on. **Whether npm keeps the flag is not safedeps' to say.** It is decided by shell state the command text does not hold: a function or alias in the agent's shell snapshot, `.zshenv`, `BASH_ENV`, or one the command defines (measured: each turned a plain rewritten `npm install` into `ignore-scripts` false). So no line says an install's scripts did not run; a line says what safedeps did ("safedeps added --ignore-scripts to this install", "did not run npm rebuild"). A rewrite holding a word the shell decides at run time writes `ignore_scripts_unread: true` to the snapshot meta, and that adds one warning (`INERT_UNREAD_LINE`: "safedeps could not read where npm keeps the --ignore-scripts in the command safedeps wrote, so the install's own scripts may have run"). The field can only add a warning: a record that lacks it loses the warning and claims nothing. Do not turn it back into a permission to say no script ran (`ignore_scripts_verified`, v2.18.0 drafts). An install is left as written only when its own arguments leave the option true, read by `safedeps_npm_read_args`, and 7d66f8c left it as written too (`inert_release_skips`: the text unquoted anywhere in the command); the text anywhere else in the command does not count (`--ignore-scripts=false` and `&& echo --ignore-scripts` each turned the inert install off silently before). An install that asks for its scripts is overridden and recorded in `advisory.log`, never denied: the rebuild runs them once the closure verifies. post-verify runs `npm rebuild` only after the closure verifies clean, only when every node npm says the rebuild would run over (`npm query '*'`, links followed into their targets) passes a check of the whole tree, and with `--global=false --location=project --prefix <the directory the gate read>`, so a rejected or unread package's lifecycle scripts never run. The check: every node is one a lockfile records at that location, version and name (a key alone is not a record: an `.npmrc` let npm write 1.0.1 over a recorded 1.0.0; and a `file:` dependency's own `node_modules` is rebuilt with the project); every node under `node_modules` has every record name a public-registry https source (`SAFEDEPS_NPM_PUBLIC_REGISTRY_RE`, the one pattern the source check uses too) that npm says it fetched from there, or is bundled by its parent, judged from the tree and never from a lockfile's `inBundle` (the parent is under `node_modules` and passes the check itself, its `package.json` on disk names the package in `bundleDependencies`/`bundledDependencies`, and no record of the nested package names a non-public source; a committed record's flag and the root's own `bundleDependencies` each let an http tarball pass as bundled before, NB1 and NB2); every node outside it is a declared workspace member. Otherwise the whole rebuild is skipped with a warning naming each node, never a rollback. **The permission to run scripts comes from that check of the whole tree, never from a judgment of the change** — scripts run over the whole tree, and three holes in the change judgment in a row (a hidden lockfile not read, links dropped, an unverified rollback target) each became a script that ran; do not add a script path that asks only what the command changed. A query that fails or does not answer skips the rebuild. **A record's URL is not where the bytes came from**: npm's default `replace-registry-host=npmjs` fetches a registry.npmjs.org URL from the configured registry and records it unchanged, and a committed `.npmrc` or `npm_config_registry` ran an impostor's scripts under a record that read as public (RH1-RH3). So npm is asked which registry it fetches from (`npm config ls --json`, the fetch facts in `lib/npm/ask.sh`), beside `npm prefix` with the statement's own words before the command, and again in the read directory after it; a public URL vouches only when both answers say npm fetched it from the public registry. npm's answer never denies or rolls back an install: a company registry, a mirror and a proxy look exactly like an impostor's registry, and nothing can approve one yet, so a non-public answer keeps the install, withholds the rebuild, and the warning names the registry and tells the agent to confirm with the user before running `npm rebuild` itself (an agent told only to rebuild would run what the check withheld). Only a `--registry` the command spells out is denied, by the text check. Approving a registry is the next release's job; do not turn the warning back into a deny or a rollback without it. A missing answer withholds the scripts and is never a reason to roll back. **Where bytes came from is a fact of the fetch, so it is recorded when the gate sees the fetch and looked up afterwards, never inferred again.** Three readings in a row answered it with something not bound to the bytes, a lockfile's `inBundle`, its `resolved`, and the configuration at rebuild time, and each was a silent pass: once the setting that fetched an impostor was gone, the next approved install, a bare `npm install`, an `npm ci` from npm's cache, a rollback to a snapshot confirmed with it, and another project's `npm ci` of the same lockfile each rebuilt it. The one value npm binds to the bytes is integrity, so each integrity digest an install brings into either lockfile that npm did not say it fetched from the public registry is written to `${SAFEDEPS_HOME}/npm-withheld` (derived from `SAFEDEPS_HOME` like `advisory.log`, one file per run, renamed into place), by both engines, before the reorg decision. "Brings in" is measured against the installed tree from before the command, one digest at a time, and that tree counts only as far as the gate observed it: the pre-guard's copy of the hidden lockfile counts only when it is byte for byte a tree record the post hook judged in that directory (its sha256 in `${SAFEDEPS_HOME}/npm-observed`, kept only for a tree record the install wrote, every integrity of which was judged and every one to record written), and within it only an entry that names one digest vouches. No lockfile counts on its own word, because each is a record nobody saw written: excluding the committed `package-lock.json` let a clone's `npm ci` from a configured impostor record nothing, so the next command rebuilt it (Q1-Q4); a committed hidden lockfile did the same with no bytes behind it (HL1-HL4); one digest the tree held beside the impostor's let the whole entry pass (Q5); and an entry pairing the impostor's digest with the public one, installed from the public registry, vouched for both (DP1). The cost is accepted and measured: an install whose answer is not the public registry records every digest of a tree the hooks have not observed, so the first `npm ci` of a clone from a company registry records its bytes, and under an unknown answer the public ones are recorded too (UK0a, UK1a): one `set -a && npm ci` in a fresh clone withholds that whole tree machine-wide. **Code the command runs first is the one unknown that records nothing, and only where npm answered the public registry**: after `source`, `.` or `eval`, or under code the command chooses for npm (a code name it sets or unsets, `env -i`, an npm named by a path that is not the hook's own; PX1-PX3), with npm answering the public registry for everything the gate can read, the install's scripts are withheld for that command and the warning says why, but nothing is recorded and the tree is not left observed (SRC1-SRC3, UK0, UK1). Whoever controls that code already runs code in the agent's shell, so a record would protect nothing against them and would cost every package of the tree, machine-wide. The pre-guard says so with `cause: "sourced"` on the unknown answer, set only when no setting the gate reads but cannot reproduce (`set -a`, a `declare -x` that changes the value it stores, an `npm_config_*` assignment, code whose own text names an `npm_config_*` setting) is among the reasons (MX1, EV1); do not widen it to those, which are configuration, not code. **The exemption never replaces an answer npm gave**: where npm names a registry that is not public, that came from the command's own words, and it stands and is recorded (VB1-VB3). The first version of the exemption overwrote it, and a no-op `. /dev/null;` in front of `npm_config_registry=<impostor> npm install` let the next approved install rebuild the impostor. The boundary left is a sourced file that sets the registry (VB4): the next install npm answers for with the public registry rebuilds what it served, and the record's `resolved` does not stop that, because a registry can serve registry.npmjs.org URLs (RH1). The record is machine-wide because npm's cache, which carries the bytes to other projects by integrity, is. The whole-tree check refuses a node that holds a recorded integrity, and a public record with no integrity at all, and skips the rebuild when the record cannot be read. Nothing releases a record in v2.18.0; the bytes leaving the tree is the only way out. The boundary is bytes the gate never saw fetched: a fetch it never judged (an install outside the hooks, one it did not recognize or recorded `UNGATED`, a registry neither ask can see), and bytes a clone carries inside `node_modules`, which nothing fetched. A counterexample of this class can come only from there; any exclusion added to the record has to rest on something the gate observed, or it is the next one. Do not read `.npmrc` or the environment for this in bash; the answer is npm's. Each lockfile field the check reads, and what it cannot vouch for, is tabled in ARCHITECTURE.md with the row that holds it. The source and install-script checks that must pass first read what the install brought into either lockfile, compared with both records from before the command, never only a changed `package-lock.json`: an install that saves nothing changes neither file, and until they read the hidden lockfile a tarball with an approved name and version passed both and the rebuild ran its scripts. A plain `npm rebuild` follows a project `.npmrc` into the global tree, and without `--prefix` it walks up from a workspace member to the root (both measured); do not drop the flags. The rollback runs no npm, so no script runs in it (it used to reinstall; measured, a plain `npm ci` toward a state nobody had verified ran the rejected package's scripts). With no confirmed snapshot the rollback restores the state from before the command, which nothing verified and which can hold the rejected package, and the message, `reorg.log` and `advisory.log` say that the snapshot was taken before this command and that no confirmed snapshot names it. Whether install scripts ran is not said. What is said is what safedeps did: the pre-guard's record that it rewrote the command with `--ignore-scripts`, and whether the command the post hook received is byte for byte the command safedeps wrote. On Codex that line is "safedeps did not add --ignore-scripts to this install" (RB1x), which says nothing about the command's own flag. Codex lacks `updatedInput`, so it falls back to detect-and-rollback — keep this asymmetry honest in code and docs.
- **OSV is the single canonical advisory truth.** KEV is a hard-risk overlay; GHSA is enrichment. Do not add a second co-equal truth.
- **No silent fallback.** A provider miss is fail-closed. Every bypass must be observable and logged.
- **`lib/truth-sources.sh` is on the PreToolUse path, so breaking it blocks Bash machine-wide.** The guard sources it on every Bash call to report a moved advisory source, unconditionally and without an environment override (an override was a silent off switch for the notice, caught in review). A parse error there takes the guard down, which the entry shim turns into an explained fail-closed deny — the right direction, and a wider blast radius than the file's size suggests. Edit it in a worktree and run `npm test` before it reaches the main checkout.
- **The install grammar is defined once, in `lib/install-grammar.sh`, and it is on the PreToolUse path.** Every recognizer in both hooks reads it: the pre-guard's install and runner patterns, ecosystem detection, spec extraction, the `--ignore-scripts` rewrite, and the post-verify backstop. It replaced seven hand-kept copies of the verb list that had drifted apart (`pnpm i`, `npm isntall`, `npx <pkg>@<ver>` and more passed the gate, v2.18.0). Add an alias, a runner, or a statement position there and nowhere else. A missing grammar is an explained fail-closed deny for every Bash call, so edit it in a worktree like `lib/truth-sources.sh`. **Its scope follows the carrier rule in ARCHITECTURE.md**: the manager's own documented spellings, every command word npm's parser accepts (`deref`: abbreviations and camelCase, measured by `scripts/measure/npm-verb-spellings.sh`), and the shell's statement grammar are in; argv-passing wrappers (`sudo`, `timeout`, `nohup`, `nice`, `xargs`) are out and pinned as unjudged in `scripts/test/consumer-forms.sh`. Moving that line is a decision to record, not a regex to widen. **Which word is the command, which is an option value and which is a package is one reader's answer, `safedeps_manager_read`, from each manager's tables in that file.** The extractor, the UNGATED record, the landing of an install that is not npm's and the runner reader read its roles and nothing else; the recognizer regexes only say that a statement may be an install, and decide no position. Four readers that each approximated a manager's grammar were each wrong somewhere (`npm --prefix x install` read as `npm x`, `pnpm --dir x add` recorded `npm:add`, `go run ./cmd a@b` recorded `go:./cmd`), so a new manager, command or value option goes into those tables, never into a reader. After the command an option the table does not list takes no value, which can only add a check or a record; before the command the word after one is read both as its value and as itself, and judged as the union. npm's part mirrors nopt with npm's own table (`scripts/measure/npm-option-reading.sh` checks it against the npm on PATH), the other managers' tables are checked the same way by `scripts/measure/manager-option-reading.sh` (an entry for an option the manager reads as a switch hides the package after it, so that direction fails; a command's own entry is looked up before `*`, and no option is listed for both), and where npm 10.8.2 defines an option differently the statement is read both ways and judged as the union. The other managers' version boundaries are class `b` in the value table (poetry's `add --optional`: a switch in 1.8.5, a value in 2.x), read both ways the same. `scripts/test/manager-variants.sh` holds the roles by spelling, not by example.
- **Beside a visible install the pipe question is the standalone one, asked of the same text; nothing is set aside first.** `command_pipes_install_to_shell` asks `payload_pipes_install_text_to_shell` of the command and its `sh -c`, eval and substitution payloads, the visible install's own words included. Do not put back a pass that sets those words aside before the search (a carve-out). Its premise, that the visible install's words print nothing into a shell, cannot be judged from the text: a producer reads the command's own text through `$_`, `$BASH_EXECUTION_STRING`, `ps` or a file. The lineage is N1 → R2 → A1–A7 → W06–W08: each carve-out (manager word only, then a whole-word search, then a word-start search, then the install's own words by grammar) left a pipe the standalone path denied and the path beside an install passed, the last because the shell hands the install's last word to the producer as `$_`. The cost is stated in README: an install and an unrelated `| sh` in one command are denied. `scripts/test/consumer-forms.sh` holds it with an S1 loop: every row beside a visible install gets the verdict of the same bytes with the install switched off by `true `.
- **A scanner that fails must not read as "no install".** Every predicate reads `command_scan_text` inside a condition or a command substitution, where `set -e` is off, so a failed awk returns empty text. Every awk reading records its failure in a per-run mark file, and so do judgment greps (`judge_grep`: 1 is no match, 2 and up did not answer) and the seds on the judgment path; one gate settles them: every path that lets a command run crosses `guard_settle_scan_failure` once, after its last reading and before its first side effect (pending state, the inert meta, the allow). If a reading failed, a command that names a package manager's executable anywhere (`SAFEDEPS_G_EXECUTABLES`, any case, bash regex, no subprocess) is an `UNDECIDED` deny; anything else runs with the failure on stderr and in `advisory.log`. A deny that reports a finding calls `guard_undecided_if_scan_failed` first. A reader that cannot read its input to the end says so the same way rather than reading what it reached: the `sh -c`/`eval` payload reader marks a failed reading when a payload word in live code goes on past the quote it stops at, and the pieces view marks a `$'...'` escape whose value it cannot name. So: a new allow path crosses the gate, a new reading of the command goes before it, a new awk reading writes the mark on failure and carries a `safedeps:<function>` marker line, a new judgment grep goes through `judge_grep`, and `scripts/measure/scan-failure-census.sh` (quick subset in `npm run test:release`) must still count zero weakened, mislabeled, after-gate and pending-on-deny. The marker is enforced, not remembered: the census fails on any awk call that carries no marker, or a marker it has no kind for, because it can fail only what it can name. Twice a hand-kept list of marked readings missed one, and the census reported zero over it. grep and sed carry no marker, so the census numbers their calls and fails each one alone (`grep-k`, `sed-k`) as well as all at once. The quick subset keeps `sed-k` and leaves `grep-k` to the full census, to keep the release run short; the two grep sites `grep-k` found (the read of the lexer's `UNTERM` flag and `guard_command_has_npm_install`) are held by rows in `scripts/test/scan-contract.sh` that fail each of their calls alone. With every sed failing, the first judgment sed's mark covers every later site, so a site that had lost its own mark still read as `UNDECIDED`. The census compares the pending record's trace and attribution as well as its directory: a failed call that changed only those compared as the same. A grep that reads one of the lexer's flags goes through `guard_lex_flag_set`, where a grep that cannot answer counts as the flag being set; it used to read as "the command closes".
- **The command is read by one lexer, `shell_lex`, and every reader takes a view of it.** Quotes, escapes, comments, heredocs, arithmetic, substitutions and continuations are lexed in one awk pass; `command_scan_text`, `strip_heredoc_bodies` and `join_line_continuations` are views of that pass, not parsers of their own, and so are the prefix stripping in `normalize_install_text` (the `unprefixed` view), the substitution extractor (the `substs` view), and the spec extractor's statements: their redirections (the `noredir` view), their quote removal and their cuts at `;` `|` `&` (the `pieces` view). The last three each had a reader with its own copy of the quoting, and each copy was a silent pass where it disagreed with the shell (v2.18.0: a `>` inside `"$(echo ">'")"` read as a redirection took the pinned spec after it along). A new reader of the command takes a view -- never a second parser, because three that had to agree did not, and each disagreement hid the lines after it (fail-open). The scan, code and noredir views keep byte length and are idempotent, so an offset in one is the offset in the command and reading one twice changes nothing; scan-contract checks both properties on the recorded shell forms and on random input, and checks the pieces view's words against the argv bash and zsh produced (`scripts/measure/word-reading-forms.json`). The joined view drops continuations on purpose and has neither property. **A reading is a shell -- bash, zsh or dash -- and every reader reads inside one reading.** The guard's driver (`guard_reading_detect`, `guard_reading_facts`, `guard_reading_ungated`, `guard_reading_effects`) is the only place `SAFEDEPS_READING` is set; `shell_lex` takes no reading argument and fails a call made with none set, and scan-contract checks both. Text one reader hands another is lexed again in the same reading: a per-call reading let a reader re-lex a zsh reading under bash's rules and hide the line again (form SL1). The bash reading runs first and reports `DIVERGE` where the shells answer differently (the table in ARCHITECTURE.md); only then do zsh and dash run, and scan-contract checks that where it reports none the other two views are the bash views byte for byte. The verdict is the union: a finding in any reading is a finding, and `UNDECIDED` needs a failed step or no reading that closes. A side effect that changes the command (`--ignore-scripts`) needs every reading to agree; otherwise `UNDECIDED` with its own reason. Readings collected per divergence ("axes") could not close: zsh decides `((` per site (form M1). A form a shell runs must get a verdict, and its own shell's reading must show the line it ran: `scripts/test/shell-reading.sh` checks both against the recorded values (macOS bash, zsh, sh, dash and the agent's wrapper; Linux bash and dash), `scripts/measure/shell-reading-measure.sh` re-measures them on the platform it runs on, and `scripts/measure/shell-reading-fuzz.sh` runs seeded random forms against the real shells.
- **The guard's awk runs under the macOS awk (BWK), and what is cheap in gawk or mawk is not cheap there.** Two things cost the square of the text on macOS and close to nothing on Linux. A string built a byte at a time with `s = s c`: BWK copies the whole string on every concatenation. And `sub`, `gsub` or `match()` with a pattern that can run long from every start: `sub(/.*\//, "", word)` is tried from every byte and runs to the end of the word from each, where a `~` test is one pass. One such `sub` in the lexer's `cscripts` view put a 64KB install at 38s on an M1, past the self-budget, so it was answered `UNDECIDED`; the scan view, the only one `scan-cost.sh` timed, was linear the whole time (fixed in v2.18.1). So a string built from the command's bytes goes through the builder (`sb_reset`, `sb_add`, `sb_get`, the same lines in every awk program that needs them), a regex function is not run over a command-sized string where a `~` test or an index answers, and `scripts/measure/scan-cost.sh` times every view of the lexer beside the whole gate. "Linear" is a claim about the shapes that file measures, on the host it ran on. Measure on macOS before writing it: Linux showed nothing for a release.
- **Quotes and backslashes are read the way the shell reads them.** Inside double quotes backslashes pair up; outside quotes a backslash escapes the next byte, and an escaped operator (`\;`, `\|`, `\&`, `\!`, ...) is a character, not syntax; there are no escapes in single quotes; `!` and `{` open a statement only where a statement starts; an escaped newline and a newline inside quotes do not end a statement and are joined before anything splits the command into lines. Each earlier approximation blanked text the shell executes, which is a bypass, not a false negative to tune. `scripts/test/scan-contract.sh` holds the rules as a runnable reference.
- **`advisory.log` is derived from `SAFEDEPS_HOME`, never from its own variable.** It is not just a log: `re-check` reads it as the oracle for whether an approval ever happened, so a movable path let the same environment that forges a ledger entry also supply its provenance (measured — the forgery flag disappeared). Record and ledger move together or not at all. Moved advisory sources (provider URLs, closure fixtures, a non-default ledger TTL) stay allowed and are announced there once per run: a run that answered from a mirror must not look like a run that answered from OSV.
- **No SaaS dependency** — local CLI + public DBs only. The tool itself has **zero npm dependencies**; keep it that way (it is a security property, not an oversight).
- The ledger is a same-user convenience cache, **not** a security boundary against a same-user attacker (until signing/re-query lands). Do not document it as one.

## Hooks

See the `skill-hook-authoring` skill for the full payload/decision schema. Essentials:

- Read `tool_input.command` (single field). `permissionDecision` is `allow`/`deny`/`ask`. `updatedInput` rewrites the command but is **Claude-only** — gate it on engine.
- `chmod +x` every hook and commit mode `100755`; a missing exec bit is `Permission denied` in every session.
- **Registration has one channel: the installer.** `SKILL.md` does not declare hooks, and that is a decision, not an oversight. Claude does document skill-frontmatter hooks (`hooks: {PreToolUse: [{matcher, hooks: [{type, command}]}]}`), but they are **scoped to the skill's lifecycle — they only run while the skill is active**, and this gate has to judge every Bash call whether or not the skill was invoked. So the documented form cannot do this job, and a second declaration of a registration is a second thing to keep true. The smoke drift check deliberately fails only on the legacy `script:` shape that no schema reads; it does not forbid the documented shape, because blocking a working feature by grep is not the same as removing a dead one.
- The registered command for both events is the entry shim `scripts/safedeps-hook-entry.sh pre|post`, not the hook scripts directly. The shim turns a broken hook source (mid-merge checkout, crash, missing file) into an explained fail-closed deny. It relies on one contract: **the real hooks exit 0 on every designed path** (decisions travel as JSON) — never add an intentional non-zero exit to a hook script. The shim also answers for its own stops: bash exits 128 (3.2) or 254 (5, after about 15 seconds of retries) when it cannot start a process, both engines read either as non-blocking, so an EXIT trap turns any exit the shim did not choose into an explained exit 2. Every designed exit sets `answered=1` first, and the messages are written with builtins, because a report that needs a process cannot report that no process can start.
- Hooks block clearly and explain; never a silent fallback.
- Installed copies under `~/.claude`/`~/.codex` are symlinks to this repo — edit the repo, never the installed copy.

## Testing

- Two commands, one runner (`scripts/test/run-all.sh`). `npm test` is the development run: every battery except the quick scan-failure census and `effect-trace-grid.sh`. `npm run test:release` runs every battery, those two included. The two left out took most of a release's CI time (v2.18.0 on macOS: the census 4,324 of 7,166 seconds, and `effect-trace-grid.sh`, which waits for it, 2,840), and both measure what a release ships. A change that reaches the scan readings or the effect gate runs them by name: `scripts/measure/scan-failure-census.sh --quick`, `scripts/test/effect-trace-grid.sh`. Keep both commands green.
- `run-all.sh --list` prints the batteries a run would start, with `--release` or `--group NAME` as for a run.
- The batteries run in parallel. They keep their state apart: each makes its own mktemp root, points `HOME` or `SAFEDEPS_HOME` into it, and starts its fixture servers on a port the kernel picks. Measured with a fresh `HOME` and `TMPDIR`, a full run left only npm's own cache and logs in the inherited `HOME`. A new battery keeps the same isolation, or it cannot run beside the others.
- The runner never takes the whole machine by default. At most `SAFEDEPS_TEST_JOBS` batteries run at once, and the census runs that many guards. The default is half the CPUs, rounded up. Raise it on a dedicated machine, or set it to 1 for the least load. Developer machines are shared: an uncapped run on a 16-CPU Mac already at load 100 took it past 300. Run alone, the census takes the same default, and `--jobs N` overrides it.
- Two batteries start only after the census finishes, because a busy machine turns them red without a defect and the census is what loads the machine: `self-budget.sh` times the guard's answers against its budgets, and `effect-trace-grid.sh` needs an npm install to write its lockfile inside the wall-clock second the pre-guard ran in. A run without the census has nothing to wait for, and they start in order.
- CI splits the release run into five test jobs per OS, so its wall clock is the longest job rather than the sum. Five, because GitHub runs at most five macOS jobs of one account at once (https://docs.github.com/en/actions/reference/limits, read 2026-10-05); a sixth would wait for a free runner. `run-all.sh --group a`, `--group b` and `--group timing` each run on their own runner (`timing` holds `self-budget.sh`, `effect-trace-grid.sh` and `install-dir-differential.sh`, which a loaded runner turns red without a defect, and nothing that loads it); the census runs in two shards (`scan-failure-census.sh --quick --shard I/2 --out DIR`), each making every case's clean and counting runs and every second failing run. A `verdict (<os>)` job then checks, with `scripts/test/ci-verdict.sh`, that the jobs of that OS ran every battery with a CI group once, and that the shards made every run of the census once and left no failure mode idle (`scripts/measure/census-shards.sh combine`). `scripts/measure/census-shards.sh cover` is the list comparison behind the split: it lists the census's (case, mode, K) runs unsharded and per shard and fails unless the shards' union is the unsharded set. Which battery runs in which group is a column of `run-all.sh`'s table; a group added there needs its job in `ci.yml` and its name in `publish.yml`'s `ci-green`.
- Each battery writes its own log. At the end the runner prints every log in a fixed order, then one summary line per battery: exit code, `ok` and `not ok` counts, seconds, and the load at start and end. Then it prints the tail of each failed log. It exits non-zero when any battery exits non-zero or prints `not ok`, and it names them.
- `SAFEDEPS_TEST_SERIAL=1 npm test` runs the batteries one at a time, in the order of the old `&&` chain. When a battery fails only in parallel, rerun it this way before you call it a defect or a flake. `SAFEDEPS_TEST_LOG_DIR=<dir>` keeps the logs in a directory you choose.
- A security change needs **both** a bypass harness (the threat must DENY/REORG) and a regression check (normal installs still pass; no false positives on `echo`/heredoc/`npm run`/`npx`).
- **Cite counts a reader can reproduce from the repo.** "159 forms" measured in a scratch corpus is decoration — nobody can check it, and a number nobody can check reads as verification without being any. Quote the battery's own form count or `npm test`'s ok lines, or commit the corpus you counted.

### What to run, and where

Measurement time is the release's bottleneck. A judgment costs seconds on macOS, a battery row about ten, and a fix that reran everything on both platforms took three and a half hours of host time before a validator ran the same again. So each measurement runs once, at the level where it can fail.

- **Per change** (one plan's branch): the batteries the change reaches, once on macOS and once on Linux; one mutation control per fix, on a copy, where reverting the fix turns its new row red; and any measurement the plan's Done Criteria names. Nothing else.
- **Per release** (the integration tree, before main moves): `npm run test:release` on both platforms (the quick scan-failure census and `effect-trace-grid.sh` included), and the judgment grids, corpora and replays of the areas the release changed. These do not run per branch unless the plan's Done Criteria names one.
- **A validator** reads the worker's own logs on the hosts and checks them against the claim. Its own runs are counterexample probes the author did not write, and one control showing a probe can fail. It does not rerun the worker's batteries.
- **A second rejection of the same class stops the patching.** When review rejects one class of defect twice, the next round starts with a design judgment, not a third shape fix. The pipe check took three rejections before its design changed, and each one cost a full round of measurement.

The bypass-harness and regression rule above still holds for every security change; this section only says where each run happens.

## Verification hygiene

The verification procedure has its own shared state, and three defects came out
of it in one round. All three had the same shape: two actors each behaving
correctly, overlapping into a wrong result.

- **Run mutations on a copy, never in the plan worktree.** The validator is
  dispatched into that worktree and the author may still be working there, so
  both hold write access to one tree. Worse, if a mutation is restored with
  `git checkout -- <file>`, it discards *every* uncommitted change to that file,
  including the author's, and the file returns to a HEAD state that looks
  correct. Copy the tree (`git archive HEAD | tar -x -C "$(mktemp -d)"`), mutate
  there, and throw it away -- not restoring is the safest restore there is. "The
  worktree belongs to the validator" is a discipline someone has to remember;
  mutating a copy is a structure with nothing to remember. Use an archive, not
  `git worktree add`: a worktree is registered in the repository and stays
  listed until someone removes it, so copies made that way pile up beside the
  plan worktrees.
- **Sandbox names come from `mktemp`, not from `$$-$RANDOM`.** `$$` is constant
  within a run, so isolation rests on `RANDOM` alone, and `mkdir -p` succeeds on
  an existing directory -- a collision is undetectable rather than merely
  unlikely. That undetectability is the reason, so it does not need re-arguing
  when call counts change.
- **A test that suspends a process reaps it three ways.** An EXIT trap covers
  ordinary exits; a marker sweep at suite start covers SIGKILL, which defeats
  traps and is this repo's core scenario rather than a hypothetical; and
  spawning children with a cwd outside the worktree removes what the leak costs,
  since an orphan holding the plan worktree makes the close gate refuse to
  prescribe removal at finalize. (Measured, after review corrected it: `git
  worktree remove` itself exits 0 with a stopped process sitting in that cwd --
  the machine that refuses is kuma's live-cwd close gate, not git. The effect and
  the fix were right; the named cause was not.) Scope any sweep with a marker only your own children carry.
  A marker string shared by every run is not that: one run's sweep killed another
  run's fixtures, twice in one round. The marker carries the run's pid, and the
  sweep reaps only markers whose run is gone. Its name must not contain an older
  marker either, or a checkout still sweeping by that substring matches it.

### Citing a zero

A run that found nothing is a claim about a measurement, and three ways of
making that claim are wrong. Each of these was measured the wrong way first in
the round that produced this section.

1. **A zero from a harness with no control is not evidence.** If the check
   cannot fail, its silence says nothing. 27 clean runs were reported before the
   control was tried, and the control turned out to be broken itself.
2. **A trial whose condition was not measured is not an observation of that
   condition.** "Quiet machine" was inferred from who else was working; `uptime`
   showed load 19 during those runs. Record the condition per trial or the
   batches can neither be compared nor combined.
3. **Say whether a label came from measurement or from someone saying so.**
   Hearsay carries no sense of not having measured, so it passes check 2. A
   label that crossed between two people hardened at each hop while nothing at
   the origin had ever been measured -- and then a statistical test was run on
   top of it, which made it look verified rather than merely elaborated.

The failure mode behind all three: **elaboration feels like verification.**
Handling numbers produces the sensation of handling data, and the step that asks
where the input came from gets skipped entirely.

## Workflow

- Branch off `main`; do not commit to `main` directly.
- Do **not** commit or push unless asked. Use logical commits with clear messages.
- **Never resolve merge conflicts in the main checkout.** The installed hooks execute the main checkout live; conflict markers there blocked Bash machine-wide on 2026-08-04. Integrate in your worktree (merge `main` into your branch, resolve, test), then move `main` forward fast-forward-only (`git merge --ff-only`). The entry shim softens the blast, but the discipline removes the window.
- **Write commit messages through a quoted heredoc** (`git commit -F - <<'EOF'`), never `-m "..."`. Inside double quotes a backtick is command substitution, and this repo's messages quote install commands in backticks as a matter of course: a message about a bypass would run the bypass. The live gate caught one on 2026-10-01; do not rely on that.
- **A harness judges commands; it never runs them.** Feed a form to the guard as a payload. Do not `bash -c` it to "see what the shell does" -- the form is an install by construction. When shell semantics are the question, use an `echo` in place of the package manager.
  **The one exception is a battery that measures the package manager itself** -- what npm writes and where, what `npm rebuild` executes -- because no payload can answer that. `scripts/test/lockless-forms.sh` and `scripts/test/effect-trace-grid.sh` are the two, and both source `scripts/test/lib/npm-sandbox.sh`. `scripts/measure/manager-option-reading.sh` runs bun the same way, through consumer-forms: synthetic local packages only, every registry setting on a closed local port so any fetch fails, its own home, cache and global directory, and no inherited `npm_config_*` or `BUN_*` setting. Such a battery runs installs only when all four of these hold, and each is enforced in that file rather than remembered: every package is synthetic and packed by the battery; the registry is a fixture on 127.0.0.1, with npm's proxies pointed at a closed local port so any other request fails, and the gate lets that one registry through only by name (`SAFEDEPS_NPM_TEST_REGISTRY`, a loopback URL, announced in `advisory.log` on every run); the battery asserts at the end that the fixture saw requests for its own packages and nothing else; and it unsets every inherited `npm_config_*` before setting its own home, userconfig, globalconfig, cache and prefix, then checks with `npm config get` that the prefix is inside the sandbox before the first install. The last one was paid for: `npm test` exports npm's own configuration to its scripts, and an inherited `npm_config_prefix` sent the battery's global-install forms into the machine's real global prefix.

## Release procedure

A release is every step below, in order. The list exists because steps were
skipped and nothing noticed: v2.16.0 through v2.17.1 were never tagged,
released or published, so npm sat on 2.15.8 until v2.17.2 caught it up; v2.17.2
shipped with no ROADMAP entry and a stale "current" line; and tags and a
publish went out while ubuntu CI had been red for eight pushes. Do not start a
release without the intent to finish it, and do not report one finished while
any step is open.

1. **Integrate in a worktree.** Merge every finished plan branch into
   `plan/release-vX.Y.Z` and resolve conflicts there, never in the main checkout.
2. **Bump the version once.** `package.json` `version` and `bin/safedeps`
   `SAFEDEPS_VERSION` together (see Version SSoT). A change that moves a verdict
   is a feature for this purpose: minor, not patch.
3. **Record it.** A `ROADMAP.md` section for the version -- what changed, how it
   was verified, measured numbers with the conditions they were measured under
   -- and the same change in `ROADMAP.ko.md`. Update the "current: vX.Y.Z" line.
   Update README, ARCHITECTURE and SKILL, with their `.ko` mirrors, wherever a
   stated proposition moved. Credit issue reporters.
4. **Run the consistency audit** (next section) and read its ceiling. Then have
   someone other than the author re-read the changed propositions.
5. **Test on both platforms before anything leaves the machine.** Run the
   release tree, not a plan branch, on two machines, and record `uptime` beside
   each run:
   - **macOS:** `npm run test:release`.
   - **Linux:** a Debian or Ubuntu machine -- a VM, or an `ubuntu:24.04`
     container -- with bash, jq, procps, git, node, npm, shellcheck, and the
     gitleaks version `ci.yml` pins (`GITLEAKS_VERSION`, checked against its
     sha256). Run CI's four Linux steps there, each as `ci.yml` writes it: the
     ShellCheck step's exact file list, `npm run test:release` (CI runs the
     same batteries split into jobs; see Testing),
     `./bin/safedeps scan secrets --repo`, and the package-contents step
     (zero runtime dependencies, `npm pack --dry-run`).

   A step the Linux machine cannot run is named in the ROADMAP section with the
   reason, and step 8's CI run carries it. v2.18.0 ran the full suite on a Debian VM
   and left the other three to CI after the push; that is the form to record,
   not to leave unsaid. CI is the authority either way: it runs on GitHub's
   runners from a clean checkout. This step exists to keep a red tree off `main`:
   Linux-only failures (GNU `stat -f`, the 128KB `E2BIG` limit, ext4 directory
   order) were invisible on macOS and kept CI red for a month.
6. **Run the release gates.** The package has zero runtime dependencies
   (`jq '(.dependencies // {}) + (.optionalDependencies // {}) | length'
   package.json` prints 0), `./bin/safedeps scan secrets --repo` passes, and
   `npm pack --dry-run` lists only what `files` allows. `scripts/release-gates.sh
   --strict` is not the gate for this repo, because it cannot pass here: its
   dependency audit needs a lockfile, a package with no dependencies has none,
   and the audit exits 2 without one on every machine. Its install-guard check
   also fails wherever safedeps is not installed. Both were measured on v2.18.0,
   and the first has been true since this step was written; the step said
   "passes" and no run of it is recorded.
7. **Move main forward.** From the main checkout, `git merge --ff-only
   plan/release-vX.Y.Z`. The installed hooks now run the new code: push one
   benign command and one install through `scripts/safedeps-hook-entry.sh pre`
   and read both answers before going on.
8. **Push and watch CI.** `git push origin main`, then wait for the run on that
   commit. Every job must be green: per OS, `batteries a`, `batteries b`,
   `batteries timing`, `census 1/2`, `census 2/2` and `verdict`. Red stops
   the release: fix forward, and do not tag a red commit.
9. **Tag and publish the GitHub release.** An annotated tag `vX.Y.Z` on the
   green commit, pushed (the push starts step 10's publish), and
   `gh release create vX.Y.Z --notes-file <notes>`.
   The notes cover every user-visible change since the previous tag (derive them
   from `git log <previous-tag>..vX.Y.Z` and the ROADMAP section): security
   fixes first, each with what could get past before and how it is verified
   now, then fixes, then anything a user has to do. Then read it back:
   `gh release view vX.Y.Z --json isDraft,isPrerelease,tagName` must show
   `false`, `false` and the tag, and `gh release view --json tagName` (the
   latest release) must name it. A draft is not a release: users and
   `releases/latest` never see it.
10. **Publish to npm.** Pushing the tag in step 9 starts
    `.github/workflows/publish.yml`, which publishes by trusted publishing:
    npm accepts the job's GitHub OIDC token, so there is no npm token, no
    login and no 2FA prompt, and npm attaches provenance. Watch it:
    `gh run list --workflow publish.yml -L 1`, then `gh run watch <id>`. The
    run must be green. Its jobs, in order:
    - `ci-green` reads the CI run on a push to `main` for the tagged commit and
      stops unless the run and every job step 8 names concluded `success`, on
      both OSes. It also stops on a job in the run it does not name, so a job
      added to `ci.yml` without its name here stops the release instead of
      passing unread. It does not run the suite again. A tag pushed before CI
      finished fails here; rerun it with `gh run rerun <id>` once CI is green.
    - `publish` checks that npm is at least 11.5.1, that the tag, `package.json`
      and `bin/safedeps` name the same version, runs `npm publish --provenance`,
      then reads the release back from the registry: the version's
      `_npmUser.trustedPublisher.id` must be `github`, its
      `dist.attestations.provenance` must exist, and the published tarball's
      file list must equal `npm pack --dry-run` of the tag. The registry can
      answer 404 for minutes after a publish (v2.18.1, run 37265447356: five
      minutes of 404 on the runner), so each try asks the version document and
      the package document with a fresh query string and no-cache, for up to
      20 minutes. A failed `npm publish` and a failed read-back print different
      errors: the second says the version was published.

    Then confirm it yourself: `npm view @aldegad/safedeps version` is X.Y.Z, and
    `npm view @aldegad/safedeps@X.Y.Z dist.attestations.provenance.predicateType`
    prints an SLSA provenance URL. A failure at `npm publish` (ENEEDAUTH, 403)
    means the trusted publisher on npmjs.com does not match this workflow; check
    it against the setup below, then rerun. A failure in the read-back comes
    after the publish: the version is already published and cannot be published
    again. Read `npm view` first, then fix forward in the next patch. Do not fall back to publishing
    from a laptop. That needs the owner's login and 2FA and ships without
    provenance, so it is the owner's decision, and the ROADMAP section says so
    if it happens.

    **One-time setup on npmjs.com (owner, logged in).** Package
    `@aldegad/safedeps` → Settings → Trusted publishing → GitHub Actions, with
    the fields exactly as below (npm does not check them when they are saved,
    and a mismatch first shows as a failed publish):
    Organization or user `aldegad`, Repository `safedeps`, Workflow filename
    `publish.yml`, Environment name `npm-publish`, and under Allowed actions
    select `npm publish` (a connection created after 2026-09-03 allows only
    `npm stage publish` until it is selected). A connection cannot be edited,
    only deleted and created again, so renaming the workflow file or its
    `environment` means doing this again. On GitHub, the `npm-publish`
    environment allows deployments only from tags matching `v*` (Settings →
    Environments → npm-publish → Deployment branches and tags; set on
    2026-10-05). npm checks only the workflow filename and the environment, so
    without that rule anyone with write access could run the workflow from
    another ref and publish. After the
    first green publish, Settings → Publishing access → "Require two-factor
    authentication and disallow tokens" closes the token path; that and staged
    publishing (`npm stage publish`, approved with 2FA) are the owner's choices.
11. **Close the loop.** Reply on every GitHub issue the release fixes with the
    fix commit and the release link, and close it.

## Consistency audit (before release or doc changes)

```bash
# version SSoT
[ "$(jq -r .version package.json)" = "$(./bin/safedeps --json version | jq -r .version)" ] || echo "VERSION MISMATCH"
grep -rqiE 'current.*2\.[0-9]+\.[0-9]+' ROADMAP*.md   # sanity-check the "current vX.Y.Z" line is right
# language purity: English docs have no Korean prose (ko-link lines excepted)
for f in README.md ROADMAP.md ARCHITECTURE.md; do
  grep -vP '\]\(\./[A-Za-z]+\.ko\.md\)' "$f" | grep -qP '[\x{AC00}-\x{D7A3}]' && echo "KOREAN IN $f"
done
# concept presence, per file. `grep -lq` over a file list exits on the FIRST
# match, so the old form passed when ONE of three documents still carried the
# concept -- it could only catch "all of them lost it at once", never drift
# between them. AGENTS.md is in the list because it owns the invariants.
for f in README.md README.ko.md ARCHITECTURE.md ARCHITECTURE.ko.md SKILL.md AGENTS.md; do
  grep -qi 'inert\|--ignore-scripts' "$f" || echo "inert-install missing from $f"
done
npm test
```

### What that check cannot do

It answers "is the concept absent from a file", not "do these files state the
same proposition". Measured against the real v2.16.1 drift, where AGENTS.md got
a liveness qualifier and the other documents kept the old file-existence
reading:

- **False negatives, 2 of 3.** Both ARCHITECTUREs were drifted and both already
  contained the word `pid` -- from an unrelated paragraph about the budget
  deadline killing a process tree. A per-file vocabulary check would have
  flagged only README.
- **False positive, 1.** After the fix, README.md states the new proposition
  correctly without using `pid` or `liveness` -- it is user-facing prose and says
  "the process that wrote it is gone" on purpose. A vocabulary check turns it
  red, and the way to clear the red is to plant jargon in user-facing prose,
  which the Docs section above forbids. The check and the convention would push
  against each other. (Cross-validation corrected this from 2: ARCHITECTURE.ko.md
  does use `pid` in that paragraph, so it would not be flagged. The count is the
  kind of claim this very section warns about -- re-derive it before quoting it:
  `git show 9b43aee^:README.md | grep -ci pid`.)

The cause is the direction of the approximation: a check like this approximates
a proposition by its vocabulary, and every document layer states the same
proposition in different words on purpose.

So the layers are:

1. **Concept absence** -- the loop above. Real, and this is its ceiling.
2. **Proposition declaration** -- have each document declare which version of a
   proposition it reflects, and bump the declaration when the proposition moves.
   Better than "did the commit touch all of them", because a declaration is an
   explicit claim by the author rather than an incidental co-edit. Not built.
3. **Proposition agreement** -- not mechanizable. Re-review owns this: another
   person reading the same object. That is a design decision, not a gap. Every
   defect in the v2.16.x round -- a fail-open early return, this prose drift, and
   a prescription written without opening the check it prescribed -- was invisible
   to any grep and was caught by someone re-reading.
