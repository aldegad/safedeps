# AGENTS.md — safedeps

Conventions for agents (Claude Code, Codex CLI) working in this repo. Claude Code reads this through the `CLAUDE.md` symlink. Edit **this** file, not `CLAUDE.md`.

safedeps gates development dependency installs (npm/pip/cargo/go/gem/maven/nuget) with OSV-backed advisory checks, an approved-spec ledger, and post-install reorg rollback. Full design: [`ARCHITECTURE.md`](./ARCHITECTURE.md).

## Engine support

Claude Code + Codex CLI only — not Grok/Hermes yet. When a hook capability differs between engines, **detect and branch; never assume parity.** Codex sends `turn_id`/`model` in the hook payload; Claude does not.

## Architecture invariants (do not break)

- **npm enforcement authority = the PostToolUse effect gate** (lockfile closure vs ledger + OSV batch). The PreToolUse command guard is a fast advisory/UX layer, *not* the authority. **It reads npm's two records of a project install — `package-lock.json` and the hidden `node_modules/.package-lock.json` — in one directory, chosen before the command runs by asking npm: `npm prefix` and `npm root`, run where the command runs npm and with the statement's own arguments and environment (`rust/src/ask.rs`).** **The ask never runs the command's code.** It is always the hook's own npm on the hook's PATH, and a name that chooses code when npm starts (`PATH`, `NODE_OPTIONS`, `NODE_PATH`, the OpenSSL and dynamic-loader settings, `BASH_ENV`, `npm_config_node_options`: `ask::code_name`) is never carried, whatever the command says. The ask used to carry them, and `PATH=<dir> npm install x`, `NODE_OPTIONS=--require=<file> npm install x` and `<dir>/npm install x` ran the command's code three times per judgment, a command the gate then denied included. A gate must not run a command's code to decide whether to let it run. Do not answer that question from the command's text again. The ask's own flags go after the command's words, so npm is not asked when those words would take them as a value or an operand (`npm install x --cache` made npm create `--json` in the project; `npm_ask_words_end` in `rust/src/manager.rs`), and each ask names a cache in its own scratch directory, because npm creates its cache directory on start. The install itself no longer creates `--ignore-scripts` after a one-statement `npm install x --cache`: the core denies that command as `UNDECIDED` instead of sending a flag npm would take as the cache directory (`end-flag-not-an-option`, below). The Bash guard sent it, as 7d66f8c did. Two copies of npm's rules each disagreed with npm and each disagreement was a silent pass: the named directory itself sent the gate to `src` while npm wrote the project's lockfiles, and a workspace resolver that resolved symlinks climbed to a root npm did not. **An install counts as read only when the directory the gate read shows this call's install trace; prediction chooses where to look, never whether it was covered.** Just before the command runs, the pre hook touches a baseline file and notes the inode of both lockfiles there; the post hook counts a lockfile whose modification time is later than the baseline's, at the resolution the filesystem keeps, or one with another inode, as the trace (`Install::settle` in `rust/src/post/trace.rs`). Where neither shows one it records `UNGATED` as the check that found nothing ("no install trace in <dir>: neither npm lockfile there is newer than the baseline taken before this command or has another inode") and runs no rebuild there. The record does not guess where the install went: "the install landed elsewhere or installed nothing" was a cause nobody had checked. Three rounds made the prediction better and each left a silent pass (a `cd` that never ran, `command cd`, a symlinked member); with the trace, a wrong prediction is a record. Do not compare content or whole seconds: a reinstall of what is already there rewrites the hidden lockfile with the same bytes, often inside the second the baseline was touched in. Two or more lockfile-writing npm statements share one trace only when nothing but inert statements (`echo`, `printf`, `tail`, `head`, `grep`, `ls`, `cat`, `true`, without redirection or substitution) runs between them and none relocates itself; otherwise the command is `UNGATED`, because the first one's trace hid the second one landing elsewhere. A `cd` that may not run (after `&&` or `||`, or inside a compound command) is followed only along the `&&` chain after it; `cd X || exit` is followed. Where npm cannot be asked or does not answer within its deadline, and where the command carries a word the shell decides at run time, the target is `?`, the reason is recorded, and the gate looks in the cwd. npm masks anything shaped like a UUID or a token in what it prints, paths included (11.19.0, measured), so a masked answer is never used as a path: it stands for the one directory from the cwd up that reads the same, and is `?` otherwise. npm's answer covers every `.npmrc` it reads. The environment it is asked with is every name the statement and the statements before it export, assign or unset (as `env -u`), not only `npm_config_*`, except the code names above: `export HOME=<dir>` makes npm read `<dir>/.npmrc`, and an export branch that carried only npm settings missed it (XH1-XH5). Whether npm writes a record where it installs is a separate question npm cannot be asked before the install, so the pre hook still reads `global` and `location` in the project's and the user's `.npmrc` for that, and only for that: it can turn a read install into an `UNGATED` one, never choose a directory. `scripts/test/install-dir-differential.sh` holds the gate to `npm prefix` over 237 layouts. **This holds inside the hook budget only** — both hooks are killed at their registered timeout (30s) and the effect gate's work is network- and project-bound, so do not write "npm is covered" without that qualifier. **The range is measured, so quote it rather than the word "structural"**, and say which gate it was measured on. The Bash gate crossed 30s at a closure of *four* packages until v2.16.0 stopped re-reading the whole ledger per package, and it crossed near 390 packages after (30s measured 2026-08-04). Those figures belong to the Bash hook, measured on macOS against the real network, and nothing here compares them with the core's. The core's post backstop was measured on 2026-10-07 on an Apple M1 (8 CPUs, 16 GiB, macOS 15.6.1) at commit 188ccdf with `scripts/measure/effect-gate-cost.sh`, which runs `scripts/measure/core-post-cost.py`: a synthetic `package-lock.json` (v3) of N packages is handed to the core's public post, with a ledger that is empty or approves all N, and with the advisory caches prefilled or empty and served by a fixture on 127.0.0.1. No install command runs. The first measured size to exceed 30 seconds was 128,000 packages in all four conditions (33.55 to 72.92 seconds), and 64,000 took 12.77 to 29.60 seconds. Each cell is one observation, and the sizes between were not sampled, so these samples establish no exact package-count limit. The harness let each run finish and compared its time with 30 seconds, so the runtime's kill was not measured. The fixture is not the real OSV or CISA service, so their latency, response sizes and limits were not measured, and rollback, rebuild, a hidden lockfile, a real node tree and the registered entry shim are not in it. The load average was 2.93 to 7.26, and the binary still printed 2.18.1. Re-measure before writing a number — the crossing moves with host, network and cache, and a number from someone else's machine is decoration.
- **The effect gate cannot deny, so its answer to "I did not finish" is a record, not a block.** The install already ran. A rollback writes its journal entry *before* the first destructive act and clears it after it has reported itself, so an entry that outlives its run is itself the report — the next PostToolUse turns it into a durable incident plus a `REORG INTERRUPTED` line in `reorg.log`. **"Outlives its run" is a liveness claim, not a file test**: a rollback in progress has its own entry on disk by design, so the report is gated on the entry's recorded pid being gone (v2.16.1 — an unrelated Bash call used to read a live entry and report a working rollback as interrupted). The state lock cannot stand in for that check; it is released before the rollback begins. pid reuse is settled by process start time, and an owner that cannot be resolved counts as gone, because the failure to prefer is noise over silence. The core reads the owner's state without starting `ps` (`rust/src/post/process.rs`: `proc_pidinfo` on macOS, `/proc` on Linux), and a query that returns no usable data is the unresolved case and says so (`owner-native-query-failed`). A zombie counts as gone too (v2.16.2): it keeps its table entry and its start time, so it clears both other tests, and it never goes away — reading one as alive loses the report permanently rather than delaying it. **A stopped owner is a third answer, not a gone one** (v2.17.0), so "gated on the pid being gone" is not the whole rule: a suspended process has not died and is not progressing, and calling it either way reproduces one of the two defects above. It is reported with its pid still alive, and the report says the owner pid is stopped. Stopped is judged only after the start-time check confirms the pid still belongs to this entry — ahead of it, any stopped process holding a recycled pid turned a genuinely interrupted rollback into "suspended, resume it" (caught in review). Do not move the record back after the work; that ordering is the whole defect (measured: a kill mid-rollback left `reorg.log` at zero lines with the project already reverted). And do not sell this as atomicity — safedeps does not own the atomicity of an npm tree rebuild. **A rollback runs no package manager.** It restores the files it snapshotted and removes the project's own `node_modules` only when that is a real directory and the command is seen to have written the project's node tree (an install trace in the directory, a node manifest or lockfile that differs from the snapshot taken before the command, or a `node_modules` that differs from the pre hook's listing or is newer than that snapshot; compared before the restore, since the restore goes to the confirmed snapshot, which can be older, and by each file's own time at the resolution the filesystem keeps, never whole seconds: the Bash guard needed `find -newer` for that, because bash 3.2's `-nt` compares whole seconds), so every path it writes or removes is one it checked itself. The second condition keeps a rollback that has nothing to roll back from taking the project's dependencies with it. The closure is judged whether or not the command changed it (no install trace means `UNGATED` and no rebuild, not no judgment), so a command misread as an install, in a project whose closure was never approved, reaches the rollback, and the old reinstall had been hiding the removal. **The command-independent backstop (a command the pre hook did not read as an install but the backstop pattern, `backstop_re` in `rust/src/grammar.rs`, matches) judges the closure only where that command left a trace in the cwd's node tree**: the pre hook writes an entry named by the call's top-level `tool_use_id` (both engines send it in PreToolUse and PostToolUse, measured) with the inodes of both npm lockfiles and `node_modules`, the lockfiles' status change times, and a baseline file (each value the path's own and, through a symbolic link, its target's: a write through a linked lockfile changes only the target's, and an entry that held the link's alone missed it, lumi r2 S1), and the post hook of the same call looks for another inode, a lockfile or `node_modules` that appeared or went away, a lockfile change time that is not the recorded one, or an entry under `node_modules` whose status change time is later than the baseline's (`backstop` and `walk` in `rust/src/post/trace.rs`; the walk follows a link at its root and no other). The baseline is set two seconds back unless the baseline file and every part of the project's node tree it reads, link targets included, show a time below the second: set back everywhere, it counted a pull 0.3 seconds before a grep as the grep's trace (lumi r1 R1), and left in place where one part was enough, it missed a write into a whole-second `node_modules` beside a nanosecond lockfile (lumi r2 P3). The post hook reads the call's entry before any record: the pre hook writes a record or an entry for a call, never both, so a call with an entry is judged by its entry alone, whatever the entry holds, and no record is read or removed for it; read after the records, a grep was judged by another call's record whose snapshot was gone and rolled the project back (lumi r3 REC), and an entry taken in another directory than the post hook's sent its call on to the records (MM, lumi r4). Only a call with no entry (no `tool_use_id`, or an entry the pre hook could not write) reaches the backstop through a record, and it counts as traced there, so it can be rolled back. Which install record is an install call's own is its `tool_use_id` (below). The post hook reads only its own call's entry. An entry whose post hook never ran (a call refused after the pre-guard let it through, one cancelled while it runs, or a failed one on Claude Code where `PostToolUseFailure` is not registered) moves no later call's baseline and is swept after a day; when entries were read by project and command, the oldest one made every later call judge from the one before it (lumi r1 P1). An input with no `tool_use_id` gets no entry and is judged as before, a trace. No trace is a `BACKSTOP UNTRACED` line in advisory.log and nothing else. Its pattern matches `grep -n "npm install" README.md`, and before this a grep rolled back any project whose closure had become unapproved outside the gate (a pull, an expired approval) and removed its `node_modules`. Three conditions that read npm's hidden lockfile to keep `node_modules` failed review the same way, the record not describing the disk, so do not put a record back in its place. What the check cannot settle (no entry, a gone baseline, a walk that fails or passes its deadline, five seconds, `SAFEDEPS_BACKSTOP_WALK_SECONDS`, which can be lowered and not raised) counts as a trace, which is the old behavior; the reinstall is the next install, which the gate checks like any other, and a target that is a symbolic link is refused and named (`REORG REFUSED` in `reorg.log`), never followed. Each npm a rollback used to run reached past the project some way the gate had not predicted -- a linked `node_modules` (`npm ci` empties whatever it resolves to), the walk up to an enclosing project, a linked lockfile, a workspace outside, a `file:` dependency's scripts and bin links -- and three rounds of review found a new one each time, so do not put npm back into the rollback. The refusal is a warning on the rollback, not a stop. The rebuild after a verified inert install is not a rollback, and it is the one place safedeps still runs npm. It runs only when no root npm file is a link (`reach_blocker` in `rust/src/post/report.rs`) and the whole tree passes the check described under inert install, and it carries `--global=false --location=project --prefix <the project>`. A rebuild skipped for a link reports the link as the reason, never as a place to run npm, and a reason is a fact read from disk, never what npm would do with it ("npm would work in an enclosing project" was false where a real npm stayed put). The rollback and the interrupted-rollback report say what they did and what the files are, and give no reinstall command: three rounds of review found advice that sent the user's npm outside (a missing `package.json`, a workspace outside, a workspace member whose bare `npm ci` empties the workspace root), each time past a judgment that was silent.
- **What a rollback, a refused step, a skipped rebuild and the unfinished-rollback report say is a closed set of line forms, and the output is what is checked.** Every such line is printed by a function in `rust/src/post/report.rs` that runs its own check when it is called and prints what the check returned: a path and what a test of it returned, the OS error number an operation returned or that it returned none, or one of safedeps' own acts. No line names `cp`, `rm` or an exit status, because no such program runs: a failed copy says `copy returned OS error N`, `copy returned without error` or `copy returned an error without an OS code`, and a failed removal says the same of `removal`. The Bash hook printed `cp exit 1` and `rm exit 1`. A line never says what a path contains, why something happened, what npm would do, or what to do next. The same report was sent back three times for a false sentence, and each time the false part was a clause attached behind a true fact ("is still there, with whatever this install wrote in it" after an `rm -rf` that had removed most of it; "install scripts have not run" after the command's own `npm rebuild`; "most likely the hook hit the runtime's timeout" after a failed `cp`). A vocabulary check did not see them, and reading did not converge. So `scripts/test/e2e.sh` hands every line the post hook prints to `scripts/test/lib/report-oracle.sh`. A line is a frame matched whole, or it matches one anchored form and has that form's claim checked again on disk, or the run fails. The form table fails on a form no line matched. The reorg.log entries are read with the same grammar, not as a superset of the message: the oracle builds the entries the message calls for and the appended entries must be exactly those (advisory.log: only its two rollback lines, each a repeat of message lines). The oracle also reads the disk around a rollback (every changed top-level entry has a step line; "changed nothing" and `kept` against the listing and the pre-hook checks), a call that prints no message appends nothing to reorg.log, and prose is allowed per block with a cap. **A fact the hook and the oracle both read is read by the oracle with a different method** (a Python walk, `scripts/test/lib/report-oracle-read.py`): they once ran the same wrong check and agreed (F1 a find without `-H`). **Neither reads the shell command for a report line.** Whether it carries `--ignore-scripts` was read by both, the hook with the install grammar and the oracle with `shlex` and `npm config get`, and three rounds found both wrong on the same commands (F2 a substring test, F3 an assignment or an export of `npm_config_ignore_scripts` and a project `.npmrc`), because the two readers shared one model of a shell statement. So the line is a comparison of two strings, and a reader of the command is not put back. `scripts/test/report-mutations.sh` is the control: the 44 mutations named in `scripts/test/lib/report-mutations.json`, each applied to a copy of the core's source built from an archive, never to the tree. Each names the harness that runs it and the selector it runs. It builds serially on the host runner's slot and is run by name; neither `npm test` nor `npm run test:release` starts it. A new line needs a fact function, a form with its check, and a row that prints it, in one change. Rule sentences live in the README, not in messages. A restore or a removal that fails is a line and the rollback goes on (in the Bash hook a bare `cp` under `set -e` ended the hook mid-rollback; in the core an error is a value the report states). "safedeps added --ignore-scripts" is said only when the command the post hook received is byte for byte the command safedeps wrote (`updated_command` in the snapshot's meta); the pre-guard's record alone is "asked". A hook that did not find this command's record (the backstop) says none of the three, because the record can exist under a key it did not compute (bamdori r18 F4: `sh -c 'npm ci'`, rewritten, got "did not add"); the oracle finds an unused record by what it holds, not by the hook's key, and checks each record against the rewrite the pre-guard printed. A rewrite whose record cannot be written is not sent. A record the post hook cannot read gets no `--ignore-scripts` line and one `advisory.log` line, never "did not add" (that fallback was a silent one); the oracle learns of the failed read from the row that causes it, not from the hook. **A line is said only from a fact the record states, as version 2** (`"record": 2`, v2.18.0): `did not add` needs `ignore_scripts_injected` false, `added` and `asked` need it true and `updated_command` a string, and every other shape (no file, no version or another, a string, a null) says no line and names the record in `advisory.log`. No branch that says a line is reached by a default. Four rounds found a record answered by its missing field (F4, a failed read, a non-object, bamdori r22 U3), and a v2.17.2 false does not mean no rewrite (U3b), so do not add a fallback that turns a missing fact into one of the three. The oracle reads the same rule from the parsed record in Python, not with the hook's own reader. **A record belongs to one call** (v2.18.1): the pre hook keeps it as `pending/id-<tool_use_id>.json` (`rust/src/callid.rs`, the one reading of the id for both halves of the core), and the post hook of a call that names a `tool_use_id` reads that record and no other. Found by the directory the command ran in and the command with `--ignore-scripts` set aside, as v2.18.0 did, two calls of the same command that overlapped in the same directory each spoke from the other's record (bamdori r19 X1), a call whose post hook never ran left a record the next call of the command rolled back to, losing an edit made in between (O2), and the oracle, reading the record each call took, agreed. Do not put a lookup by directory and command back for a call that names an id, not even as a fallback for a record that is missing: that record is another call's. A call that names no `tool_use_id` keeps that lookup and both hooks say so in `advisory.log`; both engines send one (measured: Claude Code 2.1.288 and 2.1.289 `toolu_...`, Codex CLI 0.160.0 `exec-<uuid>`, the same in both hooks). The oracle reads the call from the hook input in Python and is red when the hook consumes a record that holds another call's id, and e2e runs overlapping calls (OV1, OV2, O2, MM). Records a pre-#5 pre-guard left (`current_state`, `current_snapshot_id`) are not read: they name no call, and a call one did not match ended the hook with no judgment. **A failed call is judged.** Claude Code runs PostToolUse only after a tool call succeeds and `PostToolUseFailure` after a Bash call that ran and failed, with the same `tool_use_id` and an `error` in place of `tool_response` (https://code.claude.com/docs/en/hooks, verified 2026-10-04), so the installer registers the post hook for both on Claude Code, and a failed install is judged and leaves no record. Codex runs PostToolUse after a failed Bash call too and documents no `PostToolUseFailure` (https://learn.chatgpt.com/docs/hooks), so its config gets PostToolUse alone. A call the user refuses after the pre-guard let it through still runs no post hook, and its record waits for the 24-hour sweep, where no other call reads it. A record whose snapshot has no meta file goes to the backstop, with one `advisory.log` line naming it and a headline that says the record was found and its snapshot has no meta file; the post hook used to exit there with nothing said, so the install was never judged (bamdori r23, since e315244). A record that names no snapshot (a damaged pending state) goes the same way, under a headline that says the record names no snapshot. So does a record that is not one JSON object, under a headline that says so: in the Bash hook its jq read under `set -e` ended the hook, and the record, left in place, ended it on every call of the command for 24 hours. Do not put any of these exits back. A record with no `project_dir` is judged in the payload's `cwd`, never the hook's own working directory, which judged a directory the command never ran in. The hash that picks the confirmed snapshot is always computed from the project being judged, never read from the record: a record naming X with Z's hash restored Z's confirmed snapshot into X (bamdori J), and the oracle, which read the record's hash too, agreed. A record's fields count only as strings: a `snapshot_id` of 5 names no snapshot. Each call claims a snapshot id of its own (`<seconds>_<dir hash>-<pid>`, created exclusively): one id per second let a second call write over the first's record and lockfile copies (bamdori r19 SAME), and `oracle_pre` is red on a pre-guard call that writes over a record that was there before it. The effect gate's rebuild warnings ("review it, then run `npm rebuild` yourself", "confirm with the user before") are instructions by design and stay prose: the oracle lists them by exact prefix and counts them, and their grammar is a later plan's. Do not write "no false line is possible": the oracle checks each line it reads, not which lines were chosen, and not a check that it and the code both get wrong.
- **A line says what a process or an I/O operation returned only as an `Outcome`, never as a number or a name a caller chooses.** This kind of defect came back three times. The report lines printed `cp exit 1` and `rm exit 1` for programs that no longer ran. Then the user-facing text named awk, grep and sed as the steps that had failed, and the backstop's walk said `failed (find exit 1)`, where no `find` ran and the 1 was an internal marker. The rebuild said `ran npm rebuild: exit 127` where npm had never started: a failed start was folded into the number 127, and a signal into 128 plus its number. Each repair fixed the sentence found, and the next one stood beside it. The third time a read-only judgment ran before the repair (verdict kongkongi-20261007-192121), and it showed that a list of names or of literals does not close the class. A literal the code already holds, `grep`, put in the copy line adds no new literal and passes a membership check, and `npm` is an allowed name that did not run. What is wrong is a message that states the result of something that was not observed, and no vocabulary shows that. So the design changed in four parts. **(1)** `crate::outcome::{Outcome, Action, Form}` (`rust/src/outcome.rs`) holds what was observed: a finished process with its real `ExitStatus`, a failed start, a failed status read, a deadline, or an I/O result. `Action` is a closed set (`Npm`, `NpmConfig`, `NpmQuery`, `NpmRebuild`, `Judgment`, `Walk(path)`, `Copy`, `Removal`), and `Outcome::describe(Action, Form)` is the one function that turns a result into words. No API takes a free actor string or an integer status, and `report::io_outcome` is gone. A signal is `terminated by signal S`, a failed start is `could not start npm rebuild: OS error N`, a failed status read is its own sentence, a walk that could not finish says `returned OS error N`, and a deadline is a deadline and never an I/O error. The rebuild's start and wait are two operations. **(2)** The oracle checks the advisory.log lines that carry a result, by form, against observations the test owns (`scripts/test/lib/outcome-oracle.py`, `ask-outcomes.py`, `rebuild-outcomes.py` and `backstop-walk-io.py`). Before this the oracle did not read advisory.log in general, so the `find exit` line passed every row. It still does not read it in general: only the walk's I/O line, the npm query, config and prefix failures that name a signal, and the four rebuild forms (`rebuild-start-added`, `rebuild-start`, `rebuild-signal-added`, `rebuild-signal`). **(3)** The exit gate generates the core's output exits from `rust/src` (test code excluded) and compares them with a committed list: the generator is `scripts/measure/output-sinks.py`, the list is `scripts/measure/output-sinks.tsv`, and the battery is `scripts/test/output-sinks.sh`, a development battery in `run-all.sh`. An exit is a source occurrence: a stream write, a file write or append, a call of the core's advisory or report writers, and, as boundary entries, an imported output API, an FFI declaration or a macro definition. Its identity is a count per (file, function, role, exit kind, callee, kinds of argument origin). Position, token order and a function's body are not part of it. Adding or removing an exit, or changing the origin kind of an argument to an exit that speaks to a person, is red. An unrelated line or an ordinary import is green. The list has 421 identities and 505 counted occurrences: 154 speak to a person, 94 are data (serializers, snapshots, copies, captured child output) and 257 are boundary. Three of the human exits take their text from the result renderer: `Report::rebuild` and the copy and removal lines of `Report`. **The gate is a lexical census, not a type or taint analysis and not a truth oracle.** It does not say the words are true within one kind of origin, it does not follow an origin across a function return, it does not read the body of an existing macro or foreign function, and it does not vouch for what a child process writes. **The rule: a change that adds or removes an exit regenerates the list in the same commit, and the list's diff is read.** Regenerating without reading turns the gate into a stamp. The battery has a control for each of its claims. Copies of the source with an added stdout write, stderr write, raw-identifier write, file append, direct log string, aliased write or platform-gated write, with a listed exit deleted or duplicated, or with a changed origin, must be red. An unrelated line, an ordinary import, a read-only open, comments, quoted data and test code must stay green. **(4)** What was not done is a broad migration of every message to a typed form. An enumeration of the core's string literals and an independent list taken from the binary's strings found this kind of defect only at the places already fixed, so part (1) holds those, part (3) holds new places, and part (2) holds the lines that carry a result. Of the 14 places that call `describe`, the gate could follow 3 (copy, removal and the rebuild) to a human-facing exit. The other 11 (the walk, the npm asks, the judgment's end) are read by other tests, and a change upstream of an exit that keeps the argument's kind is invisible to the gate. A dedicated result oracle (`scripts/test/lib/outcome-oracle.py`, called by `backstop-walk-io.py`, `ask-outcomes.py` and `rebuild-outcomes.py` from `scripts/test/e2e.sh`) reads the walk's I/O line, the npm ask lines that name a signal, and the rebuild forms. The walk's deadline line and the hung ask's `did not finish within` line are asserted by rows of `e2e.sh` and `lockless-forms.sh`, and the judgment's `ended without a usable answer (signal 9)` line by a row of `self-budget.sh`. The start-failure and status-read sentences of the npm asks are held by `ask::outcome_tests::wait_failure_is_not_a_deadline` and `outcome::tests` and by no row that reads a hook's output. The general grammar of `report-oracle.sh` does not cover those places. Held by `outcome::tests::claims_keep_observed_outcomes_distinct`, `ask::outcome_tests::wait_failure_is_not_a_deadline` and `post::trace::tests::walk_preserves_io_error_and_distinguishes_deadline`, and by e2e rows that make the real failure happen (an unreadable directory, an npm that deletes itself before the rebuild, a process killed by signal 9). Three source copies, each with one of the old renderings put back, went red at those rows (carenine, 2026-10-07).
- **A hook that runs out of time must answer before the runtime kills it.** The runtime's timeout is fail-open: the hook dies and the tool call proceeds. So the pre hook keeps its own smaller budget (`SAFEDEPS_SELF_BUDGET_SECONDS`) and denies when its judgment does not finish. The core runs the judgment as a child process of its own, in a process group of its own, and the parent owns the clock (`rust/src/pre/budget.rs`). **The deadline is read from the clock, never added up from the sleeps it asked for**: a loaded machine stretches every sleep, so the sum runs late by all the stretches together. The parent compares a monotonic `Instant` with the deadline each time it runs, so time already elapsed is never waited for again. That is a property of the comparison and not a bound on the answer. It asks for a 20 ms sleep between looks, and while the supervisor gets no chance to run, its answer is late too; no code bounds that. What absorbs the lateness is the 5 seconds between the ceiling and the runtime's 30. A stall longer than that lets the runtime kill the hook, and the call then proceeds unjudged, which is the fail-open this budget exists to avoid. So "must answer before the runtime kills it" is the requirement the design is built to meet, and it is not a guarantee. The Bash guard counted bash's `SECONDS` for the same reason, because bash 3.2 has no finer clock that costs no process. That clock is gone and the rule is not. **There are three outcomes, and the wording says which one happened.** The judgment answers. Or the deadline passes: "could not finish judging this command within its Ns budget". Or the judgment process ends before its deadline without an answer: "the judgment process ended without a usable answer (signal N)", with no budget wording, because the budget did not run out. Both non-answers are `UNDECIDED` denies. Keep them phrased as *undecided*, never as a detection: the two are different claims, and conflating them teaches people to route around the gate. **A stopped judgment process is not an exited one.** The supervisor waits to its deadline and then answers. It reads `si_code` of `waitid`, because macOS reports a stopped child to `waitid` with `WEXITED` alone. A supervisor that read `si_signo` took the stop for an exit and answered `UNDECIDED` at about 0.3 seconds whatever the budget (found on 2026-10-07 by a probe outside the core). It was the right verdict at the wrong time. Each way out of the supervisor's wait kills the whole process group (`reap_group`), so a process the judgment started does not outlive the supervisor's answer, unless the supervisor itself is killed first. **That budget is clamped below the runtime's, and the clamp is part of the boundary, not a nicety**: any value at or above the registered hook timeout hands the kill back to the runtime and restores the fail-open, and the motive to raise it (an `UNDECIDED` on a big command reads as "the budget is short") is ordinary enough that leaving it open is the same as leaving it off. The runtime timeout is 30 seconds and the ceiling is 25 (`safedeps-core budget-config` prints both, with the other numbers the batteries check against what the installer registers). Lowering stays free, and the clamp says out loud that it happened. **The same holds for `SAFEDEPS_BUDGET_ENGAGE_BYTES`**, which decides whether the budget runs at all: it is clamped to 4KB, because a tuning knob that can be raised without limit is an off switch. Turning the deadline off is a separate, differently named act (`SAFEDEPS_BUDGET_DISABLED`) that logs every use. The battery's mutation check needs it, and a test that cannot produce the unbounded case only knows it passes, not that it catches anything. Keep tuning and disabling separate levers. **The parent/child marker lives in argv, never in the environment**: as an environment variable it was a second, unnamed off switch (export it and the parent skipped the deadline, silently). The parent starts its child with `pre --budget-child`, and the environment cannot reach argv. A `SAFEDEPS_BUDGET_CHILD` in the environment is ignored and said so in `advisory.log`. Measured on the M1 host (alex-macbook-m1, 2026-10-07, command at nice 10 and a measured niceness of 15, load 7.52 to 6.79 at the start and end, not a quiet host): budgets of 2 and 6 seconds answered at 2.084 and 6.077 seconds, three runs of an over-large budget answered at 25.083, 25.094 and 25.091 seconds before the runtime's 30, a judgment killed before its deadline answered in 345 milliseconds, and a row that stopped the supervisor for the budget plus 0.5 seconds got `UNDECIDED` after 4,896 ms against a 4-second budget, 71 ms after the supervisor was resumed (`scripts/test/lib/native-budget-run.py`). Each is one observation, and none is a bound. Linux and WSL1 were not measured.
- **Two windows are left open, both read from the source and neither measured by running it.** After the pre hook's judgment process settles its last reading, it writes the snapshot, the pending record and the rewrite mark in that order. If the parent's deadline kills it inside that stretch, a half-written snapshot or pending record can stay beside the `UNDECIDED` deny. A kill during the readings leaves nothing. The Bash guard had the same window and a wider one, because it wrote the snapshot and the meta before it judged (the integration review of 2026-10-07 read it so). And a judgment killed while it holds `state.lock` leaves the lock: the next call removes one older than 60 seconds, and an install call that cannot take the lock before then is denied fail-closed (`StateLock::acquire` in `rust/src/state.rs`). The Bash guard behaved the same way.
- **effect-primary is npm-only.** pip/cargo/go/gem/maven/nuget stay on the v2.1 command-gate + reorg model until their closure resolvers land.
- **Inert install (Claude only).** The PreToolUse hook injects `--ignore-scripts` through `hookSpecificOutput.updatedInput`. The core reads each npm install from the lexer's structure of the text it stands in (`rust/src/inert/read.rs`). A statement whose command word is npm is an install, and which word is its verb and what npm makes of the rest is the manager reader's answer (`manager::Reader`, the tables the recognizers use). The flag goes at the first place, from the end of the last argument of each install (before a `--`, a redirection, a comment or the statement's end) back to its verb, where npm reads the statement with the flag there as it reads it without, and the option comes out true. The last argument is tried first because npm keeps the last value an option is given, so a later `=false` cannot outlast the flag there. A last word that takes the next word as its value (`--cache`, `-C`) took the flag there and the install ran its scripts, so a place is never assumed: each one is asked of npm's option tables (`Install::flag_after`). **No reader looks for a verb or an end in the bytes of a view.** The Bash rewrite did, with a search for the verb, an end finder that counted depth and backticks again, and two patches for what those missed, and each of its rejected defects was that reader reading a nested text with the outer level's quoting. Text nested in another is a payload (a `sh -c` or `eval` script, a substitution body), and it is read by asking the same question of the payload. A place in a payload is a place in the command only through the payload's source map, and only once it reads back: the text the payload came from, with the flag there, is lexed again, and the same payload must come out with the flag at its place. A place that does not read back is not placed. A word that says `npm` where the structure sees no command (`echo npm ci x`, `sudo npm ci x`, an array value, a word a parameter expansion holds) is not an install the rewrite read. The record sees it, and the floor below decides what it owes.
- **Every rewrite holds the floor**, 7d66f8c's rewrite, the one safedeps made before it read an install's words: the flag right after every verb, always, and for a command 7d66f8c appended to (one statement, no comment or heredoc: `inert_release_appends`), its flag at the end. 7d66f8c is a tree of this release cycle, not the published v2.17.2 (bb0787d). The floor's positions are kept in `rust/src/inert/floor.rs` as that rewrite's own search found them. They say where a flag goes and nothing else: not whether a statement is an install, where it ends, whether its `npm` was read, or what npm makes of its options. **Where the floor cannot be had together with the command's data and with npm reading the flag as the option, the whole command is `UNDECIDED` and no rewrite is sent.** The Bash guard sent the floor anyway. It wrote a flag into a heredoc body that another command reads as data, gave `npm install x --cache` a flag that `--cache` took as its value, kept the verb flag on `npm install true`, and recorded `npm -- ci -- x` as a downgrade. The core names the reason in `advisory.log`: `floor-outside-command`, `floor-not-an-option`, `floor-value-unread`, `end-flag-outside-command`, `end-flag-not-an-option` or `end-flag-value-unread`. The reason the user reads says that required `--ignore-scripts` flags could not be placed while preserving command data and how npm reads its options. The cost is plain: those commands are denied, and the user rewrites them. A record does not stand in for a flag, and the floor is not dropped to let the command run. A collision is settled before the readings are compared and before any state is written, so a denied command leaves none (`no-state-on-deny`). **The readings must agree.** Bash, zsh and dash read each statement from their own lexing, and where they end a statement or a word apart (a glob group, an extglob, a `}` zsh reads as a group close) their places differ. Then the command is `UNDECIDED` too, because no single edit is inert for every shell. The rows where the core answers apart from the Bash guard on purpose are `scripts/measure/core-intended-battery-rows.tsv` (per battery row, with its effect and reason) and `scripts/measure/core-intended-readings.tsv`. No row there is a weaker verdict. Say that of the rows in those tables, and not of the core in general: the owner decided on 2026-10-07 that the Bash and Rust guards are not compared on a corpus, and the criterion is the existing test sets running on the core.
- **A script the Bash rewrite could not read as the shell will is a payload the core reads.** A script handed to `sh -c`, `bash -c`, `zsh -c`, `dash -c`, another shell (`ksh -c`) or `eval`, with a backslash, a backquote or `$(` in it or not, is read at its own top level through the quoting the lexer removed (`script-payload-read` in `scripts/measure/core-intended-inert.tsv`). The Bash rewrite put the flag where v2.17.2 did in such text, right after each verb that a blank follows or that ends its line, and recorded the command as one whose flag nobody read. The core places the flag where it reads npm keeping it true, and it still records the command as one whose flag nobody read (`ignore_scripts_unread: true`), because the record reads the bytes and not the structure. `unread_case_native` in `scripts/test/smoke.sh` holds 13 commands to their measured rewrites. A heredoc body piped to another command is not read as a payload. It keeps v2.17.2's flag after each verb that a blank follows or that ends its line, and a verb no blank follows gets none: in `npm i x && sh <<E | tee log` with `npm ci&&true` in the body, the install gets its flags and the body gets none. Beside an install that already carries the flag, the same command gets no rewrite and is a recorded downgrade. v2.18.0 dropped every flag of such a command, the readable installs' too, a recorded downgrade where v2.17.2 had flagged it. Do not put back a path that drops the whole rewrite because one install cannot be read. `scripts/measure/inert-downgrade-grid.sh`, which judged two trees on 292 forms, is retired with the Bash rewrite it compared.
- **The record is an allow-list over the command's bytes**, with two inputs: the bytes, and the verbs the rewrite read. A verb is read only where its `npm` is the command word of the text it was read in (the lexer's `cmdword` view: prefixes the recognizers strip are blanked in place; a path's last part counts; a glued script word's first segment and a verb flagged where v2.17.2 put it do not; `rust/src/inert/record.rs`). Each read `npm` is set aside, outer comments blanked and quotes and backslashes removed, and the text is read again through the shell's own quote removal, level by level up to three, with each `$'...'` decoded in place at the level that reads it; an npm install verb left anywhere in any of these records the command (`inert_bytes_left_unread`). That verb is the recognizers' (`npm`, the options grammar `O`, a verb; `rust/src/grammar.rs`) with nothing required in front of `npm` (`env -S'npm ci'`), and an unread `npm` inside a word the shell computes (`$(...)`, `${...}`, `<(...)`, backquotes) records the command too (`hash -p "$(command -v npm)" n`). So does a word the shell computes, by the allow-list of `shell_expands` (below) read per word, as the command word of any statement or as the word npm reads as its command, in the command, the scripts it hands on and the quote-removed levels with `<` read as a newline (`inert_dynamic_command_word`: `{npm,ci}`, `npm $V x`, `npm "$@"`, `bash <<< 'npm $V x'`); a list of `$` and the backquote stood there and braces, globs and the tilde passed it. It is recorded as one whose flag nobody read where another install got a flag, and as a downgrade where none did, beside an install that already carries the flag too. The record used to list the ways text reaches a shell, and three rounds of review each found a way the list missed (a script word beside a settled install, a heredoc body fed to `sh` and piped on, then shell options, here-strings, builtins, files and quoted command words: `scripts/measure/inert-record-gen.py`, kept as a corpus). Do not put a list of ways back, and do not add a kind of text to fix a new miss: a miss is a defect in the definition of a read verb, and that definition is the one place to fix it. The cost is noise, install text that is data beside an install (`scripts/measure/inert-record-data.jsonl`), and it is reported, not failed. The boundary is text another program computes at run time (`printf '\156pm ci' | sh`, the `cmp` probes), an alias (bash runs one in a script only after `shopt -s expand_aliases`), and the recognizers: a command they do not call an npm install is neither rewritten nor recorded. The record's rows are held by the native batteries, not by the Bash grids. `scripts/measure/inert-record-invariant.sh` and its reach table, which held every form of its sets that made an npm call without the flag to an inert record, are retired with the Bash rewrite (`scripts/measure/native-measure-disposition.json`). Their corpora remain as inputs (`inert-record-gen.jsonl`, `inert-record-data.jsonl`, `inert-record-forms.json`, `inert-record-variants.jsonl`), and their historical counts are not native coverage.
- **Where no place reads as true, and where no rewrite is sent.** A statement where no place reads as true keeps only the floor and is recorded as a downgrade, unless the floor collides, which is the deny above. The one other case with no rewrite is a pre hook that cannot write its record (a disk failure, logged in `advisory.log`): it sends no rewrite, because a version 2 record that says safedeps did not rewrite would then make the post hook say "did not add" of a command safedeps wrote. 7d66f8c sent the rewrite there; this is a disk-fault path, not a command form. Where the core sends no rewrite, the command is denied (a collision), or every install it holds already leaves the option true, or it is a recorded downgrade. So deleting some of the flags safedeps inserted gives 7d66f8c's rewrite, which `scripts/test/lib/release-floor.sh` checks on every rewrite smoke and lockless sees, against 7d66f8c's own output recorded in `scripts/test/inert-release-rewrites.json`. That property is the guarantee: npm receives at least the words 7d66f8c gave it. An exception that left the verb flag off where it changed npm's reading (`npm install true`) let a shell alias take the one flag left, so there is none. Where the flag changes npm's reading, the command is a collision. A statement holding a word the shell decides at run time gets the flag after its verb and after its last argument and is recorded in `advisory.log` as unread, and a statement where no place passes keeps the floor and is a recorded downgrade. One shape of it is a collision: `npm install $X --cache` is denied, because the flag after the last argument would be the value of `--cache` (`end-flag-value-unread`).
- **Which words the shell decides is an allow-list, never a list of what expands** (`shell_expands` in `rust/src/inert/read.rs`): a word is read as written only when every byte outside quotes is in `INERT_BYTES` (`rust/src/inert/record.rs`) (letters, digits, `._/@:+,=%-`) and it does not start with `~` or `=`; any other byte makes it dynamic. Bytes are read in their quoting: the lexer's flat view for the set, the words' values after quote removal for `$` and backquotes, which expand inside double quotes. The expansion table in ARCHITECTURE.md is the reason for the set, not the judgment. Two deny-lists each missed a kind: the first knew `$`, backquotes and globs and not the tilde (`HOME=--cache; npm install x ~` gave npm `--cache` before the trailing flag, and the install ran its scripts with nothing recorded), and its `{` never fired because the pieces view blanks grouping characters inside a word; the second listed the expansion steps and missed zsh's named directories, its alternation glob and bash's extglob. Do not put a deny-list back, and do not widen the set past bytes no shell expansion acts on.
- **Whether npm keeps the flag is not safedeps' to say.** It is decided by shell state the command text does not hold: a function or alias in the agent's shell snapshot, `.zshenv`, `BASH_ENV`, or one the command defines (measured: each turned a plain rewritten `npm install` into `ignore-scripts` false). So no line says an install's scripts did not run; a line says what safedeps did ("safedeps added --ignore-scripts to this install", "did not run npm rebuild"). A rewrite holding a word the shell decides at run time writes `ignore_scripts_unread: true` to the snapshot meta, and that adds one warning (`UNREAD` in `rust/src/post/report.rs`: "safedeps did not read all of the command it wrote as the shell will"), a fact about what safedeps read; it used to add "so the install's own scripts may have run", a consequence nothing checked. The field can only add a warning: a record that lacks it loses the warning and claims nothing. Do not turn it back into a permission to say no script ran (`ignore_scripts_verified`, v2.18.0 drafts).

The post hook runs `npm rebuild` only after the closure verifies clean, only when every node npm says the rebuild would run over (`npm query '*'`, links followed into their targets) passes a check of the whole tree, and with `--global=false --location=project --prefix <the directory the gate read>`, so a rejected or unread package's lifecycle scripts never run. The check: every node is one a lockfile records at that location, version and name (a key alone is not a record: an `.npmrc` let npm write 1.0.1 over a recorded 1.0.0; and a `file:` dependency's own `node_modules` is rebuilt with the project); every node under `node_modules` has every record name a public-registry https source (the public rule is `https://registry.npmjs.org/` or `https://registry.yarnpkg.com/`, spelled in more than one place: `registry_public` in `rust/src/ask/fetch.rs` for what npm answers, `public_registry_url` in `rust/src/post/closure.rs` for a lockfile's `resolved`, which folds ASCII case only, and the constant `SAFEDEPS_NPM_PUBLIC_REGISTRY_RE` in `lib/npm/ask.sh` that the CLI reads; the rust-core unit `ask::fetch::public_registry_rule_matches_cli` holds the constant equal to the pattern in `registry_public` and asserts how the CLI, `registry_public` and `public_registry_url` judge 14 URLs; they differ in one application: with no trailing slash the CLI and `public_registry_url` say false, while `registry_public` adds the slash first and says true) that npm says it fetched from there, or is bundled by its parent, judged from the tree and never from a lockfile's `inBundle` (the parent is under `node_modules` and passes the check itself, its `package.json` on disk names the package in `bundleDependencies`/`bundledDependencies`, and no record of the nested package names a non-public source; a committed record's flag and the root's own `bundleDependencies` each let an http tarball pass as bundled before, NB1 and NB2); every node outside it is a declared workspace member. A query that fails or does not answer skips the rebuild.
- **A record's URL is not where the bytes came from**: npm's default `replace-registry-host=npmjs` fetches a registry.npmjs.org URL from the configured registry and records it unchanged, and a committed `.npmrc` or `npm_config_registry` ran an impostor's scripts under a record that read as public (RH1-RH3). So npm is asked which registry it fetches from (`npm config ls --json`, the fetch facts in `rust/src/ask.rs`), beside `npm prefix` with the statement's own words before the command, and again in the read directory after it; a public URL vouches only when both answers say npm fetched it from the public registry. npm's answer never denies or rolls back an install: a company registry, a mirror and a proxy look exactly like an impostor's registry, and nothing can approve one yet, so a non-public answer keeps the install, withholds the rebuild, and the warning names the registry and tells the agent to confirm with the user before running `npm rebuild` itself (an agent told only to rebuild would run what the check withheld). - **Code the command runs first is the one unknown that records nothing, and only where npm answered the public registry**: after `source`, `.` or `eval`, or under code the command chooses for npm (a code name it sets or unsets, `env -i`, an npm named by a path that is not the hook's own; PX1-PX3), with npm answering the public registry for everything the gate can read, the install's scripts are withheld for that command and the warning says why, but nothing is recorded and the tree is not left observed (SRC1-SRC3, UK0, UK1). - **The exemption never replaces an answer npm gave**: where npm names a registry that is not public, that came from the command's own words, and it stands and is recorded (VB1-VB3). The first version of the exemption overwrote it, and a no-op `. /dev/null;` in front of `npm_config_registry=<impostor> npm install` let the next approved install rebuild the impostor. The core starts these programs and no others: `npm` (the asks, and the rebuild), `curl` (the provider queries), `file` and `gzip` (the post hook's classification and the advisory log's archive), and its own judgment process under the pre hook's budget. They are the `Command::new` calls in `rust/src/ask.rs`, `post/npm.rs`, `post/providers.rs`, `post/heuristics.rs`, `state/log.rs` and `pre/budget.rs`; the others are in tests. Edit the core or the shim in a worktree, and run the batteries the change reaches before it reaches the main checkout, because the installed hooks execute the main checkout live.
- **The install grammar is defined once, in the core, and it is on the PreToolUse path.** Every recognizer in both halves of the core reads it: the pre hook's install and runner patterns, ecosystem detection, spec extraction, the `--ignore-scripts` rewrite, and the post hook's backstop. It replaced seven hand-kept copies of the verb list that had drifted apart (`pnpm i`, `npm isntall`, `npx <pkg>@<ver>` and more passed the gate, v2.18.0). The vocabulary and patterns are `rust/src/grammar.rs`, the option and command tables are `rust/src/tables.rs`, and the manager reader is `rust/src/manager.rs`. `safedeps-core grammar` prints every value, named `SAFEDEPS_G_*`, and `safedeps-core manager` answers the reader's queries, which is how the measurement scripts and the batteries read it. The Bash definition, `lib/install-grammar.sh`, is gone, and with it the check that held two copies equal: there is one. Add an alias, a runner, or a statement position there and nowhere else. A word ends there where the shell ends it (`SAFEDEPS_G_END`): at a blank, the end of the line, an operator (`;` `&` `|` `(` `)` `<` `>`) or a closing backtick, and for zsh at a `}` that closes a group. Which `}` closes a group is the lexer's answer (`group_close` in the lexer, `rust/src/lex.rs`), not the pattern's: a glued `}` that closes none is a character in the views the recognizers and the rewrite read, because the rewrite acts on what the grammar reads, and an end read where no shell ends the word turned `npm ci}`, which bash hands npm as `ci}`, into a command bash runs as `npm ci` (caught in review). Which `{` opens a group is the walk's answer too (the walk of `starts()`, in each shell), never a byte rule beside it: a rule that knew separators and reserved words opened no group after zsh's `function f {`, `f() {`, `() {`, `repeat 1 {` and `for i (1) {`, so once the walk read those heads the glued form alone passed with nothing recorded (verdict tookdaki-20261005-144303, N2; `scripts/test/consumer-forms.sh` holds each glued form to its spaced form). The decision is made at the top level, where the walk reads the words. A `}` nested in a substitution is decided where its body is read as a payload, and the inert rewrite reads the body there too: a body that holds `npm` and such a `}` is read as a payload, at its own top level and in the same reading, and its flags map back to the command through the payload's source map. The rewrite used to read that body as part of the command, where the `}` is a character. With the `}` on the verb, the install got no flag and only a record (R1, verdict tookdaki-20261006-112251). With the `}` on the last word, `x=$( { npm ci --ignore-scripts=false} )` read as already true and passed with no flag and no record, and zsh ran its scripts (R2, verdict tookdaki-20261006-135807). Two shape fixes of one class were rejected, so the reading changed; do not add a third shape for a `}` in a body. Such a body is read at the depth of the text it stands in, with no bound: it is always shorter than that text, so the reading ends. A recognizer that ended the last word only at a blank read no install in `npm ci; echo x`, `go get;` or `{ npm ci}` (v2.17.2 through v2.18.0; `scripts/measure/glued-verb-reading.sh` holds every manager to the spaced form), so a new pattern ends its last word with `SAFEDEPS_G_END`, never with a blank. The two readers that keep 7d66f8c's blank end on purpose (`inert_release_appends` and the heredoc check in `inert_rewrite_in_place`) say why where they stand. The grammar is compiled into the binary on the hook path, so a defect in it reaches every Bash call: edit it in a worktree and run the batteries the change reaches first. **Its scope follows the carrier rule in ARCHITECTURE.md**: the manager's own documented spellings, every command word npm's parser accepts (`deref`: abbreviations and camelCase, measured by `scripts/measure/npm-verb-spellings.sh`), and the shell's statement grammar are in; argv-passing wrappers (`sudo`, `timeout`, `nohup`, `nice`, `xargs`) are out and pinned as unjudged in `scripts/test/consumer-forms.sh`. Moving that line is a decision to record, not a regex to widen. **Which word is the command, which is an option value and which is a package is one reader's answer, the manager reader (`Reader::read` in `rust/src/manager.rs`), from each manager's tables in `rust/src/tables.rs`.** The extractor, the UNGATED record, the landing of an install that is not npm's and the runner reader read its roles and nothing else; the recognizer regexes only say that a statement may be an install, and decide no position. Four readers that each approximated a manager's grammar were each wrong somewhere (`npm --prefix x install` read as `npm x`, `pnpm --dir x add` recorded `npm:add`, `go run ./cmd a@b` recorded `go:./cmd`), so a new manager, command or value option goes into those tables, never into a reader. After the command an option the table does not list takes no value, which can only add a check or a record; before the command the word after one is read both as its value and as itself, and judged as the union. npm's part mirrors nopt with npm's own table (`scripts/measure/npm-option-reading.sh` checks it against the npm on PATH), the other managers' tables are checked the same way by `scripts/measure/manager-option-reading.sh` (an entry for an option the manager reads as a switch hides the package after it, so that direction fails; a command's own entry is looked up before `*`, and no option is listed for both), and where npm 10.8.2 defines an option differently the statement is read both ways and judged as the union. The other managers' version boundaries are class `b` in the value table (poetry's `add --optional`: a switch in 1.8.5, a value in 2.x), read both ways the same. `scripts/test/manager-variants.sh` holds the roles by spelling, not by example.
- **Beside a visible install the pipe question is the standalone one, asked of the same text; nothing is set aside first.** `Run::pipes_install_to_shell` (`rust/src/core.rs`) asks `payload_pipes` of the command and of each `sh -c`, eval and substitution text in it, the visible install's own words included. Do not put back a pass that sets those words aside before the search (a carve-out). Its premise, that the visible install's words print nothing into a shell, cannot be judged from the text: a producer reads the command's own text through `$_`, `$BASH_EXECUTION_STRING`, `ps` or a file. The lineage is N1 → R2 → A1–A7 → W06–W08: each carve-out (manager word only, then a whole-word search, then a word-start search, then the install's own words by grammar) left a pipe the standalone path denied and the path beside an install passed, the last because the shell hands the install's last word to the producer as `$_`. The cost is stated in README: an install and an unrelated `| sh` in one command are denied. `scripts/test/consumer-forms.sh` holds it with an S1 loop: every row beside a visible install gets the verdict of the same bytes with the install switched off by `true `.
- **A reading that cannot finish must not read as "no install".** The Bash guard read a command through awk, grep and sed inside conditions and command substitutions, where `set -e` is off, so a failed awk returned empty text and empty text read as a command with no install. That is the failure this rule was written for. The core runs none of those programs, so the failure that is left is a reader that stops short of the whole command. Every such step sets `failed` on the run (`Run` in `rust/src/core.rs`) instead of returning what it reached: a reading that was never set, a lexer view that does not exist, a payload record whose offsets do not fit the text, a `$'...'` escape whose value it cannot name, and a `sh -c` or `eval` word in live code that goes on past the quote it stops at. A step that cannot answer is a failure, never an absent flag. One settlement decides what a failure means (`settle_scan_failure` in `rust/src/pre.rs`, called for an install in `rust/src/pre/install.rs`). Every path that lets a command run crosses it once, after its last reading and before its first side effect. The side effects are the snapshot, the pending record, the inert meta and the allow, so a command denied for a failed reading leaves none of them (`no-state-on-deny`). If a reading failed, a command that names a package manager's executable anywhere (`grammar::EXECUTABLES`, in any case, line continuations removed) is an `UNDECIDED` deny. Anything else runs with the failure on stderr and in `advisory.log`. A deny that reports a finding settles first, and a finding read from a failed scan is `UNDECIDED`, not a finding. **The census is generated from the source, never kept by hand.** `scripts/test/native-scan-failures.sh` reads every failure assignment in the reader methods of `rust/src/core.rs` (`lex_unterm`, `pieces`, `payloads`, `payload_build` and `lex_payloads`) and compares the list with `scripts/measure/native-scan-sites.json`. It stops when the source holds an assignment the registry does not name, or a method whose text changed. Whole-method hashes catch a new failure return that has no assignment. For each of the 14 registered sites it builds a copy of the source from an archive, forces that producer's failure branch, and runs the unchanged public pre hook on three commands: one that names a package manager, one that installs, and one that names none. That is 42 public rows. The first two must be `UNDECIDED` denies with no rewrite, no pending record and no snapshot meta. The third must be allowed with the failure on stderr and in `advisory.log`. A baseline run of the same three rows without the fault must pass first, and `--control` shows that a failure erased before settling is rejected. Twice a hand-kept list of marked readings missed one, and the Bash census reported zero over it, which is why the registry is checked against the source. The census proves that a failure at each producer reaches the settlement, not that every branch is naturally reachable on every input. It is a release battery (`npm run test:release`), not part of `npm test`. So: a new place where a reader can end without the whole command sets `failed` and is registered with its fault in `scripts/measure/native-scan-sites.json` and `scripts/measure/native-scan-failures.py`; a new allow path crosses the settlement.
- **The command is read by one lexer, `Lex` in `rust/src/lex.rs`, and every reader takes a view of it.** Quotes, escapes, comments, heredocs, arithmetic, substitutions and continuations are lexed in one pass, and `safedeps-core lex <view>` prints any view of it. The scan view (what the detection predicates read), the recognize view (what the recognizers read) and the heredoc-body stripping are views of that pass, not parsers of their own, and so are the prefix stripping (the `recognize` view, and the prefix-free words of the `pieces` view), the substitution extractor (the `substs` view, process substitution bodies included), and the spec extractor's statements: their redirections (the `noredir` view), their quote removal and their cuts at `;` `|` `&` (the `pieces` view). So is the extent of the text the inert rewrite cannot read, a quoted script word or a piped heredoc body (the `classes` view, one class letter per byte): the first matching quote after `-c` is the script's end only when nothing in it is escaped or nested, so that text is bounded by the lexer and not by a quote search. So is where the inert record finds a command word (the `cmdword` and `noprefix` views, each the command's bytes in place with the prefixes the walk set aside at each start blanked). The last three each had a reader with its own copy of the quoting, and each copy was a silent pass where it disagreed with the shell (v2.18.0: a `>` inside `"$(echo ">'")"` read as a redirection took the pinned spec after it along). A new reader of the command takes a view -- never a second parser, because three that had to agree did not, and each disagreement hid the lines after it (fail-open). The scan, code and noredir views keep byte length and are idempotent, so an offset in one is the offset in the command and reading one twice changes nothing; `scripts/test/scan-contract.sh` checks both properties on the recorded shell forms and on random input in each of the three readings, and checks the pieces view's words against the argv bash and zsh produced (`scripts/measure/word-reading-forms.json`, re-measured by `scripts/measure/word-reading-measure.sh`).
- **Where a command starts is an event, not a byte:** the walk (`starts()`) finds every statement start from the shell grammar (after a separator, a case pattern close, a reserved word, a function head (`function NAME` before any compound command too, which bash 5 runs), `time`, `coproc`, the zsh short forms and `&!`, and at a subshell that stands where a command does after words of its statement, `function f { (...)` or `do(...)`) and hands each on as an event, a place between two bytes: where the command starts, at the first byte of its prefixes, and where the walk reads its command word. Readers take the events and never look for a start in bytes. The recognizers read the recognize view: the stmts bytes (a nested `;&|` blanked to `_`) with each command's prefixes removed, every other top-level redirection blanked, a line continuation dropped, and a `;` put in at each start no separator stands before. `command_statements` cuts at those starts (the stmtcuts view), and the bash reading's `DIVERGE` compares the three walks' event sets. Do not write a start over a byte: the stmts view did, a start glued to the token before it had no byte of its own, and three review rounds each borrowed one more neighbouring byte (a case close, a head's `)`, zsh's `{`) before the fourth could borrow none. Where a word starts is the walk's answer too: a descriptor word and a subscript assignment start where the walk starts a command (zsh `{2>/dev/null pip install x; }`, `{a[1]=x pip install x; }`), and zsh and dash read one digit before a redirection operator as its descriptor, bash any number. `SAFEDEPS_G_START` knows only separators, and the reserved words live in the lexer alone (`opener()` and `cbody()` for the walk, and the `cmdpos()` back-scan the lexing uses to decide where a `case` opens); a regex chain of them was a second copy that could not see grammar state, and three review rounds each found the next form it missed. The starts are the reading's like every other rule: zsh alone reads `}` anywhere, `always`, `repeat`, `foreach`, the short forms, a `{` glued to the first word and `&!`, bash alone reads `coproc NAME` before a compound command and `;;&`, a rule every reading shares may only add starts, and the bash reading says `DIVERGE` wherever the walks differ or a zsh precommand modifier stands where the others read the command, or the zsh reading that finds `repeat 1 { pip install x; }` is never asked. Keep the starts out of the scan view: written there they broke its idempotence and the `| { sh; }` pipe check. An assignment or redirection before a command gets no start of its own, or the assignment leaves the install (a lost `UNGATED` record); a redirection that comes first takes the start. The prefixes are removed at every start the walk finds (`prefixes()` reads the walk's events, never separators of its own), so `2>/dev/null pip install x` and `function f { FOO=1 pip install x; }` reach the recognizers. scan-contract holds every reader to the event contract: an event stands at top-level code, no start falls between a command's prefixes and its command word, each command word follows a separator in the recognize view, and `command_statements` cuts there.
- **A reader lexes the command as written, or a payload (a `sh -c`/`eval` script, a substitution's body), or a piece of one cut at offsets, and never a view's output.** A second lexing of a changed text looked for the starts in the bytes left and lost every start whose prefix it had removed (`then>/dev/null pip` read as `thenpip`, verdict bamdori-20261004-224625). The recognizers, the landing, the extractor, the writer attribution and the inert reading then still lexed the joined view (and the extractor the unprefixed view of it), which kept the live code of an unquoted heredoc body and blanked its terminator line, so `$(date)` stood where the command after the body did and took `pip install` for its arguments: a silent pass in every shell, on v2.18.0 and v2.18.1 too (verdict buri-20261005-145152). A comment over that reader said each text was lexed once, and a review read the comment. So a rule like this is not kept by a comment. In the Bash guard the call chain held it, measured: `scripts/test/scan-contract.sh` traced every lexing of a guard run through an awk shim and failed on a text that was not the command, a payload written beside the form as the shell runs it, or a whole statement of one. That trace is retired with the awk calls it traced (`scripts/test/lib/reader-retirements.json`). What holds the rule now is narrower. `scripts/test/lib/core-reader-check.py` checks every payload's source map: each byte of a payload is a byte of the original command, nested payloads included, and the payload has the shape the lexer's records name. It is not an inventory of every lexing the core makes, so a reader that lexes a view's output is not caught by it. Keep the rule in the structure of the code. One reader lexes a text it built: the inert record's computed-word clause reads the byte rule's quote-removed levels (`inert_dynamic_command_word`), only after the command and every payload were read and found nothing, so a finding there can only add a record, and a line its lexing hides is still read in the command. A lexing there that fails is a failed reading, and the gate denies the command as `UNDECIDED`: the exception can add a record or a deny, never take one away. The joined view and the per-line pieces reading are gone; a view no branch names fails the reading rather than printing the code view.
- **Structure leaves the lexer as a rendering or as numbers; a record that carries the command's bytes is never cut by a reader.** The payload views print a kind and offsets (`S`/`E`/`B`, ` a:n`, ` #c#c...`), the reader cuts the text it holds (`payload_build` in `rust/src/core.rs`), and inside the core a payload is a `Payload` carrying its text and where each byte stands in its source. The Bash guard's payload views printed the payload bytes, ending first in a newline and then in \035, and both times a payload holding that byte was cut in two and the install after it passed with nothing recorded (verdict buri-20261005-181919). Escaping the separator was rejected: every separator of every record would have to be remembered, which is how the class came back. `scripts/test/scan-contract.sh` holds the record alphabet on recorded forms, control bytes and random input. Its old trace built its allowed texts from the records and accepted substrings, so it could not turn red on this class, which is a second reason the trace was not carried over.
- **A redirection is one set of bytes, read once (`redirs()`), and every view that removes it removes those:** the operator, the descriptor word glued in front (a number, or `{name}`, which bash 5 and zsh read as a descriptor variable; also before a heredoc operator), and the target word cut where the shell cuts it, a process substitution whole. The unprefixed view blanks a redirection wherever it stands, so the recognizers read the statement the extractor reads (`noredir`); left between a manager and its verb, `pip 2>/dev/null install x` was an install to the extractor and to no recognizer, in every shell. The live view blanks it too, so the inert rewrite finds that verb, and keeps a process substitution's body, which runs. It keeps the body of a substitution in a target for the same reason, so the rewrite also reads the flat view, where the whole redirection is blank: read from the live view alone, `npm >$(echo f) install x` had that body between npm and its verb, and got no flag and no record. That body is a payload (`substs`), like `$(...)`: unread, `cat <(pip install x==1)` passed with no ledger check. Two reads of a redirection that disagreed (a target cut at its first `<`, `{fd}` read as the command) were each a silent pass, and `scripts/measure/redirection-grid.sh` measures the manuals' operators in every place against the shells.
- **Whether a byte ends a word is answered by the walk's depth alone.** Every parenthesis the shell's grammar puts inside a word is a context on the walk's stack: an array value (`NAME=(`, `NAME+=(`), a glob group or qualifier glued to a word, a process substitution with the `<` or `>` that opens it, zsh `=(`, and in the bash reading the subscript of an assignment word. A case pattern close ends a word only at the top level, a comment has the depth of the context it stands in, and no reader keeps a byte set of its own. `word_sep` kept one, and `a=(x) pip install x` ran with `x)` where the command stands.
- **The recognizers end a word where the lexer does:** every manager and verb ends with `SAFEDEPS_G_END`, the bytes the stmts view prints where the lexer ends a word, checked against the lexer's own `wordends` view; their `([[:space:]]|$)` was a set of their own, and `npm ci;`, `(npm install)` and `then npm ci; fi` were no install. A path in front of a manager, the options of `command`, `exec` and `env`, and which words are shells (`SAFEDEPS_G_SHELLS`, a closed list from the manuals) are read once, in the lexer and the grammar. The readers that still keep a set of their own are listed in ARCHITECTURE.md with the direction each errs in; one that keeps a set and is not on that list is a defect. What an assignment word is (a name, a subscript, `=` or `+=`) and which words zsh reads as precommand modifiers (`-`, `builtin`, `nocorrect`, `noglob`) are closed lists from the manuals, kept in the walk; a reserved word is one only as a whole word. Where the walk's own answers disagree (a `(` operator where no walk of the bash reading has a command position, or a word parenthesis inside a command name) the reading is failed, never guessed. That check must not be what closes a form: each one it finds gets a rule of its own. The grid's word forms are generated, not picked: a table of the manuals' word productions, each row with its manual section, put in every place a word stands.
- **A reading is a shell -- bash, zsh or dash -- and every reader reads inside one reading.** The pre hook's drivers (`Readings::collect` in `rust/src/pre/readings.rs` and the install driver in `rust/src/pre/install.rs`) are the only places a run's reading is set; a lexing made with none set is a failed reading, and `rust/src/core/reader_tests.rs` checks both. Text one reader hands another (a payload, a statement) is lexed in the same reading: a per-call reading let a reader re-lex a zsh reading under bash's rules and hide the line again (form SL1). The bash reading runs first and reports `DIVERGE` where the shells answer differently (the table in ARCHITECTURE.md); only then do zsh and dash run, and `scripts/test/scan-contract.sh` checks that where it reports none the other two views are the bash views byte for byte. The verdict is the union: a finding in any reading is a finding, and `UNDECIDED` needs a failed step or no reading that closes. A side effect that changes the command (`--ignore-scripts`) needs every reading to agree; otherwise `UNDECIDED` with its own reason. Readings collected per divergence ("axes") could not close: zsh decides `((` per site (form M1). A form a shell runs must get a verdict, and its own shell's reading must show the line it ran: `scripts/test/shell-reading.sh` checks both against the recorded values (macOS bash, zsh, sh, dash and the agent's wrapper with and without its `setopt` line; Linux bash and dash), `scripts/measure/shell-reading-measure.sh` re-measures them on the platform it runs on, and `scripts/measure/shell-reading-fuzz.sh` runs seeded random forms against the real shells.
- **A judgment's cost is a claim about shapes measured on a host, and a command a judgment cannot finish is answered, not killed.** The Bash guard's awk ran under the macOS awk (BWK), where two things cost the square of the text and close to nothing on Linux: a string built a byte at a time with `s = s c`, and a `sub`, `gsub` or `match()` with a pattern that can run long from every start. One such `sub` in the lexer's `cscripts` view put a 64KB install at 38 seconds on an M1, past the self-budget, so it was answered `UNDECIDED` while the scan view, the only one the cost script timed, stayed linear (fixed in v2.18.1). The core has no awk, so those two costs went with the program that had them, and the builder functions, the awk marker lines and `scan-cost.sh` are retired. The class is not retired. A reader that is linear on a short command can be quadratic on a long one, and the core's own regex engine (`rust/src/ere.rs`) and lexer are new code that nobody has timed against that class on this tree. What holds today is narrower. `scripts/test/self-budget.sh` pins that a 64KB install is judged inside the default budget and not answered `UNDECIDED`, and it pins the deadline itself. No battery here measures how the core's judgment grows with command size. Measure on macOS before writing "linear", and say which shapes and which host.
- **A cost that grows with the number of statements, not the bytes, was a defect of the Bash guard, and the core must not bring it back.** A question asked once per statement made the gate's cost grow with the statements. A dozen processes per statement put 400 one-line statements with an install at 70 seconds on the project's Linux VM with the deadline off, and one grep per statement in each reading still put 3,200 of them at 45 seconds. The core starts no process per statement, and `recognized_dependency_install_each`, with its one grep and its line-number map, no longer exists. `scripts/test/statement-batch.sh` is now a regression corpus for the readers, seeded random commands and statements of the shapes a statement reader hands the lexer one at a time. It no longer compares a batch with a single question, because the core asks no batch question. A new loop that starts a process per statement is a cost: time it on macOS before it ships.
- **Quotes and backslashes are read the way the shell reads them.** Inside double quotes backslashes pair up; outside quotes a backslash escapes the next byte, and an escaped operator (`\;`, `\|`, `\&`, `\!`, ...) is a character, not syntax; there are no escapes in single quotes; a reserved word (`!`, `{`, `then`, ...) opens a statement only where a statement starts; an escaped newline and a newline inside quotes do not end a statement, and the readers that need a word whole drop an escaped newline in the same lexing (no reader joins lines and lexes them again). Each earlier approximation blanked text the shell executes, which is a bypass, not a false negative to tune. `scripts/test/scan-contract.sh` holds the rules as a runnable reference.
- **`advisory.log` is derived from `SAFEDEPS_HOME`, never from its own variable.** It is not just a log: `re-check` reads it as the oracle for whether an approval ever happened, so a movable path let the same environment that forges a ledger entry also supply its provenance (measured — the forgery flag disappeared). Record and ledger move together or not at all. Moved advisory sources (provider URLs, closure fixtures, a non-default ledger TTL) stay allowed and are announced there once per run: a run that answered from a mirror must not look like a run that answered from OSV.
- **No SaaS dependency** — local CLI + public DBs only. The tool itself has **zero npm dependencies**; keep it that way (it is a security property, not an oversight).
- The ledger is a same-user convenience cache, **not** a security boundary against a same-user attacker (until signing/re-query lands). Do not document it as one.
- **Two implementations share the ledger's format: the core reads it and the CLI writes it.** `rust/src/ledger.rs` reads approvals and approves nothing, and `lib/ledger/ledger.sh` writes them. No row has the single job of holding the two to one format. The batteries hold them together without saying so: smoke, consumer-forms, lockless-forms, manager-variants and e2e approve with `lib/ledger/ledger.sh` (or the CLI) and then run the hook, so a format the core reads differently turns those rows red. `scripts/measure/core-ledger-differential.py` checks the core's reader against fixed expectations whose entries it builds in Python, and no battery runs it. Other values are written once in the CLI and once in the core, and four rust-core units hold them equal: `ledger::ledger_defaults_match_cli`, `post::providers::provider_endpoints_match_cli`, `post::providers::provider_cache_constants_match_cli` and `state::log::rotation_constants_match_cli`. They bind the constants, names and hashes they list and nothing wider. No row binds the providers' whole status and field protocol, every log prefix, or the rotation's handling of a malformed number. ARCHITECTURE.md, "What stays in Bash", has the table.
- **The Rust core is the hook, and there is no second authority.** The PreToolUse and PostToolUse hooks are one binary, `safedeps-core`, at `bin/native/<os>-<arch>/safedeps-core`, built from `rust/` (ARCHITECTURE.md section 14). The registered entry is still `scripts/safedeps-hook-entry.sh pre|post`, and it runs the binary. The two Bash hooks no longer exist, and nothing falls back to Bash: the entry reads no environment variable that chooses the binary or switches it off. Two authorities drift, and a silent second one is the fallback this file forbids. The Bash guard was the authority until the switch, and the core was held to it by comparisons: the grammar's values, the regex engine against the host's `grep -E`, every view of the lexer against the awk program, the guard's facts per reading, and the gate's whole answer. Those comparisons are retired, because their reference is gone. The `scripts/measure/core-*` comparison scripts exit 2 and say why (`scripts/measure/native-measure-disposition.json` lists each), and the owner decided on 2026-10-07 that the Bash and Rust guards are not compared on a corpus. The criterion is the existing test sets running on the core. The corpora and expectations the comparisons used remain as inputs, and a zero or a count from a retired comparison is not native coverage. The crate has no dependencies, and that is the package's zero-dependency property carried into it: `rust/Cargo.lock` lists the crate alone, and `scripts/build-core.sh` stops on a lockfile that lists anything else. Do not add a crate for a regex engine or a JSON reader, because the two the core needs are in it (`rust/src/ere.rs`, `rust/src/json.rs`). **The binary carries a stamp of the source it was built from**, and `safedeps-core stamp --check` compares it with the `rust/` beside it. With a mismatch the pre hook denies an install as `UNDECIDED` and lets a command that names no package manager run, with the mismatch on stderr and in `advisory.log`. The post hook reports `UNVERIFIED`. So a change to `rust/` is not live until the binary is built again, and that includes a change to a comment, which changes the digest (Release procedure, step 7).

## CI

GitHub CI is not used: no test workflow is created or run on GitHub. CI runs separately, on the infrastructure Alex set up (the remote runners and test machines named under Testing). The reason is that GitHub's CI is too slow. It is not CI: it is the trusted-publishing job that puts a tagged release on npm.

## Version SSoT

`package.json` `version` is the single source of truth. `bin/safedeps` `SAFEDEPS_VERSION`, the `version` in `rust/Cargo.toml` and the `safedeps-core` entry of `rust/Cargo.lock` must match it; the smoke test reads `package.json` to enforce all three, and the publish job checks the tag against `package.json`, `bin/safedeps`, `rust/Cargo.toml` and the built binary. Bump them together — a feature (e.g. effect/inert) is a minor bump, docs-only is a patch. A change that moves a verdict is a feature, and the bump changes the crate's source digest, so the binaries are built again.

## Hooks

See the `skill-hook-authoring` skill for the full payload/decision schema. Essentials:

- Read `tool_input.command` (single field). `permissionDecision` is `allow`/`deny`/`ask`. `updatedInput` rewrites the command but is **Claude-only** — gate it on engine.
- The hooks are one binary, `safedeps-core`: `safedeps-core pre` is the PreToolUse hook (its advisory and deny lines still say "pre-guard") and `safedeps-core post` the PostToolUse hook. `chmod +x` the entry shim and commit it as mode `100755`; a missing exec bit is `Permission denied` in every session. The binary is not committed (the root `.gitignore` names `bin/native/`): a checkout builds its own with `scripts/build-core.sh`, which gives it its mode, and the publish job builds the package's. The installer builds the core and probes the entry before it registers anything (`prepareCore` and `probeEntry` in `scripts/install/install-safedeps-hooks.mjs`).
- **Registration has one channel: the installer.** `SKILL.md` does not declare hooks, and that is a decision, not an oversight. Claude does document skill-frontmatter hooks (`hooks: {PreToolUse: [{matcher, hooks: [{type, command}]}]}`), but they are **scoped to the skill's lifecycle — they only run while the skill is active**, and this gate has to judge every Bash call whether or not the skill was invoked. So the documented form cannot do this job, and a second declaration of a registration is a second thing to keep true. The smoke drift check deliberately fails only on the legacy `script:` shape that no schema reads; it does not forbid the documented shape, because blocking a working feature by grep is not the same as removing a dead one.
- The registered command for both events is the entry shim `scripts/safedeps-hook-entry.sh pre|post`, not the binary directly. The shim turns a broken hook (a missing binary, one that cannot run, an abort or a signal, a mid-merge checkout) into an explained fail-closed exit 2. Each way the binary can fail to answer has its own sentence, and none of them runs anything in its place. It relies on one contract: **the core exits 0 on every designed path** (decisions travel as JSON) — never add an intentional non-zero exit to the core. It reads its platform from `BASH_VERSINFO`, never from `OSTYPE` or `HOSTTYPE`, which bash keeps from the environment (measured, bash 3.2.57 and 5.2.21). `scripts/test/hook-entry.sh` holds the shim's cases. The shim also answers for its own stops: bash exits 128 (3.2) or 254 (5, after about 15 seconds of retries) when it cannot start a process, both engines read either as non-blocking, so an EXIT trap turns any exit the shim did not choose into an explained exit 2. Every designed exit sets `answered=1` first, and the messages are written with builtins, because a report that needs a process cannot report that no process can start.
- Hooks block clearly and explain; never a silent fallback.
- Installed copies under `~/.claude`/`~/.codex` are symlinks to this repo — edit the repo, never the installed copy.

## Testing

- **Our CI is our own infrastructure** (owner, 2026-10-06). GitHub Actions does not run the suite, and no release step waits for it. The suite runs on our hosts: alex-macbook-m1 and carenine for macOS (runner `~/safedeps-runs/slot.sh`), and WSL1 on the home Windows PC for Windows, the environment Kuma Studio's Windows build runs in. Linux is not tested (owner, 2026-10-06): Kuma Studio ships for Windows and macOS only. A run has no time budget, and speed is not a goal (owner, 2026-10-06; the ten-minute budget written here that day was removed on 2026-10-07). `scripts/ci/run-on-hosts.sh` runs a set on several hosts at once (below). These figures are from the Bash hooks, and none describes the core. On one host `npm test` took 21 minutes and `npm run test:release` 46 to 62 (carenine, 2026-10-05). With both macOS hosts held whole, the development set took 901 seconds and was green (2026-10-06), with M1 already at load 15 from other work. One Bash guard call was 0.6 to 0.9 CPU seconds, nearly all of it spent starting about 93 external processes (measured 2026-10-06). The owner's direction for that cost was Rust, and the core starts no process per statement. **The first whole development set on the tree without the Bash hooks** ran on commit 74e72b0 on both macOS hosts on 2026-10-07: 22 units on each, every unit rc 0, 907 `ok` and 0 `not ok` on each, no skipped row. M1 took 847 seconds (5 CPUs, load 3.72 at the start and 20.79 at the end, with other work on the host). carenine took 529 seconds (9 CPUs, load 2.92 at the start and 10.08 at the end). That set does not include the release batteries, `native-scan-failures` and `effect-trace-grid`. They had not run on this tree at that commit. The release set and the WSL1 batteries ran later, at 32bf06e (Release procedure, step 5). Do not write "covered" beyond what is listed here. No per-call cost of the core is recorded in this document.
- Two commands, one runner (`scripts/test/run-all.sh`). `npm test` is the development run: every battery except the native scan-failure census (`native-scan-failures.sh`) and `effect-trace-grid.sh`. `npm run test:release` runs every battery, those two included. The two left out are the release batteries, and both measure what a release ships. The Bash census and `effect-trace-grid.sh`, which waits for it, took most of a release's time in v2.18.0 on macOS (the census 4,324 of 7,166 seconds, and `effect-trace-grid.sh` 2,840). The native census builds the core once per registered failure site, and no time for it is recorded here. A change that reaches the scan readings or the effect gate runs them by name: `scripts/test/native-scan-failures.sh`, `scripts/test/effect-trace-grid.sh`. Keep both commands green.
- `run-all.sh --list` prints the batteries a run would start, with `--release` as for a run. `--units` prints the units the host runner splits that set into, and `--plan` adds each unit's weight and seconds.
- The batteries run in parallel. They keep their state apart: each makes its own mktemp root, points `HOME` or `SAFEDEPS_HOME` into it, and starts its fixture servers on a port the kernel picks. Measured with a fresh `HOME` and `TMPDIR`, a full run left only npm's own cache and logs in the inherited `HOME`. A new battery keeps the same isolation, or it cannot run beside the others.
- The runner never takes the whole machine by default. At most `SAFEDEPS_TEST_JOBS` batteries run at once. The default is half the CPUs, rounded up. Raise it on a dedicated machine, or set it to 1 for the least load. Developer machines are shared: an uncapped run on a 16-CPU Mac already at load 100 took it past 300.
- Two batteries start only after `native-scan-failures` finishes, because a busy machine turns them red without a defect and the census, which builds the core many times, is what loads the machine: `self-budget.sh` times the hook's answers against its budgets (it delays the real npm asks with a fixture npm that stops the judgment process and continues it after a bounded time, and it reaps what it suspended the three ways under Verification hygiene), and `effect-trace-grid.sh` needs an npm install to write its lockfile inside the wall-clock second the pre hook ran in. A development run has no census to wait for, and they start in order.
- **The host runner.** `scripts/ci/run-on-hosts.sh [--release] [--hosts a,b]` ships a commit, as `git archive`, to the hosts named in `~/.config/safedeps/test-hosts`. The format is in `scripts/ci/test-hosts.example`; host addresses stay out of this public repository. On each host the run takes slots of the host's queue: one by default, or every slot (`holds`), which gives it the host to itself. It runs the set as units: a whole battery or a shard of one. **A host prepares one core binary and stamp-checks it before any unit starts** (`core-prepare/receipt.json`, `scripts/build-core.sh --receipt`), and each unit checks the receipt again without building (`run-all.sh --unit UNIT --core-receipt FILE`). A preparation that does not finish in 600 seconds fails the host. The longest units start first, each on a host with free CPUs for its weight. A unit starts detached and reports through files (`scripts/ci/remote.sh`), because a link to a host can drop for minutes while its work runs on. The run's directory on each host comes from `mktemp -d`, so two runs never share one, and each unit writes that directory's name beside its log. At the end the runner collects every log and judges them together with `scripts/test/ci-verdict.sh`. Units do not outlive the run: a host given up as failed is sent a stop at once, and again at the end if that did not reach it; an interrupted run (INT, TERM or HUP) stops every unit first; and a unit stops itself when the runner has not polled its host for ten minutes, which is what stops it after a runner killed outright. A hold whose runner is gone stops the units before it frees the queue slot. Which battery is split, into how many shards and at what weight, is a column of `run-all.sh`'s table. Its seconds were measured with the Bash hooks, so they now order the units and are not measurements of this tree.
- **Row shards.** A battery too long for one unit takes `--shard I/M` (`scripts/test/lib/shard.sh`). It numbers its rows as it reaches them, and shard I runs each row n with (n - 1) mod M = I - 1. Every shard walks the whole battery, and a row that is not its own checks nothing. So a row is reached in every shard, never in some. What a later row reads is made in every shard: a package a row publishes, an input drawn from the seed. A check that counts over many rows (a floor such as "more than 1000 events") takes the shard's share. A row's label holds nothing one run made: a temporary path, the tree's path or a fixture's port is written as a name (`shard_mask`), so shards on different hosts agree on the list. A shard prints each row it ran and, at its end, the number of rows and a checksum of their list. `scripts/test/shard-cover.sh` is the list comparison: it lists a split battery unsharded and per shard, and fails unless the shards' union is the unsharded list with no row twice.
- **The reader batteries ask the core and do not source a hook.** `scan-contract`, `shell-reading`, `statement-batch`, `manager-variants` and part of `smoke` query the core (`safedeps-core lex`, `reader`, `manager`, `grammar`) through `scripts/test/lib/core-reader.sh`. Its init refuses a binary whose stamp does not match its source, except one a control selects with `SAFEDEPS_TEST_CORE`, which says on stderr that the stamp check was omitted. They keep only transport there, so no parsing or judgment lives in the test library.
- **A battery that draws random input draws all of it before it checks anything.** `scripts/test/scan-contract.sh` takes its inputs from `scripts/test/lib/scan-inputs.sh` before any checker runs. In bash 3.2 a here-string or a heredoc consumes one `RANDOM` draw when bash makes its temporary file, and a shard skips some checkers, so drawing between checks gave the whole run and each shard different inputs from one seed.
- **The verdict is red** when a host failed, a unit left no exit status or two, a unit's files name another run's directory or none, a unit exited non-zero or printed `not ok`, a unit printed no `ok` line, a unit printed a skipped row (`ok ... SKIPPED`, or a TAP skip directive in any case, `# SKIP` or `# skip`) that `SKIP_ALLOWED` does not name, or a split battery's shards do not add up to its rows. Only the directive is read in any case: rows that pass say "skipped" in their prose. An empty log with exit status 0 used to be green. Every battery prints at least one `ok` line, the census included. A unit's files from another run (a reused `--logs` directory, which the runner now refuses, or a run directory two runs shared, which mktemp now prevents) used to be read as this run's. A host fails when the runner cannot reach it at the start, when it does not answer for three minutes, or when a unit's process there is gone with no exit status. Its running units fail with it, and the runner does not move them elsewhere. A skipped row prints `ok`, so a unit is green without it: with gitleaks installed in one CI group alone, e2e's pre-commit gate rows were skipped on both OSes and every job was green (run 37297541785). A host that never gets its queue slots runs nothing; the run says so, and its wall clock shows it. The runner exits 0 for green and 1 for red.
- Each battery writes its own log. At the end the runner prints every log in a fixed order, then one summary line per battery: exit code, `ok` and `not ok` counts, seconds, and the load at start and end. Then it prints the tail of each failed log. It exits non-zero when any battery exits non-zero, prints `not ok` or prints no `ok` line, and it names them. It does not judge skipped rows; the host runner's verdict does.
- `SAFEDEPS_TEST_SERIAL=1 npm test` runs the batteries one at a time, in the order of the old `&&` chain. When a battery fails only in parallel, rerun it this way before you call it a defect or a flake. `SAFEDEPS_TEST_LOG_DIR=<dir>` keeps the logs in a directory you choose.
- A security change needs **both** a bypass harness (the threat must DENY/REORG) and a regression check (normal installs still pass; no false positives on `echo`/heredoc/`npm run`/`npx`).
- **Cite counts a reader can reproduce from the repo.** "159 forms" measured in a scratch corpus is decoration — nobody can check it, and a number nobody can check reads as verification without being any. Quote the battery's own form count or `npm test`'s ok lines, or commit the corpus you counted.

### What to run, and where

Measurement time is the release's bottleneck. A judgment costs seconds on macOS, a battery row about ten, and a fix that reran everything on both platforms took three and a half hours of host time before a validator ran the same again. So each measurement runs once, at the level where it can fail.

- **Per change** (one plan's branch): the batteries the change reaches, once on macOS; one mutation control per fix, on a copy, where reverting the fix turns its new row red; and any measurement the plan's Done Criteria names. Nothing else.
- **Per release** (the integration tree, before main moves): `npm run test:release` on both platforms (`native-scan-failures.sh` and `effect-trace-grid.sh` included), and the judgment grids, corpora and replays of the areas the release changed. These do not run per branch unless the plan's Done Criteria names one.
- **A change to `rust/`** runs the batteries it reaches, on a core built from that change, and the release runs the whole development and release sets on both macOS hosts. The Bash comparisons that used to run per release (`scripts/measure/core-*`, the lexer comparison among them, 871,800 rows in 58 minutes on alex-macbook-m1, 2026-10-06) are retired with the Bash guard. A change that reaches the lexer, the grammar or the extractor runs `scan-contract`, `shell-reading`, `manager-variants` and `consumer-forms` by name.
- **A validator** reads the worker's own logs on the hosts and checks them against the claim. Its own runs are counterexample probes the author did not write, and one control showing a probe can fail. It does not rerun the worker's batteries.
- **A second rejection of the same class stops the patching.** When review rejects one class of defect twice, the next round starts with a design judgment, not a third shape fix. The pipe check took three rejections before its design changed, and each one cost a full round of measurement.

The bypass-harness and regression rule above still holds for every security change; this section only says where each run happens.

## Verification hygiene

The verification procedure has its own shared state, and three defects came out
of it in one round. All three had the same shape: two actors each behaving
correctly, overlapping into a wrong result.

- **Run mutations on a copy, never in the plan worktree.** The validator is
  dispatched into that worktree and the author may still be working there, so
  both hold write access to one tree. Worse, if a mutation is restored with
  `git checkout -- <file>`, it discards *every* uncommitted change to that file,
  including the author's, and the file returns to a HEAD state that looks
  correct. Copy the tree (`git archive HEAD | tar -x -C "$(mktemp -d)"`), mutate
  there, and throw it away -- not restoring is the safest restore there is. "The
  worktree belongs to the validator" is a discipline someone has to remember;
  mutating a copy is a structure with nothing to remember. Use an archive, not
  `git worktree add`: a worktree is registered in the repository and stays
  listed until someone removes it, so copies made that way pile up beside the
  plan worktrees.
- **Sandbox names come from `mktemp`, not from `$$-$RANDOM`.** `$$` is constant
  within a run, so isolation rests on `RANDOM` alone, and `mkdir -p` succeeds on
  an existing directory -- a collision is undetectable rather than merely
  unlikely. That undetectability is the reason, so it does not need re-arguing
  when call counts change.
- **A test that suspends a process reaps it three ways.** An EXIT trap covers
  ordinary exits; a marker sweep at suite start covers SIGKILL, which defeats
  traps and is this repo's core scenario rather than a hypothetical; and
  spawning children with a cwd outside the worktree removes what the leak costs,
  since an orphan holding the plan worktree makes the close gate refuse to
  prescribe removal at finalize. (Measured, after review corrected it: `git
  worktree remove` itself exits 0 with a stopped process sitting in that cwd --
  the machine that refuses is kuma's live-cwd close gate, not git. The effect and
  the fix were right; the named cause was not.) Scope any sweep with a marker only your own children carry.
  A marker string shared by every run is not that: one run's sweep killed another
  run's fixtures, twice in one round. The marker carries the run's pid, and the
  sweep reaps only markers whose run is gone. Its name must not contain an older
  marker either, or a checkout still sweeping by that substring matches it.

### Citing a zero

A run that found nothing is a claim about a measurement, and three ways of
making that claim are wrong. Each of these was measured the wrong way first in
the round that produced this section.

1. **A zero from a harness with no control is not evidence.** If the check
   cannot fail, its silence says nothing. 27 clean runs were reported before the
   control was tried, and the control turned out to be broken itself.
2. **A trial whose condition was not measured is not an observation of that
   condition.** "Quiet machine" was inferred from who else was working; `uptime`
   showed load 19 during those runs. Record the condition per trial or the
   batches can neither be compared nor combined.
3. **Say whether a label came from measurement or from someone saying so.**
   Hearsay carries no sense of not having measured, so it passes check 2. A
   label that crossed between two people hardened at each hop while nothing at
   the origin had ever been measured -- and then a statistical test was run on
   top of it, which made it look verified rather than merely elaborated.

The failure mode behind all three: **elaboration feels like verification.**
Handling numbers produces the sensation of handling data, and the step that asks
where the input came from gets skipped entirely.

## Workflow

- Branch off `main`; do not commit to `main` directly.
- Do **not** commit or push unless asked. Use logical commits with clear messages.
- **Never resolve merge conflicts in the main checkout.** The installed hooks execute the main checkout live; conflict markers there blocked Bash machine-wide on 2026-08-04. Integrate in your worktree (merge `main` into your branch, resolve, test), then move `main` forward fast-forward-only (`git merge --ff-only`). The entry shim softens the blast, but the discipline removes the window.
- **Write commit messages through a quoted heredoc** (`git commit -F - <<'EOF'`), never `-m "..."`. Inside double quotes a backtick is command substitution, and this repo's messages quote install commands in backticks as a matter of course: a message about a bypass would run the bypass. The live gate caught one on 2026-10-01; do not rely on that.
- **A harness judges commands; it never runs them.** Feed a form to the guard as a payload. Do not `bash -c` it to "see what the shell does" -- the form is an install by construction. When shell semantics are the question, use an `echo` in place of the package manager.
  **The one exception is a battery that measures the package manager itself** -- what npm writes and where, what `npm rebuild` executes -- because no payload can answer that. `scripts/test/lockless-forms.sh` and `scripts/test/effect-trace-grid.sh` are the two, and both source `scripts/test/lib/npm-sandbox.sh`. `scripts/measure/manager-option-reading.sh` runs bun the same way, through consumer-forms: synthetic local packages only, every registry setting on a closed local port so any fetch fails, its own home, cache and global directory, and no inherited `npm_config_*` or `BUN_*` setting. Such a battery runs installs only when all four of these hold, and each is enforced in that file rather than remembered: every package is synthetic and packed by the battery; the registry is a fixture on 127.0.0.1, with npm's proxies pointed at a closed local port so any other request fails, and the gate lets that one registry through only by name (`SAFEDEPS_NPM_TEST_REGISTRY`, a loopback URL, announced in `advisory.log` on every run); the battery asserts at the end that the fixture saw requests for its own packages and nothing else; and it unsets every inherited `npm_config_*` before setting its own home, userconfig, globalconfig, cache and prefix, then checks with `npm config get` that the prefix is inside the sandbox before the first install. The last one was paid for: `npm test` exports npm's own configuration to its scripts, and an inherited `npm_config_prefix` sent the battery's global-install forms into the machine's real global prefix.

## Release procedure

A release is every step below, in order. The list exists because steps were
skipped and nothing noticed: v2.16.0 through v2.17.1 were never tagged,
released or published, so npm sat on 2.15.8 until v2.17.2 caught it up; v2.17.2
shipped with no ROADMAP entry and a stale "current" line; and tags and a
publish went out while ubuntu CI had been red for eight pushes. Do not start a
release without the intent to finish it, and do not report one finished while
any step is open.

1. **Integrate in a worktree.** Merge every finished plan branch into
   `plan/release-vX.Y.Z` and resolve conflicts there, never in the main checkout.
2. **Bump the version once.** `package.json` `version` and `bin/safedeps`
   `SAFEDEPS_VERSION` together (see Version SSoT). A change that moves a verdict
   is a feature for this purpose: minor, not patch.
3. **Record it.** A `ROADMAP.md` section for the version -- what changed, how it
   was verified, measured numbers with the conditions they were measured under
   -- and the same change in `ROADMAP.ko.md`. Update the "current: vX.Y.Z" line.
   Update README, ARCHITECTURE and SKILL, with their `.ko` mirrors, wherever a
   stated proposition moved. Credit issue reporters.
4. **Run the consistency audit** (next section) and read its ceiling. Then have
   someone other than the author re-read the changed propositions.
5. **Test before anything leaves the machine.** Run the release tree, not a
   plan branch. The host runner records each host's load at the start and the
   end; record `uptime` beside any other run:
   - **macOS:** `scripts/ci/run-on-hosts.sh --release --rev <release head>
     --hosts <the macOS hosts>` (or `npm run test:release` on one host), and
     the release checks, `scripts/ci/release-checks.sh` in a clone with its
     full history: the ShellCheck file list, `./bin/safedeps scan secrets
     --repo`, and the package contents (zero runtime dependencies, `npm pack
     --dry-run`). The secret scan runs the gitleaks on PATH only when that
     binary's sha256 is the pinned release binary's; `--install-gitleaks DIR`
     installs the pinned release where it is not. ShellCheck has no such
     path: `release-checks.sh` has `--install-gitleaks` and nothing that
     prepares ShellCheck, and the tree pins no ShellCheck version. At 32bf06e
     the official 0.11.0 release was placed under the host's runs directory
     and put on PATH.
   - **Windows:** in WSL1 on the home Windows PC, in the distribution made for
     these tests (`KumaWsl1Probe`, one slot): `smoke.sh`, `self-budget.sh`,
     `effect-trace-grid.sh` and `e2e.sh`, with the fixture projects on the
     Linux root and on a Windows drive, at nice 0 (no `nice` around the
     battery). These four reach what WSL1 does differently, the cost of a
     process and the file metadata of a Windows drive. The binary is the
     `linux-x64` one, built on a macOS host the way the publish job builds it

     and checked in WSL1 with `stamp --check`. `smoke.sh`, `self-budget.sh`

     head, `rust/` included (`smoke.sh` reads `rust/Cargo.toml`). `e2e.sh`

     the binary in `bin/native/linux-x64/`. With `rust/` beside it, e2e's
     installer rows require cargo, and WSL1 has none. The four batteries ran on
     the core there at 32bf06e (2026-10-08), once on each filesystem: smoke
     80.5s and 79.7s, self-budget 126.1s and 125.0s, effect-trace-grid 750.9s

     guarded. The conditions differ from today's. ROADMAP.md (v2.19.0)
     compares the batteries one by one and holds none of the sums. e2e prints
     `# skipped rows: N; names: …` at its end, and a person reads that line:
     the rows that copy the source need Darwin and skip on Linux, and on a
     Windows drive the permission rows skip as well. A skipped row is not a
     pass. The whole release set has not been run there and is not part of a
     release. `/proc/loadavg` is a constant in WSL1, so record the Windows CPU
     beside the run instead of `uptime`. Two limits, both in ROADMAP.md
     ("Known limits in WSL1"): if effect-trace-grid goes red on one provider
     call with no answer for 20s (`OSV batch query failed status=000` in
     `advisory.log`), run the battery once more, and two reds in a row are a
     defect; and `/proc/<pid>/stat` gives a wrong nice in WSL1, so a battery
     run at a positive nice goes red at e2e's stopped-owner row, which is why
     the batteries run at nice 0.

   `npm run test:release` on one host, and each battery run by hand in WSL1,
   is judged by `run-all.sh` or by the battery alone, and neither judges
   skipped rows (Testing, above): a battery that prints `ok ... SKIPPED` or a
   TAP skip directive and exits 0 is green there, and only the host runner's
   verdict turns it red. So such a run has its logs read for skipped rows
   before it counts.

   These runs are the test of the release; no CI on GitHub stands behind them
   (owner, 2026-10-06). Linux is not tested: Kuma Studio ships for Windows and
   macOS only, and the owner dropped the Linux runs on 2026-10-06. v2.18.1
   pushed before its own suites finished and leaned on GitHub's CI; that is no
   longer a way out. This step exists to keep a red tree off `main`.
6. **Run the release gates.** The package has zero runtime dependencies
   (`jq '(.dependencies // {}) + (.optionalDependencies // {}) | length'
   package.json` prints 0), `./bin/safedeps scan secrets --repo` passes, and
   `npm pack --dry-run` lists only what `files` allows.
   `scripts/ci/release-checks.sh` runs these three. `scripts/release-gates.sh
   --strict` is not the gate for this repo, because it cannot pass here: its
   dependency audit needs a lockfile, a package with no dependencies has none,
   and the audit exits 2 without one on every machine. Its install-guard check
   also fails wherever safedeps is not installed. Both were measured on v2.18.0,
   and the first has been true since this step was written; the step said
   "passes" and no run of it is recorded.
7. **Move main forward, and give the main checkout the binary built from
   what it now holds.** The installed hooks execute the main checkout, and
   the core refuses to judge from a source other than the one it was built
   from (the stamp). So the binary in the main checkout's `bin/native/` has
   to be the one built from the new source. Build it before main moves, on a
   remote macOS host (carenine or the M1), from an archive of the release
   head with `scripts/build-core.sh`, and bring the `darwin-arm64` binary
   back: the machine that holds the main checkout does not build with cargo.
   There are two cases, and the order differs.
   - **v2.19.0, the first release with a binary.** v2.18.1 has no native
     binary, and the main checkout has no `bin/native` at all. Once main
     moves, the new entry shim finds no binary, and every Bash call in every
     session on the machine, `mkdir` and `cp` included, exits 2 with "this
     install has no safedeps-core binary at all" (measured on a copy). So the
     binary goes in first: `mkdir -p bin/native/darwin-arm64` in the main
     checkout, copy the binary to a name beside the final one, mode 755, and
     rename it to `safedeps-core`. The v2.18.1 Bash hooks do not look in
     that directory, so nothing changes while it waits. Before the merge, run
     `bin/native/darwin-arm64/safedeps-core version` there by hand, to see
     that the file runs on this Mac. Then, from the main checkout,
     `git merge --ff-only plan/release-vX.Y.Z`. The new entry shim
     finds the binary at once, and the stamp matches, because it covers the
     source only and the path does not matter. This order was checked on a
     copy with a file swap standing in for the merge, and the merge in the
     main checkout itself has not run. Doing the merge, `mkdir -p`, the copy
     and the rename in one Bash command, or from a human terminal (`!`),
     also works, because the pre hook of that call has already passed.
   - **Later releases, with a binary already there.** Build first, then
     `git merge --ff-only`, then put the new binary in the main checkout's
     `bin/native/<os>-<arch>/` by copying it to a name beside the old one and
     renaming it over, never by writing over the old file: a hook may be
     running it, and macOS kills a process whose executable was written under
     it. Between the move and the rename every install is denied `UNDECIDED`
     and every other command runs with the mismatch said on stderr (measured
     on a copy). That window is fail-closed and lasts seconds, which is why
     the build comes first: building after main moves would hold every
     session on the machine in that state for the length of a build.

   Then run `bin/native/<os>-<arch>/safedeps-core stamp --check` in the main
   checkout and read `ok`. If it does not say `ok`, the binary does not
   match the source, and the state is the out-of-date one: an install is
   denied `UNDECIDED` and every other command runs with the mismatch said on
   stderr. It is not the "no binary" state. Build again on a remote macOS
   host from the release head, and replace the binary the same way, by
   copying it beside and renaming it over. That is the second path, and it
   is written here so that it is never a silent alternative; the window then
   lasts as long as the rebuild and the copy. Then push one benign command
   and one install through `scripts/safedeps-hook-entry.sh pre` and read both
   answers before going on.
8. **Push.** `git push origin main`. Nothing waits for a CI run: step 5 on our
   own hosts is the test of this commit, and a red run there stops the release
   before this step.
9. **Tag and publish the GitHub release.** An annotated tag `vX.Y.Z` on the
   pushed commit, pushed (the push starts step 10's publish), and
   `gh release create vX.Y.Z --notes-file <notes>`.
   The notes cover every user-visible change since the previous tag (derive them
   from `git log <previous-tag>..vX.Y.Z` and the ROADMAP section): security
   fixes first, each with what could get past before and how it is verified
   now, then fixes, then anything a user has to do. Then read it back:
   `gh release view vX.Y.Z --json isDraft,isPrerelease,tagName` must show
   `false`, `false` and the tag, and `gh release view --json tagName` (the
   latest release) must name it. A draft is not a release: users and
   `releases/latest` never see it.
10. **Publish to npm.** Pushing the tag in step 9 starts
    `.github/workflows/publish.yml`, which publishes by trusted publishing:
    npm accepts the job's GitHub OIDC token, so there is no npm token, no
    login and no 2FA prompt, and npm attaches provenance. Watch it:
    `gh run list --workflow publish.yml -L 1`, then `gh run watch <id>`. The
    run must be green. Its two jobs:
    - `build`, on a macOS runner, builds the three binaries from the tagged
      source with `scripts/build-core.sh --publish` (`darwin-arm64`,
      `darwin-x64` and `linux-x64`, the last a static musl build), checks
      that it made three, and runs the `darwin-x64` binary under Rosetta
      where the runner has it. It holds no OIDC token and installs the
      toolchain, and `publish` runs no compiler.
    - `publish` places the binaries, checks them against the build job's
      digests, sets mode 755, runs the `linux-x64` one and checks its stamp
      is a publish build's, and lists what `npm pack` would carry: each
      binary with mode 755, no `rust/`, no dependency. It checks that npm is
      at least 11.5.1, that the tag, `package.json`, `bin/safedeps` and
      `rust/Cargo.toml` name the same version, runs `npm publish --provenance`,
      then reads the release back from the registry: the version's
      `_npmUser.trustedPublisher.id` must be `github`, its
      `dist.attestations.provenance` must exist, and the published tarball's
      file list must equal `npm pack --dry-run` of the tag. The registry can
      answer 404 for minutes after a publish (v2.18.1, run 37265447356: five
      minutes of 404 on the runner), so each try asks the version document and
      the package document with a fresh query string and no-cache, for up to
      20 minutes. A failed `npm publish` and a failed read-back print different
      errors: the second says the version was published.

    **Not yet observed.** This workflow, with its build job and the three
    binaries, has not run on GitHub; the `darwin-x64` binary has not run on
    Intel hardware; and no registry read-back of a package that carries the
    binaries has happened. Do not write any of these as verified before a run
    has shown it.

    Then confirm it yourself: `npm view @aldegad/safedeps version` is X.Y.Z, and
    `npm view @aldegad/safedeps@X.Y.Z dist.attestations.provenance.predicateType`
    prints an SLSA provenance URL. A failure at `npm publish` (ENEEDAUTH, 403)
    means the trusted publisher on npmjs.com does not match this workflow; check
    it against the setup below, then rerun. A failure in the read-back comes
    after the publish: the version is already published and cannot be published
    again. Read `npm view` first, then fix forward in the next patch. Do not fall back to publishing
    from a laptop. That needs the owner's login and 2FA and ships without
    provenance, so it is the owner's decision, and the ROADMAP section says so
    if it happens.

    **One-time setup on npmjs.com (owner, logged in).** Package
    `@aldegad/safedeps` → Settings → Trusted publishing → GitHub Actions, with
    the fields exactly as below (npm does not check them when they are saved,
    and a mismatch first shows as a failed publish):
    Organization or user `aldegad`, Repository `safedeps`, Workflow filename
    `publish.yml`, Environment name `npm-publish`, and under Allowed actions
    select `npm publish` (a connection created after 2026-09-03 allows only
    `npm stage publish` until it is selected). A connection cannot be edited,
    only deleted and created again, so renaming the workflow file or its
    `environment` means doing this again. On GitHub, the `npm-publish`
    environment allows deployments only from tags matching `v*` (Settings →
    Environments → npm-publish → Deployment branches and tags; set on
    2026-10-05). npm checks only the workflow filename and the environment, so
    without that rule anyone with write access could run the workflow from
    another ref and publish. After the
    first green publish, Settings → Publishing access → "Require two-factor
    authentication and disallow tokens" closes the token path; that and staged
    publishing (`npm stage publish`, approved with 2FA) are the owner's choices.
11. **Close the loop.** Reply on every GitHub issue the release fixes with the
    fix commit and the release link, and close it.

## Consistency audit (before release or doc changes)

```bash
# version SSoT
[ "$(jq -r .version package.json)" = "$(./bin/safedeps --json version | jq -r .version)" ] || echo "VERSION MISMATCH"
grep -rqiE 'current.*2\.[0-9]+\.[0-9]+' ROADMAP*.md   # sanity-check the "current vX.Y.Z" line is right
# language purity: English docs have no Korean prose (ko-link lines excepted)
for f in README.md ROADMAP.md ARCHITECTURE.md; do
  grep -vP '\]\(\./[A-Za-z]+\.ko\.md\)' "$f" | grep -qP '[\x{AC00}-\x{D7A3}]' && echo "KOREAN IN $f"
done
# concept presence, per file. `grep -lq` over a file list exits on the FIRST
# match, so the old form passed when ONE of three documents still carried the
# concept -- it could only catch "all of them lost it at once", never drift
# between them. AGENTS.md is in the list because it owns the invariants.
for f in README.md README.ko.md ARCHITECTURE.md ARCHITECTURE.ko.md SKILL.md AGENTS.md; do
  grep -qi 'inert\|--ignore-scripts' "$f" || echo "inert-install missing from $f"
done
npm test
```

### What that check cannot do

It answers "is the concept absent from a file", not "do these files state the
same proposition". Measured against the real v2.16.1 drift, where AGENTS.md got
a liveness qualifier and the other documents kept the old file-existence
reading:

- **False negatives, 2 of 3.** Both ARCHITECTUREs were drifted and both already
  contained the word `pid` -- from an unrelated paragraph about the budget
  deadline killing a process tree. A per-file vocabulary check would have
  flagged only README.
- **False positive, 1.** After the fix, README.md states the new proposition
  correctly without using `pid` or `liveness` -- it is user-facing prose and says
  "the process that wrote it is gone" on purpose. A vocabulary check turns it
  red, and the way to clear the red is to plant jargon in user-facing prose,
  which the Docs section above forbids. The check and the convention would push
  against each other. (Cross-validation corrected this from 2: ARCHITECTURE.ko.md
  does use `pid` in that paragraph, so it would not be flagged. The count is the
  kind of claim this very section warns about -- re-derive it before quoting it:
  `git show 9b43aee^:README.md | grep -ci pid`.)

The cause is the direction of the approximation: a check like this approximates
a proposition by its vocabulary, and every document layer states the same
proposition in different words on purpose.

So the layers are:

1. **Concept absence** -- the loop above. Real, and this is its ceiling.
2. **Proposition declaration** -- have each document declare which version of a
   proposition it reflects, and bump the declaration when the proposition moves.
   Better than "did the commit touch all of them", because a declaration is an
   explicit claim by the author rather than an incidental co-edit. Not built.
3. **Proposition agreement** -- not mechanizable. Re-review owns this: another
   person reading the same object. That is a design decision, not a gap. Every
   defect in the v2.16.x round -- a fail-open early return, this prose drift, and
   a prescription written without opening the check it prescribed -- was invisible
   to any grep and was caught by someone re-reading.
