## 2.26.0

- Changed `advisory.log` into a bounded record. Approval provenance is in `approvals.jsonl`, and nothing reads a verdict or provenance from the log. When the live file reaches `SAFEDEPS_ADVISORY_LOG_MAX_BYTES` (default 67108864), a rotation renames the whole file to an archive, `advisory.log.<UTC stamp>`, with `.<n>` after the stamp for a later archive of the same second. The next line any writer appends makes a new live file. No code rewrites, truncates or compacts the live file any more.
  Breaking: lines that are not `INFO` no longer stay in the live file without end. A rotation moves them to the archive with every other line, and retention removes them with that archive.
- One implementation rotates the log, the core's: `safedeps-core advisory-log rotate`. The CLI and the watch look at the size first and run the core only at the bound. The post hook rotates from its provider initialization. `lib/advisory-log-rotate.sh` is removed. Without the core, the CLI and the watch do not rotate. They say so on stderr once per run, with the path, the size and the bound, and write no line to the log for it.
- The rotation lock is `flock(2)` on `advisory.log.rotate.lock`, a regular file that is never removed. The kernel releases it when its holder exits, however it ends. A rotation that finds the lock held does not wait. `SAFEDEPS_ADVISORY_LOG_LOCK_STALE_SECONDS` is removed, because no lock is reclaimed by age.
- A rotation claims an archive name by creating it as a new empty file (`O_CREAT|O_EXCL`), then renames the live file over that file. So the volume answers whether a name is free, by its own rules of case and Unicode form. A held name is passed over for the next number, and the rotation's line names it. Archive names sort in the order the archives were made, whatever the clock reads.
- Compression waits. A new archive stays plain, because a writer that opened the live file before the rename writes into the archive after it. A later rotation gzips at most one plain archive: the oldest one whose modification time is more than `SAFEDEPS_ADVISORY_LOG_QUIET_SECONDS` (new, default 3600) seconds old. The gzip file is published by `link(2)`, so it replaces nothing. A compression that fails leaves the plain archive as it was. Just before the rename, the rotation touches the live file, setting its modification time to now. The quiet window counts from that touch, not from the rename, and a later write starts it again. A writer can still lose a line it writes to an archive after a later rotation's compression read that archive. A writer that opened the live file before the touch can lose it when it held the file open for longer than the quiet window. A writer that opened the file between the touch and the rename has less of the window, because the window has run since the touch. So it can lose a line even though it held the file open for less than the window. If the rotation paused there for longer than the window, such a writer can have none left.
- Retention counts plain and gzip archives together against `SAFEDEPS_ADVISORY_LOG_KEEP` (default 5) and `SAFEDEPS_ADVISORY_LOG_ARCHIVE_TOTAL_BYTES` (default 536870912). It removes the oldest archives first and always keeps the one just made. A rotation removes no name but those its listing read, byte for byte.
- Each line the core writes to `advisory.log` is one write. A rotation writes one `WARN advisory log rotated: <bytes> bytes moved to <archive>` line to the new live file, followed by what else it did. A rotation that finds the lock held writes no line, and `safedeps-core advisory-log rotate` exits 0 with nothing on stderr. A rotation that fails writes one `ERROR advisory log not rotated: <reason>` line, and `safedeps-core advisory-log rotate` exits 1 with the reason on stderr.
- Earlier versions do not rotate a home that holds the new lock file. Their lock was a directory at the same path, and a regular file there makes both their `mkdir` and their removal of a stale lock fail. A lock directory an earlier version left at that path is held while its modification time is 300 seconds old or less, matching that version's own stale-lock window. Once its modification time is more than 300 seconds old, it is removed, and the lock file is made in its place. Both directions were measured on macOS in isolated homes, one after the other: each lock directory and lock file was made just before its run, and for each age above 0 its modification time was then set back by that age. 2.21.0's shell and core rotations did not rotate with a lock file whose modification time was 0 or 3600 seconds old, and the lock code is the same from 2.21.0 to 2.25.0. 2.26.0's CLI and core command held directories whose modification time was 0 or 290 seconds old without rotating, and removed directories whose modification time was 310 or 3600 seconds old to make the lock file and rotate, with no log line lost in either direction. The measurement set `SAFEDEPS_ADVISORY_LOG` on the CLI runs. In both directions, for runs that did not rotate, the 2.21.0 and 2.26.0 core commands wrote no line, and each version's CLI wrote only its warning that the variable is ignored. To go back to an earlier version, remove `advisory.log.rotate.lock`, or that version never rotates the log.
- Upgrading: refresh the watch runtime with the installer, as for 2.25.0. Until then it runs the old log code and reports `agent_runtime_stale: true`. A runtime from 2.21.0 to 2.24.0 reads approval provenance from the live `advisory.log`, and 2.24.0 has the same provenance code as 2.21.0. After `safedeps approvals migrate` and a 2.26.0 rotation on macOS, a 2.21.0 watch runtime's `re-check` reported honest approvals under `suspected_forgery` with reason `missing_advisory_log_approval`, including ones made by 2.26.0 after the upgrade. `re-check` did not revoke them, the daily alert named them, and `install --runtime-only` from 2.26.0 cleared the report. Run `safedeps approvals migrate` before retention removes the archives that hold earlier approve lines, and name those archives once a rotation has run.
- Added `SAFEDEPS_ACCEPT_SOURCE='<https URL> <who decided and why>'` for one-time, person-decided acceptance of an npm package from an `https://` URL outside the public registry, placed in front of each npm install statement in the command (including `npm ci` or a bare `npm install` when the lockfile names the URL). It follows the same command-line rules as `SAFEDEPS_ACCEPT_RISK` and accepts only `https://` URLs with a non-empty host, no user name or password, printable ASCII without spaces, and neither `https://registry.npmjs.org/` nor `https://registry.yarnpkg.com/`. Commands where the override does not count, names an ineligible URL, or omits the reason are denied before the install runs without falling back. On Codex CLI the override is denied before the install (`safedeps: SAFEDEPS_ACCEPT_SOURCE does not count on Codex.`) because Codex cannot withhold install scripts; accept the source on Claude Code first, after which a later install from the lockfile on Codex, such as `npm ci`, installs the recorded bytes as an approved package.
- In an install that uses `SAFEDEPS_ACCEPT_SOURCE`, a package whose every record in the lockfile npm reads (`npm-shrinkwrap.json` where it holds a byte, else `package-lock.json`) and `node_modules/.package-lock.json` matches the named URL byte for byte and carries an `integrity` is not counted as unapproved, has its current OSV advisories accepted, and is not rolled back for its source. The override never covers a CISA KEV listing, an unreadable closure, KEV catalog, ledger, or OSV batch, suspicious install scripts, large lockfile growth, native binary findings, `http://` or `git://` sources, other non-public URLs, or a record with no integrity. When every finding is covered, safedeps writes the entries to the ledger as the last write before keeping the install (rolling back if the write fails), moves the verified baseline, runs `npm rebuild`, logs a `post-verify ACCEPTED SOURCE` line to `~/.safedeps/advisory.log`, and prints the accepted-source notice. When combined with `SAFEDEPS_ACCEPT_RISK` in one command, the keep path writes the `SAFEDEPS_ACCEPT_RISK` audit record first, then the accepted-source entries, then keeps the install while still skipping `npm rebuild` and keeping the baseline unchanged; an audit-record failure rolls back without writing entries, and an entries failure rolls back while leaving the audit record in place.
- Added `~/.safedeps/accepted-sources.jsonl`, derived from `SAFEDEPS_HOME` and nothing else, as an append-only JSON-lines ledger. Accept lines carry `at`, `op` (`"accept"`), `url`, `entries` (one or more objects of `integrity`, `package`, `version`, and `advisories`), `reason`, `project`, and `tool_use_id`, one line for each install, so its entries stand together or not at all; revoke lines carry `at`, `op` (`"revoke"`), and `url` and take back every earlier entry for that URL. `safedeps-core` is the sole reader and writer (`safedeps-core sources index`, `safedeps-core sources revoke <url>`), taking an exclusive `flock(2)` for every write and read; unfinished trailing lines are sealed by the next writer and counted as broken. A write commits when its line's newline is in the file. A failure before that rolls the install back with no entry; a failure of a step after it (the sync of the file, the sync of its directory where the write made the file, the close) keeps the install and adds `; the entries stand, and ...` to the `Accepted source` line and the advisory log line, saying what a power loss can still take away. A kill of the hook before or during the write leaves the install without an entry, and the judgment mark's `post-verify NOT JUDGED` line says so on the next post-install run.
- Later installs cover a lock record when `resolved` URL, `integrity`, package name, and version all match an entry byte for byte across the lockfile npm reads and `node_modules/.package-lock.json`, installing the package silently as approved and running `npm rebuild`. New advisories not named in the entry, CISA KEV listings, other bytes under the URL, a missing integrity, the same bytes under another package name or version, a URL spelled differently, or an unreadable ledger still roll back. Binding the integrity relies on npm's own check before extraction, measured against a real npm from a cold cache in `scripts/test/effect-trace-grid.sh` (rows NI0 and NI1).
- Changed withheld-bytes handling in `~/.safedeps/npm-withheld` so an accepted-source entry releases withheld bytes only for a package whose own lock record names the entry's URL off the public registry with that integrity. The accepting install still records the bytes as withheld so a revoke withholds them again, while later covered installs do not record them again. Bytes served by a company registry or mirror under a public-registry URL are not released by an entry.
- Added `safedeps sources` (with `--json`) to list active accepted-source entries and warn on stderr about broken lines, and `safedeps sources revoke <URL>` to revoke every entry for that URL (exiting 1 if none exist, and 4 with a `WARNING` when the revoke line was written and a step after it failed; `--json` adds `doubts`). No CLI command adds entries directly; only an install with `SAFEDEPS_ACCEPT_SOURCE` writes them.
- Updated `safedeps watch` to measure each directory by the npm lockfile npm reads there, marking the other npm lockfile or a 0-byte lockfile `ignored` (not a gap; earlier findings stay open as `stale_measurement` with `unmeasured_reason` `ignored`) and marking every npm lockfile row in the directory `unreadable` with a `lockfile_unreadable` error row when the chosen file cannot be read. Covered lockfile packages are listed as `accepted` on the lockfile's status row, counted in the summary (`accepted_sources`; `; accepted sources <N>`), and accepted advisories are closed as `source_accepted` when KEV answers that they are not listed (raising no event unless closing an already open finding). New advisories, KEV listings, and unreadable KEV catalogs remain findings, and an unreadable ledger covers nothing and records an `accepted_sources_unreadable` error row. A comparison that fails once the ledger was read marks that lockfile `unreadable` with the reason `accepted sources not compared`, and what it printed before it failed closes no finding. The ledger reaches jq through a file of the run's own, never as an argument, so a ledger of any size is compared.
- Updated `safedeps audit` (npm only) to compare npm's advisories against a single copy of the lockfile npm reads in the directory `npm prefix` names, excluding vulnerable packages covered by an accepted-source entry when every advisory npm names is named in the entry and listing them on a non-warning `npm: accepted sources (safedeps sources), not counted:` line. Each excluded package is checked against OSV and the KEV catalog, keeping any KEV-listed or unchecked package in the counts with a note; packages counted only through their dependencies are excluded once all those dependencies are, and an unreadable ledger, a comparison that fails, an unknown prefix, an unreadable or empty lockfile, or a copy failure excludes nothing and says so, a ledger not read apart from one not compared. The ledger and the lockfile reach jq through files in a directory of the audit's own, never as arguments.
- Added `scripts/test/argv-census.sh`, which holds every jq value argument in `bin/safedeps` and `lib` to a table of its class (`scripts/test/argv-census.tsv`): a new one, or a count that moved, fails until the table names it.
- Added npm lockfile selection matching npm (`npm-shrinkwrap.json` where it holds a byte, else `package-lock.json` where it holds a byte, else neither, with dangling symbolic links treated as unreadable) across both `rust/src/post/lockfile.rs` and `lib/npm/closure.sh` (`safedeps_npm_project_lockfile`), verified by `lockfile::choice_matches_cli`. The post-install hook reads the chosen lockfile and `node_modules/.package-lock.json` once for every judgment, watches `npm-shrinkwrap.json` in the install trace, snapshots and restores `npm-shrinkwrap.json` alongside `package-lock.json`, chooses the earlier lockfile from the snapshot the same way, ignores a `package-lock.json` that npm does not read, and rolls back fail-closed when a present record cannot be read. The record of withheld bytes still writes the digests the record read beside an unreadable one names, and `advisory.log` says that the digests only the unreadable record names were not written. ## 2.25.0

- Approval-store I/O, `advisory.log`, and migration JSON `outcome`/`reread_outcome` fields now use `Outcome::describe` (adding `Create`, `Open`, `Write`, `Sync`, `Rename`, and `Lock`, and using existing `Outcome::Deadline` for lock deadlines), with `outcome=` always last in `advisory.log`. Migration reads only a take-back line's keyword, timestamp, and immediately following `hash=` word, ignoring later bytes (preserving legacy `outcome=os-error-N` compatibility), and marks unrecognized lines containing `check approve(`, `check approve-undone`, or `check approve-in-doubt` as `broken`. The shell reports only `ended before it answered` plus hardlink identity when core gives no commit answer. Installer `machineCore` renders `spawnSync` results locally (start error, started error with optional signal, signal, or exit) with verbatim error codes and without interpreting errno or exposing raw Node `error.message`.

- Added `${SAFEDEPS_HOME}/approvals.jsonl`, an append-only approval provenance store that `safedeps` never rotates, compacts, truncates, renames, or rewrites.
  Fresh `clean`, `patched`, `clean closure`, and `patched closure` approvals write and sync a JSONL record (`at`, `hash`, `via`, `record`) under an exclusive `flock(2)` lock before appending to `advisory.log` and renaming the staged ledger entry; an unsynced approval stops before writing the `approve` line and renaming the ledger entry, so a store line can exist without a ledger entry and is counted as `unmatched` (a necessary limit, not an all-or-nothing guarantee across records).
  `re-check` now reads only `approvals.jsonl` as provenance—never falling back to live or archived `advisory.log`—so log rotation no longer triggers false forgery reports.
  Provenance is checked by recomputing the hash (ecosystem, package, version, and project context) from ledger entry fields with no spec-only matching, and `re-check` reports `approvals_store: {present, broken, unmatched}`.
- A cache hit is an approval the approvals store vouches for. A ledger entry the store does not vouch for is checked again from the start.
  Cache hits do not append to `approvals.jsonl`.
- Breaking: `re-check` now reports unvouched ledger entries under `suspected_forgery` with reason `unvouched`, replacing `missing_advisory_log_approval` with no old alias.
- Hardened store and binary failure handling to fail closed.
  `check` approval writing now requires the machine core (`safedeps-core`) and refuses if it is missing, writing no approval or ledger entry; missing `safedeps-core` returns `core_missing` (CLI exit `4`, naming the missing path), an unreadable store returns `approvals_store_unreadable` (CLI exit `4`, no judgments), and store lock acquisition times out after 10 seconds with an error rather than falling back unlocked.
  `approvals_store_in_doubt` indicates the check's own staged entry is not confirmed standing while records may still exist.
- Added `safedeps [--json] approvals migrate [<archive>...]` (distinct from legacy `safedeps migrate`) to import verified approvals from live `advisory.log` and any named existing archives (including `.gz`) without provider calls or ledger/log writes.
  Without migration, existing unvouched ledger entries after upgrading are checked again from the start (including a provider requery) once per entry until migrated or rechecked.
  Migration reports five counts (`inserted`, `not_inserted`, `duplicates`, `unconfirmed`, `taken_back`) summing to `approve_lines` when known, honors `approve-undone` and `approve-in-doubt` take-backs, is idempotent on re-run, and reports named failures (`input_unreadable`, `ledger_entry_unreadable`, `approvals_store_failed`, `approvals_store_write_failed`, `approvals_store_unsynced`).
- Updated the watch LaunchAgent installer to copy the machine core (`bin/native/<os>-<arch>/safedeps-core`) alongside `bin/safedeps`, `lib/`, and the wrapper, include the core binary in the runtime source digest, and refuse with `core-missing` before replacing the runtime if the core is missing, unusable, or a symlink.
  Refresh the runtime from a checkout that holds the core binary. On a host whose scheduler is the LaunchAgent, run `install` with the same `--times` (or `--hour` and `--minute`) the host was installed with, because a reinstall without them sets 09:00 and 21:00. On a host whose scheduler is something else, such as an agent's routine or cron, run `install --runtime-only`. Until then, the old runtime keeps running the old log logic and reports `agent_runtime_stale: true`.
  Scheduled runs that hit `core_missing` record `recheck_failed` with the re-check exit status and error and still raise the watch alert for that run.
- Added the `approvals-provenance` regression battery covering real `check` and `re-check` across shell log rotation with an empty live log, synthetic overlapping archives and truncated live logs (not measured concurrent rotations), forged-entry rejection, normal approval and cache flows, and legacy migration idempotency.
- Included this machine's `bin/native/<os>-<arch>/safedeps-core` in the runtime digest; when the source core is missing, scan records runtime metadata diagnostics with `source_digest_now: null`, `stale: null`, and `source_unreadable` (`step: find`, `find`'s nonzero `exit`, and `said` containing the core path) instead of `stale: true`, without failing the scan, adding an error row, or raising an alert by itself, while installer status exits `1` with `core-missing` and the path without a JSON digest or stale judgment (unsupported platforms where `safedeps_watch_core_file` cannot name a path keep scan's existing omission while the installer refuses with `core-missing`).
- Documented what the watch costs. Its ledger re-check asks OSV live for every entry on every run, so a full scan grows with the ledger. Without `GITHUB_TOKEN`, the GHSA cross-check is skipped once GitHub's unauthenticated limit is reached, with a WARN line for each skip. A manual `safedeps re-check` during a scan exits `75`.
- Changed the watch LaunchAgent default schedule from once a day (09:00 unless `--hour` and `--minute` named another time) to twice a day at 09:00 and 21:00 local time, because an advisory can be published at any hour and a slot missed while the computer slept is followed by another twelve hours later.
  `node scripts/install/install-safedeps-recheck-agent.mjs install` now writes a `StartCalendarInterval` array in ascending order, using 09:00 and 21:00 by default or the slots named by `--times HH:MM[,HH:MM...]`.
  `--hour` and `--minute` still set one slot, defaulting to hour `9` and minute `0` when one of the two is left out. Giving both forms, a slot out of range, or the same slot twice is refused before anything is built or registered.
  The install report's `schedule` is now a list of `HH:MM` strings instead of one `{hour, minute}` object, and a reinstall without slots sets 09:00 and 21:00 again.
- Added `install --runtime-only` to `install-safedeps-recheck-agent.mjs` for hosts whose scheduler is an agent's routine or cron, so refreshing the runtime does not bring a `launchd` agent back.
  It builds the runtime in `~/.safedeps/agent` with this machine's core and writes the watch options as `install` does, without writing, loading, or starting anything in `launchd`. Any existing plist stays as it was, and the report says whether one is present.
  It takes no schedule, refuses `--times`, `--hour`, and `--minute`, and refuses a checkout with no core with `core-missing`.
  `uninstall` now reports `runtime_kept`: it unloads the agent and removes its plist while leaving the runtime and the watch's state and config in place.
- Added an opt-in session-start watch notice for Claude Code via `node scripts/install/install-safedeps-hooks.mjs --watch-notice`, which registers `scripts/safedeps-watch-notice.sh` as a `SessionStart` hook (matcher `startup|resume`, timeout 10 seconds).
  The hook reads `safedeps --json watch status` and prints context for the agent only when there are unclaimed events, roots the last scan did not read in full, no published scan yet, or a status read failure with what the read said. Claimed events are not told again, and the hook exits `0` on every path without blocking anything.
  It is registered only when asked and only for Claude Code: a plain install keeps whatever notice is there, `--no-watch-notice` removes it while keeping the gate, and `--uninstall` removes it with the rest. Other engines use one line in their instruction file as given in `SKILL.md`, and the installer writes no instruction file.
  The hooks installer now refuses unknown arguments and refuses `--watch-notice` and `--no-watch-notice` given together or with `--uninstall` before registering anything ("Nothing was registered."). Added the `watch-notice` test battery, which runs the registered command the way a shell runs it.
- Documented scheduler choices for running the watch scan across `README`, `SKILL.md`, `ARCHITECTURE`, and `RELEASING`.
  Renamed the `README` section "Daily Watch With macOS Alerts" to "Re-checking What Is Already Installed": the host picks the scheduler, preferring an agent scheduler running on the user's computer, falling back to the operating system's scheduler, and never using a cloud scheduler because a cloud run can read neither the lockfiles nor `~/.safedeps/watch/`. It includes commands for `launchd` (via the installer), a systemd user timer or two crontab lines on Linux, and two `schtasks` tasks on Windows, along with what was and was not run.
  Added "Re-checking what is already installed" to `SKILL.md`: the agent asks whether an agent runs on the user's computer, offers the matching path, recommends twice a day while letting the user pick other times, and when a local agent routine fixes a finding it works on a branch with the project's tests and asks before merging.
  Documented in `ARCHITECTURE` that a macOS `launchd` job cannot read the folders macOS protects because macOS holds `/usr/bin/env` (the wrapper's interpreter) responsible and it has no Full Disk Access; such roots show as `root_walk_incomplete` in `roots walked N/M (K incomplete)`, and `safedeps` does not ask the user to give `/usr/bin/env` Full Disk Access. Updated `RELEASING` step 7 to refresh the runtime with the same slots on a LaunchAgent host and with `install --runtime-only` elsewhere.

## 2.24.0

- Ensured a post-install judgment leaves a mark while it runs. A post run that takes a call it will judge now writes one file, `~/.safedeps/judging/<pid>-<start>.json`. It is named by the run's pid and the start the kernel stored for it, and it holds the call's command, project and tool use and the time the judgment started. The run removes it when the judgment returns, whatever it returned. A run the runtime kills, or one that panics, leaves it. A run that cannot write its mark says so in `advisory.log` and in the last paragraph of its answer, and judges as before. A run that can write neither the mark nor that line does not judge. It answers at once that the install was not judged, with what each write returned, and it runs no closure check and rolls nothing back. A mark that cannot be removed after its judgment returned is a line in `advisory.log`, and the run adds a `returned_at` record to it. Before this change, a judgment the runtime killed left nothing that said it did not finish.
- Added a `post-verify NOT JUDGED` line for a judgment that did not finish. The next post run reads `judging/` before it takes a call of its own. For each mark whose run is gone, it writes one line to `advisory.log` with the call's command, project and tool use and the time its judgment started. A run is gone when the kernel holds no process under its pid, holds a zombie, or holds a process with another start. A run the kernel holds with the mark's start is alive, and a run whose start the kernel does not give is not known. Both marks are left as they are. A mark that does not name its call is reported by its path, with what is wrong with it: not one JSON object, a name its fields disagree with, a missing field, or a read that failed. Each mark is said once. The run that renames it to a claim says it, and a run that finds it gone says nothing. Before a run tries to claim a file in `judging/`, it takes the file's own lock, and it holds that lock while it says the mark. The lock is never waited for. A run that finds it held says nothing of the mark, and the run that holds it says it. A file that stays after its line was written gets a `said_at` record, and no run says it again. That covers a claim whose removal failed and a mark in a `judging/` that takes no change. Two runs that reach a mark in such a `judging/` at the same moment say it once. A run that can neither lock nor claim a mark still says it, and its line adds the sentence "It could not lock it either: <what the open or the lock returned>, so another run may say it too." A mark can be said more than once only in three cases: when that record cannot be added, when a run is killed between its line and the removal or the record, or when a run can neither lock nor claim the mark. In the first case `advisory.log` says so, and in the third the line itself says so. A mark with a `returned_at` record is never said. A run under another `SAFEDEPS_HOME` neither says nor touches a mark.

## 2.23.0

- Ensured a root whose walk did not finish is reported with what find said, and is counted in the summary line and the alert. The walk keeps find's stderr. find's exit decides whether a root's walk was whole, as before. When find exits non-zero, the error row `root_walk_incomplete` carries `root`, `exit`, `said` and `lines`. `exit` is find's exit status, `said` is the first three lines find wrote to stderr with the root's path written as `.`, and `lines` is how many lines find wrote to stderr. Every root of class `ok` has `walk: {exit, said, lines}` in `roots`, next to `partial`. A find that exits 0 but writes to stderr is a whole walk with no error row, and its words stay in `walk.said`. safedeps does not name a reason of its own and does not classify the words. The summary has the new fields `roots_walked` and `roots_walk_incomplete`. The summary line names them before `osv measured` as `roots walked N/M (K incomplete)`, and the part in parentheses is always shown, also as `(0 incomplete)`. When the scan has any `root_walk_incomplete` error, the macOS notification starts with `K of M roots not read in full (<said>); what find could not read in them was not checked.` `<said>` is the first line find said about the first such root, or `exit <n>, nothing said` when find said nothing there. The `watch_attention` record in `recheck-alerts.jsonl` carries `message`, `walk_incomplete`, `roots` and `first_walk_incomplete`. Before this change, the walk sent find's stderr to `/dev/null`, the row had only `kind` and `root`, the summary line started `population <state> <count>; osv measured A; ...`, the notification started with `<n> new, population <state>, <e> errors`, and the record had no `message`.
- Changed an unreadable source checkout to mean "cannot tell" instead of "stale". The scan hashes the source checkout the runtime was built from in four steps. The steps run in this order: `find`, `sort`, `shasum`, `digest`. Each step keeps its own exit status and its own stderr. Only a step's exit status decides whether it failed. The first step that fails ends the digest. No digest is made. `last_scan.runtime` then has `source_digest_now: null`, `stale: null`, `source_unreadable` and `error`. `source_unreadable` is `{step, exit, said, lines}`. `step` is the name of the step that failed. `exit` is that step's exit status. `said` is the first three lines that step wrote to stderr. `lines` is how many lines it wrote. `said` and `lines` are null when the words could not be read back. `error` is `source checkout unreadable: <the first line the failed step said>`. When that step said nothing, `error` is `source checkout unreadable: exit <n>, nothing said`. `<n>` is that step's exit status. A warning from a step that ends 0 changes nothing. The report's `agent_runtime_stale` is true only when `stale` is true. Here it is `null`, not `false`. It is `false` when the runtime is fresh. A scan run from a checkout has `false`, because a checkout runs its own files. The summary object has a new field `agent_runtime_stale` with the same value, and the report takes it from the summary. When the value is null, the summary line ends with `; agent runtime stale unknown (<error>)`, where `<error>` is `last_scan.runtime.error`. With no error recorded, the line ends with `; agent runtime stale unknown` alone. When the value is true or false, the line says nothing about the runtime. The `watch_attention` record in `recheck-alerts.jsonl` keeps `agent_runtime_stale` as the report gave it: true, false or null. The notification adds `, agent runtime stale unknown` when it is null. An unreadable checkout adds no error row and raises no alert of its own. It is said only in the summary line, and in the notification when the wrapper alerts for another reason. The fix for a truly stale runtime is still to reinstall the agent. Before this change, find's stderr was discarded there, a file `shasum` could not read was hashed as an empty hash, and a checkout that could not be read was reported stale although it had not changed: `stale: true` in `last_scan.runtime`, `agent_runtime_stale: true` in the report and "agent runtime stale" in the notification.
- Ensured an unfinished walk is not reported as a missing lockfile. When find does not finish walking a root, the run has the error row `root_walk_incomplete`. The scan now names that whole root's scope as unmeasured, with the reason `root_walk_incomplete`. A finding from an earlier scan whose lockfile this walk did not list stays open, marked `stale_measurement`, and its `unmeasured_reason` is `root_walk_incomplete`. It is not `lockfile_missing`, because the walk did not look everywhere. It gets no `lockfile_missing` row in `unmeasured`. A lockfile the walk did list is judged as before: measured again, it can still close a finding (`seen_fixed`). A lockfile gone from a root whose walk finished is still `lockfile_missing`. Before this change, a finding under a part the walk could not read became `lockfile_missing` and got a `lockfile_missing` row in `unmeasured`.

## 2.22.0

- Ensured an OSV advisory record is read as the one the answer named when its `modified` is the same time as the answer's. 2.21.0 required the same string. OSV's querybatch answer gives an advisory's `modified` with six fraction digits, and `/v1/vulns/<id>` gives the record's with nine. On 2026-11-19 this was measured over the 29 advisories of lodash 4.17.20, minimist 1.2.5 and axios 0.21.1. In 27 of them the record had the answer's six digits and three more, and in the other two it had the answer's own string. Both advisories of nanoid 3.3.12 were like the 27. The CLI and the core now read the two values by one rule, the microsecond rule. Both must be times as OSV's schema writes them: RFC 3339 in UTC, an upper-case `T`, at most nine fraction digits and a final `Z`. Each field must be in its range and the day within its month, and a second of 60 counts only at 23:59:60 on a month's last day. The two must have the same date and second, and their fractions must agree in the first six digits, each read with zeros after the digits it gives. An answer that gives more than six digits is held to all of them. Anything else is another time: another second, another digit, an offset even where it names the same instant, and a value that is not such a time even where the two strings are equal. A record at another time is still not used for the verdict and not kept, and the answer is still no answer. A record kept in `cache/osv-vuln/` is read again by the same rule, so a kept record with nine digits answers again for the six the answer gave. When a closure holds such an advisory's package, the effect gate now rolls it back for a vulnerable package. `SAFEDEPS_ACCEPT_RISK` can then keep it, and a KEV listing still rolls it back. The watch reports the advisory for a lockfile that holds such a package. Before this change, the record OSV served for such an advisory was refused, and the answer read as no answer. Two cases were measured on 2.21.0. A watch scan of an npm lockfile that held nanoid 3.3.12 reported `provider_unavailable` and not the advisory, in each of four runs. In the other case npm was not run and no Claude Code session was involved, and the OSV answers were live. A test harness called safedeps' hook entry with hook payloads in Claude Code's format for the Bash command `npm ci`, and before the payload for the effect gate it wrote a synthetic lockfile that held nanoid 3.3.12. The effect gate rolled that lockfile's closure back with `npm closure OSV batch verification failed; fail-closed`, not for a vulnerable package, and it rolled it back too in a second run whose payload put `SAFEDEPS_ACCEPT_RISK` in front of `npm ci`. In every one of these runs `advisory.log` had `ERROR OSV record read failed id=GHSA-28wg-ghj8-5hjv status=200`.

## 2.21.0

- Ensured OSV is asked on every check and on every effect-gate run, so no OSV answer from an earlier run is read or written. `cache/osv/` is no longer written or read, and files an earlier version left there are ignored. An answer is now the whole answer: every page is asked for, at most 20, and every advisory it names is read as its full record, so CISA KEV is judged on the record's aliases. A record is kept in `cache/osv-vuln/` only under the pair (`id`, `modified`) the answer gave. A record is the one the answer named only when its own `id` and `modified` both equal that pair. With no `modified` in the answer, only the `id` must match. A record OSV serves with another `modified` is not used for this verdict and is not kept: the check reports `provider_unavailable` and the effect gate rolls back, `SAFEDEPS_ACCEPT_RISK` or not. A file kept under the pair that holds another record is not that record either. `advisory.log` gets a WARN line, OSV is asked again, and the file is left as it was unless OSV now serves the matching record, which then replaces it. The effect gate now has one deadline, 25 seconds from its start, shared by the backstop, the native inspection, every provider request and npm's answer about the registry the install fetched from (`npm config ls`). An npm answer the deadline cut, or one not started because under 100 ms was left, is `unknown`. Then every new integrity npm was asked about is recorded as withheld, with that reason, and `npm rebuild` does not run over those bytes. On a rollback npm is still asked for that record within the deadline, but not for the public-source check. The deadline bounds the waiting on other processes before the verdict. It does not bound the walks of the lockfiles and `node_modules`, the rollback's own file work, or, on a confirmed install, `npm query`, which has its own 10 seconds, and `npm rebuild`, which has no bound. The 5 seconds after the deadline, before the runtime's 30-second kill, are the room those take, and no test shows that room is enough for every tree. Past the runtime's kill the install stands unjudged, and that kill is never counted as an answer. An answer that has not ended after 20 pages, a record that cannot be read, a record that is not the one the answer named and an OSV request the deadline cut are no answer. In that case the check reports `provider_unavailable` (exit 4), and the effect gate rolls the install back even under `SAFEDEPS_ACCEPT_RISK`. A KEV catalog download the deadline cut is a failed download. As for any failed KEV download, a local catalog answers, stale or not, with a line in `advisory.log`. - Added `safedeps watch`, the daily watch that replaces the opt-in daily re-check. One `safedeps watch scan` runs the ledger re-check, then judges the lockfiles under the registered project roots, then reports the update status of the host's JDKs. There is no `clean` state. A finding closes only on evidence: a lockfile measured again holds a version outside the affected range, OSV withdrew the advisory, or the owner recorded the root as gone for good with `safedeps watch retire`. A root that cannot be reached, a lockfile that is gone, a root dropped from the population, a provider that failed or a network mount that now hides a root keeps the finding as it was, marked `stale_measurement`. Every other lockfile kind is an unmeasured row. The runtime stage is Java first. It gives each JDK under the macOS system path and under SDKMAN one state from a closed set (`update_available`, `current_as_of`, `pre_announced`, `vendor_feed_missing`, `feed_unavailable`), from the OpenJDK Vulnerability Group advisories and the Adoptium API. - Changed the text test that decides a command after a failed reading, whose match of an install's structure kept being fooled. The test now reads the command as a set of words, in no order and with no structure. A view is the text after any sequence of eight rewrites: line continuations joined, the escapes of printf and `$'...'` expanded with an octal escape past 255 standing for its low byte, the escapes of `echo -e` and the `%b` of printf expanded, each whole `$'...'` expanded to its bytes with the text outside it left for the bare cut, quote characters dropped with backslashes kept, each `${name-word}` and `${name:-word}` replaced by its word, each expansion dropped, and a glob's group of zsh or of bash's extended globs written as the words it matches. A manager or install verb assembled across an intact `$'...'` escape boundary, where the shell makes an escape a byte inside and the ordinary char outside, now reads as the install it runs (`pip $'\x69'\nstall` is `pip install`, `\pi$'\x70'\3 install` is `pip3 install`); only a `$'...'` whose opening `$'` the outer quotes split stays out of reach, like a run-time name. A decoy `$'` in a double-quoted string or a comment cannot swallow a real opener, because a `$'...'` expands only where it closes inside one word. Each view is cut into words at blanks, quotes, `$`, backquotes, brackets, redirection and operator characters, `,`, `=` and glob characters, with and without its quotes and backslashes, and the words are folded to lower case. Brace expansions add the words they make, and a word with a glob character also stands for a name or verb it matches with at most one byte open. The words read as an install where they hold a package manager's name, as a word or as the end of a word's path, and one of that manager's install verbs as a word beside it, in any order. This denies more commands than before: any whose words name a manager and one of its verbs apart, such as a manager in a log line and a verb in a script beside it. A text with more than 1024 views (`UNSCANNED_VIEWS`), a sequence of more than 64 views (`UNSCANNED_DEPTH`), or brace expansions past 16 MB (`BRACE_BYTES`) reads as an install, because it was not all read. A view that holds a NUL byte, which any NUL-producing escape becomes, reads as an install too, because bash cuts a `$'...'` there and glues what follows.
