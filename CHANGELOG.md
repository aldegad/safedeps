## 2.23.0

- Ensured a root whose walk did not finish is reported with what find said, and is counted in the summary line and the alert. The walk keeps find's stderr. find's exit decides whether a root's walk was whole, as before. When find exits non-zero, the error row `root_walk_incomplete` carries `root`, `exit`, `said` and `lines`. `exit` is find's exit status, `said` is the first three lines find wrote to stderr with the root's path written as `.`, and `lines` is how many lines find wrote to stderr. Every root of class `ok` has `walk: {exit, said, lines}` in `roots`, next to `partial`. A find that exits 0 but writes to stderr is a whole walk with no error row, and its words stay in `walk.said`. safedeps does not name a reason of its own and does not classify the words. The summary has the new fields `roots_walked` and `roots_walk_incomplete`. The summary line names them before `osv measured` as `roots walked N/M (K incomplete)`, and the part in parentheses is always shown, also as `(0 incomplete)`. When the scan has any `root_walk_incomplete` error, the macOS notification starts with `K of M roots not read in full (<said>); what find could not read in them was not checked.` `<said>` is the first line find said about the first such root, or `exit <n>, nothing said` when find said nothing there. The `watch_attention` record in `recheck-alerts.jsonl` carries `message`, `walk_incomplete`, `roots` and `first_walk_incomplete`. Before this change, the walk sent find's stderr to `/dev/null`, the row had only `kind` and `root`, the summary line started `population <state> <count>; osv measured A; ...`, the notification started with `<n> new, population <state>, <e> errors`, and the record had no `message`.
- Changed an unreadable source checkout to mean "cannot tell" instead of "stale". The scan hashes the source checkout the runtime was built from in four steps. The steps run in this order: `find`, `sort`, `shasum`, `digest`. Each step keeps its own exit status and its own stderr. Only a step's exit status decides whether it failed. The first step that fails ends the digest. No digest is made. `last_scan.runtime` then has `source_digest_now: null`, `stale: null`, `source_unreadable` and `error`. `source_unreadable` is `{step, exit, said, lines}`. `step` is the name of the step that failed. `exit` is that step's exit status. `said` is the first three lines that step wrote to stderr. `lines` is how many lines it wrote. `said` and `lines` are null when the words could not be read back. `error` is `source checkout unreadable: <the first line the failed step said>`. When that step said nothing, `error` is `source checkout unreadable: exit <n>, nothing said`. `<n>` is that step's exit status. A warning from a step that ends 0 changes nothing. The report's `agent_runtime_stale` is true only when `stale` is true. Here it is `null`, not `false`. It is `false` when the runtime is fresh. A scan run from a checkout has `false`, because a checkout runs its own files. The summary object has a new field `agent_runtime_stale` with the same value, and the report takes it from the summary. When the value is null, the summary line ends with `; agent runtime stale unknown (<error>)`, where `<error>` is `last_scan.runtime.error`. With no error recorded, the line ends with `; agent runtime stale unknown` alone. When the value is true or false, the line says nothing about the runtime. The `watch_attention` record in `recheck-alerts.jsonl` keeps `agent_runtime_stale` as the report gave it: true, false or null. The notification adds `, agent runtime stale unknown` when it is null. An unreadable checkout adds no error row and raises no alert of its own. It is said only in the summary line, and in the notification when the wrapper alerts for another reason. The fix for a truly stale runtime is still to reinstall the agent. Before this change, find's stderr was discarded there, a file `shasum` could not read was hashed as an empty hash, and a checkout that could not be read was reported stale although it had not changed: `stale: true` in `last_scan.runtime`, `agent_runtime_stale: true` in the report and "agent runtime stale" in the notification.
- Ensured an unfinished walk is not reported as a missing lockfile. When find does not finish walking a root, the run has the error row `root_walk_incomplete`. The scan now names that whole root's scope as unmeasured, with the reason `root_walk_incomplete`. A finding from an earlier scan whose lockfile this walk did not list stays open, marked `stale_measurement`, and its `unmeasured_reason` is `root_walk_incomplete`. It is not `lockfile_missing`, because the walk did not look everywhere. It gets no `lockfile_missing` row in `unmeasured`. A lockfile the walk did list is judged as before: measured again, it can still close a finding (`seen_fixed`). A lockfile gone from a root whose walk finished is still `lockfile_missing`. Before this change, a finding under a part the walk could not read became `lockfile_missing` and got a `lockfile_missing` row in `unmeasured`.

## 2.22.0

- Ensured an OSV advisory record is read as the one the answer named when its `modified` is the same time as the answer's. 2.21.0 required the same string. OSV's querybatch answer gives an advisory's `modified` with six fraction digits, and `/v1/vulns/<id>` gives the record's with nine. On 2026-11-19 this was measured over the 29 advisories of lodash 4.17.20, minimist 1.2.5 and axios 0.21.1. In 27 of them the record had the answer's six digits and three more, and in the other two it had the answer's own string. Both advisories of nanoid 3.3.12 were like the 27. The CLI and the core now read the two values by one rule, the microsecond rule. Both must be times as OSV's schema writes them: RFC 3339 in UTC, an upper-case `T`, at most nine fraction digits and a final `Z`. Each field must be in its range and the day within its month, and a second of 60 counts only at 23:59:60 on a month's last day. The two must have the same date and second, and their fractions must agree in the first six digits, each read with zeros after the digits it gives. An answer that gives more than six digits is held to all of them. Anything else is another time: another second, another digit, an offset even where it names the same instant, and a value that is not such a time even where the two strings are equal. A record at another time is still not used for the verdict and not kept, and the answer is still no answer. A record kept in `cache/osv-vuln/` is read again by the same rule, so a kept record with nine digits answers again for the six the answer gave. When a closure holds such an advisory's package, the effect gate now rolls it back for a vulnerable package. `SAFEDEPS_ACCEPT_RISK` can then keep it, and a KEV listing still rolls it back. The watch reports the advisory for a lockfile that holds such a package. Before this change, the record OSV served for such an advisory was refused, and the answer read as no answer. Two cases were measured on 2.21.0. A watch scan of an npm lockfile that held nanoid 3.3.12 reported `provider_unavailable` and not the advisory, in each of four runs. In the other case npm was not run and no Claude Code session was involved, and the OSV answers were live. A test harness called safedeps' hook entry with hook payloads in Claude Code's format for the Bash command `npm ci`, and before the payload for the effect gate it wrote a synthetic lockfile that held nanoid 3.3.12. The effect gate rolled that lockfile's closure back with `npm closure OSV batch verification failed; fail-closed`, not for a vulnerable package, and it rolled it back too in a second run whose payload put `SAFEDEPS_ACCEPT_RISK` in front of `npm ci`. In every one of these runs `advisory.log` had `ERROR OSV record read failed id=GHSA-28wg-ghj8-5hjv status=200`.

## 2.21.0

- Ensured OSV is asked on every check and on every effect-gate run, so no OSV answer from an earlier run is read or written. `cache/osv/` is no longer written or read, and files an earlier version left there are ignored. An answer is now the whole answer: every page is asked for, at most 20, and every advisory it names is read as its full record, so CISA KEV is judged on the record's aliases. A record is kept in `cache/osv-vuln/` only under the pair (`id`, `modified`) the answer gave. A record is the one the answer named only when its own `id` and `modified` both equal that pair. With no `modified` in the answer, only the `id` must match. A record OSV serves with another `modified` is not used for this verdict and is not kept: the check reports `provider_unavailable` and the effect gate rolls back, `SAFEDEPS_ACCEPT_RISK` or not. A file kept under the pair that holds another record is not that record either. `advisory.log` gets a WARN line, OSV is asked again, and the file is left as it was unless OSV now serves the matching record, which then replaces it. The effect gate now has one deadline, 25 seconds from its start, shared by the backstop, the native inspection, every provider request and npm's answer about the registry the install fetched from (`npm config ls`). An npm answer the deadline cut, or one not started because under 100 ms was left, is `unknown`. Then every new integrity npm was asked about is recorded as withheld, with that reason, and `npm rebuild` does not run over those bytes. On a rollback npm is still asked for that record within the deadline, but not for the public-source check. The deadline bounds the waiting on other processes before the verdict. It does not bound the walks of the lockfiles and `node_modules`, the rollback's own file work, or, on a confirmed install, `npm query`, which has its own 10 seconds, and `npm rebuild`, which has no bound. The 5 seconds after the deadline, before the runtime's 30-second kill, are the room those take, and no test shows that room is enough for every tree. Past the runtime's kill the install stands unjudged, and that kill is never counted as an answer. An answer that has not ended after 20 pages, a record that cannot be read, a record that is not the one the answer named and an OSV request the deadline cut are no answer. In that case the check reports `provider_unavailable` (exit 4), and the effect gate rolls the install back even under `SAFEDEPS_ACCEPT_RISK`. A KEV catalog download the deadline cut is a failed download. As for any failed KEV download, a local catalog answers, stale or not, with a line in `advisory.log`. Only with no local catalog to read is it no answer, and the install rolls back. The INFO line `advisory.log` keeps for each package OSV answered now carries the number of pages. Before this change, an answer kept under `cache/osv/` for up to 24 hours decided approval, keeps under `SAFEDEPS_ACCEPT_RISK` and re-check's `still_clean`. A fresh "no finding" there approved a package OSV had named since, and approved anything while OSV was down.
- Ensured re-check reports a ledger entry the providers gave no answer for instead of passing over it. The entry is now neither still clean nor revoked: it is a row of `errors` with kind `provider_unavailable` and the fields `ecosystem`, `package`, `version` and `file`, one row per ledger entry. `advisory.log` gets `re-check unanswered ecosystem=<e> package=<p> version=<v> entries=<n>`, the report is printed, the command exits 1 and the entry stays in the ledger. The daily watch scan carries the row as its own error with kind `ledger_provider_unavailable`. The `SF_UNAVAILABLE` message now says "OSV or CISA KEV did not answer, or answered unreadably" and no longer says "no fresh cache". Before this change, such an entry was skipped with a warning and the command exited 0.
- Added `safedeps watch`, the daily watch that replaces the opt-in daily re-check. One `safedeps watch scan` runs the ledger re-check, then judges the lockfiles under the registered project roots, then reports the update status of the host's JDKs. There is no `clean` state. A finding closes only on evidence: a lockfile measured again holds a version outside the affected range, OSV withdrew the advisory, or the owner recorded the root as gone for good with `safedeps watch retire`. A root that cannot be reached, a lockfile that is gone, a root dropped from the population, a provider that failed or a network mount that now hides a root keeps the finding as it was, marked `stale_measurement`. Every root is classified against the mount table and the exclude prefixes before anything under it is opened. A network mount or an excluded prefix is not read. Both are counted, and one found inside a local root is pruned from that root's walk and reported. The population is the list of project roots, printed by a configured command. It is `fresh`, `stale` or `missing`, and a population that is not fresh is an error of the run and an unmeasured row. `package-lock.json` and `npm-shrinkwrap.json` are judged against OSV and the CISA KEV overlay. `pnpm-lock.yaml`, `yarn.lock` and `bun.lock`/`bun.lockb` go through each tool's native audit, which is not OSV, and `no_finding` there is not counted as OSV clean. Every other lockfile kind is an unmeasured row. The runtime stage is Java first. It gives each JDK under the macOS system path and under SDKMAN one state from a closed set (`update_available`, `current_as_of`, `pre_announced`, `vendor_feed_missing`, `feed_unavailable`), from the OpenJDK Vulnerability Group advisories and the Adoptium API. The whole run holds one exclusive lock, `~/.safedeps/watch/lock`, and publishes `~/.safedeps/watch/state.json` atomically. A new finding or a state change makes one event, and a consumer takes events with `claim` and records them with `ack`. `safedeps re-check` now reports a ledger entry that cannot be read or revoked as a row of `errors`, goes on with the other entries and exits 1 after printing the full report, instead of stopping. It now takes the watch lock first, so a manual re-check and a scheduled scan never run at once. The agent installer gained the watch options `--population-command`, `--population-arg`, `--population-timeout`, `--exclude`, `--followup` and `--tool-path`, and a `configure` command that writes only those options. Its wrapper now runs `safedeps --json watch scan`. The installer writes `.safedeps-runtime.json` into the installed runtime: the version, the source checkout and a digest of the files. When the checkout's files no longer match that digest, the scan report carries `agent_runtime_stale: true`. `safedeps watch status` reads the last published state without the lock, with `awaiting_owner` (the findings that wait for the owner's judgment, and the locally closed findings whose deployment wait the owner has not resolved) and `last_full_scan`, and `safedeps watch remediation` records the owner's and workers' decisions on a finding, where `report_acknowledged` takes `--expect` with the report it judged and `deploy_resolved` ends a deployment wait.
- Ensured every file a verdict rests on is read once, so the check and the use act on that one read. A CISA KEV catalog is now copied once into a directory private to the run, where the rule checks the copy and looks up every package while keeping the file time so a stale catalog is still reported as stale. The core now hashes and reads the tree record from before an install from the same bytes instead of reading it twice. Before this change, a KEV catalog that the rule refused and that replaced the file after the check read as no listing and the package was approved, and an OSV cache file or a ledger entry replaced in that window was read without the check too.
- Closed every read a verdict rests on that ran where errexit is off. A jq, curl, npm or find that printed and then exited non-zero no longer reads as success in `check`, `re-check`, `revoke`, `audit`, `gates run` or the effect gate's provider requests. A curl that printed 200 and failed is a failed request in the CLI and in the core. An approval is written only once its entry, its record and its report are all made. A check stopped by anything else answers `check_did_not_finish` with exit 4 instead of the exit status of whatever stopped it. A ledger whose files could not be listed answers `ledger_unlisted` with exit 4 in `ledger`, `revoke` and `re-check`, where it used to read as empty.
- Narrowed the deny after a failed reading of a command to the two cases where a reading found an install or the command's text reads as an install. A command that only names a package manager inside another word (`pipefail`) or with a manager that installs nothing (`npm run`) is now allowed, with the failure still on stderr and in `advisory.log`. An install behind a wrapper, inside a quoted script or heredoc, split by line continuations or redirections, or spelled with quotes, escapes or a path is still denied as `UNDECIDED`. The allowed message now says "does not read as an install" where it said "names no package manager", and the advisory line of a deny names which of the two answers denied it.
- Changed the text test that decides a command after a failed reading, whose match of an install's structure kept being fooled. The test now reads the command as a set of words, in no order and with no structure. A view is the text after any sequence of eight rewrites: line continuations joined, the escapes of printf and `$'...'` expanded with an octal escape past 255 standing for its low byte, the escapes of `echo -e` and the `%b` of printf expanded, each whole `$'...'` expanded to its bytes with the text outside it left for the bare cut, quote characters dropped with backslashes kept, each `${name-word}` and `${name:-word}` replaced by its word, each expansion dropped, and a glob's group of zsh or of bash's extended globs written as the words it matches. A manager or install verb assembled across an intact `$'...'` escape boundary, where the shell makes an escape a byte inside and the ordinary char outside, now reads as the install it runs (`pip $'\x69'\nstall` is `pip install`, `\pi$'\x70'\3 install` is `pip3 install`); only a `$'...'` whose opening `$'` the outer quotes split stays out of reach, like a run-time name. A decoy `$'` in a double-quoted string or a comment cannot swallow a real opener, because a `$'...'` expands only where it closes inside one word. Each view is cut into words at blanks, quotes, `$`, backquotes, brackets, redirection and operator characters, `,`, `=` and glob characters, with and without its quotes and backslashes, and the words are folded to lower case. Brace expansions add the words they make, and a word with a glob character also stands for a name or verb it matches with at most one byte open. The words read as an install where they hold a package manager's name, as a word or as the end of a word's path, and one of that manager's install verbs as a word beside it, in any order. This denies more commands than before: any whose words name a manager and one of its verbs apart, such as a manager in a log line and a verb in a script beside it. A text with more than 1024 views (`UNSCANNED_VIEWS`), a sequence of more than 64 views (`UNSCANNED_DEPTH`), or brace expansions past 16 MB (`BRACE_BYTES`) reads as an install, because it was not all read. A view that holds a NUL byte, which any NUL-producing escape becomes, reads as an install too, because bash cuts a `$'...'` there and glues what follows.
- Ensured the post-install effect gate counts the approvals scoped to the project it judges. It reads the project's resolution context the way the pre-install hook does, and counts the approvals with no context and those of this project's context. Another project's scoped approvals still do not count. A context that cannot be read is said in `advisory.log` and leaves only the context-free approvals. Before this change, an install in a repo with `overrides` was rolled back for packages its own approvals named.
- Ensured a rollback keeps a `node_modules` that was there before the command. The pre-install hook now records what `node_modules` was and lists its entries. A rollback, and the backstop, removes only the entries that listing lacks, each after a line that names it. A tree the command made, or one no record describes, is removed whole as before, and what the command changed in place keeps its bytes. Before this change, a rejected install removed the project's whole `node_modules`.
- Ensured `safedeps check` answers `provider_unavailable` (exit 4, with a line in `advisory.log`) for an advisory status outside the known list, for a provider step that failed and for a failed npm query of a direct package. Before this change, an unknown status flowed into an approval, and a failed npm query gave `cve_unpatched` with exit 2 and no record. In the same change, `cve_unpatched` lists only the requested version, `--json` reports a failed candidate batch and `ledger_write_failed`, and `already_approved` carries `install_hint`.
- Ensured a CISA KEV catalog counts as one only when it is an object with a non-empty `vulnerabilities` list whose entries carry a string `cveID`. An empty file, `null` or `{}` is not a catalog, so even a fresh one is a miss and is fetched again. With no catalog to read, `safedeps check` answers `provider_unavailable` (exit 4) and the effect gate rolls the install back. Before this change, an empty catalog, or no catalog when CISA was down, read as no listing and the package was approved.
- Changed the ledger CLI to read an expiry, `project_context: false` and an entry with two values by the core's rule. Its listing no longer uses `date`. Hook verdicts are unchanged. The output of `safedeps ledger` and of its validation changes.
- Added `SAFEDEPS_ACCEPT_RISK`, an override that keeps an npm install a person decided to accept, with an audit record. It is written in front of each npm install in the command: `SAFEDEPS_ACCEPT_RISK='<who decided and why>' npm ci`. It counts only as a prefix of every npm install in the command, read as written, with one non-blank value and nothing beside the installs but the inert builtins. Any other shape is denied before the install runs. Where it counts, the ledger gate lets unapproved npm specs through on Claude Code, where the install still runs with `--ignore-scripts`. On Codex CLI the ledger gate stands, because Codex cannot withhold install scripts. After the install, the closure check and the OSV batch run as before. Where every problem is an unapproved or vulnerable package, the install is kept: an entry goes to `~/.safedeps/accepted-risk.jsonl` first, `reorg.log` gets an `ACCEPTED RISK` block and the message is a warning. No rebuild runs and the verified baseline does not move. A KEV listing, a check that cannot run, an install-script, source or binary finding, and an audit entry that cannot be written still roll the install back. The override covers one command and the npm effect gate only, and it leaves no ledger entry and no approval.
- Replaced external `file` command with a supervised core child reading coherent image headers directly (ignoring scripts and text) across up to 20 sorted `.bin` targets and symlinks for ELF, Mach-O, and PE images. Candidates are strictly read without execution, offering no loadability or safety guarantee; inspection inability triggers fail-closed rollback. Core processes now run `npm`, `curl`, `gzip`, judgment, and native-inspection child, removing `file`.
- Added a second resolution with the package pinned to its own version in probe overrides for probe failures on npm before 11.6.0 caused by cyclic optional peer dependencies. The closure is judged only if a second run without the pin confirms that npm leaves the lockfile unchanged, reporting `npm_closure_resolution_failed` otherwise.
