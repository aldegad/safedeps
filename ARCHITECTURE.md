# Safedeps Architecture

> Internal design and runtime flow. User-facing setup lives in [`README.md`](./README.md); the skill manifest and hook declarations live in [`SKILL.md`](./SKILL.md). *(한국어 → [ARCHITECTURE.ko.md](./ARCHITECTURE.ko.md))*
>
> **Naming** — the project shipped as `npm-reorg-guard` in v1. v2 unified ecosystems and added the advisory ledger, renaming the product and CLI to **`safedeps`**. The post-install rollback engine still inherits the v1 `reorg-guard` design, and for npm the PostToolUse effect gate is the primary enforcement surface.

---

## Core idea

> Safedeps does not decide at install time from several live truths at once. It approves one dependency closure from provider evidence *first*; then the post-install hook treats the installed lockfile closure as the authority, and reorg rolls back any unapproved or newly-vulnerable effect.

Approval happens **before** the install, against canonical advisory evidence. Enforcement happens **after** the install, against what actually landed on disk. For npm, the full closure (direct + transitive) is checked through OSV `/v1/querybatch` with a 24-hour per-`pkg@version` cache. Closure resolution for the other ecosystems is future work.

---

## 1. Two lanes, one umbrella

safedeps owns security gates at two distinct moments, under one skill. It absorbed the v1 `npm-reorg-guard` (install-time reorg) and then the `security-release-gates` project (release-time checks, 2026-05-24). The goal is not to pile every "security" concern into one file — it is to give the gates a single canonical owner while keeping each lane's responsibility separate (SRP).

```text
┌──────────────────────────────────────────────────────────────────────┐
│                  safedeps — one security umbrella                     │
│                                                                      │
│   INSTALL-TIME lane                    RELEASE-TIME lane              │
│   (during development, per install)    (before a release / push)     │
│   ─────────────────────                ──────────────────            │
│   advisory check   (npm: OSV batch)    safedeps scan secrets         │
│   fast command gate (PreToolUse)       safedeps audit deps           │
│   npm effect gate  (PostToolUse)       safedeps hooks install|check  │
│                                        safedeps git pre-commit       │
│                                        optional PR required checks   │
│   scope: the package being installed   scope: the whole repo tree    │
│                                        (absorbed from                 │
│                                         security-release-gates)       │
│                                                                      │
│   shared: public DBs (OSV/KEV/GHSA) · local-first · no silent        │
│   fallback (a provider/scanner miss is fail-closed)                  │
└──────────────────────────────────────────────────────────────────────┘
```

- **Install-time lane** (sections 2–13 below) — advisory check, fast command guard, and the npm effect gate + reorg. Per-package and proactive.
- **Release-time lane** — the repo-tree checks from `security-release-gates` (secret scan, dependency audit, repo hook install/check, privacy profile), exposed under the `safedeps scan|audit|hooks|doctor` command namespace. Repo-specific policy (`.gitleaks.toml`, lockfiles) stays in the target repo; safedeps owns local execution, install, and verification. Remote repository posture is opt-in and split by cost boundary: no-runner branch rules that block direct pushes to the default branch are recommended, while Actions-backed workflows and required status checks remain explicit cost-bearing opt-in.

The two lanes differ in timing and scope (one package's effect before/after install vs. the whole repo before a release). They live under one umbrella but stay separated by command namespace.

**The secret-leak side of the release-time lane is per-repo and opt-in.** Its detection policy lives in the target repo, not in safedeps, so it does nothing until the repo provides a `.gitleaks` config and an active `.githooks/pre-commit`. `safedeps doctor` is the repo-entry diagnostic that closes that gap: it reports each piece of the secret-leak lane (`.gitleaks` policy, `pre-commit`, `core.hooksPath`, scanner availability) plus the global install-time gate, and exits non-zero when the per-repo lane has gaps. `safedeps doctor --fix` (= `safedeps hooks init` then `safedeps hooks install`) scaffolds a starter policy from `lib/gates/templates/` and activates the local hooks. The scaffold is **non-destructive** — an existing repo-owned config is never overwritten — preserving the invariant that safedeps owns *execution*, not *policy*. The scaffolded `pre-commit` runs two checks. The secret scan (`safedeps scan secrets --staged`) runs on every commit and is fail-closed: an unresolvable `safedeps` or a missing scanner blocks rather than skipping silently. The dependency audit (`safedeps audit`) also runs on every commit in a repo with a supported lockfile — npm, pnpm, yarn, or bun, auto-detected from the lockfile(s) present, each delegated to that ecosystem's native audit — not only when the lockfile changes, so a CVE disclosed *after* a package was installed is caught at the next commit by re-querying the advisory DB. The audit separates the security verdict from an availability failure via meaningful exit codes (0 clean / 1 vulnerable / 2 could-not-run): a real finding **blocks** (fail-closed), while an unreachable advisory DB makes the hook **warn and allow the commit** — an explicit, observable availability failover (per the no-silent-fallback invariant: it is logged to the commit output and does not change canonical truth), with CI and the daily re-check re-covering what the offline commit could not verify.

**Remote enforcement is deliberately opt-in and cost-aware.** `doctor` can report whether a repo already has a security workflow and can name two separate default-branch postures: block direct pushes with a branch rule (no runner minutes) and require Actions-backed PR status checks (can spend hosted-runner minutes). It does not query or mutate branch protection and `doctor --fix` never creates `.github/workflows`. Local pre-commit checks run on the developer machine; remote GitHub Actions, gitleaks-in-CI, and required PR checks are outside the no-cost bundle. The JSON schema keeps those recommendations as `lane: "remote"` checks, while `gaps`/`ok` remain scoped to the local secret-leak lane.

**The effect-primary model is npm-only.** `pip`, `cargo`, `go`, `gem`, `maven`, and `nuget` stay on the v2.1 command-gate + reorg model until their closure resolvers land; they are not described as having PostToolUse closure authority.

#### Where each ecosystem's authority lives

The command gate decides whether a command is an install by recognizing the syntactic carrier that hands text to an interpreter. It knows `sh -c`, `eval`, command substitution, and a pipe into a shell. That list is an enumeration, and the shell has unbounded ways to route text to an interpreter, so the list has a boundary. A herestring, an `xargs`-built command line, and a script written to a file and then run all fall outside it. Extending the list finds more forms rather than fewer.

**The same bypass has a different severity in each ecosystem, and that difference is the point.** For npm the boundary costs *delayed detection*: the effect gate reads the live lockfiles npm writes (`package-lock.json` and `node_modules/.package-lock.json`), and its own install recognizer is a raw text match with no carrier enumeration, so it fires on exactly the commands the command gate skipped. An unrecognized carrier that writes the project's node tree still ends in a closure check and a rollback. For `pip`, `cargo`, `go`, `gem`, `maven`, and `nuget` there is no closure resolver behind the command gate, so the same carrier is a **complete miss**. The post hook recognizes the command, finds nothing it can check it with, and records `UNVERIFIED`. Read "the command gate does not parse this form" as npm-shaped and you will conclude something is still watching. In the ecosystems where the command gate is the authority, nothing is.

**"Delayed detection" for npm holds while the effect gate finishes, and that is a measured range, not a given.** The gate is registered at 30s and the runtime kills it there. Its cost rides on the project's lockfile closure, and it used to ride on the machine's approved-spec ledger as well: the gate asked the ledger about each closure package separately, and each question walked the whole ledger directory. On a 738-entry ledger that put it past 30s at a closure of **four packages** — which is to say, on nearly every install, npm's delayed detection was no detection. v2.16.0 reads the ledger once per closure instead of once per package, and the ledger axis goes flat (0.23s at any closure size measured). What remained was the OSV/KEV pass, which is per-package: on the same machine, with a cold provider cache, the Bash gate crossed 30s at a closure near **390 packages**. Below that npm's delayed detection was real; above it — a large application's lockfile — the gate was killed and the detection did not happen. Those figures are the Bash gate's, measured on macOS in 2026-08 against the real network, and they are why the range has to be measured and quoted instead of called structural. They are not the core's, and nothing here compares the two. The core's post backstop was measured on 2026-10-07 on an Apple M1 (8 CPUs, 16 GiB, macOS 15.6.1) at commit 188ccdf, with `scripts/measure/effect-gate-cost.sh`, which runs `scripts/measure/core-post-cost.py`. The harness hands the core's public post a synthetic `package-lock.json` (v3) of N packages, with a ledger that is empty or approves all N, and with the advisory caches either prefilled or empty and served by a fixture on 127.0.0.1. No install command runs. The first measured size to exceed 30 seconds was 128,000 packages in all four conditions, 33.55 to 72.92 seconds, and 64,000 packages took 12.77 to 29.60 seconds. Each cell is one observation, and the sizes between 64,000 and 128,000 were not sampled, so these samples establish no exact package-count limit. The harness let each run finish and compared its time with 30 seconds, so the runtime's kill was not measured. The fixture is not the real OSV or CISA service, so their latency, response sizes and limits were not measured. Rollback, rebuild, a hidden lockfile, a real installed node tree and the registered entry shim are not in the measurement. The load average was 2.93 to 7.26 during it, and the binary was one that still printed 2.18.1. Measure it on the machine that matters; the crossing point moves with the host, the network, and the cache.

**When the gate is killed mid-rollback, that no longer disappears.** The rollback restores the lock and manifest files, then removes the project's own `node_modules` (it used to delete and rebuild it), and it used to write its `reorg.log` entry and its message only after all of it. A kill anywhere inside left zero lines — including at points where the project had already been fully reverted, so the user's install vanished with nothing to explain it. The gate now writes a rollback journal entry before the first destructive act and clears it once the rollback has reported itself, so an entry that outlives its run *is* the report: the next PostToolUse moves it to a durable incident record, appends `REORG INTERRUPTED` to the same `reorg.log`, and says which stage was reached, which test showed the owner is not at work, what `node_modules` is, and which monitored files are not what the snapshot holds. It gives no command and no cause. Outliving its run is a liveness claim about the writer, not the presence of the file — a rollback in progress holds its own entry by design, so the report is gated on the entry's recorded pid being gone (v2.16.1). The state lock cannot carry that check: the hook releases it before the rollback begins, so the rollback runs unlocked. This is not atomicity — safedeps does not own the atomicity of an npm tree rebuild — what it gives is that an unfinished rollback leaves a record, and the next PostToolUse turns that record into a report. Until another PostToolUse runs, nothing says it. Held by both directions in the e2e battery. `scripts/measure/rollback-kill-state.sh` and `scripts/measure/rollback-concurrent-report.sh` stay as the record of the measurements that put the journal entry first and gated its report on the owner's liveness; the rollback they aimed their kills at no longer runs npm.

The boundary is not an oversight, and widening it is not free. The two recognizers in this repo make opposite precision trades on purpose. A false positive in the effect gate costs one closure diff, so its recognizer is deliberately loose. A false positive in the command gate **denies the user's command**, so its recognizer must be precise — and precision is what an unenumerated carrier walks through. This is the same conclusion that moved npm's authority to the effect gate in the first place: command text cannot be a fail-closed authority, because deciding from text means deciding from a syntax you have to enumerate.

**The backstop rolls back only a command that left a trace.** A false positive in the effect gate cost more than a closure diff. The backstop's pattern (`backstop_re` in `rust/src/grammar.rs`) matches commands that install nothing: `grep -n "npm install" README.md`, `git log --grep="npm install"`, `npm run shell:install`. In a project with a confirmed snapshot whose closure had become unapproved outside the gate, such a command rolled the project back and removed its `node_modules`. A pull or a checkout does that to a closure, and so does an approval that expires after 30 days with nothing changed on disk. Three attempts to keep `node_modules` on a reading of npm's hidden lockfile each failed the same way: the record they trusted did not describe the disk (bun and pnpm do not write it, and npm's own check of it does not look inside a package). So the backstop no longer decides from a record. Before every command the pattern matches and the lexer did not read as an install, the pre hook writes an entry for that tool call. It notes the inode of `package-lock.json`, `node_modules/.package-lock.json` and `node_modules` in the cwd and the status change time of both lockfiles, at the resolution the filesystem keeps, and it touches a baseline file. Each value is the path's own and, where the path is a symbolic link, also that of what the link names: a write through a linked lockfile changes the target's status change time and not the link's, and while the entry held only the link's, such a write was untraced (lumi r2 S1). A link pointed at another file is a new link with another inode. The backstop then asks the disk whether the command wrote the node tree: a lockfile or `node_modules` with another inode, one that existed before and is gone, one that did not and does, a lockfile whose change time is not the recorded one, or anything under `node_modules` whose status changed after the baseline (a walk of `node_modules` that follows a link at its root and reads each entry's status change time, which a writer cannot set; `walk` in `rust/src/post/trace.rs`). The baseline is not set back where time is kept below one second. It used to be set two seconds back on every filesystem, and then a pull 0.3 seconds before a grep counted as the grep's trace and the grep removed `node_modules` (lumi r1 R1); two Bash calls in one message were measured 0.16 seconds apart. The pre hook reads the resolution from the baseline file it just touched and from the change times of the lockfiles and `node_modules` in the project, a link's target included. Unless every one of them shows a part below the second, some part of the tree keeps whole seconds, a write there in the same second would not be newer than the baseline, and the baseline is set two seconds back as before. One part with a time below the second used to be enough, and a tree whose lockfile kept nanoseconds while `node_modules` sat on a whole-second mount missed a write in the baseline's second (lumi r2 P3, 2 of 5 on a real HFS+ mount). The cost runs the other way: a filesystem that keeps hundredths, such as exFAT, prints a zero fraction about once in a hundred reads, and each such read sets the baseline back. On such a filesystem a change outside the gate in the two seconds before a matched command still counts as its trace, and so does a lockfile newer than that baseline. The entry says which rule applied. The entry belongs to one tool call. It is named by the call's top-level `tool_use_id`, which both hooks of a call receive and no other call does: measured with probe hooks, Claude Code 2.1.288 and 2.1.289 send `toolu_...` and Codex CLI 0.160.0 sends `exec-<uuid>`, the same in PreToolUse and PostToolUse. The post hook reads only its own call's entry. A call whose post hook never runs leaves its entry behind: one refused after the pre hook let it through, one cancelled while it runs, and, where `PostToolUseFailure` is not registered, a failed one on Claude Code, which runs PostToolUse only for a call that succeeded (`ls` of a missing path fails; a grep with no match does not). The installer registers the post hook for `PostToolUseFailure` too. That entry moves no later call's baseline, because no later call reads it, and the age sweep removes it after a day. Before this, the backstop read the oldest entry for the project and the command, and one failed call made every later call of that command judge from the call before it (lumi r1 P1). A hook input with no `tool_use_id`, or one that is not a plain word, gets no entry, so on such an engine the backstop judges every matched command as it did before entries existed. With no trace it runs neither the closure check nor a rollback, and records `BACKSTOP UNTRACED` with the check that found nothing in `advisory.log`; the user is not messaged, as with a clean backstop. With a trace it does what it did before. The trace entry is not the pre-guard's install record, so the backstop's headline still says it found none. The post hook reads the call's trace entry before it looks for any record. The pre-guard writes either a record or an entry for a call, never both, and the entry carries the call's `tool_use_id`, so a call with an entry was not read as an install and has no record. Such a call is judged by its entry alone, whatever the entry holds, and no record is read or removed for it. Before this order, a call with an entry was judged by another call's record whose snapshot was gone, or by an empty legacy record, and a command that installed nothing rolled the project back and removed `node_modules` (lumi r3 REC). A command reaches the backstop through a record (one whose snapshot has no meta file, one that names no snapshot, one that is not one JSON object) only when its call has no entry, and there it counts as traced: the closure is checked, and a closure that fails is rolled back. That holds for a call whose input names no `tool_use_id` and for one whose pre hook could not write its entry. A call whose entry was taken for another directory or command, as when its pre hook ran in a parent of the directory its post hook names, reads no record either: it counts as traced, and its headline says the hook found no record. It used to go on to the records and be judged by another call's (MM, lumi r4). Which install record belongs to which install call is the call's `tool_use_id` (section 5, the report's checks). Everything the check cannot settle counts as a trace, which is the old behavior: no entry (a pre hook that died or predates this, or an input with no `tool_use_id`), an entry it cannot read or one taken for another directory or command, a baseline that is gone, a walk that fails or does not finish within its deadline. The walk visits every entry when it finds nothing, so it has a deadline (`SAFEDEPS_BACKSTOP_WALK_SECONDS`, 5s, which can be lowered and not raised). The Bash hook's walk was `find`, and `scripts/measure/backstop-walk-cost.sh` measured that walk when it found nothing, warm: on an M1 Mac under bash 3.2, 250k entries took 1.4s, 500k 3.0s and 1M 14s, and on a Linux VM 1M took 2.4s. Those figures are `find`'s. The script now measures the core. Its walk mode runs the core's `post-probe` trace query (`op=trace`) over a synthetic `node_modules` in which nothing changed. That includes the core's process start, the record and metadata checks and the core's own walk with its deadline (`walk` in `rust/src/post/trace.rs`), and it leaves out the whole post hook, OSV, the ledger and a rollback. It reports the walks that finished (the answer `no trace`) apart from those that hit the five-second deadline, and it uses the system `find` only to build the tree, count its entries and check that nothing in it is newer than the baseline. Its pre mode times the registered entry's whole pre hook on two inputs. Nobody has run it on this tree, so no value is recorded for the core's walk, and no size is claimed below which it finishes. A walk that does not finish within its deadline counts as a trace. The Bash hook paid one grep per command it did not read as an install, and an entry for one the pattern matched, and the cost of that was measured then: on the Linux VM at load 0.7, `scripts/measure/backstop-walk-cost.sh pre` with 15 reps gave a median guard of 0.131s and 0.129s before the trace check (64903ac) and 0.142s and 0.155s after it (2f889da) for `ls -la`, and 0.152s and 0.170s before and 0.220s and 0.227s after for the grep above; on the M1 Mac at load 4 the medians were 0.144s to 0.147s and 0.171s to 0.255s (621b0dd). Those are the Bash hook's costs. The core starts none of those processes, and the script's pre mode, which times the registered native entry on the same two inputs, has not been run on this tree. A trace belongs to the directory, so another process writing `node_modules` during the command, a dev server's cache among them, makes a matched command read as written. In `scripts/test/e2e.sh` no row waits after the change outside the gate. A grep right after a pull, a grep right after the lockfile was written in place, and a `git log` after the ledger expired roll nothing back. So does a grep after a call that left its entry, and every grep after it, and a call with an entry beside another call's record, whole or with its snapshot gone, or beside a record a pre-#5 pre-guard left. An install the pre-guard did not read, a write through a linked lockfile, a lockfile link pointed at another file, a write only into `node_modules`, a call with no `tool_use_id`, a grep on a simulated whole-second filesystem and a walk past its deadline are rolled back. A write into a simulated whole-second `node_modules` beside a lockfile that keeps nanoseconds is a trace. `scripts/test/effect-trace-grid.sh` section 5 runs the same with real npm: an `npm run` whose script installs nothing keeps `node_modules`, and one whose script installs `sd-victim` is rolled back.

The rule for changing the command gate follows from that. Applying a rule the gate already states, at a place that skipped it, is in scope — normalizing `| /bin/sh` and `| env sh` to `| sh` is the gate's own existing statement that a path-qualified or env-prefixed invocation is the bare one, applied to the consumer side of the pipe instead of only the producer side. Two more are the same move (v2.18.0). The consumer is read through the shell's operators and groups, so `| sh; echo`, `(… | sh)` and `|&` are the pipe the gate already names; they had passed unjudged because the check wanted a blank after the shell's name. A compound command the pipe feeds is read through as well (v2.18.1): every command in `| { :; sh; }`, `| if true; then sh; fi` or a loop reads the pipe until one has read it all, so a shell anywhere a command stands in it is the consumer. A `||` is not a pipe: the shell after it reads the caller's input. And a visible install no longer switches the pipe check off: `pip install requests==2.0.0 && printf 'pip install evil' | sh` checked `requests` and ran `evil` unchecked. Beside a visible install the gate asks the pipe question it asks with nothing beside one, of the same text: the whole command, the visible install included, and each `sh -c`, `eval` and substitution script in it. It does not set the visible install's words aside first. Three attempts did, and each left a pipe the standalone check denies and the check beside an install passed: a whole-word search missed `printf '\npip install evil' | sh`, a word-start search missed `%spip` and `cut -c2-` (v2.18.0), and setting aside the install's own words missed `echo "$_ install evil" | sh`, where the shell hands the producer the install's last word. A producer can read the command's own text through `$_`, the exec string, `ps` or a file, and the gate cannot list those ways, so it cannot claim that any word of the visible install stays out of the shell. The cost is a command that mixes an install with an unrelated pipe into a shell: it is denied, and the two run as separate commands (v2.18.1). Adding a new carrier syntax to the recognizer is not, because that is where the enumeration grows without converging.

Reading a parser gap as npm-shaped was a misreading with more than one instance. The ledger gate itself is gated on a parseable `pkg@version` operand, and the code's stated reason for that is npm-shaped too: a bare `npm install` is a lockfile install that names no new package, so letting it fall through is correct *for npm*. `pip install evil` is not a lockfile install. It names a package. The same reasoning was carried into the ecosystems where this command gate is the authority, and there it means an unpinned install is never checked at all.

The direction is also inverted, which is the part enumeration would never surface. The hidden path denies when no spec can be extracted, and the plain path allows under the identical condition. One predicate is read in opposite directions inside one file: `printf 'pip install evil' | sh` is refused fail-closed, while `pip install evil` proceeds.

That case now writes an `UNGATED` record naming the ecosystem and the command. The exemption from it is keyed on the effect gate actually reading the result, not on the ledger ecosystem: pnpm, yarn and bun share npm's ledger ecosystem without the `package-lock.json` the gate reads, and until v2.18.0 that let an unpinned `pnpm add x` through with no record (GitHub #22). Only an npm CLI install that the lockfiles record is exempt now, and only because the PostToolUse hook keeps the record for it: an npm install that left no trace where the gate looked is recorded `UNGATED` there, whatever it named (see "A directory is where the gate looks" below). Runners that fetch a package are recorded here, `npm link <pkg>` too, since only the link lands in the project, and a runner of a binary the project already has is not a fetch. "Reads" has one definition: the record walks the statements the target walk lists (`rust/src/pre/targets.rs`), the same walk that chooses the directory the gate reads, and each statement carries its kind (`ungated` in `rust/src/pre/readings.rs`). Before v2.18.0 the record kept its own definition, a list of flags that stop npm writing `package-lock.json`, and the two disagreed in both directions. The list missed `--no-save` and `--save=false`, which the gate did not read then. And it named `--no-package-lock`, which the gate now reads through npm's hidden lockfile. An npm install inside a `sh -c` or `eval` payload is recorded, because where it lands is decided inside the payload. The record's unit is the operand, and it reads each statement through the same parse the spec extractor uses: an operand counts as pinned only when the extractor read a spec from that very token. So a command that pins one package and names another without a pin is recorded, and so is one that pins a package and names the same package again without a pin, in the same statement or another (`pnpm add x@1 && pnpm add x`). Until then the record was a second parser that asked the extractor by name, and each narrower name key (token shape, then name, then ecosystem and name) still let a same-named pin quiet an unpinned install. The same split ran the other way, recording the version after `gem install rails -v 7.1.0` as an unpinned package. One parse also means a misread shows: when the extractor reads a token wrongly, the token is not a spec it produced, and it is recorded. The line names each operand it recorded. Some records are harmless and declared rather than removed, because removing them needs runtime knowledge the gate does not have: pip resolving `pip install x==1 x` to the pin, a second install of a pinned package that is a no-op, a runner whose binary an earlier statement installs, and a flag the record does not know takes a value. It changes no verdict. Denying every unpinned install is a policy change that would break ordinary workflows, so it stays the repo owner's call; the record is what makes that call answerable from evidence rather than guesswork. The record's silence is scoped as deliberately as its noise, and the line is whether a package is named -- not which flags appear. A bare lockfile install names none, and neither does `pip install .`, which builds from the working tree instead of fetching. A source flag consumes only its own argument, and which flags take one is a property of the tool: pip's `-r`/`-c`/`-t`/`-f` do, while gem's `-r` is `--remote` and go's `-t` is a boolean. A record that fires on routine installs is background noise and background noise is the same as no record, but one that goes quiet whenever a flag appears is worse -- it reads as coverage it does not have.

**Which file, and which directory, was a bypass of its own.** The exemption was keyed on flag spellings, and the gate read `package-lock.json` in the directory the command started in. Measured with npm 11.19.0 against a local registry, with a synthetic package whose lifecycle scripts leave a mark:

| Form | Where npm recorded it | Before v2.18.0 | Now |
|---|---|---|---|
| `--no-save`, `--save=false`, `npm_config_save=false`, `save=false` in `.npmrc` | `node_modules/.package-lock.json` only | confirmed clean, then `npm rebuild` ran the package's scripts | rolled back, no script runs |
| `--no-package-lock`, `--package-lock false`, `npm_config_package_lock=false` | `node_modules/.package-lock.json` and `package.json` | the same (`--no-package-lock` was also recorded `UNGATED`) | rolled back, no script runs |
| `npm -C sub install x`, `cd sub && npm install x`, `cd sub; npm install x` | `sub/package-lock.json` | confirmed clean, never rebuilt | rolled back |
| `npm install x` with the hook's cwd in `src/` (no `package.json`) or in a workspace member | the project's, or the workspace root's, lockfiles | nothing read, no record | rolled back |
| `npm_config_global=true npm install x` | npm's global prefix, no lockfile | confirmed clean, no record | recorded `UNGATED` |
| `global` or `location=global` in the project's or the user's `.npmrc` | npm's global prefix, no lockfile | confirmed clean, no record | recorded `UNGATED`, naming the file |
| `global=0` in `.npmrc`, or `location=global` there with `--location=project` | `node_modules`, in neither lockfile | confirmed clean, then `npm rebuild` ran the package's scripts | recorded `UNGATED`, rebuild skipped with a warning |
| The same settings, installing or updating a package already on record | a new version in `node_modules`, the old one still in both lockfiles | confirmed clean, then `npm rebuild` ran the new version's scripts | recorded `UNGATED`, rebuild skipped with a warning naming both versions |
| `npm install x -w packages/a` in a workspace | the root lockfiles and `packages/a/package.json` | the member key read as an unapproved package `packages`, and the rollback left `x` on disk | rolled back, member manifest included |

So the gate reads both of npm's records, in the directory npm installs in, and it asks npm which directory that is. the target walk (`rust/src/pre/targets.rs`) follows the command to where it runs npm: a literal `cd` to a directory that exists, or `env -C`. There it runs `npm prefix` and `npm root` with the install's own arguments and the environment the command gives it (`rust/src/ask.rs`). It runs them with its own npm, on the hook's `PATH`, and never with code the command chooses. A name that chooses code when npm starts is never carried: `PATH` picks npm and the node its `#!/usr/bin/env node` starts, `NODE_OPTIONS` preloads a module, `NODE_PATH` serves one npm does not find beside it, `OPENSSL_CONF` and `OPENSSL_MODULES` name a provider library node loads at start, `LD_*` and `DYLD_*` reach the dynamic loader, `BASH_ENV` runs first where npm is a bash script, and `npm_config_node_options` becomes the scripts' `NODE_OPTIONS` (`ask::code_name`). The first four were measured with node 26.7.0; the rest are what the loader, OpenSSL and bash document. The ask used to carry them, and the npm word with them: `PATH=<dir> npm install x`, `NODE_OPTIONS=--require=<file> npm install x` and `<dir>/npm install x` each ran the command's code three times per judgment, and a command the gate then denied ran it all the same. A gate that runs a command's code to decide whether to let it run has already let it run. What the command assigns, exports or unsets otherwise is carried, `unset NAME` as `env -u NAME`. `npm prefix` names the local prefix: npm's walk to the nearest `package.json` or `node_modules`, its workspace roots, every `.npmrc` it reads, and `--prefix` or `-C`. `npm root` names the directory npm installs into, which is `<prefix>/node_modules` only for a project install; anything else is npm's global prefix, where no lockfile is written. The two run in parallel, under a deadline of 8 seconds for every install in one command.

This replaced a copy of npm's rules in bash, and the copy is why. Each version of it disagreed with npm somewhere, and each disagreement was a silent pass. Taking the named directory as the install directory sent the gate to `src` while `cd src && npm install x` wrote the project's lockfiles. The workspace resolver that fixed that resolved symlinks, and npm does not: from `real/a`, a member that the root's glob reaches as `packages/a -> ../real/a`, npm installs in `real/a`, and the resolver climbed to the root, read it clean, and left the package on disk (validator round 2, F1). A third copy would fail a third way. `scripts/test/install-dir-differential.sh` now holds the gate to `npm prefix` over the validator's 237 layouts and eighteen command forms, with no difference allowed.

Where npm cannot answer, the gate records why and looks in the cwd; it does not choose a directory some other way. The trace then says whether the install was there (below). The reasons are npm missing from the hook's `PATH`, npm failing (it refuses a `workspaces` value it cannot read, and so does the install), npm not answering within the deadline, and a command that hands npm something the shell decides at run time (`cd "$DIR"`, `npm install "$PKG"`, an export set from a variable) or an `env` option this gate does not reproduce. The last reason is the ask's own flags. They go after the install's words, so that `--global=false` outlasts a `-g`, and an install whose last word takes the next word as its value (`npm install x --cache`) took them instead: npm created `--json` and `--global=false` in the project while the gate was judging the command. So the install's words are read with a probe word after them (`npm_ask_words_end` in `rust/src/manager.rs`), and npm is not asked when the probe would be a value or an operand. npm also creates its cache directory when it starts, so an install's own `--cache dir` made the ask create `dir`. The install itself is another matter. The Bash guard kept 7d66f8c's flag at the end of a one-statement `npm install x --cache`, npm took it as the cache directory, and the install created `--ignore-scripts` in the project, as 7d66f8c's rewrite did; `-C` there sent the install into `./--ignore-scripts`. The core sends no such rewrite: that command is denied as `UNDECIDED` (`end-flag-not-an-option`, below), so nothing creates the directory. Each ask names a cache in its own scratch directory, which decides nothing it is asked. Workspace selectors (`-w`, `--workspace`, `--workspaces`) are left off the ask, because npm refuses them on `prefix` and `root` and its `loadLocalPrefix` reads only a false `workspaces`, which is kept. Words are read the way the shell splits them, so a quoted `--prefix "/tmp/x y"` is one path. `npm_config_prefix` in the environment does not move a project install, and npm says so too: measured, it landed in the cwd project. `scripts/test/lockless-forms.sh` runs every row end to end, and it is red on the tree before the repair.

**npm masks parts of what it prints, so a masked answer is read, never used as a path.** npm 11.19.0 writes `***` over anything in its output shaped like a UUID or an npm token, paths included, and no setting turns that off. In a project under a session UUID, which is where an agent's scratch directory often is, `npm prefix` answered `.../***/project`. The gate looked for a project there and denied an approved install. npm cannot be asked for the unmasked path, so the gate reads the masked one against the directories from the cwd up, where the local prefix npm finds by itself always is. The answer stands for one of them only when exactly one reads the same, with each `***` taken as a hidden part of one path segment. Otherwise npm has not said where, and the target is `?` with that reason: a masked `--prefix` below the cwd, or anywhere else. A `--prefix` elsewhere that happens to read the same as a directory above the cwd sends the gate to that directory, which shows no trace of the install, so it is recorded `UNGATED`. The differential holds eight forms under a UUID-named directory to npm's answer for an unmasked twin of the same layout, and `scripts/test/effect-trace-grid.sh` runs them end to end.

**An `.npmrc` moves an install the command does not show, and npm reads it.** Where an install lands is npm's answer, so every `.npmrc` npm reads is in it, the global and builtin ones included: `global=true` in any of them makes `npm root` name the global tree, and the install is recorded `UNGATED`. Whether npm writes a record where it lands is a different question, and npm cannot be asked it before the install. Two settings answer it without moving the install: measured, `global=0`, and `location=global` beside `--location=project`, put the package in the project's `node_modules` and in neither lockfile. So the pre-guard still reads `global` and `location` in two files for that question alone: the project's, in npm's local prefix, and the user's, from `--userconfig`, then `npm_config_userconfig`, then `~/.npmrc`. It reads them the way npm did in the measurements. Keys are case-sensitive, the last line wins, and the project file outranks the user file. Only `global=false`, `global=null`, `location=user` and `location=project` left an install on record, so any other value is read as off the record. This reading never chooses a directory. It can only turn an install the gate would read into an `UNGATED` one, and a wrong guess that way costs one line. The install is recorded, not checked: checking it would mean finding the package by name wherever npm put it, and that is left as a boundary. The same two settings in the global or builtin npmrc are not read for this question.

**A directory is where the gate looks; the install's trace says whether it was read.** Asking npm fixed how npm places an install. It did not fix which directory npm runs in, or with what environment, because the shell decides that, and validation round 3 found the text read wrong again. `false && cd sub; npm install x` installs in the cwd, and the gate followed the `cd` that never ran to `sub`. `command cd sub`, `builtin cd sub`, `eval cd sub` and a `cd` in a `case` arm install in `sub`, and the gate read the cwd. Each read a directory the install never touched, confirmed it clean and passed the install unread. Rounds 1 and 2 had the same shape. A design judgment then ran the forms of all three rounds and new ones end to end, counted 21 silent Claude Code rows, and found that no spelling list closes it: a command can change what npm reads (`npm init -y`, an `.npmrc` it writes, an inherited `CDPATH`) where no text shows it. So the prediction now only picks where to look, and the PostToolUse hook decides whether the install was there.

Just before the command runs, the pre hook touches a baseline file and notes the inode of both npm lockfiles in the directory it picked. Afterwards, a lockfile with a later modification time than the baseline's, at the resolution the filesystem keeps, or one with another inode, is this command's trace (`Install::settle` in `rust/src/post/trace.rs`). npm rewrote `node_modules/.package-lock.json` on every install that installed anything, a reinstall of what was already there included, with the same content and a new mtime; `npm ci` replaced the file. Content and whole seconds are therefore no use: a no-op reinstall shows nothing in either, and it often finishes inside the second the baseline was touched in. Where neither lockfile shows a trace, the install is recorded `UNGATED` with the check that found nothing, `no install trace in <dir>: neither npm lockfile there is newer than the baseline taken before this command or has another inode`. No rebuild runs there, and on Claude Code the user is told that safedeps did not run one. The check starts no npm. It cannot tell a dry run or a failed install from an install that went elsewhere, so the record names the check and gives no cause; that is noise, never a pass.

One trace answers for one npm statement. With two lockfile writers in one command, the first one's trace hid the second one landing elsewhere: `npm install a; command cd sub; npm install b` wrote both directories' lockfiles, and the gate found a trace in the one it read. So two or more npm statements that write a lockfile (every subcommand but the ones that only read, run or publish) share one trace only when nothing but inert statements runs between them (`echo`, `printf`, `tail`, `head`, `grep`, `ls`, `cat`, `true`, with no substitution and no redirection except to `/dev/null` or another descriptor) and none of them relocates itself (a directory or global flag, an `npm_config_*` setting or another word in front of `npm`, a group, a run-time word). An npm install inside a `sh -c`, `eval` or `$(...)` payload beside another one counts as relocated too. Otherwise the command is recorded `UNGATED`, naming what sits between.

The prediction keeps one change of its own. A `cd` that may not run, after `&&` or `||` or inside an `if`, `while`, `until`, `for` or `case` body, holds only along the `&&` chain after it, where every statement runs only if the `cd` succeeded; past that the directory is the one before it. That brings back the rollback of `false && cd sub; npm install x`, and `cd X || exit` is still followed. A conditional `cd` that did run (`[ -d sub ] && cd sub; npm install x`) is then recorded rather than read. With the trace deciding, a better reading of `cd` is coverage, fewer `UNGATED` lines, and no longer safety.

`scripts/test/effect-trace-grid.sh` runs the grid end to end: every row is rolled back or recorded, no Claude row runs a script of the unapproved package, 17 forms that installed something leave a trace and confirm quietly, and a no-op reinstall inside the baseline's second is caught. **The install grammar applies that rule, once.** v2.18.0 measured the recognizer against the spellings the managers document and the shell allows, and most of them passed with no verdict and no record: aliases (`pnpm i`, `npm isntall`, `yarn up`, `bun a`), several options before the verb (`pip --quiet install`), versioned interpreters (`pip3.11`), runners (`npx <pkg>@<ver>` matched a one-character name only; `npm exec`, `bunx`, `uvx`, `pipx run` were unknown), statement positions (`( ... )`, `then`, `do`, `!`, `time`), quoted specs, and flag-carried versions (`cargo install x --version 1`). None of these is a carrier: each is the install command itself. The verb list had seven hand-kept copies that had drifted apart, so the core's grammar (`rust/src/grammar.rs`, with the tables in `tables.rs` and the manager reader in `manager.rs`) now defines it once and every recognizer in both halves of the core reads it. The Bash file that held it, `lib/install-grammar.sh`, is gone. Argv-passing wrappers (`sudo`, `timeout`, `nohup`, `nice`, `xargs`) run the install unchanged and are left out on purpose: the list of programs that exec their arguments does not converge, which is the carrier argument again.

Two spec readings checked the wrong identity, and an agent follows the deny message's prescription by itself, so both were bypasses. A Go module lost everything before its last path element, so `go get example.com/x@v1` prescribed `safedeps check go x@v1`, which approves a name no advisory mentions and then passes any `.../x@v1`. And every spec took the first ecosystem named in the command, so `npm run build && pip install evil==1` checked `evil` as an npm package. Go specs keep the whole module path now, and each spec carries the ecosystem of the statement it came from. Three more readings did the same, and each approved when checked. A version flag was bound to the first token after the verb that was not a flag, so an option's value in front of the package took its place: `gem install --source <url> rake -v 13.0.0` prescribed `check rubygems <url>@13.0.0`, `cargo install --root <dir> …` and `dotnet tool install --tool-path <dir> …` the same with a directory, and every later install with that option and version passed. A name that starts with a digit was read from its first letter (`poetry add 3to2@1.1.1` checked `to2`) or not read at all (`pip install 3to2==1.1.1`). And an npm alias `left-pad@npm:evil-pkg` prescribed `left-pad@npm`, which names neither package and never approves. A version flag now binds to every operand of the verb, and an option's value is left out only when the manager's own help documents a mandatory value for it, so a gap in that list adds a check instead of skipping the package. A name is read whole, and an alias is read as its target. A runner's options did the same with no version flag involved. Every option in front of the package was skipped and the next token taken as the package, so `uvx --python 3.12 ruff==0.1.0` ran ruff unchecked and recorded `pypi:3.12`, and `npx --cache /tmp/c evil@1.0.0` did the same with the cache directory. Each runner now has its own table, read from its own help or definitions. Some options name the package (`--from`, `--spec`, `--package`). Some add a package beside it (`--with`, which is now checked as well). The rest take a value that is not a package. Two parsers needed more than a table, and both were measured against the parser itself. `npm exec` hands its arguments to nopt, which lets a boolean take a following `true` or `false`, while npx's own first pass makes that token the package. And pipx accepts an abbreviated long option, so `--pyth` is `--python`.

**A command word is what the manager's parser accepts, and a `create` is checked as the package it runs.** npm does not read its command word from the documented aliases. Its `deref` (lib/utils/cmd-list.js) reads a camelCase word as dashed and takes any unique abbreviation of a command or an alias, so `npm upd`, `npm install-te`, `npm installTest`, `npm exe` and `npm cr` all install or run a package. A grammar copied from the aliases let every one of them through with no verdict. The npm spellings in the core's grammar are now what `deref` maps to each command, and `scripts/measure/npm-verb-spellings.sh` regenerates them from the npm on PATH and fails when npm accepts one the grammar lacks. Each manager's `create` is a runner that rewrites its operand before it runs it. `npm init vite` runs `create-vite`, `npm init @usr/foo@2.0.0` runs `@usr/create-foo@2.0.0`, and `npm init @usr` runs `@usr/create`. pnpm keeps a name that already starts with `create-`, Yarn 2+ keeps one that matches `create` or `create-*` while Yarn 1 does not, and bun prefixes every name it hands to bunx. The prescription and the record name the rewritten package, read from each manager's source. Prescribing `vite@5.0.0` would have approved a package that never runs and left `create-vite@5.0.0` unchecked. Where Yarn 1 and Yarn 2+ disagree, both are checked, since the command does not say which yarn runs it. `npm init` with no initializer writes a `package.json` and fetches nothing, so it stays quiet. `npm link` (`ln`) reads every argument the way npm-package-arg does and installs each one the global tree lacks into npm's global prefix, then links it into the project (lib/commands/link.js:92-104). A registry argument -- a name, a version, a range, a tag or an `npm:` alias -- comes from the registry, so a pinned one is checked and an unpinned one is recorded `UNGATED`, wherever it stands among the arguments. The recognizer used to read only the first one, so a path in front hid the package after it: `npm link ./lib evil@1.0.0` installed evil globally and ran its install scripts with no verdict and no record. A path or a tarball links local code, and a git or URL argument names no registry package; these stay quiet, and so does `npm link` with no argument. `scripts/measure/npm-link-operands.sh` checks that reading against npm-package-arg itself. And a redirection is the shell's wherever it stands: bash reads an unquoted `>` or `<` as an operator in the middle of a word too, so `pip install requests==2.19.0>/dev/null` installs the pinned package. A reader that took an operator only at the start of a word read the whole word as an unpinned operand and checked nothing.

**A word ends where the shell ends it, so an install's last word may stand against an operator.** The shell ends a word at a blank, at `;`, `&`, `|`, `)`, `<` and `>`, and at a closing backtick, so `npm ci; echo x` hands npm the word `ci`, exactly as `npm ci ; echo x` does. The recognizers ended the last word only at a blank or the end of the line. So an install whose verb stood against the operator was no install to v2.17.2, 7d66f8c or v2.18.0. `npm ci; echo x`, `(go get)`, `dotnet package update&& dotnet build` and `mvn -Dartifact=g:a:1.0.0 dependency:get;` got no check, no record and no `--ignore-scripts`. For npm the backstop still judged the closure afterwards. For pip, cargo, go, gem, maven and nuget this gate is the only one, so the miss was complete. `SAFEDEPS_G_END` in the core's grammar (`rust/src/grammar.rs`) is now that word end, and every recognizer reads it. The lexer ends a word at a `(` that is an operator as well (below); no shell hands the word before it on there, so reading it as an end can only make a recognizer wider. An install inside backticks was read before too, from the substitution's body; the closing backtick is what gives it its `--ignore-scripts` (`` echo `npm ci` ``). A pattern cannot tell a closing backtick from an opening one, and an opening one continues the word: `` npm ci`echo x` `` hands npm `cix`. The recognizers read that as `npm ci`, an over-read that costs a record: the guard still lets the command run, as it did before, and writes one `advisory.log` line about it. The rewrite reads the backticks before the verb and places no flag there, so it does not turn the command into `npm ci`.

zsh also ends a word at a `}` that closes a `{` group: `{ npm ci}` runs `npm ci` there (zsh 5.9, measured), while bash and dash refuse the group. Outside a group, zsh refuses such a `}`, and bash keeps it in the word and hands npm `ci}`, which npm refuses as a command. The first version of this end read every glued `}` as an end, and through the rewrite that changed what ran: `npm ci}` became `npm ci --ignore-scripts} --ignore-scripts`, which bash runs as `npm ci`, and `{ npm ci}` became `{ npm ci --ignore-scripts} --ignore-scripts`, which zsh will not parse. So the lexer decides which `}` closes a group (`group_close` in the lexer), from the `{` groups its walk opened. Which `{` opens one is the walk's answer, the same one that puts a command start after it: zsh opens a group after `function f`, `f()`, `()`, `repeat 1` and the list of `for i (1)`, as well as after a separator or a reserved word. The first version counted the groups with a byte rule of its own beside the walk, which knew only the latter. Once the walk read those heads, `function f { npm ci}; f` closed no group in that rule, its `}` was a character, and the glued form alone passed with nothing recorded while the spaced form was read (verdict tookdaki-20261005-144303, N2). `scripts/test/consumer-forms.sh` holds each of those glued forms, for npm and for maven, to its spaced form. A glued `}` with none open is a character in the views the recognizers and the rewrite read (`%`, a byte with no role in the lexer: `_` is a byte of a name, so `}=(` read again became the array assignment `_=(`): no recognizer reads `npm ci}` as `npm ci`, and it gets no rewrite. One that closes a zsh group stays `}`, ends the statement, and gets its flag before the `}` (`{ npm ci --ignore-scripts}`), which zsh runs with the flag and bash still refuses. The words the extractor reads end there too, so `{ mvn -Dartifact=g:evil:1.0.0 dependency:get}` is checked as its spaced form is; read as a grouping character inside the word, that `}` left the goal unnamed and the install unchecked. The bash reading reads such a `}` as zsh does only where bash leaves a group open at the end of the text, since bash then refuses the text and runs none of it. Where bash closes the group later, as in `{ npm ci}; }`, bash runs `npm ci}` and zsh refuses the last `}`. The readings then rewrite the command differently, so it is `UNDECIDED`. A group that spans lines (`{` on one line, `npm ci}` on the next) needs nothing more, since the lexer reads the command whole. The decision is made at the top level, where the walk reads the words. A `}` nested in a substitution is decided where its body is read as a payload. The recognizers read `` echo `{ npm ci}` `` there, as an install, and the rewrite reads it there too. A substitution body that holds `npm` and a `}` the lexer left to the payload's reading is read as a payload, at its own top level and in the same reading. Its flags map back to the command through the payload's source map, so `` echo `{ npm ci}` `` becomes `` echo `{ npm ci --ignore-scripts}` ``, which zsh runs with the flag. The rewrite used to read such a body as part of the command, where that `}` is a character. With the `}` on the verb, the install got no flag and was recorded as kept to the floor. With the `}` on the last word, as in `x=$( { npm ci --ignore-scripts=false} )`, the statement read as already true, because npm reads `false}` as true. It got no flag and no record, and zsh ran the install's scripts. Those were two shapes of one class, so the rewrite now reads the body where the recognizers do, and no shape of the `}` is a case of its own. Such a body is read at the depth of the text it stands in, with no bound. It is always shorter than that text, so the reading ends. A body the shells read differently is `UNDECIDED`, as the same text is at the top level: `x=$( { npm ci}; echo; } )`, where bash closes the group at the last `}`, and `` echo `repeat 1 { npm ci}` ``, which only zsh parses. Read as part of the command, they were rewritten with no flag for the install in the body.

The views the recognizers read blank the backslash of an escaped operator, so `npm ci\;` still reads as `npm ci`, as it did before, though the shell hands npm `ci;`: an over-read that costs a rewrite of a command that installs nothing. `scripts/measure/glued-verb-reading.sh` writes each manager's install with its last word against each operator and again with a blank before it, asks the guard for both, and prints what bash, zsh and dash hand the manager. It also runs every rewrite through the three shells with a stand-in for the manager: each shell must hand the stand-in the words it handed for the command as written, plus `--ignore-scripts`, and refuse the rewrite exactly where it refused the original. Of its 455 forms (35 installs across 13 managers, against 13 endings), v2.17.2 (bb0787d) read 70 differently from the spaced form and did not read 171 more either way. This tree reads none differently and leaves none unread (macOS, npm 11.19.0, load 4 to 7; `--tree` measures another checkout). Each of its 49 rewrites hands every shell the words the command as written handed it, plus `--ignore-scripts`, and is refused exactly where that command was, with one exception. In `{ npm install evil@1.0.0}` the flag 7d66f8c appended to a one-statement install stands after the closing `}`, and zsh refuses the rewrite as it refused 7d66f8c's own; the table names that row `floor-zsh`. In 84 forms the install names no package and is no npm install (`go get;`, `pnpm install;`), so neither form gets an answer whether it is read or not, and the table marks them silent rather than agreeing. The 35 `nogroup}` forms have no spaced form and are held to their rewrite alone. A heredoc fed to a shell (`bash <<E` with an install in its body) is a carrier the enumeration leaves out, so the table prints it and does not judge it.

**The scanner reads quotes and backslashes the way the shell does, and a reading that fails is not an empty one.** Every predicate reads the scan view of the lexer, which blanks quoted text, so blanking text the shell executes hides it from all of them at once. Four readings did that until v2.18.0: `"a\\"` read as an escaped quote, `\"` outside quotes read as an opening quote, a line continuation split into two lines, and a multi-line quoted string scanned line by line, whose closing quote then read as an opening one. Backslashes now pair up inside double quotes, escape the next byte outside them (an escaped `;` or `|` is a character, not the end of a statement), and do nothing inside single quotes; an escaped newline is dropped where the shell joins the bytes around it, and a newline inside quotes ends no statement. The spec readers take their words from the same lexing (below). They used to delete the quote characters and keep every backslash, so `pip install ev\il==6.6.6`, which installs evil 6.6.6, was recorded as unpinned and never checked, and `pnpm add ev\il@6.6.6` prescribed `check npm il@6.6.6`. In the Bash guard every predicate read the scan through awk, grep and sed inside conditions, where `set -e` is off, so a failed awk used to read as "no install". The core runs none of those programs. What can fail there is a reader that stops short of the whole command, and it sets `failed` on the run (`Run` in `rust/src/core.rs`) instead of returning what it reached. One gate settles it: every path that lets a command run crosses it once, after its last reading and before its first side effect (the snapshot, the pending record, the inert meta, the allow), so a command denied for a failed reading leaves no state. If a reading failed, a command that names a package manager's executable anywhere, in any case, is denied as `UNDECIDED`, and anything else runs with the failure on record (`settle_scan_failure` in `rust/src/pre.rs`). The test is the grammar's executable list (`grammar::EXECUTABLES`) matched in process. The version it replaced in the Bash guard re-ran a second recognizer through grep, sed and the join awk, went quiet with them, and could not match everything the scanned recognizers match (three review rounds). A deny that reports a finding after a failed reading reports `UNDECIDED` instead. `scripts/test/native-scan-failures.sh` is the census. It reads every failure assignment in the core's reader methods, compares them with `scripts/measure/native-scan-sites.json`, and for each of the 14 registered sites builds a copy of the source that forces that producer's failure branch and runs the unchanged public pre hook on three commands: one that names a package manager, one that installs, and one that names none (42 rows). The first two must be `UNDECIDED` denies that leave no rewrite, no pending record and no snapshot meta, and the third must be allowed with the failure on stderr and in `advisory.log`. The census is generated from the source because a hand-kept list of marked readings missed one twice in the Bash census. It proves that a failure at each producer reaches the settlement, not that every branch is naturally reachable. It is a release battery. The Bash census, which failed every awk, grep and sed call one at a time and all at once, is retired with those programs.

**The command is read in one pass, the way the shell lexes it.** One lexer (`Lex` in `rust/src/lex.rs`, carried over function by function from the awk program `shell_lex` of the Bash guard) follows the lexical state the shell keeps: single, double and `$'...'` quotes, escapes, comments, heredoc operators and their bodies, arithmetic, command and parameter substitution, backticks and line continuations. Every reader of the command takes a view of that one lexing. The detection predicates read the scan view, with quoted text, comments and heredoc bodies blanked. The payload readers read the scripts the command hands to a shell and the bodies of its substitutions, each one as the lexer delimits it. A substitution in the body of a heredoc whose delimiter is unquoted is live code there, because the shell runs it; the body is walked by the same lexer, so a substitution in it may span lines, nest, or hold a case statement, where a separate line-at-a-time scanner had missed all three (caught in review). The prefixes a statement may start with -- assignments, redirections with their targets, `env` with its options and assignments, `command`, `exec` -- are read off the same lexing before an install is matched, so a value is one word however it is quoted or nested: `FOO="a b" pip install ...` and `FOO=$(cmd arg) pip install ...` passed with no verdict while a regex read the value as the bytes up to the first blank or quote. The lexer replaced three state machines that ran in turn -- a line-based heredoc pattern, a line joiner and the quote scanner -- and had to agree. Across three review rounds they did not: a heredoc was stripped twice, opened where there was none (a herestring, an arithmetic shift, a quoted `<<EOF`), or not opened where there was one (a digit delimiter, a multi-line string closing on the line that opens it), and each time every line after it vanished from the gate. `scripts/measure/shell-reading-forms.json` records each form with the values the shells produce for it, and `scripts/test/shell-reading.sh` requires a verdict on every form a shell runs to its last line; `scripts/measure/shell-reading-measure.sh` re-measures the shells.

**A command is read once per shell: bash, zsh and dash.** The shells lex the same text differently in a few places, and a line one of them runs can be quoted text, a heredoc body or arithmetic to another. So the lexer has three readings, and each reading is a shell. Every reader of the command reads it inside one reading, and text one reader hands another -- a `sh -c` script, a substitution's body, a statement -- is lexed in the same reading, never in another one. The gate judges the union. A finding in any reading is a finding, the targets and the specs are those of every reading, and a command is `UNDECIDED` only when no reading closes or a step of one reading failed. The readings agree byte for byte up to the first place where the shells differ, and the bash reading reaches that place in the same state, so the bash reading runs first and says whether the other two are needed. A command that never reaches such a place costs one reading.

Rewriting the command is not reading it. `--ignore-scripts` changes the text every shell reads, so it is added only where every reading puts the npm installs in the same place. Otherwise the command is `UNDECIDED`, and the reason says the shells read its npm installs in different places. Adding the flag where any reading saw an install would edit text that another shell reads as data, and a heredoc delimiter is one place where that changes what the shell reads next.

This replaced a reading per divergence ("axes") collected from the first reading, and the round that made the readings shells measured why that could not close. zsh decides a `((` at each site, so one command held a subshell `((` and an arithmetic one (form M1), and no switch for the whole command can follow that. Readers after the join lexed a zsh reading again under bash's rules and hid the line a second time (form SL1: `echo "${x:-'}"; <install>; echo "'}"`, which zsh and the agent's wrapper run). And dash, which reads a `sh -c` script on Linux, reads `((` like bash and the apostrophe like zsh (form D1). Inert installs had the same gap: zsh ran an `npm ci` that bash read as quoted text, with no flag, no record and a meta that said inert (forms I2, I3).

A command that never closes -- an open quote, a heredoc without its terminator -- is a command the lexer could not finish, so it is treated as a failed reading: `UNDECIDED` when it names a package manager. The lexer does not model shell options or aliases set in a user's rc files, shells and versions other than those measured, or bash's own parse errors. The same shell state decides whether npm keeps `--ignore-scripts`: a function or alias in the agent's shell snapshot, `.zshenv` (which `zsh -c` always reads), `BASH_ENV`, or a function or alias the command itself defines can change the words npm receives, and each turned a plain rewritten `npm install` into `ignore-scripts` false when measured. None of it is in the command text, so no reading of the text can settle it, and safedeps does not claim it: its records say what it added and ran, and the rewrite holds 7d66f8c's (above), so this state can take from the install only what it could take from 7d66f8c's. One of those is measured: where bash takes a `$((` for a substitution, it finds the end of that substitution without reading heredocs, and a line it then runs can be hidden in the bash reading. In 400 seeded random forms this happened once, on macOS and Linux alike (F346). The zsh and dash readings showed the line, so the gate judged it. One form is unfaithful the other way on macOS (F19): zsh runs the line after a heredoc body that leaves an arithmetic open, and the zsh reading does not close; the bash and dash readings show it, so the gate judged it too.

**The lexer also owns where a statement and a substitution end.** A `case` pattern ends at its `)`, and that `)` is a statement boundary in the view the recognizers read, so an install in a case arm is judged; a grammar pattern could not tell that `)` from any other, so case arms used to sit outside the gate. The body of every command substitution comes from the lexer too -- `$(...)` as the shell delimits it, a backtick body unescaped the way the shell unescapes it, with `\`` nesting -- replacing a string scan that cut a body at its first `)`. So does the body of a process substitution, which the shell runs the same way (below). A `((` is decided wherever it stands, not only where a command starts; a hand list of command positions let a heredoc swallow the line after it (caught in review). A `#` opens a comment only at the start of a word, which is a question about the token before it rather than the byte: after an unescaped blank, a newline, or an operator, and not after an escaped byte or the `)` that closes a `$(...)`, a `$((...))`, a process substitution or a zsh glob word, which are parts of a word (`echo $(echo a)#b` prints `a#b` in every shell measured). A line continuation is no byte at all: the shell removes it before it splits tokens, so the byte before it decides (`a \` then `#x` on the next line is a comment, `a\` then `#x` is the word `a#x`). Read by the byte, the lexer took such a `#` for a comment, and a comment that swallowed the close of a substitution hid the lines after it (forms G1-G4); read as a byte, a continuation turned a comment into a word whose quote hid the lines after it (LC1-LC3). The `)` of a subshell or an arithmetic command does end a token, and a `#` after it is a comment everywhere (G7, G8). The forms WB1-WB22 pin the answer for each kind of byte before a `#`, measured in every shell. A comment that starts a backtick body ends at the closing backtick, and a heredoc opened inside a substitution that closes on its own line has no body.

**Where a command starts is the lexer's to say as well.** The recognizers used to find a statement start with a regex: a separator, then a chain of the reserved words that may stand before a command (`{`, `!`, `then`, `do`, `time`, and so on). A chain names the words before a command. It cannot see the shell state that puts a command there, and three review rounds in v2.18.0 each found the next form it missed. A function body passed (`f() { pip install evil==1.0.0; }; f`), and so did a function with more than one name (`f g() {`, `function f g {`), `time -p {`, `coproc NAME {`, zsh's short forms (`for i (1) {`, `repeat 1 {`, `if [[ 1 ]] pip install ...`, `} always {`) and `for ((i=0;i<1;i++)) {`. The last form showed a second fault: the statement split cut at the `;` inside the arithmetic, so even a pattern that matched the whole command found no install in any statement. The lexer now walks the words with the shell's grammar state and finds every place a command starts: after a separator, a case pattern, a reserved word, a function head, `time` and its options, `coproc`, and the zsh short forms. A function head is an empty `()`, `function NAME... {`, or `function NAME` right before any other compound command, because bash 5 reads `function WORD function_body`: `function f if pip install evil==1.0.0; then :; fi; f` runs the install there, and it passed until the walk read that form. bash 3.2, zsh, sh and dash fail to parse it, and bash 5 does too after a second name, so the rule is shared and adds starts only. A subshell that is the body (`f() ( pip install evil==1.0.0 ); f`, `function f ( ... )`, and in bash `coproc NAME ( ... )`) starts at its `(`, glued to the `()` or not; without that start the statement began at the function name, and the extractor read the install as arguments of `f`. The same holds for any subshell that stands where a command does, with words of its statement before it. No word follows the `{` of `function f { (pip install ...); }`, the `do` of `for i do (...)` or the `then` of `if (true) then (...)` to carry a start. So the statement began at `function`, `for` or `if`, no manager was read in it, and each of these passed on main; bash, zsh and dash run the ones they have. The walk now starts a command at such a `(`, glued to the word before it or not (`do(`, `then(`). It also reads the place after a subshell's `)` as one where a command may start, which is what lets `then` follow `(true)`. A `(` among the arguments opens no subshell, and its `)` ends nothing. A function head may hold a blank between its parentheses (`f( ) { ... }`, which bash and dash run). A case arm starts right after its pattern's `)`. A `;`, `&` or `|` that is not at the top level ends nothing, inside arithmetic or a substitution. The install patterns anchor at separators only, and each start reaches them as one (below). The statement split that the spec extractor and the target walk share cuts at the same starts, so the recognizer and the extractor read one set of statement starts in each reading.

The starts are part of the reading, like everything else the lexer decides. Each rule belongs to the shells that have the form, measured in each shell rather than assumed. zsh alone reads a `}` wherever it stands, `always`, `repeat`, `foreach`, `for NAME (WORDS)`, a command right after `[[ ... ]]` or `((...))`, `case WORD {`, and `;|` ending a case arm. bash alone reads `coproc NAME` before a compound command (`coproc WORD shell_command`: `{`, `if`, `while` and the rest) and `;;&`. A rule every reading shares may only add starts, at a form the shells without it fail to parse: dash runs `f() pip install ...` and bash does not, and dash runs no `function` at all. Where the bash reading would place a start differently from zsh or dash, it says `DIVERGE`, so the zsh reading that finds `repeat 1 { pip install x; }` runs. The same words in an argument open nothing (`echo { pip install x }`, `echo then pip install x`). An assignment or a redirection before a command stays with it: a start between `npm_config_global=true` and `npm install` took the assignment off the install and lost its `UNGATED` record. A redirection that comes first takes the start itself. Both are removed with the command's other prefixes before an install is matched, at every start the walk finds, and a redirection anywhere else is blanked (below). Redirections were not removed at all at first: `2>/dev/null pip install evil==1.0.0`, which every shell runs, put a word between the start and the install and passed with no verdict. Assignments were removed only after a separator or a reserved word, because the prefix stripper found starts on its own, so `function f { FOO=1 pip install evil==1.0.0; }; f` passed the same way. dash has no `&>` (the table above): it ends the command at the `&` and starts the next one at the `>`, so `echo a &>/dev/null pip install evil==1.0.0` runs the install in dash, the `/bin/sh` of Debian and Ubuntu. Every reading read a redirection there and none said `DIVERGE`, so it passed. The statement split decided `&>` by itself too, and now reads it from the view. The starts are never written into the scan view: a prototype that did broke that view's idempotence and the pipe check that reads it (`| { sh; }`). The inert rewrite needs no starts of its own: it rewrites every npm install verb in live code, and whether to rewrite is each reading's recognizer's answer, read from the recognize view. So a form that only some shells parse follows the agreement rule above: `time -p { npm install x; }` and a case arm get the flag in every reading, while `repeat 1 { npm install x; }` or `for ((i=0;i<1;i++)) { npm install x; }` is `UNDECIDED`, because a reading that cannot parse the form finds no install to agree on. The judgment behind this measured 60 forms against bash 3.2, bash 5, zsh, sh and dash. Of the 38 that some shell runs, the release before it denied 17, and the lexer's starts deny all 38, with no new record on the 17 data forms except one: zsh reads `echo () pip install x` as a definition of a function named `echo`, and it is recorded. zsh's `case x {` is read as a case that never closes, so it is `UNDECIDED`. `scripts/test/consumer-forms.sh` holds the forms with what each shell ran, and `scripts/test/scan-contract.sh` holds the rules of the starts and the shell runs they rest on.

**A start is a place between two bytes, and the walk hands it on as one.** The first design of the walk handed the starts on as bytes: the walk found each one, and the stmts view wrote a `;` over the byte before it. A command glued to the token before it has no such byte. Three review rounds each found the next place where that happened, and each repair borrowed one more byte of a neighbouring token: a case pattern's `)`, the `)` that closes a head, zsh's glued `{`. The fourth place could not be borrowed at all. A redirection, an assignment or a precommand glued to a reserved word, `!`, a head's close or zsh's `{` puts the start on the first byte of that prefix (`if true; then>/dev/null pip install evil==1.0.0; fi`, `!>/dev/null pip install ...`, zsh `{X=1 pip install ...; }`), and the prefix is what the recognizers' text removes. The prefixes were removed by a second lexing of a text the first lexing had already changed, which looked for the starts again in the bytes that were left, and found `thenpip`. Every shell runs that install. A table generated from the simple-command grammar (POSIX `cmd_prefix` and `Bang`, the bash and zsh additions, the precommands) and put in every place of the manuals' compound commands found 403 forms of this kind that some shell runs and the gate passed with no record, 108 of them in all four macOS shells; main, asked about 111 of them, passed each. The verdict on this class (bamdori-20261004-224625) kept the walk and changed how a start reaches its readers.

The walk now hands each start on as an event, a place between two bytes: one where a command starts, at its first byte with any prefix, and one where it reads the command word. Every reader takes the events, and none looks for a start in bytes. The recognizers read the recognize view: the stmts bytes with each command's prefixes removed, every other top-level redirection blanked, a line continuation dropped, and a `;` put in at each start that no separator already stands before. The statement split cuts at those same starts (the stmtcuts view). And the bash reading compares the event sets of its three walks, so a start that only one shell reads still brings that shell's reading in. Every rule that borrowed a byte is gone. Two readings that asked whether a word starts at a byte now ask the walk too: a descriptor word glued to a redirection (zsh `{2>/dev/null pip install x; }`) and a subscript assignment (zsh `{a[1]=x pip install x; }`) start where the walk starts a command. zsh and dash read one digit before a redirection operator as its descriptor, and bash reads any number (measured: `echo 12>/dev/null` prints `12` into /dev/null in zsh and dash), so in zsh `repeat 12>&1 pip install x` runs the install twelve times, and the bash reading says `DIVERGE` there. zsh reads `&!` as one list terminator, so `true&!pip install x` runs the install in zsh alone, where bash and dash read `!pip` as a command name. A zsh precommand modifier where the other shells read the command (`exec -- noglob pip install x`) makes the bash reading say `DIVERGE` as well; the second lexing used to say it by accident.

**A reader lexes the command, or a payload, and never a view's output.** The recognize view was described above as one lexing of the text, and it was not: the recognizers lexed the joined view of the command, which another lexing had already made. So did the landing, the spec extractor, the writer attribution and the inert reading, each through the joined view or the code view, and the extractor once more through the unprefixed view. The joined view blanked a heredoc body and its terminator line but kept the live code in an unquoted body, because the shell runs it. Lexed again, `cat <<E`, `$(date)`, `E`, `pip install evil==6.6.6` read as `$(date)   pip install evil==6.6.6`: a command named by a substitution, with the install as its arguments. Every shell measured runs that install (macOS bash 3.2, GNU bash 5.2, zsh, sh and dash; Linux bash and dash), and the gate passed it with no record, on v2.18.1 and v2.18.0 too. An npm install there ran without `--ignore-scripts`, and `git commit -F - <<EOF` with a `$(date)` in its message is an ordinary agent command (verdict buri-20261005-145152). Each reader now lexes the command as written, once per reading, and takes every view it needs from that lexing: the recognize view, the pieces view (cut where the statement split cuts, with each statement's words after quote removal, with and without its prefixes, and its recognize bytes), and the stmtraw view, from which the statement split reads words, with a body and its live code blank and a line continuation stepped over. A payload is the one other text a reader lexes: the scripts the command hands to `sh -c` or `eval` and the body of each substitution, which the inner shell reads as a script of its own. The joined view and the per-line reading of the pieces view are gone, so no reader can lex them again. In the Bash guard `scripts/test/scan-contract.sh` held this as a structure, not a comment: an awk shim recorded every lexing of a guard run, and each text lexed had to be the command, a payload, or a whole statement of one (a statement, or the inert reading's statement with the flag put in). The payloads it allowed were written by hand beside each form, as the shell runs them, never taken from the code, and a mutated copy that lexed the live view of the command again turned that check red, with the rows for this form in `scripts/test/consumer-forms.sh`. That trace is retired with the awk calls it traced (`scripts/test/lib/reader-retirements.json`), and the rows in `scripts/test/consumer-forms.sh` remain. What holds the rule now is narrower: `scripts/test/lib/core-reader-check.py` checks every payload's source map, that each byte of a payload is a byte of the original command, nested payloads included, and that the payload has the shape the lexer's records name. It is not an inventory of every lexing the core makes, so a reader that lexed a view's output would not be caught by it.

`scripts/test/scan-contract.sh` holds the contract every reader relies on, on each event of the recorded shell forms, a spread of the generated first places and random input, in each reading. An event stands at top-level code, never inside quotes, a substitution, arithmetic or a heredoc. No start falls between a command's prefixes and its command word. The recognizers read each command word right after a separator. And the statement split cuts there. The redirection grid's first places are the generated ones now (`FIRSTS` in `scripts/measure/redirection-grid.sh`, the list `scripts/measure/first-place-grid.sh` reads), not four picked by hand. With them the grid holds 8438 forms, 7047 of which some shell runs, and `check` holds each of those to a verdict that names the package. Two payloads read by a grammar that is not the shell's are left for a later plan and pinned as passes in `scripts/test/consumer-forms.sh`: `env -S STRING`, which env(1) splits by its own rules (its options, `--`, `\_`, `#`) where the payload reader reads a script, and code in a zsh glob qualifier (`*(e:'...':)`), which no reader reads.

**What the lexer hands its readers is a rendering or numbers.** Structure leaves the lexer in two shapes. A rendering prints one byte for each byte of the command: scan, stmts, recognize, live, flat, noredir, code and wordends. A byte that is not code there becomes a blank or `_` (a `}` that closes no group, `%`), so a byte a reader reads as structure (`;` `&` `|` a newline, a parenthesis) stands only where the shell reads structure, and no byte the command writes can move it. A record is cut by its reader at a separator byte. Where the record carries the command's bytes as content, the command can write that separator, and the reader then cuts where the shell does not. That happened twice to the payloads. The `sh -c` and `eval` scripts and the substitution bodies went out one per line, and a newline in a payload split it; then each ended in \035, and a \035 in a payload split it, the halves were lexed alone, and the install after the byte passed with nothing recorded (verdict buri-20261005-181919: `x=$(echo "<\035>"; pip install evil==6.6.6)` and five more forms that v2.18.1 denied; a `sh -c` or `eval` script holding a \035 passed the same way from v2.18.1 on). Escaping the separator would close that byte and leave the class: each separator of each record would have to be remembered, which is how the same class was rejected twice. So the payload views print numbers: a kind (`S` a `sh -c` script, `E` an `eval` or `env -S` script, `B` a substitution body), then ` a:n` for n bytes of the lexed text from byte a, and ` #c#c...` for bytes by code, which an escape decoded or a join put in. The reader holds the text and cuts it (`payload_build` in `rust/src/core.rs`); a unit it cannot place, outside the text or a code outside 1-127, is a failed reading. Inside the core a payload is a `Payload` that carries its text and where each byte stands in its source, never a stream with a separator. The Bash guard moved payloads between readers as bash arrays for the same reason. scan-contract holds the alphabet: every line of both views is `!` or matches `^[BSE]( [0-9]+:[0-9]+| #[0-9]+(#[0-9]+)*)*$`, and every unit lies in the text, on the recorded shell forms, on each control byte in four payload places and on random input that mixes the payload grammar with every byte from 0x01 to 0x7f.

| The floor's script-word search (`inert_payload_spans`, kept in `rust/src/inert/floor.rs`) | Its own search for a `sh -c` or `eval` head and the first quote after it | Not a record: a second reader of the scripts, kept so the floor holds. It decides only where v2.17.2's flag goes, and the structural reader (`rust/src/inert/read.rs`) does the reading. |

A lexing fact is the same whichever view asks for it. The table of `$'...'` escapes was loaded for the pieces view alone, so the cscripts view read `sh -c $'echo a\npip install evil==6.6.6'` as a backslash and an `n`, one statement after `echo`, and the install passed with nothing recorded from v2.18.1 on; it is loaded for every view now. Four facts are still computed only for the views that print them. Each is listed with whether two views can say different things:

| Fact | Computed for | Can two views differ? |
|---|---|---|
| Statement starts (`starts_all`) | recognize, stmtcuts, events, cwords, unprefixed, pieces, in a reading that closes | Yes, through the next row: `fdword` reads the starts. |
| Redirections (`redirs`, `fdword`) | pieces, cscripts, stmts, recognize, stmtcuts, cwords always; noredir, live, flat in a reading that closes | Yes, twice. In a reading that does not close, noredir, live and flat blank no redirection and the others do; such a command is `UNDECIDED` before any of them is read for a verdict. And the descriptor word after a `{` zsh reads as glued (`{2>/dev/null pip install x; }`) is part of the redirection where the starts are known and a byte of the word before it elsewhere (noredir, live, flat, stmts, cscripts), so those views keep a `2` the others drop. Not measured to move a verdict. |
| Prefixes (`prefixes`) | unprefixed, recognize, cwords, pieces, in a reading that closes | No reader compares them with another view's. The cscripts view keeps a prefix word and looks for a shell name in every word, which can only find more. |
| Array assignments (`AR`) | The starts views | No: only the starts read them. |

**The spec extractor's words come from the lexer too.** The extractor reads each install statement as words: its redirections taken out, the shell's quote removal applied, and the statement cut at `;`, `|` and `&`. Each of those had a reader of its own until v2.18.0, and each reader had its own model of the quoting, which was the lexer's model approximated. An awk that knew `'...'`, `"..."` and a backslash read the `>` inside `"$(echo ">'")"` or `$'...\'>'` as a redirection and took the rest of the line as its target, so the pinned install after it passed unchecked. The sed it replaced read a redirection only at the start of a word and kept a quoted target as operands. And the cut read no quotes at all, so `pip install --log "a;b" evil==1.0.0` left `evil==1.0.0` in a piece that was not an install. Each copy was wrong somewhere, and the place it was wrong was a silent pass. All three now read the lexer's classes: a redirection is an operator byte in top-level code, a quote is removed where the lexer opened it at the top level, a `$'...'` escape is decoded, and a cut is a separator in top-level code. `scripts/measure/word-reading-forms.json` records the argv bash and zsh hand a stand-in for the manager on each word form, and `scripts/test/scan-contract.sh` requires the extractor's words to be that argv. Inside a word, a byte the extractor would cut at -- a blank or a grouping character -- is carried as a marker, and the empty word is a marker alone, so a word stays one word and an empty one keeps its place. Split on blanks, `uvx --python $(which python3) ruff==0.1.0` and `uvx --python "" evil==1.0.0` each gave the option the wrong value, and the pin went unchecked. The spec reader then reads a word the way the manager does: past the blanks at its ends, and for a Python requirement past every blank in it, so `pip install "requests == 2.19.0"` is the pin PEP 508 says it is. One reading is still short of the shell's, and it is named rather than approximated: a `$'...'` escape whose value depends on the locale (`\u`, `\U`, `\c`) or is not one plain byte is a failed reading, so the install is `UNDECIDED`. The recognizers are a separate matter. They read the recognize view, where a quoted word is blank as in the scan view, so a command word the shell assembles from quotes (`'pip' install`) and a runner whose quoted package has nothing but options after it (`npx "evil@1.0.0"`) are not recognized. v2.17.2 missed both. Reading them the way the shell does is the plan safedeps/command-words-read-as-the-shell-dequotes.

**A redirection is read the way the shell reads it, and the recognizers read the statement without it.** A redirection is an operator, the file descriptor word glued in front of it, and its target word, and the lexer reads all three by the shell's rules. The descriptor word is a number, or a name in braces, which bash 4.1 and later and zsh read as a variable the shell opens a descriptor into. Read as the command name, `{fd}` let `{fd}>/dev/null pip install evil==1.0.0` pass with no verdict, and bash 5 runs that install. bash 3.2 and dash read `{fd}` as a word, and every reading reads it as a descriptor anyway: that can only show them a command they do not run. A descriptor word glued to a heredoc operator (`0<<E`) is part of the operator. The target is one word as the shell cuts it, and a process substitution is one word whatever it holds. The target of `< <(true) pip install evil==1.0.0` was cut at its `<`, the empty word, so `<(true)` stood where the command name stands; bash 3.2, bash 5 and zsh run that install. zsh reads a `!` after `>` as part of the operator, where bash and dash read the start of the target (the table above), so the bash reading says `DIVERGE` where a blank after the `!` moves the target.

The recognizers read every statement with its redirections blanked, the statement the spec extractor reads. They used to drop a redirection only where it came first, so one between the manager and its verb hid the install from every recognizer while the extractor read it: `pip 2>/dev/null install evil==1.0.0`, `cargo 2>&1 add`, `gem >/dev/null install` and `npm >/dev/null install evil@1.0.0` passed with no verdict in every shell, and the npm form ran its lifecycle scripts. The inert rewrite reads the live view, which blanks the same redirections, so it finds that verb and puts `--ignore-scripts` right after it in the command as written. A target that holds a substitution needed a second view. The live view keeps that body, because the shell runs it and an npm install inside it needs a flag of its own. So in `npm >$(echo f) install x` the body stood between npm and its verb, no verb was found, and the command ran its lifecycle scripts with no flag and no record, in every shell and on main too. The rewrite now also reads the flat view, which is the live view with the whole redirection blank, and finds the verb there. A redirection target no longer passes for the flag either: `npm install x > --ignore-scripts` read as an install that already had it, and got no rewrite. The body of a process substitution runs, so it is a payload like a command substitution, and its installs reach the extractor. That closed a second silent pass: in `cat <(pip install evil==1.0.0)`, `tee >(pip install evil==1.0.0)` and `diff <(cargo add evil@1.0.0) x` the recognizer found the install, the extractor never saw its spec, and the command passed with no ledger check. The npm form was allowed with only `--ignore-scripts`. Plain process substitutions with no install in them (`diff <(sort a) <(sort b)`, `while read l; do echo "$l"; done < <(ls)`) stay unjudged.

**Where a word ends is the walk's depth, and nothing else.** The shell's grammar puts parentheses inside words: the value of an array assignment (`a=(x y)`, `a+=(x)`), a glob group or qualifier (`/dev/(null|zero)`, `*.py(N)`, bash's `@(a|b)`), a process substitution, and zsh's `=(...)`. The lexer walk follows that grammar. The function that cut words, `word_sep`, answered from a fixed set of bytes instead, so a blank or a `)` inside such a word ended it. Where the two answers differed, what followed the word was a statement no recognizer read. `a=(x) pip install evil==1.0.0` runs in bash and zsh; the gate read `x)` where the command stands and passed it, and the npm form lost its `--ignore-scripts` as well. main denied that form, so this was a regression of the release that moved the prefixes into the lexer. Three more classes passed on main too. The `)` of a case pattern inside a substitution ended a value or a target (`>$(case a in a) echo f;; esac) pip install ...`). zsh's `=(...)` and a glob qualifier in a target were cut at the `(` (`< =(true) pip install ...`, `>/dev/null(N) pip install ...`). And zsh's precommand modifiers were read as commands (`noglob pip install ...`).

Each of those parentheses is now a context on the walk's stack, like `$(...)`, and every byte up to its close is nested. A process substitution takes the `<` or `>` that opens it into the word. A case pattern close is a separator only at the top level. A comment has the depth of the context it stands in, so one among the elements of an array ends no word outside it. `word_sep` and the pieces view read the depth and keep no byte set of their own. What the walk needs beside the depth comes from the manuals, as closed lists. An assignment word is a name, an optional subscript, and `=` or `+=`. bash pairs the brackets of the subscript whatever they hold, so `a[1 + 1]=x pip install ...` runs the install in bash alone, and the bash reading takes the blank as part of the word. zsh has six precommand modifiers: `-`, `builtin`, `command`, `exec`, `nocorrect` and `noglob`. The two every shell has were read already, and the other four are prefixes and starts in the zsh reading. zsh also reads `<N-M>` as a glob for a range of numbers, so `pip >f<1-2> install ...` has one target and an install there, where bash and dash read two redirections. Where the shells differ, the bash reading says `DIVERGE` (the table above). And a reserved word is one only as a whole word: read by its letters, the `do` in `>f-do(.)` and the `!` in `>f!(x)` each put a command after it, and the `(` that followed took the verb of `pip >f!(x) install ...` away.

The walk also checks its own answers. Which `(` belongs to a word is decided while lexing, partly from the bytes before it. Where a command may start is decided by the walk, from the grammar. A `(` left as an operator where none of the bash reading's three walks has a command, or a word parenthesis inside the word they read as the command name, means one of the two misread the command. The reading is then failed, and a command that names a package manager is `UNDECIDED`. This check closes none of the forms above, and it must not be what closes one: when it found the `!` case, that got a rule of its own. It stays for the next place the two disagree.

**The recognizers end a word where the lexer does.** Each install pattern ended a manager or a verb with `([[:space:]]|$)`, a set of its own. The lexer ends a word at a `;`, an operator and a parenthesis too, so `npm ci;`, `(npm install)`, `then npm ci; fi`, `npm ci&& ...` and `npm ci|tail` were no install to any recognizer: no check, no `--ignore-scripts`, no pending state. Every shell runs each of them, and v2.17.2 already passed them. Now every recognizer ends a word with `SAFEDEPS_G_END`. It is not a judgment of its own: the stmts view prints each byte where the lexer ends a word as a blank, `;` `&` `|` or `(` `)` `<` `>`, and scan-contract checks that against the lexer's own answer (the `wordends` view) on the recorded forms and on random input. The same round moved three more lists into one place each. A path in front of a command word reads as the executable at its end, wherever the path points (`.venv/bin/pip`, `$VENV/bin/pip`, `/usr/bin/env`); a sed read only absolute paths, between bytes of its own start and end sets. The words that are shells are one closed list from the manuals (`SAFEDEPS_G_SHELLS`), read by the `-c` script reader, the pipe check and the path strip; one reader took any name ending in sh and another knew three, so `printf 'pip install x' | dash` passed. And the options of `command`, `exec` and `env` are read as their manuals give them: `--` ends them, `exec -aa` is the name `a`, `env -P DIR` takes a value, and `env -S STRING` is read as a script like the words after `eval`. That is the shell's grammar and not env(1)'s, and a string the two split differently passes (a stated boundary, above). `time` takes `-p`, and in dash, where it is /usr/bin/time, options up to `--` with `-o` and `-f` taking a value; the walk and the prefix reader skip the same words. Two places the generated grid found are starts as well: zsh reads a `{` glued to the first word as the group opener (`{pip install x; }` runs in zsh alone), and a subshell glued to a case pattern close (`*)(pip install x);;`) starts its arm. A command glued to the `)` that closes a head (zsh `for i (1)pip install x`, `if ((1))pip install x`) starts between that `)` and its first byte, like any other.

Some readers still keep a set or a list of their own. Each is below, with the direction it errs in. A reader that keeps one and is not on this list is a defect.

npm installs after an arithmetic `for ((...))` head are `UNDECIDED` rather than rewritten: dash reads `((` as two subshells, so the readings put the install in different places, and no one rewrite is inert for every shell. That is fail-closed.

`scripts/test/consumer-forms.sh` holds 90 forms that some shell runs to a verdict that names the package, each with the shells that ran it (macOS bash 3.2, zsh, sh, dash, the agent's wrapper with and without its `setopt` line, and GNU bash 5.2). The same words as data, and ordinary commands that hold a word parenthesis (`files=(src/*.ts); npm run lint`, `ls *.ts(N)`), are held to a pass with no record. `scripts/test/scan-contract.sh` holds the depth of every word parenthesis, the two closed lists, and the walk's check against every place a shell does read a `(`.

`scripts/measure/redirection-grid.sh` puts every operator the bash, zsh and dash manuals list in every place a redirection can stand, and a set of target words after four of them. Those target words were picked by hand, and the review after them found the words nobody had picked. So the words are generated as well: a table of what the manuals say a word may be made of, 87 rows, each with its manual section (bash Quoting, Brace Expansion, Tilde Expansion, Shell Parameter Expansion, Command Substitution, Arithmetic Expansion, Process Substitution, Pattern Matching, Arrays and Shell Parameters; zsh Array Parameters, Process Substitution, Filename Generation, Glob Qualifiers and Precommand Modifiers), put in every place such a word stands: the value of an assignment prefix, a redirection target (glued, after a blank, between the command word and its arguments, after a separator, in a function body), and an argument of echo, where the install words are data. That table found three more forms before the release: zsh's `<N-M>`, the `do` that was read as a reserved word, and a comment inside a substitution in a target, which ended the target (the verdict held there by another reader; the reading did not). The places a subshell stands where a command does are generated the same way: after `{`, a function head, `do`, `then`, `else`, `!`, `time`, `coproc`, a case arm, `if`, `while` and `until`, each with a blank before the `(` and glued to what is before it, and each reserved word that may follow its `)`. That is 61 forms. Some shell runs 58 of them, and each is held to a verdict that reads the install, not to `UNDECIDED`; the other three are data. Before the walk read these places, eight of the 58 passed. It measures each form in the shells, with a stub in place of the manager that marks only the exact install arguments, and requires a verdict wherever a shell runs one. In the committed grid, 8438 forms, 7047 run the install in at least one of the nine shell columns (macOS bash 3.2, zsh, sh, dash, the agent's wrapper with and without its `setopt` line, and GNU bash 5.2; Linux bash 5.2 and dash), and none of the 450 data forms runs it (an operator that starts with `&>` is no data place: dash ends the command at its `&`); `check` requires a verdict on each of the first and a pass on each of the second. The grid also found the measurement's own faults: a marker file named after the stub matched the stub on a volume that ignores case, and bash 5.2 read the `&` of an operator spliced into a form as the matched text, so Linux generated other forms under the same names. The measure script now checks that its markers can say no, and `check` compares the generated forms with the committed ones.

**Which word is the command, which is a value and which is a package is the manager's grammar, read once.** The lexer says where a shell word starts and ends. Which word is the manager's command, which words are option values and which are packages is a question for the manager's own parser, and until v2.18.0 four readers each answered it their own way. The recognizer regexes tried both readings of an option that may take a value, and where both matched they picked one: `npm --prefix x install evil@1.0.0` read as `npm x`, an exec, so the pinned install was allowed without a ledger check, and `bun --cwd x add evil@1.0.0` read as `bun x` passed the same way. The extractor knew the value options of four managers, so `cargo --config x install evil --version 1.0.0` passed unchecked and `pip --cache-dir x install evil==1.0.0` recorded the package `install`. The record walk took the first word that looked like a verb (`pnpm --dir x add` recorded `npm:add`). The landing read `--prefix`, `--cwd`, `--dir` and `--install-dir` wherever they stood. And the runner reader took the first word after `go run` for a module, so `go run ./cmd user@example.com` recorded `go:./cmd`. Each was a copy of a manager's grammar, and each was wrong somewhere.

Now one reader, the manager reader in `rust/src/manager.rs` (`safedeps_manager_read` in the Bash grammar it carried over), gives every word of a statement a role: the manager, a command word, an option, an option value, an operand, the package a runner runs, or the runner's program arguments. It reads each manager's tables there. They list the command paths (`uv pip install`, `yarn workspace <name> add`, `dotnet add <project> package`) and the options that take a value, by command and by class: a plain value, a directory, a version every operand is pinned to, a package (`npx --package`, `pip -e`), or a package added beside the one that runs (`uvx --with`). Each comes from that manager's help or source, named beside the table. After the command, an option the table does not list takes no value, so its value is read as an operand, which costs a check or a record and never skips a package. Before the command, the word after such an option is read both as its value and as what it is otherwise, and the gate judges both readings: `bun --zzz x add evil@1.0.0` is checked whether bun runs `x add` or installs evil. The extractor, the record, the landing of an install that is not npm's, and the runner reader all read the roles and nothing else. The recognizer regexes are now a filter that says whether a statement may be an install. Their option slot lets a value run over several words of the scan view, as a substitution does there, so the filter is wider than the installs the reader finds, never narrower.

npm's roles come from npm's own parser. npm reads its arguments with nopt and the option types in `@npmcli/config`, so the reader mirrors nopt with npm's table: value and Boolean types, `=` values, `--no-`, unique abbreviations and shorthand expansion. npx first runs a pass of its own, which takes the next word for any option it does not know as a switch, and then hands the result to npm. `scripts/measure/npm-option-reading.sh` builds the table from the npm on PATH and runs nopt itself on four thousand argument lists. The table is npm 11.19.0's, and npm 10.8.2, which GitHub CI and many machines run, does not define 26 of its options. To npm 10 the word after one of those is a command or an operand, not a value: `npm --min-release-age install evil@1.0.0` installs evil under npm 10. So a statement that names one of them is read a second time with npm 10.8.2's definitions, and the gate judges the union. Any other npm version is checked against the table, and the options it defines differently are named as that version's boundary.

The other managers' tables are held against the manager too, wherever it can be asked. A missing entry costs a check. An entry for an option the manager reads as a switch costs a package: the word after the option is taken for its value, and when that word is the package, nothing checks it. A draft of the bun table listed bun's runtime options (`--print`, `--eval`, `--preload`, `--port` and about thirty more from `bun --help`) for every bun command. bun reads them as switches where it installs, so `bun add --print evil@1.0.0` passed with no check and no record. `scripts/measure/manager-option-reading.sh` asks each manager on PATH but npm how it reads a form, and compares the reader's roles with the answer. It runs bun against synthetic local packages, with every registry setting on a closed port. It asks pip's own parser, runs python, and reads the help of uv, cargo and go. A form where the manager installs a word the reader takes for a value fails it. Two facts came out of it for bun 1.4.2. bun takes for its command the first word that does not start with `-`, so no option takes a value before the command (`bun --cwd x add y` runs `bun x add y`), and the reader reads such a word both ways. And `-c, --config` takes a value only after `=`. A command's own entry is looked up before `*`, and no option is listed for both, so a command's reading is never decided by a manager-wide entry. pnpm, yarn, pipx, poetry, pipenv, gem, bundle, dotnet and mvn are skipped by name where they are not installed, and their tables stay what their help and source say. Where two versions of a manager define an option differently, the statement is read both ways, as npm's is. poetry 1.8.5 reads `add --optional` as a switch, and poetry 2.x reads it as an option that takes the extra's name. So `poetry add --optional evil==1.0.0` adds evil under 1.8.5, and the gate checks it.

The per-word readers run in the core's own process, so none can fail the way a subprocess fails and read as "no spec". In the Bash guard `scripts/test/scan-contract.sh` checked that they started no process, and that check is retired with the processes. The grammar is held by spelling rather than by example. `scripts/test/manager-variants.sh` writes a value in each place it can stand -- a manager's option before its command, a command's option, a runner's option, a word after a runner's package -- spelled nine ways, and requires the verdict, the prescription and the record to be the same for every spelling. It also puts each of bun's runtime options right before the package in every bun install spelling, and checks the table itself: a command's entry is read first, and every scope is a command path the reader can reach. `scripts/measure/tuple-replay.sh` replays those three answers at two revisions and fails on any moved row that is not classified as a missing check or record, a false one, or a reasoned verdict move.

**A script handed to a shell is read as the word the shell passes.** The `sh -c` and `eval` readers used to take the payload as one quoted word, up to the first matching quote. A word that went on past that point -- an escaped quote inside it (`sh -c "echo \"hi\"; pip install ..."`), more quoting glued to it, an ANSI-C word, an unquoted word with escapes -- was read as far as it went, and the install the shell runs after that point passed with no verdict. A floor that marked every such word as a failed reading closed that, but made ordinary commands `UNDECIDED`: 24 of 30 measured, among them `bash -c "cd \"$dir\" && npm run build"`. The readers now take the script from a lexer view (`cscripts`) that cuts words where the shell cuts them and applies the shell's quote removal, and they read the scripts inside a script too. Each bypass form is judged as the install it runs, with the real prescription; the ordinary commands pass; a `sh -c` named inside quoted text is data. Only an ANSI-C escape the lexer cannot name is still a failed reading.

`scripts/test/consumer-forms.sh` holds the measurement. It pins the forms the gate catches, the forms it deliberately leaves unjudged, the ecosystem consequence of each miss, and a third set that matters as much: **decoys**. `sh -c "sh -c "…""` reads as double nesting but the outer quotes close at the inner ones and nothing is installed, and `xargs sh -c` without `-I` or `-0` hands the line to `sh` as `$0` rather than as a script. The battery proves each form's status by running it against a fake package manager, so a form counts as a gap only when it actually reaches one.

### Install-time flow

```
   intent ("I want to install this package")
      │
      ▼
   ┌─────────────┐     OSV.dev  ──canonical──►
   │ safedeps    │     CISA KEV ──hard-risk──►   advisory check
   │   check     │     GHSA     ──enrichment─►   (Phase 1)
   └──────┬──────┘
          │  approve
          ▼
   ┌──────────────────────┐
   │ approved-spec ledger │   ~/.safedeps/approved-specs/<hash>.json
   │ ecosystem · pkg@ver  │   + transitive_specs (npm closure)
   │ approved_at/expires  │
   └──────────────────────┘
          │
          ▼
   install command issued ──► PreToolUse hook (fast command guard, Phase 2)
                                  │  ledger match?  ── miss ──► BLOCK + "run safedeps check first"
                                  │  match ──► run
                                  ▼
                              install runs
                                  │
                                  ▼
                              PostToolUse hook (npm effect gate, Phase 3)
                                  │  lockfile closure vs ledger + OSV batch
                                  ├─ approved & clean ──► CONFIRM (new safe baseline)
                                  └─ unapproved / vulnerable ──► REORG (roll back to last confirmed)
```

- **Phase 1 — advisory check.** For npm, safedeps builds a script-free lockfile in a temp dir (`npm install <pkg>@<version> --package-lock-only --ignore-scripts`), extracts the full closure, and queries OSV `/v1/querybatch` for direct and transitive packages together. When clean, the direct ledger entry records `transitive_specs`.
- **Phase 2 — fast command gate.** The PreToolUse hook parses the command, blocks obvious unapproved installs, and snapshots dependency files. It is a best-effort advisory layer that gives the agent immediate feedback — not the final authority. On Claude Code it also rewrites an npm install to add `--ignore-scripts` (via the hook `updatedInput` capability), so the install runs inert and no lifecycle script executes until the effect gate has verified the closure.
- **Phase 3 — npm primary effect gate.** The PostToolUse hook compares the actual closure, read from `package-lock.json` and npm's hidden `node_modules/.package-lock.json`, against the ledger's direct entries and their `transitive_specs`, and re-queries OSV in batch. Any unapproved or vulnerable package triggers a reorg to the last confirmed snapshot. This authority is scoped to the npm closure.

## 2. Advisory sources — one canonical truth

```
TIER 1 — PRIMARY (canonical truth)
  OSV.dev
    • multi-ecosystem (npm, pip, cargo, go, gem, maven, nuget, …)
    • normalized package@version queries · free JSON API (Google)
    • aggregates GHSA, RustSec, GoVulnDB, and more
    → the first query target for every advisory

TIER 2 — OVERLAY (hard-risk signal)
  CISA KEV (Known Exploited Vulnerabilities)
    • only "confirmed exploited in the wild"
    • cross-referenced with OSV results; a KEV match is a hard block (no override)
    → the line between an ordinary CVE and an urgent one

TIER 3 — ENRICHMENT / CROSS-CHECK
  GitHub Advisory (GHSA) — developer-friendly patched-version metadata; surfaced when it disagrees with OSV
  NVD       — CVE source, CVSS scores, KEV flag (for score-based prioritization)
  deps.dev  — OSV-based package graph metadata (transitive risk)
  Snyk DB   — optional configured feed only (free-quota limited)
```

Design principle: **OSV is the one canonical truth.** Every other source is overlay or enrichment. Treating several live sources as co-equal truths invites cross-fire; instead OSV is the truth, and KEV/GHSA/NVD/deps.dev only surface signals that disagree with OSV or that OSV did not see.

## 3. Approved-spec ledger (SSoT)

`~/.safedeps/approved-specs/<hash>.json`:

```json
{
  "hash": "sha256:abc123…",
  "ecosystem": "npm",
  "package": "@jackwener/opencli",
  "version": "1.7.16",
  "version_range": "^1.7.16",
  "approved_at": "2026-05-18T13:00:00Z",
  "expires_at": "2026-06-18T13:00:00Z",
  "approved_by": "user@example.com",
  "evidence": {
    "closure_checked": true,
    "provider": { "type": "osv-querybatch", "results": [] },
    "closure": []
  },
  "transitive_specs": [
    { "ecosystem": "npm", "package": "…", "version": "…" }
  ],
  "project_context": null
}
```

Key fields:

- `hash` — a deterministic hash of `(ecosystem, package, version)`, folded together with `project_context.context_hash` when one is present. The hook derives the same hash from a command (plus the live project context, if any) and looks the ledger up by it.
- `approved_at` / `expires_at` — lifecycle TTL, 30 days by default. After expiry a new CVE may exist, so the spec is auto-revoked and re-check is forced.
- `evidence` — which source saw what, at approval time. An audit trail.
- `transitive_specs` — the full transitive closure the direct entry approved. The npm effect gate reorgs any `pkg@version` that appears in the lockfile but is in neither the direct entry nor this array.
- `project_context` — `null` for an ordinary published-package approval, or `{ type, context_hash, project_root, manifest_path, lockfile_path, input_sha256, input_files }` when the approval came from a Yarn project's resolved closure (see "Yarn project-scoped closure" in section 4). `context_hash` is a hash of the project directory, its root `resolutions`, its `yarn.lock` content, and its canonical input set. `type` is `yarn-project-lockfile` when the package was already in the project lockfile, or `yarn-project-materialized-lockfile` when the candidate was resolved in an isolated mirror; the materialized form additionally carries `materialization { candidate, input_sha256, generated_lockfile_sha256, command, isolation }`. `safedeps_ledger_validate_json` requires those fields and rejects an entry whose `materialization.input_sha256` disagrees with the context `input_sha256`. The CLI writes and validates the ledger in Bash (`lib/ledger/ledger.sh`), and a hook reads it with the core's reader (`valid` and `check` in `rust/src/ledger.rs`), which reads the same format and approves nothing.

`project_context.type` is also `npm-overrides-probe` when the published-package probe applied the consuming repo's npm `overrides`. That context carries `project_root`, `overrides_source` (the manifest path, or `env`), `overrides_sha256`, and the `overrides` themselves; `context_hash` is a hash of the project root and the canonical (key-sorted) override set, so two equivalent sets share one key. `safedeps_ledger_validate_json` requires those fields and rejects an entry with an empty override set. The rule behind it: a published-package approval may be global only because it is project-independent. Applying `overrides` makes the resolved closure a function of the consuming project, so that approval must be keyed like the Yarn project closure is — otherwise an approval earned in a repo that patched a transitive would satisfy the check in a repo that did not, whose real install resolves the vulnerable version. Repos with no `overrides` get no context and keep the ordinary global approval.

**Project-scoped isolation.** A `project_context` approval is keyed by `context_hash` in addition to `(ecosystem, package, version)`, so it lives at a different ledger path than a package-only approval of the same spec and cannot satisfy a lookup from a different project or from the same project after `resolutions`/`yarn.lock` changes (the hash changes with them). `safedeps_ledger_check` compares the caller's live context hash against the stored one and denies with `reason: "context_mismatch"` on any difference — an approval never silently leaks across project boundaries.

Lifecycle:

```
approve            install            confirm              re-check (daily)
───────            ───────            ───────              ────────────────
ledger entry  ──►  hook passes   ──►  post-verify match  ──►  OSV re-query
approved_at=now    spec matches       confirmed = true          │
expires_at=+30d                                                 ▼
                                                    still clean ──► extend expiry
                                                    new CVE     ──► revoke + warn (+ optional reorg)
```

## 4. Runtime flow in detail

### Phase 1 — `safedeps check <ecosystem> <pkg>@<range>`

```
safedeps check npm "@jackwener/opencli@^1.7.0"
        │
        ├─► ledger lookup ── hit (valid) ──► "already safe, install is fine"
        │                  └ miss/expired ──► proceed to check
        ▼
   resolve range → concrete version(s)
        │
        ▼
   OSV query  ──►  KEV overlay  ──►  GHSA cross-check
        │
        ▼
   classify:
     • clean              → approve
     • patched available  → approve, rewrite spec to the fixed version (^1.7.0 → ^1.7.16)
     • KEV hit            → HARD BLOCK ("exploited in the wild; do not install")
     • CVE, no patch      → WARN (user decision required)
        │
        ▼
   write a new approved-spec ledger entry
```

For npm, "OSV query" runs over the **whole resolved closure** in one `/v1/querybatch` call, and the approved entry records every transitive package in `transitive_specs`.

**Yarn project-scoped closure.** Before falling back to a fresh published-package probe, `safedeps_npm_yarn_project_closure` (in `lib/npm/closure.sh`) looks for a canonical Yarn project context:

```
resolve project context (walk up from cwd, stop at .git boundary):
        │
        ├─► package.json has non-empty root `resolutions` + a yarn.lock next to it
        │        │
        │        ├─► yarn.lock has no `__metadata:` marker ──► INVALID CONTEXT (fail-closed)
        │        └─► valid Berry lockfile
        │                 │
        │                 ▼
        │        context_hash = sha256(project_root, sha256(resolutions), sha256(yarn.lock))
        │                 │
        │                 ▼
        │        `yarn info -A -R --json` → full project locator graph
        │                 │
        │                 ▼
        │        traverse from the requested `pkg@npm:version` locator
        │                 │
        │                 ├─► locator found  ──► resolved project closure (approvable)
        │                 └─► locator absent  ──► materialize the candidate (see below)
        │                                          ├─► materialized ──► generated closure (approvable)
        │                                          └─► failed ──────► project-candidate-materialization-unavailable
        │                                                              (deny; the published closure is not used)
        │
        └─► no resolutions / no yarn.lock in this Git worktree ──► ordinary npm package-only check
```

Yarn owns descriptor-to-locator resolution; safedeps consumes `yarn info`'s machine-readable graph rather than re-implementing lockfile resolution. When the context resolves, the approved-spec ledger entry carries `project_context` (section 3) so the approval is scoped to that exact project and cannot leak to a different one or survive a `resolutions`/`yarn.lock` change.

**Yarn candidate materialization.** A locator is absent from `yarn.lock` precisely when the package has not been added yet, which is the normal pre-install check. `safedeps_npm_yarn_materialize_candidate_closure` resolves that candidate in an isolated mirror rather than denying it or falling back to the published closure:

```
locator absent from the project lockfile
        │
        ▼
   mktemp private mirror ◄── copy canonical inputs ONLY:
        │                     root + workspace package.json, yarn.lock, .yarnrc.yml,
        │                     .yarn/{releases,plugins,patches}
        │                     (never node_modules, caches, unplugged, install state, VCS)
        ▼
   re-hash inputs in the mirror; must equal the caller's input_sha256
        │
        ▼
   add the candidate to the MIRROR manifest only
        │
        ▼
   `yarn install --mode=update-lockfile --no-immutable` (no link step, no lifecycle scripts)
        │
        ▼
   re-hash the caller's inputs again ── changed? ──► INVALIDATE (concurrent project edit)
        │
        ▼
   `yarn info -A -R --json` over the GENERATED lockfile → candidate closure
        │
        ▼
   project_context.type = "yarn-project-materialized-lockfile"
   + materialization { candidate, input_sha256, generated_lockfile_sha256, command, isolation }
```

The caller's tree is read-only for the whole operation; only the mirror is mutated. The input recheck before and after Yarn closes the read/copy race, so a manifest or lockfile edit that lands mid-flight invalidates the candidate instead of yielding an approval for a mixed project state. Approval truth is neither a registry probe nor the caller's stale lockfile — it is the Yarn resolution derived from a hash-bound copy of the caller's own inputs, and both the input hash and the generated lockfile hash are recorded as ledger evidence. Every failure path (input copy, context drift, Yarn invocation, unresolvable candidate) returns `project-candidate-materialization-unavailable` and denies. There is no published-closure fallback.

### Phase 2 — fast command guard (PreToolUse / `safedeps-core pre`)

```
Claude runs: npm install @jackwener/opencli@^1.7.16
        │
        ▼
   parse command → ecosystem, package, version_range
   compute spec hash → ledger lookup
        │
        ├─ hit (approved, not expired) ──► PASS (run the command)
        └─ miss / expired ──────────────► BLOCK + "run `safedeps check …` first, then retry"
```

The guard also snapshots lockfiles/manifests and keeps the v1 hardcoded pattern blocks (see section 5). It is fast and advisory; the authority is the post-install gate. In this document the pre-guard is `safedeps-core pre` and the post hook is `safedeps-core post`; the advisory and deny lines the core prints still say `pre-guard` and `post-verify`.

**The guard keeps a budget of its own.** The runtime gives this hook a fixed budget (the installer registers it) and kills it when that expires, after which the tool call proceeds — measured on Claude Code, 2026-08-04. The Bash guard's command scan was superlinear in command length, so that budget was reachable by padding: measured then, 28KB of command text took 29s and 32KB took 38s. The scan was linear from v2.18.0 and the whole judgment on macOS from v2.18.1. The core is a different program, and no battery measures how its cost grows with the command (`scripts/test/self-budget.sh` holds a 64KB install inside the default budget), so a command large enough to reach the budget is still assumed to exist. Past that line the gate used to disappear without saying anything, which for `pip`/`cargo`/`go`/`gem` — where this gate is the authority, not an advisory layer — is a bypass that needs no knowledge of the scanner at all.

The runtime's timeout behavior is not safedeps' to change; answering before it fires is. The guard runs its judgment in a child process of its own (`safedeps-core pre --budget-child`, in a process group of its own, `rust/src/pre/budget.rs`) under `SAFEDEPS_SELF_BUDGET_SECONDS` (default 20), and if that child has not answered by the deadline the guard answers for it: deny, because an install it could not judge must not run. Two properties that deny must keep — it is fail-closed but **not a finding** (the reason leads with `UNDECIDED, not unsafe` and says nothing was detected, because a reader who confuses "did not finish" with "found something" learns to route around the gate), and it is recorded to `advisory.log` like every other bypass or unavailability.

**That budget can be lowered, not raised.** `SAFEDEPS_SELF_BUDGET_SECONDS` is clamped to a ceiling of 25s; lowering it stays free, because a shorter budget only denies earlier. A budget at or above the runtime's is not a budget at all — the runtime kills the hook first and the tool call proceeds, which is the exact fail-open this machinery exists to remove. The motive to raise it is an ordinary one: someone who hits `UNDECIDED` on a large command reads it as "the budget is short" and turns off a security boundary without ever meaning to. A boundary the user can move is a default, not a boundary. The clamp is announced wherever the budget is in play — stderr, `advisory.log`, and the deny reason — because a silently reduced budget leaves the user debugging against a number that was never true.

The value is normalized before anything compares it, and only the normalized digits reach arithmetic. That ordering was load-bearing in the Bash guard: bash arithmetic accepts a wider grammar than a `^[0-9]+$` check, so validating with the regex while the deadline consumed the raw string let `+40`, ` 40` and `0x28` skip the clamp and then evaluate to 40 anyway — the fail-open, restored by a space. The core keeps the rule the guard had, so a value means the same in both (`normalize_knob` in `rust/src/pre.rs`). Surrounding whitespace and a leading `+` are read the way whoever typed them meant; anything else is not a budget and falls back to the default, which is inside the ceiling and is announced on the same channels as the clamp.

Length is checked before magnitude, and in the string domain. Bash integers are 64-bit and wrap silently, so in the Bash guard a value that wrapped negative was not greater than the ceiling, passed the clamp untouched, and multiplying it into milliseconds wrapped it again into a deadline that never arrived — measured, a 30-digit budget produced no answer for over 600s. Which way a value wraps depends on the value, so nothing about the wrap can be relied on. The core parses the digits into an unsigned integer and keeps the rule: a run of digits longer than nine (`KNOB_MAX_DIGITS`) is clamped on its digit count, before arithmetic sees it, and a value longer than 32 characters (`KNOB_MAX_INPUT_CHARS`) is not a budget. Nine digits is about 31 years of seconds, far past any real budget.

**Where the 30s comes from, and what would make it stale.** The hook payload does not carry the runtime's budget, and hook registrations from several settings files all fire, so the guard cannot tell at runtime which registration launched it. What it can do is name the number safedeps itself registers: `PRE_HOOK_TIMEOUT_SECONDS` in `scripts/install/install-safedeps-hooks.mjs`, 30s, matching the measured kill time. The core holds the same number (`RUNTIME_BUDGET_SECONDS` in `rust/src/pre.rs`, printed by `safedeps-core budget-config`), and the smoke test pins the two together, so an installer change cannot leave the guard computing its ceiling against a stale number. The 5s between the ceiling and that budget is the margin for what the guard spends outside the budget window. In the Bash guard that was up to one poll step past the deadline, the TERM grace and the start of a few processes, a 1.6s structural worst case against 0.73 to 1.05s measured end to end (2026-08-04). The core's supervisor polls every 20 ms, sends TERM to the process group, waits 50 ms and then kills it, and no code bounds how late it runs when it is not scheduled (see the clock paragraph below). Measured on the M1 host on 2026-10-07 (load 7.52 at the start of the run and 6.79 at the end, niceness 15, not a quiet host), three runs of an over-large budget answered at 25.083, 25.094 and 25.091 seconds, before the runtime's 30. Linux and WSL1 were not measured. A user who hand-edits the registered timeout below 30s is outside what this constant can know.

**The deadline reads the clock.** It used to add up the sleep time its polls asked for. On a loaded machine a sleep takes longer than it asks for, so the real wait ran past the budget by whatever load added to every poll. Past the runtime's budget the hook is killed and the install runs unjudged. The Bash guard then read bash's `SECONDS`, which exists in bash 3.2 (the shell macOS runs hooks under) and costs no process to read, and compared its distance from the starting value, because bash seeds `SECONDS` from the environment and an exported `SECONDS` would otherwise have been one more off switch. The core compares a monotonic `Instant` with the deadline each time the supervisor runs (`rust/src/pre/budget.rs`), so time already elapsed is never waited for again and a sum of requested sleeps cannot mislead it. It asks for a 20 ms sleep between looks. That says how often it checks the deadline while it is running, not how late an answer can be: while the supervisor gets no chance to run, the answer is late too, and the code states no bound on that. After the deadline it still sends TERM to the process group and waits 50 ms before it kills it. What absorbs that lateness is the 5 seconds between the ceiling of 25 and the runtime's 30. A stall longer than that margin lets the runtime kill the hook, and the tool call then proceeds with no judgment, which is the fail-open this budget exists to avoid. That boundary is part of the contract, and the budget does not remove it. One observation: on the M1 host on 2026-10-07, a row that stopped the supervisor for the budget plus 0.5 seconds (`scripts/test/lib/native-budget-run.py`) got `UNDECIDED` after 4,896 ms against a 4 s budget, and answered 71 ms after the supervisor was resumed. It is one observation, not a bound. The deadline counts from the process's own start, because the runtime's timer starts with the hook, not with the judgment. There are three outcomes and the wording says which one happened: an answer; the deadline passed ("could not finish judging this command within its Ns budget"); or the judgment process ended before its deadline without an answer ("the judgment process ended without a usable answer (signal N)", with no budget wording, because the budget did not run out). Both non-answers are `UNDECIDED` denies and say they are not a finding. A stopped judgment process is not an exited one: the supervisor waits to its deadline, because macOS reports a stopped child to `waitid` even with `WEXITED` alone and the core reads `si_code`. A supervisor that read `si_signo` took the stop for an exit and answered `UNDECIDED` at about 0.3 seconds whatever the budget (found on 2026-10-07 by a probe outside the core). Measured on the same M1 run, budgets of 2 and 6 seconds answered at 2.084 and 6.077 seconds, and a judgment killed before its deadline answered in 345 milliseconds. Regression: the loaded-machine rows in `scripts/test/self-budget.sh`, which delay the real npm asks with a fixture npm and stop the judgment process, and which check that an exported `SECONDS` moves nothing.

The deadline is enforced against the judgment process's whole group, not just its leader. A process the judgment started, an npm ask among them, must not outlive the answer. The supervisor does not reap the leader before the last signal to the group is sent, so the pid cannot be reused while it signals. It sends TERM, waits 50 ms and sends KILL (`reap_group`, `rust/src/pre/budget.rs`). The Bash guard enforced the same against the child's whole process tree for a reason of its own: a shell does not act on a signal while a foreground external command is running, and the expensive part of the judgment is exactly such a command, so signalling the shell alone landed whenever that command happened to finish, measured 9.1s late against a 20s budget. It resolved descendants from the child's own pid, never by name pattern, and trapped only `EXIT` and never `TERM`, because naming a signal in `trap` replaces its default disposition and a child that traps TERM survives its own deadline.

Only commands at least `SAFEDEPS_BUDGET_ENGAGE_BYTES` long (default 1KB) pay for the extra process; below that the judgment finished about 300x inside the budget in the Bash guard, so the machinery would be pure overhead on every Bash call. That engage size is a performance gate, not a security boundary — the security boundary is the wall-clock budget, which stays honest on machines faster or slower than the one these numbers were measured on.

**But a performance gate that can be raised without limit is an off switch.** The engage size is the only condition on the whole deadline, so raising it past the commands that matter removes the deadline for all of them — measured on the Bash guard, a 32KB padded `pip install` answered in 21s at the default engage size and took 198s with it raised, against a runtime that kills the hook at its budget either way. It is therefore clamped to 4KB, where a command just under the line was judged in about 0.68s by the Bash guard, some 44x inside the runtime budget. Tuning between the 1KB default and that ceiling is what the knob is for and stays available; the clamp announces itself on the same three channels as the budget's.

The marker that tells the spawned child it is the child travels in argv, not in the environment. As an environment variable it was a second off switch with no name on it: exporting it made the parent believe it was already the child and skip the deadline, measured at 32s on an input that answers in 3s, with nothing on stderr and nothing in `advisory.log`. The engines invoke the hook through the shim, which hands the core the subcommand and nothing else, and a hook started with any other argument is denied, so argv is a channel the environment cannot reach and only the parent's own spawn (`pre --budget-child`) carries the marker. The old variable is still noticed and reported as ignored, because a signal that used to switch the deadline off should not become quietly inert either.

Turning the deadline off is a separate act with a separate name: `SAFEDEPS_BUDGET_DISABLED`. The battery needs it — a test that only knows it passes, and not that it catches the defect, is not evidence, so the mutation check has to be able to produce the unbounded case. Routing that through the engage size made tuning and disabling the same gesture, which is exactly how a friction adjustment silences a boundary without anyone deciding to. The off switch does nothing else, says what it does in its name, and logs every time it takes effect. Regression: `scripts/test/self-budget.sh`.

**The record cannot be moved out from under the check.** `advisory.log` is where every bypass and unavailability is written, and `re-check` also reads it as the oracle for whether a ledger approval ever happened. While its path came from `SAFEDEPS_ADVISORY_LOG`, the same environment that writes a forged ledger entry could hand that oracle its own evidence — measured, an entry `re-check` flags as `suspected_forgery` stopped being flagged when the variable pointed at a caller-written file saying the approval had happened. The path is derived from `SAFEDEPS_HOME` now, so the record and the ledger it vouches for move together or not at all, and a set-but-ignored variable says so on stderr and in the log.

**A run judged against a moved source says so — on every path, and the list is not a completeness claim.** Pointing `SAFEDEPS_OSV_API_URL` (or the KEV/GHSA URLs, the closure fixtures, or a non-default ledger TTL) somewhere else is a real need — a mirror on a network that blocks osv.dev, a fixture in the test suite — so none of it is refused. What would be wrong is a run that answered from a moved truth looking exactly like a run that answered from OSV. Each deviation is recorded once per run, named, in `advisory.log`. The notice is compiled into the core (`truth_sources_moved` in `rust/src/state.rs`), so the hook says it on every Bash call with nothing to source, and the CLI keeps its own copy in `lib/truth-sources.sh`. Defaults and the comparison live together in each, so a run is measured against the value it was assigned. The two copies of the list are held equal by the rust-core unit `state::truth_sources_match_cli`, which compares the environment names each copy reads and the notice each says for the same environment. The CLI's cheaper prefilter also watches the retired `SAFEDEPS_ADVISORY_LOG` override, which the core does not. The set of knobs listed is what has been found: two of them were found by a validator after the enumeration that preceded them called itself complete, so it is written as a growing list.

For an npm-ecosystem command, the guard resolves the same Yarn project context described above (`SAFEDEPS_NPM_PROJECT_DIR` pinned to the project directory) and folds its `context_hash` into the ledger lookup, so a project-scoped approval only passes the guard inside its own project. An invalid context (resolutions present, lockfile unusable) denies the command outright rather than falling back to a package-only lookup.

### Phase 3 — npm primary effect gate + reorg (PostToolUse / `safedeps-core post`)

```
install done → safedeps-core post
        │
        ▼
   read the actual closure: package-lock.json + node_modules/.package-lock.json
   check every pkg@version against the ledger (direct entries + transitive_specs)
   re-query OSV in batch for the whole closure
   inspect what the install brought into either record, against the records
     from before it: install scripts, resolved sources (v1 reorg-guard logic)
   record, by integrity, the bytes it brought in that npm did not say came
     from the public registry (machine-wide, before any rollback)
   inspect native binaries
        │
        ├─ all approved, clean, no suspicion ──► CONFIRM (new safe baseline)
        └─ unapproved / vulnerable / suspicious ──► REORG:
                 • restore lockfile from the last confirmed snapshot, or from
                   just before the command when there is none (and say so)
                 • remove the project's own node_modules (a real directory,
                   and only when the command wrote the project's node tree);
                   no package manager runs -- the next install reinstalls,
                   through the gate (a symbolic link is refused and named)
                 • append to reorg.log; message the agent
```

**The baseline is the state the last verified install left behind, as the checks read it.** Before the checks read the project, post-verify copies its lock and manifest files into a new snapshot (`verified-<id>`, whose `verified_from` names the pre-install snapshot). On CONFIRM it compares the project with that copy. Only if every file still holds the same bytes does it write the snapshot's `meta.json` and point `confirmed_${dir_hash}` at it. It used to confirm the pre-install snapshot instead, so the baseline ran one install behind. Measured with a real npm against a local registry, on Claude Code and Codex: an approved `npm install a` followed by an unapproved `npm install b` rolled back to a project without `a` in `package.json`, `package-lock.json` or `node_modules`, and after a second approved install the one lost was the last verified, not the first. `scripts/test/lockless-forms.sh` pins both, and it no longer needs the extra verified `npm install` it used to move the baseline forward.

The copy comes before the checks because a copy taken after them recorded whatever the project held by then. Measured with the same battery and a pinned schedule: a second Bash call's unapproved install finished between the closure check and the copy, and went into the baseline. Its own rollback could not remove it, and the rollback's `npm ci` ran its install scripts. The battery pins that schedule on Claude Code, where `npm rebuild` sits between the checks and the record. Codex has no rebuild there, so its window is shorter but has the same shape, and the same code closes it (not measured). The comparison is what ties the copy to the checks. Without it, a file that changed between the copy and the closure check would be recorded although the check read something else; with the copy alone, the pinned schedule above already stays out of the baseline, so the battery pins the comparison by the message it produces. What is compared is equal bytes before and after the checks. A change undone to the same bytes in between is not seen, but the bytes recorded are still the ones the project held at both ends.

Three boundaries follow from what the baseline is:

- **It is files, not `node_modules`.** The rollback removes `node_modules`, and the next install builds it again from the restored files. So a verified install that saved nothing (`--no-save`) is not in the baseline, and its packages leave with `node_modules` at a later rollback.
- **Only an install that passed the whole gate moves it.** The command-independent backstop runs the npm closure check alone, so a parser-missed install it finds clean is logged and left in place, but it is not confirmed. A later rollback returns to the baseline before it.
- **A baseline that cannot be recorded does not move.** That covers a copy that fails, a `meta.json` that cannot be written, and files that changed while the checks ran. In each case the pointer stays where it was, `advisory.log` says why, and the user is told that a later rollback would undo this install too. The new snapshot's `meta.json` is written last, through a rename, and every reader requires it, so a run killed part-way never leaves a baseline with files missing. It does leave the copied files behind, and they are not pruned: pruning lists `*_meta.json`, and a snapshot without one is also what a run in progress holds while its checks run. Nothing on disk tells the two apart, and pruning one in progress would let its `meta.json` land over missing files. So a killed run costs a few small files of disk, never a wrong baseline. A pre-install snapshot killed before its `meta.json` is left the same way.

**This gate has the same budget, and it is killed the same way — measured, not assumed.** Using the protocol that established the PreToolUse behavior (a sandbox project, a hook that records when it starts and when it finishes, a control inside the budget and an experiment past it), a PostToolUse hook given 20s of work against a 5s budget started and never finished, while the 1s control finished. The work above is bounded by the user's project and the network rather than by anything safedeps controls: `npm ci`, `npm install`, `npm rebuild`, and an OSV batch over the whole closure.

So the sentence "the effect gate backs up the command gate" holds *inside* the budget and not past it, and it fails worse in kind: a killed pre-hook lets one unjudged command through, while a killed post-hook can land in the middle of a rollback. The pre-hook's answer to running out of time is to deny (Phase 2), but a post-install gate cannot deny — the command has already run — so its answer is a different design question, tracked as `safedeps/effect-gate-killed-mid-rollback` and not solved here. Codex CLI timeout behavior remains unmeasured on both hooks; parity is not assumed.

### Phase 0 — the installed command is an entry shim (`safedeps-hook-entry.sh`)

Both engines register one command per hook event: `…/skills/safedeps/scripts/safedeps-hook-entry.sh pre|post`. That path resolves through the `~/.claude`/`~/.codex` skill symlink into the live repo checkout, on every Bash tool call. The working tree *is* the runtime. A checkout that is mid-merge, mid-edit, or mid-update therefore changes hook behavior instantly — and before the shim existed, what happened next was decided by accidental exit codes. A bash syntax error (merge conflict markers) exits 2, which both engines treat as a blocking deny, so every session on the machine lost Bash with only a raw parser message as explanation (this happened on 2026-08-04). A missing file exits 127 and a runtime crash exits 1 — both are *non-blocking* hook failures, so those breakage shapes silently removed the install gate entirely.

The shim makes both outcomes designed. The core exits 0 on every intended path (decisions travel as JSON), so any other exit means the hook is unwell. The shim then classifies the breakage (no binary at all, none for this platform, a missing or unrunnable one at exit 126 or 127, an abort, which is a panic in the core, a signal, or another non-zero exit) and exits 2 with a message that names the machine-wide breadth, the cause, and the recovery path. Nothing runs in the binary's place. Fail-closed stays fail-closed; it stops being anonymous, and the fail-open shapes stop being silent.

The shim also answers for its own stops. bash ends a script at the first process it cannot start -- bash 3.2 at once with exit 128, bash 5 after about 15 seconds of retries with exit 254 -- and both engines read either as a non-blocking failure, so on a machine out of processes the tool call ran with no gate. The same condition once produced a wrong diagnosis: a failed fork inside `dirname` left the shim resolving its own location to `/`, and it reported the hook as missing from a checkout there. The shim now finds its location by parameter expansion, writes its messages with builtins, and sets an EXIT trap that turns any stop it did not choose into an explained exit 2. Measured on bash 3.2 and bash 5.2: exit 128 and 254 before, a deny that names the failed fork after. `scripts/test/hook-entry.sh` reproduces the condition with a process limit of 1; root is exempt from that limit, so there the row reports itself skipped.

Measured cost, with the Bash guard behind it: ~7 ms per Bash call on top of a ~34 ms guard baseline. The shim's cost with the core behind it is not recorded here. Residual windows, kept honest: if the shim itself is broken, behavior degrades to the pre-shim status quo (blocking with a raw parse error — never wider), and the shim is a small, rarely edited file, unlike the actively developed guard; if the shim file is missing during a checkout transition (milliseconds), that call is a silent non-blocking failure, same as the pre-shim behavior for any missing hook. The regression battery for all of this is `scripts/test/hook-entry.sh`.

```
ADVISORY CHECK (safedeps check)
  • known-CVE matching (OSV, multi-ecosystem)
  • KEV match → hard block (no user override)
  • patched-available → auto-rewrite the spec to the fixed version
  • transitive vulns recorded in the ledger, so sub-dependency compromise is detectable

FAST COMMAND GUARD (safedeps-core pre)
  v1 hardcoded patterns (defense-in-depth): typosquat list · curl|bash pipes ·
  non-standard registry (--registry, or npm's own answer) · install-script-safety disabling · eval/subshell indirection
  + fast advisory ledger check: missing/expired spec → block with advisory-gate guidance

npm PRIMARY EFFECT GATE + REORG (safedeps-core post)
  • install-script network / code-execution / sensitive-path access
```

**Install-script timing.** A package's `postinstall` script runs *during* `npm install`. On Claude Code, the Phase 2 hook injects `--ignore-scripts`, so that the install is inert and scripts run only after the effect gate confirms the closure (via `npm rebuild`), and a rejected package's scripts do not run. That is what the rewrite is for, not what safedeps can promise: whether npm keeps the flag is decided by shell state the command does not show (see the boundary below), so the records say that safedeps added the flag, never that no script ran. The flag goes where npm reads it as true, and that is checked rather than assumed. npm keeps the last value an option is given, so a flag placed right after the verb lost to a later `--ignore-scripts=false`, to an abbreviation npm expands (`--no-ignore`, `--ign=false`), and to a word the shell expands at run time. The first place tried is therefore after the last argument of each npm install, before a `--`, a redirection, a comment or the end of the statement. That place failed too: an install whose last word takes the next word as its value (`--cache`, `-C`, `--reg`, `--fetch-retries`) took the flag as that value and ran its scripts with nothing recorded (npm 11.19.0). So each place is read back with the flag in it (the manager reader, `npm_read_args` in `rust/src/manager.rs`, both npm versions), and it stands only where ignore-scripts comes out true and the positional words, option values and other switches read as before. The reader takes each install from the lexer's structure of the text it stands in (`rust/src/inert/read.rs`), never from the bytes of a view. The Bash rewrite searched for the verb and for the statement's end in the bytes, counted depth and backticks again, and patched what that missed, and each of its rejected defects was that search reading a nested text with the outer level's quoting. Text nested in another is a payload and is read by asking the same question of the payload. A place in a payload is a place in the command only through the payload's source map, and only once it reads back: the text the payload came from, with the flag there, is lexed again, and the same payload must come out with the flag at its place. Places are tried from the last argument back to the verb, so `x --cache` gets the flag before `--cache`. The rewrite also always holds 7d66f8c's, the rewrite safedeps made before it read an install's words: a flag right after every verb, and, for a command 7d66f8c appended to (one statement with no `;&|()$`, comment or heredoc: `inert_release_appends`), its flag at the end. That is the floor, and its positions are kept in `rust/src/inert/floor.rs` as that rewrite's own search found them. They say where a flag goes and nothing else. 7d66f8c is a tree of this release cycle, not the published v2.17.2 (bb0787d). **Where the floor cannot be had together with the command's data and with npm reading the flag as the option, the whole command is `UNDECIDED` and no rewrite is sent.** The Bash guard sent the floor anyway. It wrote a flag into a heredoc body that another command reads as data, gave `npm install x --cache` a flag that `--cache` took as its value, kept the verb flag on `npm install true`, and recorded `npm -- ci -- x` as a downgrade. The core names the reason in `advisory.log`: `floor-outside-command`, `floor-not-an-option`, `floor-value-unread`, `end-flag-outside-command`, `end-flag-not-an-option` or `end-flag-value-unread`. The reason the user reads says that required `--ignore-scripts` flags could not be placed while preserving command data and how npm reads its options. The cost is plain: those commands are denied, and the user rewrites them. A collision is settled before the readings are compared and before any state is written, so a denied command leaves none. Bash, zsh and dash read each statement from their own lexing, and where they end a statement or a word apart their places differ; the command is then `UNDECIDED` too, because no single edit is inert for every shell. The rows where the core answers apart from the Bash guard on purpose are `scripts/measure/core-intended-battery-rows.tsv` and `core-intended-readings.tsv`; no row there is a weaker verdict, which is a statement about those rows and not about the core, because the owner decided on 2026-10-07 that the guards are not compared on a corpus. A script the Bash rewrite could not read as the shell will is a payload the core reads. A script handed to `sh -c`, `bash -c`, `zsh -c`, `dash -c`, another shell (`ksh -c`) or `eval`, with a backslash, a backquote or `$(` in it or not, is read at its own top level through the quoting the lexer removed (`script-payload-read` in `scripts/measure/core-intended-inert.tsv`). The Bash rewrite put the flag where v2.17.2 did in such text, right after each verb that a blank follows or that ends its line, and recorded the command as one whose flag nobody read; v2.18.0 gave such a command no `--ignore-scripts` at all, its readable installs included. The core places the flag where it reads npm keeping it true, and it still records the command as one whose flag nobody read (`ignore_scripts_unread: true`), because the record reads the bytes and not the structure. `unread_case_native` in `scripts/test/smoke.sh` holds 13 commands to their measured rewrites. A heredoc body piped to another command is not read as a payload. It keeps v2.17.2's flag after each verb that a blank follows or that ends its line, and a verb no blank follows gets none: `sh <<E | tee log` with `npm ci&&true` in the body gets none, while the same install in a `sh -c` script is read and flagged. Beside an install that already carries the flag, that command gets no rewrite and is a recorded downgrade. `scripts/measure/inert-downgrade-grid.sh`, which judged two trees on the same forms, is retired with the Bash rewrite it compared. The record of an install the rewrite did not read is an allow-list over the command's bytes, with two inputs: the bytes, and the verbs the rewrite read. A verb counts as read only where its `npm` is the command word of the text it was read in, the command or a script the rewrite read: at the start, after a separator, a `(`, a backquote or a reserved word a command follows (`then`, `do`, `!`), once the prefixes the recognizers strip (assignments, redirections, `env` and its options, `command`, `exec`) are set aside, or as the last part of a path there (`./node_modules/.bin/npm`). That position is read on the lexer's `cmdword` view, which blanks in place the prefixes the walk set aside at each start, so an offset in it is an offset in the command. A verb glued to a `}` nested in a substitution, which the rewrite cannot reach, is not read either, so the record sees it beside the floor it keeps. A verb in the first quoted segment of a glued script word, or one that got its flag where v2.17.2 put it, is not read. Every read `npm` is then set aside, the command's own comments (class `m`) are blanked, and the text is read with every quote and backslash taken out, and again through the shell's own quote removal, one level at a time for up to three levels, as a script handed on reads what the level above it left. Each `$'...'` is decoded where it stands at the level that reads it, so a decoded byte joins the text beside it (`n$'\x70'm`), a decoded newline starts a line (`true$'\n'npm ci`), and an ANSI-C string inside a single-quoted here-string is decoded by the shell it is handed to. If an npm install verb is left anywhere in any of these, ending at a byte that is not a letter, a digit, `_` or `-`, the command is recorded (`inert_bytes_left_unread`). The verb is the recognizers' own: `npm`, their option grammar (`SAFEDEPS_G_O`, where a value can be empty or several words, as npm reads `--heading=` and `--heading 'a b'`), then a verb. Nothing has to stand in front of `npm`, because a program that takes its command glued to an option reads it there (`env -S'npm ci x'`, `env -Snpm\ ci\ x`). An `npm` the rewrite did not read inside a word the shell computes (`$(...)`, `${...}`, `<(...)`, `>(...)`, backquotes) records the command as well, install verb or not: bash's `hash -p "$(command -v npm)" n && n ci x` runs npm from a statement no byte of which names it. A word the shell computes where npm or its command can stand records the command too (`inert_dynamic_command_word`): the command word of any statement, in the command or a script or substitution it hands on, each lexed as written and read on the `noprefix` view (the noredir view with those prefixes blanked in place), or in a text the quote removal above produced, with every `<` read as a newline so a here-string or a heredoc body handed to a shell starts statements of its own (`$(echo npm) ci`, `{npm,ci,x}`, `bash <<< 'npm $V x'`), and, in a statement whose command word is npm, the word npm reads as its command, which is the first word after `npm` unless an option comes first and any later word if one does (`npm $V x`, `npm "$@"`, `npm c? x`). Whether a word is computed is `shell_expands`' allow-list, read per word (below); the clause used to look for `$` and a backquote, a list of what expands, and braces, globs and the tilde passed it. Reserved words (`{`, `}`, `!`, `[[`) and a lone `[` are read as written, and a case pattern is not a command word. The quote-removed texts are the one text a reader lexes that is neither the command nor a payload, against the rule that a reader never lexes a view's output: they are read only after the command and every payload found no computed word, so a finding there can only add a record. A lexing of them that fails is a failed reading, and the gate denies the command as `UNDECIDED`, so the exception adds a record or a deny and never takes one away. Either way the command is recorded as one whose flag nobody read where another install in it got a flag, and as a downgrade where none did, beside an install that already carries the flag too. The record used to list the ways text reaches a shell: a script word, then any unread text that names `npm`, then the install verbs the recognizers still found once the read ones were set aside. Three rounds of review each found a way past the list, the third many: shell options before or after `-c`, here-strings, process substitution, a script written to a file and run, builtins that run their arguments, and a quoted or escaped command word. `scripts/measure/inert-record-gen.py` generates such forms from the shells' own option, builtin and reserved-word tables and from the redirection and expansion sections of bash(1) and zsh(1), and 5b5a775 let 806 of its 1,856 forms make an unflagged npm call with no record. Those forms held the npm statement at `npm ci x`, and a fourth review found the definition of a read verb narrower than npm's and the shell's reading twice: an option value that is empty or two words, and a byte glued in front of `npm`, hid the verb, and words the shell computes outside the command word were not looked at. So the generator also varies the npm statement's own words (G5: option shapes, a computed verb, bytes in front of `npm`). A list of ways is a deny-list, like the list of expansions `shell_expands` replaced, so the record now passes only what the rewrite read. A defect left to find is in the definition of a read verb, not a missing way; fix that definition rather than adding a kind of text. The cost is noise: install text that is data next to an install, in an `echo`, a commit message or a heredoc written to a file, is recorded too (22 of the 25 forms of `scripts/measure/inert-record-data.jsonl`), and a comment is not. The boundary is text another program computes at run time, an alias, and the recognizers. Text another program builds while the command runs (`printf '\156pm ci' | sh`, `base64 -d | sh`, `rev | sh`) has no byte that spells the install, so it is the effect gate's to check; a name an alias binds to npm runs it from a statement that does not name it, and bash runs aliases in a script only after `shopt -s expand_aliases`; and a command the recognizers do not call an npm install is neither rewritten nor recorded. `scripts/measure/inert-record-invariant.sh` checked the rule as a property of the output: each form of its sets went through one tree's pre hook, the command that would run went through bash and zsh with a stub npm, and a form that made an npm call without the flag had to have an inert record in `advisory.log`, with `vac` rows and a reach table so that no row passed because it never reached its npm. It is retired with the Bash rewrite (`scripts/measure/native-measure-disposition.json`), its corpora remain as inputs, and their historical counts are not native coverage. A statement where no place passes keeps only the floor and is a recorded downgrade, unless the floor collides, which is the deny above. It used to lose its rewrite, which gave it less than 7d66f8c. Where no rewrite is sent, the command is denied (a collision), or every install it holds already leaves the option true, or it is a recorded downgrade, and the one other case is a pre hook that cannot write its record (a disk failure, logged in `advisory.log`), which sends none because a version 2 record that says safedeps did not rewrite would then make the post hook say "did not add" of a command safedeps wrote. Before this, `npm ci eval "\npm"` ran its project's `postinstall`, where 7d66f8c's `npm ci eval "\npm" --ignore-scripts` ran none (npm 11.19.0). So deleting some of the flags safedeps inserted gives 7d66f8c's rewrite of the same command: npm receives at least the words 7d66f8c gave it, whatever the shell does to them. `scripts/test/lib/release-floor.sh` checks that on every rewrite smoke and lockless see, against 7d66f8c's own output recorded in `scripts/test/inert-release-rewrites.json`. A flag after the verb alone is not 7d66f8c's rewrite: for a one-statement command 7d66f8c appended at the end, and where a word after the read place turns into `--no-ignore-scripts`, that end flag is the one that stands (under `alias -g --cache=--no-ignore-scripts`, `npm install x --cache` keeps 7d66f8c's end flag true, while a flag after the verb and one before `--cache` both lose). An exception that left the verb flag off where it changed npm's reading (`npm install true`) is gone: under `alias -g left-pad@1.3.0='left-pad@1.3.0 --cache'` it left one flag, which the alias's `--cache` took, where 7d66f8c's flag after the verb stood. Where the verb flag itself changes npm's reading, the core does not leave it off either: that command is a collision (`floor-not-an-option`) and is denied. An install is left as written only when its own arguments leave the option true, read with the grammar's nopt reader (`npm_read_args`), so a word that is another option's value (`--cache --ignore-scripts`) does not count, and only where 7d66f8c left it as written too: 7d66f8c skipped a command only when the text `--ignore-scripts` stood unquoted in it, so a quoted `"--ignore-scripts"` or `--no-no-ignore-scripts` keeps 7d66f8c's rewrite. The statement's words are read from one lexing of it as written, the whole statement at a time, so a newline inside quotes, a continuation and a comment read as the shell reads them: read one line at a time, `--message "a<newline>--ignore-scripts"` read as the flag. The guard used to look for the text anywhere in the command, and `npm install x --ignore-scripts=false` or `npm install x && echo --ignore-scripts` then ran the install scripts with nothing recorded. An install that asked for its scripts is made inert anyway, and `advisory.log` says so. A `--` before the verb leaves no such place, so that install keeps the floor and is a recorded downgrade, like one whose end cannot be found. A statement holding a word the shell decides at run time cannot be read that way, because the word can be an option that sets ignore-scripts, one that takes the next word, or a `--`. Which words those are is an allow-list, not a list of what expands (`shell_expands`): a word is read as written only when every byte of it outside quotes is a letter, a digit or one of `._/@:+,=%-` (`INERT_BYTES` in `rust/src/inert/record.rs`) and it does not start with `~` or `=`. Every other byte makes the word one the shell decides at run time, wherever it stands. The set is what the shell's expansions leave alone, in the order bash's manual gives them, with what zsh and dash add: brace (`{`), tilde (`~` at a word's start, zsh's named directories `~name`, and `~` after `=` or `:` as in `a=x:~`), zsh's `=cmd` (`=` at a word's start), parameter, command and arithmetic substitution (`$`, backquote), process substitution (`<(`, `>(`, zsh's `=(`), pathname (`*`, `?`, `[`, bash's extglob `@(...)` once a command turns it on, zsh's alternation `(a|b)`, qualifiers and numeric ranges, and with extendedglob `^`, `#` and `~` inside a word) and history (`!`, `^`). Word splitting acts only on what those produce. The table is the reason for the set; the judgment is the set, so an expansion the table forgot still makes its word dynamic. Bytes are read in the quoting they are in: the statement's flat view, where redirections, comments and quoted text are blank, for the set, and its words after quote removal for `$` and backquotes, which expand inside double quotes too. Two deny-lists stood here first, and each missed a kind of expansion. The first knew `$`, backquotes and globs and not the tilde, so `HOME=--cache; npm install x ~` was read as written, the flag went after `~` alone, the shell handed npm `--cache` there, and the install ran its scripts with nothing recorded. Its `{` never fired either: the pieces view the reader used turns grouping characters inside a word into word-internal blanks, so `{--cache,}` reached it without its braces (the same miss 7d66f8c had). The second listed the expansion steps and still missed zsh's named directories, its alternation glob and bash's extglob. The set costs a record where nothing expands: an unquoted `foo@~1.2.3` or `foo@^1.2.3`, and a `}` bash hands npm as a word, are read as dynamic. Such an install keeps both flags and is recorded, and the snapshot meta says the flag went in unread (`ignore_scripts_unread: true`), which adds one line to what the PostToolUse hook says: "safedeps did not read all of the command it wrote as the shell will". The line states what safedeps did not read; it used to add "so the install's own scripts may have run", a consequence nothing checked, and beside an install verb in an `echo` it was not true. The field can only add that warning; a record without it claims nothing more. It gets the flag after its verb, where only a later word can undo it, and after its last argument, where only an earlier word can, and `advisory.log` records the install as one whose flag nobody read. One run-time word that is either kind leaves one of the two standing (`npm ci $(printf -- --)` runs no script). Two run-time words, or one unquoted that splits into an override and a value option, can defeat both; that is the run-time-word boundary of the command guard, and it is recorded, not silent. On Codex CLI, which does not expose the `updatedInput` hook capability, the install runs normally and a malicious install script can execute once before the post-install reorg cleans up. (The package's *runtime* code is removed before your app runs it on both engines; only install-time lifecycle scripts have this Codex window.) The flag goes in only where bash, zsh and dash all read the npm installs in the same places. Where they do not, the command is `UNDECIDED` rather than half inert (see the readings above).

The rebuild covers only the tree the gate read. It runs with `--global=false --location=project --prefix <the directory the gate read>`. With `global=true` in a project `.npmrc`, a plain `npm rebuild` rebuilt npm's global tree and ran the scripts of a globally installed package nobody had verified; each of the first two flags alone failed against one of `global=true` and `location=global`, and the pair held against both. Without `--prefix`, npm walks up from where it runs the way an install does: after `npm install x --no-workspaces` in a workspace member, the gate read the member's lockfiles while `npm rebuild` there would have run over the workspace root.

And the rebuild is skipped, with a warning, when `node_modules` has no `.package-lock.json`, or when the tree npm would rebuild holds a package, or a version of one, that neither lockfile records. Which packages that tree holds is asked of npm, with the same flags: `npm query '*'` loads the tree the way `npm rebuild` does and names every package by location, name and version, and each is compared with what the two lockfiles record under that location. This replaced a walk of `node_modules` in bash, which twice covered less than npm rebuilds. It took a key on record for the package under it: with `global=0` in the project `.npmrc`, `npm install x` wrote 1.0.1 over a recorded 1.0.0 and left both lockfiles at 1.0.0, so the gate read the approved version and `npm rebuild` ran the other one's scripts. And it stopped at links: `npm rebuild` follows a `file:` dependency into its target and rebuilds the target's own `node_modules`, which no lockfile of the project records, so an approved install in the project ran the scripts of a package sitting unrecorded in the linked library (validator round 2, F2). npm's query lists that package as `../lib/node_modules/x`, and the warning names it. A link is not a node of its own there; its target is. A name is compared where the lockfile records one or the location implies one, which an `npm:` alias needs. A query that fails, or does not answer within 10 seconds, skips the rebuild too: then the tree is not known. `npm query` needs npm 8.16 or later; an older npm skips every rebuild with that warning. The skipped rebuild is a warning, not a rollback: an install off the record is already recorded `UNGATED`, and enforcing on such installs is a separate decision.

**Permission to run scripts is a check of the whole tree, not a judgment of the change.** Scripts used to run in two places, and both ran over the whole tree: the rebuild after an inert install, and the reinstall the rollback ran. Both were allowed by the judgment that nothing this command brought in was rejected. Every hole in that judgment then became a script that ran, and three did in a row: a reader that did not open the hidden lockfile, a reader that dropped links, and a rollback whose target nobody had verified. The rollback no longer runs npm at all, as the paragraph after the workspace one below says. For the rebuild, two more conditions join the record check above, read from `npm query` and the two lockfiles for every node. A package under `node_modules` must have every record of it name a source on the public registry, read as a scheme and a host at the start of the value (the same pattern as the source check), or be bundled by the package it is nested under. Bundling is read from the tree, not from the lockfile's `inBundle`: a committed lockfile sets that field as it likes, and npm writes it into the hidden lockfile for whatever the root project's own `bundleDependencies` names. Either way, measured, a tarball from an http URL with an approved name and version passed as bundled and the rebuild ran its scripts (NB1, NB2). So a package at `<parent>/node_modules/<name>` counts as bundled only when the parent is under `node_modules` and passes this check itself, the parent's own `package.json` on disk names it in `bundleDependencies` or `bundledDependencies` (or says `true` with the name in its dependencies, as npm reads it), and no record of the nested package names a source other than the public registry. What the root project or a workspace member bundles is checked like any other dependency. A package nested inside a bundled one that its own parent does not name is not counted as bundled, though npm counts it; the rebuild is then skipped with a warning, the safe direction. A directory outside `node_modules` must be a member that the project's `package.json` declares as a workspace. When any node fails, the whole rebuild is skipped, and the warning names each node by kind: off the record, not recorded as coming from the public registry, or a directory that is not a declared workspace member. Nothing is rolled back for it. This stops the rebuild for a committed lockfile edited to send an approved name to another tarball, under `npm ci` and a bare `npm install` alike (L1, L2), and for a directory an earlier `UNGATED` install linked (CH1b). The rebuild ran all three. It also stops the rebuild in a project with a committed `file:` directory dependency, a tarball or git source, or `omit-lockfile-registry-resolved`, which records no source. Those projects install and are not rebuilt (`scripts/test/effect-trace-grid.sh` section 1d: K2-K7, OM1). Workspace members, the nested install strategy and a public package's bundled dependency are rebuilt (K8, K9, NS1, BD1, BD2). A nested package sent to another tarball is installed and not rebuilt, whether its committed record says `inBundle` or the root bundles its parent (NB0-NB2n).

**A record on the public registry is checked against where npm fetched it.** The source checks above read `resolved`, and `resolved` says where npm would have fetched a package with no registry configured. npm's default `replace-registry-host=npmjs` fetches every `https://registry.npmjs.org/` URL from the registry npm is configured with and records the URL unchanged; the local registry the test batteries run against depends on exactly that. So a committed `.npmrc` with `registry=<anywhere>`, or `npm_config_registry` in front of the command, sent an approved name and version to another tarball. Both lockfiles recorded the public URL, and the rebuild ran the impostor's scripts: in a new project (RH1), in a clone whose committed lockfile carried only the impostor's integrity (RH2), and from the command's environment (RH3). Where npm fetches from is npm's configuration, so it is asked of npm, like where an install lands. `npm config ls --json` prints `registry`, `replace-registry-host` and every `@scope:registry` from every layer npm reads. The pre-guard asks it beside `npm prefix` and `npm root`, in the same directory, with the statement's own arguments and environment and under the same deadline (`rust/src/ask.rs`, the fetch facts). The answer does not deny the install. A company registry, a mirror and a proxy are configured exactly this way, there is no path yet to approve one, and a deny would leave those users nothing to do; the text check still denies a `--registry` the command spells out. The answer travels in the pending state, and the post hook asks again in the directory it read, after the command, because an `.npmrc` the command wrote is not there before it and the rollback's reinstall runs with the hook's environment. Every check that judges a public URL (the rebuild's whole-tree check and the source check of what an install brought in) then asks whether npm swapped its host, which is npm's rule applied to npm's answer: the host is swapped when `replace-registry-host` is `always` or names it, and the bytes come from the default `registry`. A record vouches for the public registry only when both answers say the bytes came from there. A scope's own registry is judged too, for a package under that scope, though npm 11.19.0 does not fetch a recorded URL from it (pacote hands the tarball fetch the default registry); judging it costs a skipped rebuild at most. An answer that is missing is never a default: npm missing, failing or past its deadline, a value npm will not print (one holding a credential), and an earlier statement that can change npm's environment unseen (`source`, `.`, `eval`, `set -a`, a `declare -xi` that changes the value it stores, a lone `npm_config_*` assignment, an export whose value the shell decides at run time) each leave it unknown. The environment the pre-guard asks with is every name the command exports, assigns on a line of its own or sets in front of npm, with a literal value, and not only `npm_config_*`: npm reads its user `.npmrc` from `HOME`. An export branch that carried only npm settings asked `export HOME=<dir>; npm install x` under the hook's `HOME`, both asks answered the public registry, and the rebuild ran what the registry in `<dir>/.npmrc` served (XH1-XH3; `declare -x` left the answer unknown, XH4). An assignment the command does not export is carried too, since `HOME` is exported already (XH5). Where it does not reach npm, npm runs with the hook's environment, which is what the post hook asks with, so one of the two answers is npm's either way. After `source`, `.` or `eval` alone, an answer in which npm names another registry stands instead (below). An unknown answer skips the rebuild with a warning that names the reason. It does not roll back, because a rollback for an answer that never came would undo ordinary installs. A known non-public registry is not rolled back either, for the same reason as the deny: the install is kept and nothing is rebuilt (RH1-RH3e, RH1w, RH2w, RH8). The warning says that safedeps did not run `npm rebuild` because of it, names the registry, and tells the agent to confirm with the user before running `npm rebuild <pkg>` itself, because an agent told only "run npm rebuild yourself" would run the scripts this check withheld. On Codex safedeps cannot add `--ignore-scripts`, and the warning says that it did not add it, so the install's scripts may already have run (RH3x). Where safedeps asked for the flag and the command the post hook received is not the one it wrote, the warning says that instead (RH3c). It says what safedeps did, never what npm did. A registry approval path is planned for the next release. The local test registry passes only by name: `SAFEDEPS_NPM_TEST_REGISTRY` takes one loopback URL, nothing else, and every run that sets it says so in `advisory.log` with the moved advisory sources.

**Where bytes came from is recorded when they are fetched, and looked up after.** The paragraph above judges the command that fetched them. It says nothing about the next command, which reads the same records under another configuration, or none. A one-shot `npm_config_registry` or an `.npmrc` removed after the warning left the impostor on disk under a public URL, and the next approved install rebuilt it (P1, P2). So did an `npm ci` after `node_modules` was removed, because npm's cache hands back the same bytes by integrity (P3), a rollback to a snapshot confirmed with the impostor in it (P4), and another project's `npm ci` of the same lockfile on the same machine (P5). That was the third counterexample of one kind in a row. The bundling exemption read `inBundle`, the source check read `resolved`, and this read the configuration at rebuild time; each answered "where did these bytes come from" with something not bound to the bytes. The one value npm binds to them is `integrity`: it checks the bytes against it when it extracts them, and its cache is keyed by it.

So the post hook records the fact when it sees the fetch. Each integrity digest that either lockfile holds after the command and the installed tree did not hold before it is written to `${SAFEDEPS_HOME}/npm-withheld` when npm did not say it fetched those bytes from the public registry: a record on it that npm says it fetched from elsewhere or could not say (the unknown answer, except after code the command ran first, below), a source off it, or no source at all, which npm fetches from the registry it is configured with. The record holds the package, where it came from and the first project. Both engines write it, before the reorg decision, so a rollback does not lose it. It is one file per run, written under a temporary name and renamed, and it is machine-wide, because the cache that carries the bytes to other projects is; a record per project missed P5 (measured by mutation). Its path comes from `SAFEDEPS_HOME` and nothing else, as `advisory.log`'s does.

"The installed tree before the command" is the pre-guard's copy of `node_modules/.package-lock.json`, and only as far as the gate observed it. The copy says what the file said, and the file is a record anyone can commit, as `package-lock.json` is. Counting the committed `package-lock.json` as already there let a clone's `npm ci` through a committed `.npmrc` or a one-shot `npm_config_registry` record nothing, although its own warning named the impostor's registry; then a bare `npm install`, an approved install, an `npm ci` from the cache and another project's `npm ci` each rebuilt the impostor (Q1-Q4). A committed tree record did the same with no bytes behind it: a clone that carried only `node_modules/.package-lock.json`, naming the impostor's integrity, had its first fetch from the impostor left out, and the same four commands rebuilt it (HL1-HL4). So the post hook keeps, for each project directory, the sha256 of the last tree record it judged there, in `${SAFEDEPS_HOME}/npm-observed`, a path derived the same way as the record's. It keeps one only for a tree record the install wrote during the command, every integrity of which it judged, with every one to record written. The pre-guard's copy counts as the tree before the command only when it matches that hash byte for byte. Each integrity in it was then recorded, said by npm to come from the public registry in the run that brought it in, or held before under the same rule. Any other copy counts for nothing. Within an observed copy, an entry vouches only when it names one digest. npm checks bytes against the strongest algorithm an integrity names and accepts any digest of it, so an entry that pairs the impostor's sha512 with the public one, installed from the public registry, says nothing about the impostor's (DP1). The test is per digest for the same reason: a committed integrity that paired the impostor's sha512 with one the tree already held passed whole (Q5).

The cost falls on installs whose answer is not the public registry. In a tree the hooks have not observed, such an install records every integrity the tree holds. Under a company registry or a mirror, that tree is mostly what the registry served, which is recorded when it is fetched in any case. Under an unknown answer it includes public packages. A `set -a && npm ci` in a fresh clone withholds every package of that tree on this machine (UK1a, and UK1d and UK1v for `declare -xi` and an `npm_config_*` assignment). So does the first such install in a tree installed before this version, outside the hooks, or rewritten by anything else since its last gated install (UK0a). No tree that holds one of those packages is rebuilt automatically after that, and the core has no way to release them. An install that npm answers for with the public registry records nothing and leaves the tree observed, so an unknown install after it records only what it brings in (UK2). The rows measure one package; on a real tree it is every package in it. Leaving out every digest npm once said came from the public registry would narrow this, but a digest npm did not check is the DP1 problem again, so it is left for the release that approves registries.

**An install after code the command ran first records nothing, unless npm names another registry.** The same holds for code the command chooses for npm to run with: a code name it sets or unsets (above), `env -i`, which leaves env to find npm on a path of its own, and an npm named by a path that is not the hook's own. The ask runs none of that code, so its answer is the hook's npm's, not the command's, which is the reason an answer after `source` is not the command's npm's either. Before this, `export PATH="<dir>:$PATH" && npm ci`, the form a version manager writes, was an unknown with no cause and recorded every package of a tree the hooks had not observed (PX1-PX3; PX4 names the impostor's registry in the same command and is recorded). `source ~/.nvm/nvm.sh && npm ci` is a common agent command, and under the rule above it withheld the whole tree on the machine. The answer there is unknown because `source`, `.` and `eval` run code the gate does not read. Whoever controls that code already runs code in the agent's shell, `curl … | sh` included, so a record would protect nothing against them. So when that is the only reason, and npm answered the public registry for everything the gate can read, the pre-guard marks the unknown answer `cause: "sourced"`. The post hook still skips the rebuild and its warning says why. It then leaves the pre-guard's answer out of the record and does not leave the tree observed, so the next install here counts the whole tree as new. Its own answer still counts, so a project `.npmrc` naming another registry is recorded as before. The next install npm answers for with the public registry rebuilds the tree (SRC1-SRC3, UK0, UK1). Where npm names a registry that is not public, the answer came from the command's own words, which the code cannot take back. It stands as npm gave it and is recorded like any other (VB1-VB3). The first version of this exemption replaced it with the sourced unknown, so a no-op `. /dev/null;` in front of `npm_config_registry=<impostor> npm install x` recorded nothing, and the next approved install rebuilt the impostor's bytes. A setting the gate reads but cannot reproduce is configuration, not code, and is recorded as before, alone or beside a `source` (UK0a, UK1a, UK1d, UK1v, MX1). So is code whose own text names an npm setting, such as `eval "export npm_config_registry=…"` or a here-string handed to `.` that says it (EV1).

The whole-tree check then refuses a package under `node_modules` whose record carries a recorded integrity, and says where the bytes were first fetched from and into which project. It also refuses a record on the public registry with no integrity at all, because nothing can match it against the record: stripping both lockfiles' `integrity` had the impostor rebuilt (P7). A record that cannot be read skips the rebuild and says why. The record is released only by the bytes leaving the tree: a reinstall from the public registry brings other bytes, with another integrity, and is rebuilt as before (P6). There is still no command to release it. A person who has checked the registry runs `npm rebuild` themselves, and approving a registry, with the content check that compares a recorded integrity with the public registry's `dist.integrity` for that name and version, is planned for the next release. Until then a package fetched once through a mirror is not rebuilt automatically in any project, because a mirror serves the public bytes. Nothing is denied or rolled back for it. The record is local state under the same user, so it is the ledger's boundary too: a same-user attacker can delete it.

What each lockfile field the rebuild's check reads can and cannot vouch for:

| Field | What it vouches for | What it does not, and the row that holds it |
| --- | --- | --- |
| `resolved` | Where npm would fetch with no registry configured, and the kind of source (registry, tarball, git, directory) | That the bytes came from there: npm swaps the host for the configured registry (RH1-RH3, RH1w, RH2w); that a committed URL was ever checked (L1, L2) |
| `integrity` | That the bytes on disk are the bytes npm checked when it extracted them, and so the key a record of withheld bytes is looked up by (P1-P5) | That those bytes are the public registry's: a committed lockfile sets it as it likes (RH2, RH2w), so a committed integrity is no reason to leave bytes out of the record (Q1-Q4), nor is a committed tree record (HL1-HL4), nor one digest beside another (Q5), and within a tree record the gate judged, an entry with two digests vouches for neither (DP1); a record with none cannot be matched, so it does not pass (P7) |
| `inBundle` | Nothing the gate reads: bundling is read from the parent's `package.json` on disk | That the package came inside its parent: a committed record or the root's `bundleDependencies` sets it (NB1, NB2, NB2i, NB2n) |
| `link` | That npm placed a symlink there, to the target it records | That the target is the project's: a `file:` directory nobody approved (K4-K7, CH1b, A1-A4); that a real node is not sitting where a link is recorded, which the check reports as off the record (LK1) |
| `version` (and `name`) | What the ledger and OSV judged | What is on disk: an `.npmrc` wrote 1.0.1 over a recorded 1.0.0; the check compares `npm query`'s version with the record (`scripts/test/lockless-forms.sh`, the `global=0` rows) |

**The source and install-script checks read what the install brought in, from both records.** They used to run only when `package-lock.json` or `package.json` changed, and the closure check was the only one that read the hidden lockfile. An install that saves nothing changes neither file. So a tarball carrying the approved name and version passed both checks when it came from a `file:` path, an http URL or a tarball argument with `--no-save` or `npm_config_save=false`, and the inert rebuild ran its scripts; so did an approved package whose install script the heuristics flag when it is saved (validator round 4). The closure did not help, because it names packages by name and version, and so does the rebuild precondition.

Both checks now read what either record holds that no record held before the command (`new_records` in `rust/src/post/closure.rs`). The pre-guard keeps a copy of `node_modules/.package-lock.json` beside the copy of `package-lock.json` it always kept. It copies the file through a temporary name and never touches the original, whose mtime and inode are the install trace. A source is new when no earlier record names that resolved URL. An installed package is new when no earlier record has it at that key with that version, resolved URL and integrity, so a tarball written over an approved install at the same path counts. The new sources go to the non-standard and insecure URL checks. A source is on a public registry only when its value starts with `https://registry.npmjs.org/` or `https://registry.yarnpkg.com/`. A substring test passed `file:registry.npmjs.org/x.tgz` as the registry. The new packages' `package.json` files go to the install-script heuristics, in one pass for all of them. The 50-entry count stays on `package-lock.json`: with no earlier record, every first install of a project with more than 50 dependencies would cross it.

The two earlier records are read together, not in turn. Read against the tree record first, `package-lock.json` would bring in again, on every install, the optional packages it records for other platforms. And a lockfile pulled from a teammate would make its new sources read as new to the next `npm ci`, which is the committed-lockfile case below. A link is read too. npm records a directory dependency as a link and its target (`node_modules/x {resolved: "../x", link: true}` and `../x`), in both records whether or not the install saved, and `npm rebuild` runs the target's install scripts through the link. So a link the install brought in is a new source outside the public registries, and its target goes to the install-script heuristics. Leaving links out let `npm install ../dir` pass while the rebuild ran the directory's scripts (validator round 5). A workspace member is the exception: a directory the project's `package.json` declares as a workspace, inside the project, is part of the project, and the rebuild runs its scripts as `npm install` would. Where the patterns use a glob the gate does not read, such as a negation, no directory counts as a member: a new member there is rolled back, and `advisory.log` says why. The project's own entry is left out for the same reason. A project with no lockfile and no installed tree has no earlier record, so everything its first install brings in is new. A source outside the public registries is therefore rolled back on that first install, as it already was when added to a project that had a lockfile. It used to pass there only because no snapshot existed to compare with. The rollback names each such source by record and resolved URL.

In a workspace, the root lockfile keys each member by its path (`packages/a`). The closure skips every key outside `node_modules`, because those are directories of the project rather than package names; read as one, `packages/a` was an unapproved package `packages`. And an install into a member writes the member's `package.json`, so the snapshot keeps every member's manifest. Without it, the rollback of `npm install x -w packages/a` restored the root lockfile, `npm ci` refused the member's new dependency, and the fallback reinstall put `x` back.

The snapshot keeps every member, not the ones an install is expected to write. Which members `npm install` writes is npm's to decide, and guessing it would be one more copy of npm's rules in bash. What kept that affordable in the Bash guard was the process count. All the manifests went through one `tar` copy and one `shasum`, so the hook started the same processes for 10 members as for 1000, where a `cp` and a `shasum` per member took a workspace of 1000 members 20-33s to judge, past the runtime's 30s kill, where the command runs unjudged. The core copies and hashes the manifests in its own process (`members` in `rust/src/pre/snapshot.rs`). `scripts/test/workspace-snapshot-count.sh` still counts the programs the hook starts through a shim on every command in `PATH`, which load cannot move the way it moves a time, for 10 members and for 1000, and it checks that every member's manifest is in the snapshot byte for byte. The Bash guard's cost was measured with `scripts/measure/npm-ask-cost.sh` on one machine (macOS arm64, npm 11.19.0): the whole pre-guard took 2.7s, 5.5s and 19.5s for 100, 300 and 1000 members before the change (load 18-21), and the medians were 0.9s, 1.0s and 1.7s after it (load 22-31). Those are the Bash guard's figures, and the core's has not been measured. When the copy fails, the install is denied as undecided rather than run without a way back.

**The rollback runs no package manager.** It restores the files it snapshotted and removes the project's own `node_modules` when that is a real directory. The reinstall is the next install, which the gate checks like any other. A target that is a symbolic link is refused and named (`REORG REFUSED` in `reorg.log`), never followed, and the rollback goes on with the rest. The rollback used to reinstall, and each way it did so went somewhere nobody had checked. With `global=true` in the project `.npmrc`, a plain reinstall installed the project itself into the global prefix and left its `node_modules` empty. With no lockfile to install from, or after a failed `npm ci`, it resolved `package.json` again: measured, a `^1.0.0` range came back as a 1.0.1 published after the approval, and the reinstall ran its scripts. A project with no confirmed snapshot is rolled back to the snapshot taken just before the command, which nobody verified. Measured: a fresh clone whose committed lockfile held an unapproved package was rolled back to that same lockfile, and `npm ci` ran the package's scripts (RB1). The same happened when the lockfile held the package before an approved install (RB2), and when an earlier `UNGATED` install had put it there (CH2b). Flags and `--ignore-scripts` closed those. Review then found the reinstall reaching past the project in ways no flag covers: `npm ci` empties whatever a linked `node_modules` resolves to, npm walks up to an enclosing project where there is no `package.json`, a fallback install saves a lockfile through a link, `npm ci` empties a workspace that lies outside, and a `file:` dependency's bin links are rewritten in its own directory. Three rounds found a new one each time, so the rollback stopped asking npm where its hands go. After a rollback the message says which paths were restored and removed, and what a test of `package.json`, `package-lock.json` and `npm-shrinkwrap.json` returned afterwards. It gives no reinstall command, because where a reinstall would write is npm's to decide. After a rollback with no confirmed snapshot, the message, `reorg.log` and `advisory.log` say that the snapshot was taken before this command and that no confirmed snapshot names it. What ran before the rollback differs by engine, and the records say what the hook saw. On Claude Code that is "safedeps added --ignore-scripts to this install". On Codex it is "safedeps did not add --ignore-scripts to this install; the command this hook received does not carry it" (RB1x).

**What a rollback says is a closed set of lines.** The rollback message, a refused step, the rebuild skipped after an inert install and the unfinished-rollback report are built from the functions in `rust/src/post/report.rs` (carried over from `lib/gates/report-facts.sh`, which is gone). Each function runs its own check when it is called and prints what the check returned, so no line exists without a check.

| Form | The check behind it |
|---|---|
| `Rollback snapshot: <id>, a confirmed snapshot` | the project's confirmed record names `<id>` |
| `Rollback snapshot: <id>, taken before this command; no confirmed snapshot names it` | `<id>` is the pre-guard's snapshot for this command, and the confirmed record does not name it |
| `restored <path>` / `not restored <path>: copy returned OS error <n>; <path> differs from the snapshot` / `...: copy returned without error; <path> does not exist` | the copy, then a byte comparison with the snapshot. The line names the OS error the operation returned, or that it returned none. The Bash hook printed `cp exit <n>` |
| `not restored <path>: <path> exists and is not a regular file` | a test of the path before any copy: `cp` into a directory wrote a file inside it and exited 0, so the test comes first |
| `removed <path>` / `not removed <path>: removal returned OS error <n>; <path> exists` | the removal, then a test of the path |
| `refused restore of <path>: <fact>` / `refused removal of <path>: <fact>` | the path is a symbolic link, named with the physical path it leads to, or the project directory does not resolve |
| `<path> exists` / `<path> does not exist` / `<path> is a symbolic link to <physical path>` | a test of the path |
| `<dir>/package.json has the key workspaces` | a read of the file's JSON |
| `kept <path>` and the lines after it | no install trace, no node manifest or lockfile that differed from the pre-command snapshot when the rollback began, no entry in `node_modules` or `.bin` that the pre-command listing lacks, and nothing newer than the pre-command snapshot: one line per check. A linked `node_modules` is listed through the link, by the pre-guard and here (a walk that follows a link at its root), and a kept one is said as a link right after `kept` |
| a reason line, then `removed <path>/node_modules` | the first of the same checks that showed a write, as one line: the lockfile that carries the install trace, the node file that differed, the package or `.bin` entry the listing lacks, the path newer than the snapshot, or no snapshot from before the command |
| `The rollback changed nothing.` | no step ran a copy or a removal; a failed removal removes what it can, and a failed copy can truncate |
| `no install trace in <dir>: ...` | the lockfiles against the baseline, or the baseline file is gone |
| `safedeps added --ignore-scripts to this install` / `safedeps asked for --ignore-scripts on this install; the command this hook received is not the one safedeps wrote` / `safedeps did not add --ignore-scripts to this install` | the pre-guard's record that it rewrote the command, with the command it wrote (`updated_command` in the snapshot's meta), compared with the command in the post hook's input. The command is not read for the flag. A call whose record the post hook did not find has no `--ignore-scripts` line: the backstop runs because it found none, says so in its headline (`this hook found no record of this command from before it ran`), and does not say what safedeps did. A pre-guard that cannot write the record writes no rewrite and says so in `advisory.log`. A post hook that cannot read the record says no `--ignore-scripts` line either and says so in `advisory.log`; a failed read used to fall through to `did not add`. Each line is said only from a fact the record states, and only a version 2 record (`"record": 2`, written since v2.18.0) states one: `did not add` needs `ignore_scripts_injected` to be the JSON false, and `added` or `asked` need it to be true with `updated_command` a string. No other shape says a line: no record file, a record of another version or of none (v2.17.2's false did not mean no rewrite, because its write could fail and the rewrite went out, and its true holds no command), a string `"true"`, a null command. advisory.log then names the record as one that does not state whether safedeps rewrote the command. No branch that says a line is reached by a default |
| `... did not run npm rebuild: <fact>` / `... ran npm rebuild: exit <n>` / `npm rebuild terminated by signal <s>` / `could not start npm rebuild: OS error <n>` / `could not read npm rebuild process status: OS error <n>` | a root npm file that is a link, a missing trace, or what the rebuild was observed to do: its exit code, its signal, a failed start or a failed status read. The oracle checks the signal and start forms against a receipt the test owns; the status-read form is held by a unit input only |
| `Rollback snapshot: <id>, a confirmed snapshot` / `Rollback snapshot: <id>; no confirmed snapshot names it` in the unfinished-rollback report | the project's confirmed record when the report is written |
| `Journal:`, `Owner:`, `<path> differs from the snapshot <id>` and the other lines of the unfinished-rollback report | the journal entry, the test of the owner that answered, and a comparison of each monitored file with the snapshot; a file that matches is not a line |
| `Details log: <path>` / `Incident record: <path>` / `Rollback log: <path>` | the file exists; otherwise the line ends `is not a file` |

The pre-guard's record, the snapshot taken before this command and the install-trace baseline in these checks are those of the pending state the post hook used, and that state is this call's own. **A result a line states is an `Outcome`, never a number or a name a caller chooses.** The report lines had already been through three false sentences, and the same kind of defect then came back in other places: the report printed `cp exit 1` and `rm exit 1` for programs that no longer ran, the user-facing text named awk, grep and sed as the steps that had failed, and the backstop's walk said `failed (find exit 1)` where no `find` ran and the 1 was an internal marker. The third recurrence also showed a worse form. The rebuild said `ran npm rebuild: exit 127` where npm had never started, because a failed start was folded into the number 127 and a signal into 128 plus its number. A read-only judgment ran before that repair (verdict kongkongi-20261007-192121). It showed that a list of names or of literals cannot close the class: a literal the code already holds, `grep`, put in the copy line adds no new literal and passes a membership check, and `npm` is an allowed name that did not run. The defect is a message that states the result of something that was not observed.

So the core keeps what was observed in one closed type (`rust/src/outcome.rs`). `Outcome` is a finished process with its real `ExitStatus`, a failed start, a failed status read, a deadline, or an I/O result. `Action` is a closed set (`Npm`, `NpmConfig`, `NpmQuery`, `NpmRebuild`, `Judgment`, `Walk(path)`, `Copy`, `Removal`), and `Outcome::describe(Action, Form)` is the one function that turns a result into words. No API takes a free actor string or an integer status, and the old `report::io_outcome` is deleted. The sentences, before and after:

| Observed | Before | After |
|---|---|---|
| The walk could not read a directory | `the walk of <path> failed (find exit 1)` | `the walk of <path> returned OS error N` (or `returned an error without an OS code`) |
| The walk reached its deadline | `the walk of <path> did not finish within Ns` | unchanged, and stored as a deadline, never as an I/O error |
| The rebuild was killed by signal S | `ran npm rebuild: exit 128+S` | `npm rebuild terminated by signal S` |
| The rebuild could not start | `ran npm rebuild: exit 127` | `could not start npm rebuild: OS error N` |
| The rebuild's status could not be read | `ran npm rebuild: exit 127` | `could not read npm rebuild process status: OS error N` |
| An npm ask was killed by signal S | `npm query failed (exit 128+S: no output)` | `npm query failed (signal S: no output)`, and the same for config, prefix and root |
| An npm ask could not start | `npm query could not start: <the error as displayed>` | `could not start npm query: OS error N` |
| An npm ask did not answer in time | `npm query did not answer within 10s` | `npm query did not finish within 10s`, and a failed status read is its own sentence |
| The judgment process ended with neither code nor signal | `... (signal 0)` | `... (no exit code or signal)` |
| A copy or a removal | `copy returned OS error N` | the same words, now produced by `Outcome::describe` |

The sentence after is said only for the observation named in the first column. The rebuild's start and its wait are two operations, so a failed start is never reported as an exit.

Three further parts hold it. The oracle checks the advisory.log lines that carry a result, by form, against observations the test owns (`scripts/test/lib/outcome-oracle.py`, `ask-outcomes.py`, `rebuild-outcomes.py` and `backstop-walk-io.py`): the walk's I/O line, an npm ask killed by a signal, and the four rebuild forms in the table above. The oracle still does not read advisory.log in general, which is why the `find exit` line passed every row before. The exit gate (`scripts/measure/output-sinks.py`, the committed list `scripts/measure/output-sinks.tsv` and the development battery `scripts/test/output-sinks.sh`) generates the core's output exits from `rust/src`, test code excluded, and compares them with that list. An exit is a source occurrence: a stream write, a file write or append, a call of the core's advisory or report writers, and, as boundary entries, an imported output API, an FFI declaration or a macro definition. The identity is a count per file, function, role, exit kind, callee and kinds of argument origin, and not a position, a token order or a function body. So adding or removing an exit, or changing the origin kind of an argument to an exit that speaks to a person, is red, while an unrelated line or an ordinary import is green. The list has 421 identities and 505 counted occurrences: 154 speak to a person, 94 are data and 257 are boundary, and three of the human exits take their text from the result renderer. It is a lexical census. It is not a type or taint analysis and not a truth oracle: it does not say the words are true within one kind of origin, does not follow an origin across a function return, does not read the body of an existing macro or foreign function, and does not vouch for what a child process writes. A change that adds or removes an exit regenerates the list in the same commit, and the list's diff is read, because regenerating without reading makes the gate a stamp. And a broad migration of every message to a typed form was not done. An enumeration of the core's string literals and an independent list from the binary's strings found this kind of defect only at the places already fixed. Of the 14 places that call `describe`, the gate could follow 3 (copy, removal and the rebuild) to a human-facing exit. The other 11 (the walk, the npm asks, the judgment's end) are read by other tests, and a change upstream of an exit that keeps the argument's kind is invisible to the gate. A dedicated result oracle (`scripts/test/lib/outcome-oracle.py`, called by `backstop-walk-io.py`, `ask-outcomes.py` and `rebuild-outcomes.py` from `scripts/test/e2e.sh`) reads the walk's I/O line, the npm ask lines that name a signal, and the rebuild forms. The walk's deadline line and the hung ask's `did not finish within` line are asserted by rows of `e2e.sh` and `lockless-forms.sh`, and the judgment's `ended without a usable answer (signal 9)` line by a row of `self-budget.sh`. The general grammar of `report-oracle.sh` does not cover those places. The types are held by `outcome::tests::claims_keep_observed_outcomes_distinct`, `ask::outcome_tests::wait_failure_is_not_a_deadline` and `post::trace::tests::walk_preserves_io_error_and_distinguishes_deadline`, and by e2e rows that make the real failure happen: an unreadable directory, an npm that deletes itself before the rebuild, and a process killed by signal 9. What this does not cover is stated rather than claimed. The oracle checks each line it reads. It does not check which lines were chosen, so a true line can still mislead and a line can be missing. A line left out is caught only where the oracle knows from the disk or from a record that it had to be there: a changed top-level entry, a refusal reorg.log carries, the report's `node_modules` line. It shares no code with the hook, but a check both get wrong passes. A line is true when it is written, not later. The listing it compares is the project's top level, so a change below it, in a nested directory or a workspace member, is caught only through a line about it. A workspace member's restored `package.json` would be checked by its own line, but no row of e2e restores one, so that check does not run in this suite. The package lists under `kept` read three levels below `node_modules`, and a package written deeper is in neither the hook's lists nor the oracle's. The reasons under "Detected problems" are the checks' own strings and are outside the grammar: the oracle checks only that the message and reorg.log carry the same reasons, so a change to the reasons themselves passes. The effect gate's rebuild warnings ("review it, then run `npm rebuild` yourself if it is what you expect", "confirm with the user before running") are instructions on purpose and are still sentences. The oracle lists each by exact prefix with the blocks it may appear in and the most lines this suite may show (zero for all seven today), and their facts come from a record file rather than from disk, so their forms are a later plan's.

**What it does not stop (current limits):**

- A zero-day discovered *after* `approved_at` — only the daily re-check catches it, not the install itself.
- Compromise of the npm registry itself.
- An install that an `.npmrc` moves or keeps off the record. It is recorded `UNGATED` but not checked: npm names the global tree for any `.npmrc` it reads, and the project's and the user's are read for the settings that keep a project install unrecorded. The same settings in the global or builtin npmrc are not read for that, so such an install there is not recorded. Either way the package and its binaries land unverified. Its scripts do not run: the install is inert, and the rebuild is skipped when the tree npm would rebuild holds a package, or a version of one, that neither lockfile records.
- An npm install that left no trace where the gate looked: one sent elsewhere by something the text did not show, and one whose directory npm could not be asked about (npm missing from the hook's `PATH`, failing, not answering within 8 seconds, or handed a value the shell decides at run time) that did not land in the cwd. It is recorded `UNGATED`, and not checked. A dry run and a failed install are recorded the same way, because the trace cannot tell them apart.
- A trace the install did not leave. The trace belongs to the directory, not to the command: another npm writing to the same directory while the command runs makes one, and so does the command touching a lockfile itself. The second is a same-user attacker, the same boundary as the ledger's. A filesystem that keeps whole-second mtimes shows no trace for a lockfile written in the baseline's second, so there the install is recorded `UNGATED`: noise, not a pass.
- A registry set where npm's two answers cannot see it: in the environment of the agent's shell but not of the hook processes, or in an `.npmrc` the command writes and removes again. The rebuild then runs whatever that registry served under a public URL. What the command itself exports or assigns is in the ask whatever its name (XH1-XH5), and an earlier statement that can change npm's environment unseen, an export whose value the shell decides at run time included, leaves the answer unknown, and the rebuild is skipped. A registry outside the public ones that npm reads from its configuration is not denied, a company registry or a mirror included: what it serves under a public-registry URL is installed, and its scripts do not run. Its bytes are recorded by integrity, so no tree on the machine that holds them is rebuilt automatically, and there is no way yet to release that record: a person who has checked the registry rebuilds, and automatic rebuilds of those bytes stay off until a later release can approve a registry. A record under the registry's own URL is a non-standard source, as before. On Codex they ran during the install. Approving a registry is planned for the next release.
- Bytes the gate never saw fetched. The record of withheld bytes is written only when the post hook sees the fetch. Bytes fetched by an install outside the hooks, by one the command hook did not recognize, by one recorded `UNGATED`, or from a registry neither of npm's answers can see (above) reach npm's cache unrecorded, and a lockfile that names their integrity installs them from there under a public URL. Bytes a clone carries inside `node_modules` were never fetched at all, so nothing records them, and the rebuild trusts them as it finds them. A tree record carried without its bytes leaves nothing out of the record: what the record leaves out rests only on a tree record the gate judged (HL1-HL4). A counterexample of the kind P1-P7, Q1-Q5, HL1-HL4 and DP1 closed can come only from here.
- Bytes fetched after code the command ran first, where npm answered the public registry. An install after `source`, `.` or `eval` is not rebuilt, but its bytes are not recorded either. If that code pointed npm at another registry, as a sourced file that exports `npm_config_registry` does, the next install that npm answers for with the public registry rebuilds what it served (VB4). The record's `resolved` does not stop it: a registry that serves registry.npmjs.org tarball URLs is fetched under those URLs and recorded with them, as in RH1. This is chosen, not missed: whoever controls that code already runs code in the agent's shell, without npm. It holds whoever wrote the code, a file the command or an earlier one wrote included. A setting written out in the command itself is recorded, whatever code runs before it: a `npm_config_registry=…` in front of npm or an `export` of it, which npm answers for (EXP1, VB1-VB3), and an `eval` whose own text names an npm setting (EV1).
- The configuration an npm the command chooses reads. Where the command runs npm under a `PATH` of its own or names it by a path, safedeps asks its own npm, so a global or builtin `.npmrc` only the command's npm reads is in neither answer. Where that npm's configuration points at another registry, the command's own scripts are withheld and nothing is recorded, and the next install npm answers for with the public registry rebuilds what it served, as in VB4. The reason is the same: whoever chose that npm already runs it in the agent's shell.
- A committed lockfile's sources. The source check reads what an install brought in against the records from before the command, and a committed `package-lock.json` is one of them. So `npm ci` in a fresh clone, or a bare `npm install` that follows the lockfile, installs the sources the lockfile names, an edited one that sends an approved name and version to another tarball included. The same holds for a tree record a clone carries in `node_modules`, which the source check also reads as a record from before the command. Its scripts do not run: the rebuild's whole-tree check finds the source and skips the rebuild. Reading a missing earlier record as empty would catch the install itself, and it would also roll back the first `npm ci` of every project that installs from a private registry, a git URL or a tarball. There is no way yet to approve a source, so that would be a policy change users see, and it is left for a later release. The install-script heuristics read only what an install brought in, too, so an approved public-registry package that is already on record is not read by them again (as in v2.17.2).
- No automatic rebuild in a project whose tree holds a source or a directory nobody approved: a package not recorded as coming from the public registry, a record with no source (`omit-lockfile-registry-resolved`), or a `file:` directory dependency that is not a declared workspace member. The rebuild is all or nothing, so the approved packages' scripts do not run either, and the user runs `npm rebuild` after reviewing what the warning names. v2.17.2 rolled such installs back when the project had a committed `file:` directory dependency (measured, npm 10.8.2). Approving a source, and rebuilding only the nodes that pass, are left for a later release.
- Two lockfile-writing npm statements with something between them are recorded `UNGATED` even when both landed where the gate looked. The rule cannot tell, and it errs toward the record.
- On Codex CLI, an install that left no trace has already run its scripts wherever it landed. The record is all there is (the existing Codex asymmetry).
- A manual package-manager install run outside the configured Claude/Codex hook path; release-time gates are the backstop for those changes, not proof of install-time approval.
- An attacker writing to `~/.safedeps/approved-specs/` directly under the same OS user. The ledger is a local convenience cache; until signing/HMAC or install-time re-validation is added, it is not a security boundary against a same-user attacker. (The effect gate's OSV re-query does, however, still catch a forged approval for a *known-vulnerable* package — see [`ROADMAP.md`](./ROADMAP.md) "Ledger tamper resistance".)

## 6. Provider failure modes (no silent fallback)

```
OSV.dev — no response / timeout
  • first: use the local provider cache (24h TTL)
  • cache miss → fail-closed (block; "no OSV response, retry")
  • no install-time CLI bypass flag exists; retry when OSV or the cache can answer

CISA KEV — no response
  • KEV is a static catalog downloaded once a day; only the local cache is used
  • warn when it is more than 24h stale

GHSA / NVD — no response
  • enrichment only, so fail-open is allowed
  • proceed on OSV alone and log "GHSA cross-check skipped"
```

Design principle: **no silent fallback.** When the canonical truth (OSV) cannot answer and the cache misses, safedeps fails closed instead of inventing a secondary truth or hidden bypass.

## 13. Limits and future direction

**Current limits:**

- A zero-day discovered after `approved_at` is caught only by the daily re-check.
- A compromise of the registry itself (npm/PyPI/…) is out of reach.
- KEV updates once a day; a KEV listed in between is not caught until the next refresh.
- Transitive-closure checking can grow the ledger to hundreds of entries; this needs optimization.
- Yarn project-scoped closure requires the Yarn CLI on `PATH` and a Yarn Berry lockfile (`__metadata:` present); Yarn Classic (`yarn.lock` v1) and workspaces without a root `resolutions` entry fall back to the ordinary npm package-only check.
- Candidate materialization additionally requires that Yarn can resolve the mirror offline or from the network, and that the root manifest's `workspaces` patterns are plain relative globs. An absolute, escaping, `**`, or negated workspace pattern is refused rather than guessed at, and the candidate is denied.

**Future direction** (see [`ROADMAP.md`](./ROADMAP.md)):

- Effect-based closure enforcement for the non-npm ecosystems.
- Ledger tamper resistance (OSV-as-authority + tamper detection; no local signing).
- Plugin providers, a `.safedeps.toml` policy file, CI mode, multi-machine ledger sync, and agent-suggested safe replacements.

## 14. The Rust core

The PreToolUse and PostToolUse hooks are one Rust binary, `safedeps-core`, at `bin/native/<os>-<arch>/safedeps-core`. The registered entry is still `scripts/safedeps-hook-entry.sh pre|post`, and it runs the binary. The two Bash hooks, `scripts/safedeps-pre-guard.sh` and `scripts/safedeps-post-verify.sh`, no longer exist, and nothing falls back to Bash: the entry reads no environment variable that chooses the binary or switches it off. Two authorities drift, and a silent second one is what the no-silent-fallback rule forbids. The CLI, `bin/safedeps`, is still Bash.

**Why.** One judgment in the Bash guard started about 93 processes, and nearly all of its time went there (AGENTS.md, Testing). Its lexer was an awk program of some 2,000 lines that bash ran once per view. A Rust binary reads the command in one process. The core starts only `npm`, `curl`, `file` and `gzip`, and its own judgment process under the pre hook's budget.

### What is in the crate

`rust/` holds one crate, `safedeps-core`. It has no dependencies: the regex engine and the JSON reader are its own, `rust/Cargo.lock` lists the crate alone, and `scripts/build-core.sh` stops on a lockfile that lists anything else. So the npm package still has zero runtime dependencies.

| Module | What it is |
|---|---|
| `lex.rs` | The lexer: every view, the three readings, the start events, `UNTERM`, `DIVERGE`, and the walk's own check. It was written function by function from the awk program `shell_lex` of the Bash guard, with the same names and the same order of rules. |
| `ere.rs` | POSIX extended regular expressions, as `grep -E` and bash `=~` read the grammar's patterns. |
| `grammar.rs`, `tables.rs`, `manager.rs` | The install grammar, defined once: the vocabulary and patterns, the option and command tables, and the manager reader. `safedeps-core grammar` and `safedeps-core manager` print them for the batteries. They were carried over from `lib/install-grammar.sh`, which is gone. |
| `extract.rs`, `core.rs` | The spec extractor, the payload readers, the recognizers, the pipe checks, the statement split, and the driver that runs detection and the facts per reading. |
| `pre.rs`, `pre/` | The PreToolUse hook: the self budget (`budget.rs`), the landing and the UNGATED record (`targets.rs`), the install driver and its settlement (`install.rs`), the snapshot, the pending record and the trace baseline. |
| `inert.rs`, `inert/` | The inert rewrite: the structural reader (`read.rs`), the floor (`floor.rs`) and the record of what it did not read (`record.rs`). |
| `ask.rs` | The asks of the hook's own npm: where an install lands, which registry it fetches from, and the tree `npm rebuild` would run over. |
| `post.rs`, `post/` | The PostToolUse hook: the closure check, the install trace and the backstop, the rollback and its journal, the report lines, the rebuild check, and the provider queries. |
| `ledger.rs`, `state.rs`, `callid.rs`, `stamp.rs`, `os.rs` | The ledger reader (it approves nothing), the state directory and `advisory.log`, the call id, the source stamp, and the system calls. |

### How it was held to the Bash guard

While the Bash guard was the authority, each layer compared the core with it on the same input. The Bash side was the reference, a difference had to be named in a class file, and each harness had a `--control` that damaged the reference and had to then report differences, because a comparison that cannot fail measures nothing. Those comparisons are retired, because their reference is gone: the `scripts/measure/core-*` comparison scripts exit 2 and say why, and `scripts/measure/native-measure-disposition.json` lists each. The owner decided on 2026-10-07 that the Bash and Rust guards are not compared on a corpus. The criterion is the existing test sets running on the core, and a count from a retired comparison is not native coverage. The record of what was measured stays:

| Layer | Harness (`scripts/measure/`) | What was compared |
|---|---|---|
| Grammar | `core-grammar-drift.sh` | Each value the core carried, with the shell file's value after it was sourced |
| Regex | `core-ere-differential.py` | The recognizers' patterns, through the host's `grep -E` and through the core, on the lines the recognizers read |
| Lexer | `core-lex-differential.py` | The awk program cut out of the guard and the core: the view, the status, `UNTERM`, `DIVERGE` and the failure mark, for every text, reading and view |
| Facts | `core-facts-differential.py` | A scratch copy of the guard that wrote what it knew after its readings, beside `safedeps-core facts` |
| Whole answer | `core-hybrid.py` with `tuple-replay.sh` | A copy of the tree whose guard lexed with the core, replayed against the tree: the verdict, the packages a deny prescribes, the operands a record names |

Measured on 2026-10-06, on the corpora committed under `scripts/measure/` and `scripts/test/` and on seeded random input:

|---|---|---|---|

The lexer and facts controls damaged the reference. The other two damaged the core's side, and so did two more mutant cores built from a `git archive` copy. With the regex engine's defect put back (below), 13 of 80 commands differed in the facts layer and every pattern differed in the regex layer. The facts layer found a defect in the Bash guard. `pip --cache x install evil==1.0.0` ended the guard with `BASH_REMATCH[2]: unbound variable` (`safedeps_manager_long_option`, under `set -u`). It happened when a long option that is a unique abbreviation stood before the command word, for a parser that takes abbreviations (pip, pipx, gem). The entry shim turned the exit into a deny, so the command did not run, and the reason it gave named a broken checkout, which was not the cause. The class file named this case (`guard-crash`). The core reads the unset element as empty, which is what the next line of the shell function expected. The first facts run also found a defect in the core's regex engine: a cached state was keyed without its match, so two states that differed only there answered for each other. The regex layer then held the engine on its own, below the layers that used it.

### What the switch changed on purpose

The contract is unchanged: what is blocked, what is recorded and what is said. Where the core's verdict differs from the Bash guard's, the rows are in `scripts/measure/core-intended-battery-rows.tsv` and `core-intended-readings.tsv`, each with its effect and reason. No row there is a weaker verdict, which is a statement about those rows and not about the core. The differences are these.

- **A collision is denied.** Where a required `--ignore-scripts` flag cannot be placed while preserving the command's data and how npm reads its options, the whole command is `UNDECIDED` and no rewrite is sent (section 5, install-script timing). The cost is stated plainly: those commands are denied and the user rewrites them.
- **More readings are placed apart.** The zsh reading follows zsh more closely (a lone closing brace, glob qualifiers, alternation, extglob groups), so more forms are `UNDECIDED` because the readings put the npm installs in different places.
- **Script payloads are read.** A `sh -c` or `eval` script is read structurally, and a flag goes inside it where the Bash rewrite recorded a downgrade (section 5).
- **A deny leaves no state.** The core writes the snapshot, the pending record and the meta only after the last reading is settled, so a command denied for a finding or for a failed reading leaves none. The Bash guard took its snapshot first, so a denied install left one behind.
- **The report names the OS error.** A failed copy or removal says what the operation returned (`copy returned OS error 13`), and no line names `cp`, `rm` or an exit status, because no such program runs.
- **A judgment that does not finish says which way.** The deadline passing and the judgment process ending without an answer are different wordings, and a stopped process waits for the deadline (section 4, Phase 2).

### How it ships

- **Binaries in the package, one per platform**, under `bin/native/<os>-<arch>/safedeps-core`: darwin-arm64, darwin-x64 and linux-x64. The package already ships `bin/`, so `files` does not change, and no dependency is added. A per-platform optional package would be a dependency, and the release gate counts those. No binary is committed (the root `.gitignore` names `bin/native/`).
- **A checkout builds its own.** `scripts/build-core.sh` runs cargo with `--release --locked --offline`, checks the new binary beside the old one, and replaces the old one by rename, never by writing over it: a hook may be running the old file, and macOS kills a process whose executable was written under it. The installer builds the core and probes the entry before it registers anything (`prepareCore` and `probeEntry` in `scripts/install/install-safedeps-hooks.mjs`), and a failure stops the install with the reason.
- **The publish job builds the package's, from the tagged source** (owner, 2026-10-06). `.github/workflows/publish.yml` has two jobs. The `build` job, on a macOS runner, builds all three targets with `scripts/build-core.sh --publish`, because linking a darwin binary needs Apple's SDK; the linux-x64 binary is a static musl build linked with `rust-lld`, so it does not depend on the host's libc. The build job holds no publish credential. The `publish` job takes the binaries, checks their digests against the list the build job wrote, restores their exec bits, runs the linux-x64 one and checks its stamp is a publish build's, lists what `npm pack` would carry (each binary with mode 755, nothing of `rust/`), publishes, and reads the release back from the registry. The read-back compares the published file list with `npm pack --dry-run` of the job's tree after the binaries are in place.
- **The binary carries a stamp of the source it was built from.** The installed hooks are links into a checkout, so when the checkout moves the source moves and the binary does not. A hook that starts as a checkout's binary hashes `rust/` again and answers only when the digest is the one it was built with (`safedeps-core stamp --check`). With a mismatch the pre hook denies an install as `UNDECIDED` and lets a command that names no package manager run, with the mismatch on stderr and in `advisory.log`, and the post hook reports `UNVERIFIED`. A package holds no `rust/`, so the publish job's binaries are marked when they are built and skip the check only where their own tree has none. Because the stamp covers every `.rs` file, a change to a comment changes the digest. The release procedure builds before main moves and renames the binary in (AGENTS.md, step 7).
- **The entry shim keeps its contract.** It runs the binary where it ran `bash <hook>` before. The binary exits 0 on every designed path and its decisions travel as JSON. It aborts on a panic, so any other exit still means the hook is unwell, and the shim turns that into an explained exit 2. A missing binary, one that cannot run, or a platform with none is a deny that says so, and it never falls back to the Bash guard. The shim reads the platform from bash's `BASH_VERSINFO`, the machine bash was built for, and not from `OSTYPE` and `HOSTTYPE`, which bash keeps from the environment (measured, bash 3.2.57 and 5.2.21), so it starts no process to find its binary.

`scripts/measure/core-pack-probe.sh` checks the packaging with npm itself. It packs a copy of the tree with the binary in place, installs the tarball offline into a sandbox project, and runs the installed binary. It was measured before the switch, on macOS (darwin-arm64, npm 11.19.0) and in WSL1 (linux-x64, npm 10.9.8): the package named no dependency, `npm pack` carried the binary and nothing of `rust/`, the exec bit survived the install, and the installed binary was byte for byte the one packed.

**Not measured.** The workflow with its build job has not run on GitHub, and no registry read-back of a package that carries the binaries has happened. The darwin-x64 binary has not run on Intel hardware, and no arm64 Linux binary exists. The core has not run in WSL1 or on Linux on the tree without the Bash hooks. The release batteries (`native-scan-failures` and `effect-trace-grid`) have not run on it either; the tools for the cost of the whole hook through the entry (`scripts/measure/core-cost.py`) and for the backstop's walk (`scripts/measure/backstop-walk-cost.sh`) exist, and no value from either has been recorded for this tree.

### What stays in Bash

The CLI, `bin/safedeps`, is Bash and sources `lib/providers/providers.sh`, `lib/ledger/ledger.sh`, `lib/npm/closure.sh` (which reads the one-line public-registry constant in `lib/npm/ask.sh`) and `lib/truth-sources.sh` through the providers. `lib/advisory-log-rotate.sh` and `lib/gates/` (`scan.sh`, `audit.sh`, `hooks.sh`, `doctor.sh`, `repo-profile.sh` and their templates) serve the CLI and the release-time lane.
